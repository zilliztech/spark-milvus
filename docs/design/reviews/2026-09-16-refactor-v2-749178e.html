01 · P1 · Int8 标量写入时只记日志，非 null 值变成 null

触发：collection 有普通 Int8 字段，DataFrame 对应 ByteType 列写入非 null 值，例如 7；执行 append，或通过 backfill 写该字段。

证据：ArrowConverter.scala:863。SparkTypes.scala:121 将 Int8 映射为 ByteType，SparkSchemaMapper.scala:101 创建 TinyIntVector；但 sparkValueToArrowValue 从 609 行到 865 行没有 ByteType 分支，最终仅输出 warning，没有写值或设置 validity。MilvusV3Writer.scala:387 仍递增行数并提交批次，文件中该值成为 null。这是已可达的错误数据写入。

修改建议：增加 ByteType → TinyIntVector 的写入分支；未支持类型的兜底分支应抛异常，不能继续提交。

验收：从 InternalRow 经真实转换器写入 -128、0、7、127 和 null，再读回比较。现有 ArrowCDataRefcountTest 的 Int8 测试直接调用 TinyIntVector.setSafe，绕过了缺陷位置。

02 · P1 · 同一 Spark application 的第二次 backfill 复用第一份作业清单

触发：同一 SparkSession、相同 stagingRoot，未显式指定 jobId，连续运行两个不同 backfill。

证据：MilvusBackfill.scala:80。默认 jobId 取 spark.sparkContext.applicationId，两次相同。第二次已完成 segment 写入后才调用 writeJobManifest；Committer.scala:76 发现第一次的 _committed，返回 AlreadyCommitted，调用处却丢弃结果并返回成功及同一 stagingPrefix。随后 Register.scala:89 读取第一次的 manifest；第一次已登记时直接返回 already_registered。第二次新写出的版本因此没有登记。

修改建议：每次独立 run 默认生成独立 jobId，并在此次调用内保持一致。显式复用 jobId 时，应在写段前识别重跑或冲突，不能写完新版本后忽略 AlreadyCommitted。

验收：同一 SparkSession 用默认 jobId 连续做两次 backfill，断言 stagingPrefix 不同，两个 manifest 与登记请求各自对应本次版本；另测显式重跑相同 jobId 的预期行为。

03 · P1 · exists 把访问失败当作不存在，破坏提交标记的判断

触发：查询已有 _committed 或 _registered 时，原生 stat 返回权限错误或网络错误；并非返回 NotFound。

证据：NativeObjectStore.scala:27。exists 对全部 StorageNativeException 返回 false。C 入口 filesystem_c.cpp:220 已区分 LOON_ARROW_ERROR 和 LOON_FILE_NOT_FOUND，Java 异常也保留 errorCode()。Committer.scala:76 据 false 决定是否写 manifest：标记查询失败、后续写请求成功时，会覆盖已提交清单。isRegistered 同样会把查询失败当作未登记；快照入口也会把存储访问失败误报为无快照。

修改建议：只有明确的原生 NotFound 状态返回 false；其他错误保留原始原因并终止本次操作。

验收：分别覆盖不存在、存在、权限错误和网络错误。后两种情况下必须抛错，且不得调用 manifest/marker 写入或登记 RPC。

04 · P2 · 普通 Array 字段创建 writer 时失败，写入格式也与 Milvus 不一致

触发：向包含普通 Array<Int32> 等标量数组的 collection 执行 schema 合法的 append/backfill。

证据：SparkSchemaMapper.scala:118。mapper 把普通 Array 构造成 Arrow List，SparkSchemaMapper.scala:148 的 new Field(..., null) 又没有提供 child。MilvusV3Writer.scala:378 创建 VectorSchemaRoot 时，Arrow ListVector 要求恰有一个 child，因而报 Lists have one child Field. Found: none。本轮核对了本机 Arrow 18.1.0 源码的 ListVector.initializeChildrenFromFields。此外 ArrowTypes.scala:33 和 ArrayCodec.scala:5 已规定 Milvus Array 以 Binary 保存，每行是 protobuf ScalarField；仅给 List 补 child 仍不是正确的 Milvus 文件格式。

修改建议：按 collection 中的 Array 逻辑类型与 elementType 生成 Binary 字段，并序列化 ScalarField；与读取侧共用数组格式契约。

验收：对所有支持的标量数组执行 InternalRow → writer → reader 一致性验证，覆盖空数组、null 和正常数组。现有写入 UAT 主要覆盖 Int64、VarChar、FloatVector，没有覆盖这条路径。

05 · P2 · 行式读取把 Float、Int8、Int16 标量数组当作向量

触发：读取非 null Array<Float>、Array<Int8> 或 Array<Int16>，显式设置 milvus.read.columnar=false。当前默认列式读取不受此分支影响。

证据：ArrowConverter.scala:178。isBinaryBackedVector 对 VarBinaryVector 为 true，而普通 Array 的 ScalarField 恰好存放在 VarBinary 中。ArrowConverter.scala:163 的 Short 分支和 178 行的 Float 分支先于通用 Array 解码，遇到 milvusType=Array 就报向量类型不匹配，无法到达 ArrowConverter.scala:188 的 decodeStoredArray。SparkTypes.scala:165 明确把 Int8/Int16 数组元素映射为 Short、Float 映射为 Float，因此这些分支可达。

修改建议：先区分 Milvus 逻辑类型 Array 与向量，再按 Arrow 物理类型解码。不能仅凭 Binary 的布局决定它是向量。

验收：同一份 Float、Int8、Int16 数组数据，分别以行式和列式读取并比较 null、空数组和数值；现有数组用例集中在 Long/String。

06 · P2 · 合法用户字段 timestamp 会挡住系统 field ID 1

触发：collection 有小写用户字段 timestamp，field ID ≥100；读取需要应用删除文件的 V3 段。

证据：SchemaMapper.scala:43。missingSystemFields 只要发现同名或别名，就认为系统 Timestamp 已存在，漏补 field ID 1。V3 按 ID 命名，ColumnBinding.scala:432 应用删除时仍请求列 1，C reader 在 reader.cpp:1139 因 schema 缺列而失败。快照 JSON 只过滤精确名字 Timestamp，小写用户字段会保留。Milvus 的 保留字段校验 按精确名称匹配，小写 timestamp 是合法用户字段；现有 SchemaMapperTest 也构造了该形状。

修改建议：按 field ID 判断系统列是否存在，保证 V3 的 0/1 与用户字段互不替代；V2 的名称别名兼容在其列绑定处单独处理。

验收：用户 timestamp(id≥100) 与系统 Timestamp(id=1) 必须同时保留；验证带删除文件的 V3 读取以及系统时间戳元数据投影。

07 · P2 · 选择最新或指定快照时，未选中的旧 V2 文件也必须可读

触发：同一 collection 的快照目录有旧快照 A 和完整的新快照 B；A 的某个 V2 列组用于读取 footer 的首个 parquet 文件已被 GC 回收。选择 latest 或指定 B。

证据：SnapshotCatalog.scala:200。select 先对全部 JSON 调用完整 read，之后才按名字或时间筛选。SnapshotCatalog.scala:302 在 read 内执行 V2 resolver，FooterV2SegmentResolver.scala:202 会读取旧段 parquet footer。因此 A 的数据文件缺失会在选择 B 之前直接中断。Catalog 设计已明确不提供快照保留策略、旧文件可能被回收；失败应属于选中的快照，不能使未选中的旧段成为 B 的读取前提。

修改建议：拆开快照元数据解析与 segment materialization：先根据 JSON 的 name/create_ts 选中一个候选，再仅解析它的 Avro/footer。仍严格报告元数据本身的歧义或损坏。

验收：A 的 JSON 合法但其 parquet 缺失，B 完整；latest/byName(B) 成功且不打开 A 的数据文件，byName(A) 保留明确缺文件错误。

08 · P2 · 按桶静态 provider 被继承的全局 AssumeRole ARN 覆盖

触发：全局使用 AssumedRoleCredentialProvider 并配置 role ARN；目标桶 B 显式覆盖为 SimpleAWSCredentialsProvider，同时设置 B 的静态 access/secret key。

证据：HadoopStorageKeys.scala:35。翻译代码逐键按桶优先、全局兜底，但不读取有效 aws.credentials.provider，于是仍继承全局 ARN。StorageProperties.scala:136 看到 ARN 后删除 B 的静态 keys；s3_filesystem_producer.cpp:181 随后选择 AssumeRole，实际使用的身份与配置指定的身份不同。项目 MilvusBackfill.scala:2654 本身会为静态目标桶生成 Simple provider 覆盖，属于实际支持场景。

修改建议：先求目标桶的有效 provider，再决定输出 role、静态 keys 或 IAM 属性；与 BackfillConfig 已有的 effective-provider 判断统一。

验收：全局 AssumeRole + 按桶 Simple + 按桶静态 keys 时，最终属性必须保留 B 的 keys 且不带全局 role；另测按桶 AssumeRole 覆盖和纯全局配置。

09 · P2 · Hadoop 的 TLS 配置没有传给原生存储，HTTPS 被改为 HTTP

触发：部署通过 spark.hadoop.fs.s3a.connection.ssl.enabled=true 或按桶同名配置启用 TLS，endpoint 为 minio.example:443，后端仅接受 HTTPS；没有重复设置 fs.use_ssl。

证据：HadoopStorageKeys.scala:34。映射表缺少 connection.ssl.enabled。StorageOptions.scala:187 也没有补取 Hadoop 的 SSL 开关，随后 StorageProperties.scala:45 默认写入 fs.use_ssl=false；C 在 s3_filesystem_producer.cpp:152 根据它选择 HTTP，连接 TLS-only 后端失败。该兼容入口明示支持已有 Hadoop 配置，因此不应要求用户额外重复一套开关。

修改建议：将有效的按桶/全局 SSL 配置转换到 fs.use_ssl，并保持显式原生选项的优先级；同时核对同一映射表的 path.style.access。

验收：无需真实服务即可断言按桶 true 覆盖全局 false，并生成 fs.use_ssl=true；显式 fs.use_ssl 的优先级也应固定。端到端另验证 TLS-only 后端。

10 · P2 · writer 没有使用读取侧解析后的存储配置

触发：环境有可用 IAM 身份，只给 snapshot path、fs.bucket_name、fs.address、fs.use_ssl=true，未给静态 keys、role_arn、use_iam；同配置读取成功后执行合法 schema 的 append。Hadoop-only endpoint/keys 部署也受影响。

证据：MilvusV3Writer.scala:232。读取侧 StorageOptions.scala:168 会翻译 Hadoop 配置、别名并补 IAM；但 MilvusTable → WriteBuilder → WriterFactory 原样传 MilvusOption，executor 直接 StorageProperties.from(originalOptions)，因缺静态 key 抛 fs.access_key_id must be set。Hadoop-only endpoint 则会报缺 fs.address。MilvusV3Writer.scala:155 的 job committer 也没有翻译 Hadoop 配置，不能修补这一差异。

修改建议：在 driver 解析一次完整原生属性包，让 task writer 与 job committer 共用；不要只在 executor 补 IAM 而继续遗漏 Hadoop 配置。

验收：对 IAM 环境配置、Hadoop-only 静态配置和原生 fs.* 三种输入，断言 driver、task writer、committer 获得一致的属性；通过公开 DataFrame append 入口验证。

11 · P2 · Linux Make 检查的 JNI 路径与 CMake 输出路径不同

触发：Linux 上从干净产物开始执行 make build-native-jni 或 make copy-native-libs。

证据：Makefile:44。Make 期望 cpp/build/Release/lib/libnative-storage-jni.so。自身 CMakeLists.txt:21 优先找到 Release 下的 libmilvus-storage，CMakeLists.txt:98 随即把自身 JNI 也输出到 Release。上游 CMakeLists.txt:265 的 POST_BUILD 先复制上游两库及依赖到 lib/，并不认识之后才生成的自身 JNI。于是编译完成后，Makefile:127 的存在性检查仍失败，打包也收不到它。Docker 已使用正确目录，此意见针对 Make 工作流。

修改建议：显式约定一个自身 JNI 输出位置，并让 Make 的检查与复制使用该位置；保留上游 lib/ 的依赖收集用途。

验收：干净 Linux 构建能通过 make build-native-jni 和 copy-native-libs，并确认 resources 中存在自身 JNI 及其依赖。此次仅核对脚本，没有执行构建。

12 · P2 · VarChar 主键统计用 UTF-16 排序，生成与 Milvus 相反的范围

触发：一个 segment 同时含合法 VarChar 主键 U+E000 和 U+1F600（😀）。

证据：PrimaryKeyStats.scala:103。Java String.compareTo 按 UTF-16 比较，当前生成 minPk=😀, maxPk=U+E000；Milvus 的 primary_key.go:172 使用 Go 字符串的 UTF-8 字节顺序，恰好相反。segment_loader.go:1283 直接载入文件边界，pk_statistics.go:85 在检查 Bloom filter 前先按此范围排除主键。当前 writer 已经会写出错误范围；当前新 append 段尚不能通过 Register 登记，本条不声称线上已发生删除遗漏。

修改建议：用与 Milvus 一致的无符号 UTF-8 字节顺序计算 min/max，不使用 Java UTF-16 字符串顺序。

验收：以 U+E000 与 U+1F600 以及 ASCII、中文混合键验证边界；按 Milvus 的范围规则断言所有输入键都不被排除。

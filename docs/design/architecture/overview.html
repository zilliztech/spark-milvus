01分层与模块

1.x 的七条路径各带一套入口、配置、凭证和类型处理，没有一层封装 Milvus Storage 的读写。2.0 把这一层抽出来：接口层只做翻译，核心层做全部计算，原生层只封装两个 C++ 库。

我们写的代码 我们写的模块 不改的：Spark、Milvus、对象存储 卡在 Milvus 侧

02目录与包

每个模块一个目录，每个包一个职责。spark/base 和 apps/base 不是独立模块，只是四条 Spark 线共同引用的源码目录；1.x 的代码还在根目录的 src/ 里，迁移一个模块一个模块来。

03读路径

读全程不经 Milvus 服务：driver 只碰元数据，从快照定分区和谓词；executor 只碰自己那一片，把删除和谓词合成一张位图，交出列批。

拷贝账：多出来的四次都在布局一致的地方

04写路径与登记

写止于作业清单。段按 Milvus Storage 格式直接落对象存储，把它们变成 collection 的一部分是 Milvus 的动作。今天两种登记的现状不同：给已有段加列组有接口，登记新段没有。

纠正一处早先的判断。此前把登记写成「走 External Collection refresh」，是我看表面得出的误判。refresh 是给 external collection 扫描外部数据源用的，它会重新切段、分配新段 id、在 Milvus 自己的路径下重建 Manifest，不采纳写入方的段目录，对原生 collection 直接拒绝。设计里已经删掉这条。

05构建矩阵

跟 lance-spark 一样：一份源码，每条维护中的 Spark 线编译一次，各自钉本线的 Spark、Arrow、antlr 和 Java 版本。共用模块必须按最低的那条线编译。

Arrow 和 antlr 不能钉在核心层。核心层是四条线共用的单一产物，钉一个 Arrow 版本就等于重犯 1.x 的病根：1.x 把 Arrow 钉在 17.0.0，而 Spark 4 用的是 18，部署时只能靠 userClassPathFirst 顶着。antlr 同理，Spark 3.5 带 4.9.3、4.x 带 4.13.1，生成的解析器不通用，放哪还没定。

07顺序

只有依赖，没有日期。判据是先做让下游列式算子能接上的部分：读路径是一切的基础，写路径的 append 等 Milvus 侧的接口，搜索层依赖列式读。

  1. 拆模块P0sbt 拆 core、native、spark 四条线，依赖规则进构建。不拆，后面每一项都在旧结构上打补丁。
  2. 核心层对象模型P0SnapshotCatalog 与 Snapshot、Segment、Manifest；四份类型映射合并成一份；路径归一。
  3. 列式读P0自有 storage JNI、ColumnVector、DeleteBitset。拷贝从 6 次降到 2 次，下游算子拿得到地址。
  4. 接口层P1Catalog、元数据列、统计、V2 谓词、Limit。三段名和回表在这一步到位。
  5. 谓词求值P1ExprTranslator、中间表示、求值器。语义按 Milvus 源码逐条复刻。
  6. 写路径P1SegmentWriter、Committer、register。backfill 分支可先做，append 等 Milvus 的 RPC，两件事可以并行谈。
  7. 向量层P2knowhere 的 C shim 与 JNI、索引加载与写出、暴力搜索；backfill 改成写模式。
  8. 产物与基准P3native jar 打包、四条 Spark 线的 CI 矩阵、读吞吐与拷贝次数与写端到端的基准；macOS 与 GPU 产物。
  9. 2.0.0 发布P3云上作业切换坐标与 SHA。

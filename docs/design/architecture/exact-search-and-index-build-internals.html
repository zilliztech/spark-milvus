精确搜索与大段建索引的代码级原理

精确搜索每核慢十倍，出在「谁来切工作」切错了层；6.2 GB 的段建不了索引，出在 64 位的链路中间夹了两处 32 位整数。算法本身没有问题。

  1. 问题一：精确搜索每核慢十倍。现象：Spark 任务拿几百到几千条查询对一段底库算全部距离，CPU 时间是应有的 10 倍。原因：Knowhere 把一次调用拆成每条查询一个任务，faiss 收到的永远是单条查询，只能走逐行内核，底库每个数搬进来只做一次乘加，瓶颈是内存带宽。修法：新入口把整批查询一次交给 faiss 走矩阵乘（SGEMM），一个数搬进来服务整批查询；并行改由 Spark 的任务数承担，调用内部单线程。
  2. 问题二：6.2 GB 的段建不了索引。现象：一个 segment 的向量超过 2 GiB，build_index 直接报错。原因：从连接器到 Knowhere C 层是一条 64 位的链路，中间却夹着两处 int：Java 的 ByteBuffer 容量是 int，连接器交出 ByteBuffer 时又自己写死了 2 GiB 上限。修法：加一个按地址和 64 位长度建索引的入口，跳过这两步，向量从 Arrow 的缓冲直接进 C 层。
  3. 问题三，测试时发现：Cardinal 构建下建出的 HNSW 读不回。现象：index 模式读回 build_index 写出的 HNSW 时整段拒绝。原因：带 Cardinal 的 Knowhere 里 HNSW 是 Cardinal 的索引，文件格式与 faiss 的不同，连接器读文件时只认 faiss 的头。修法：格式探测也认 Cardinal 的头（PR #164）。

一、精确搜索：为什么每核慢十倍，批量入口怎么快回来

1.1 老入口怎么拆：nq 条查询拆成 nq 个单条任务

Knowhere 收到 nq 条查询后，按条拆成 nq 个任务丢进自己的进程级线程池，每个任务只拿一条查询去调 faiss，所以 faiss 永远只看到 nx = 1。代码在 src/common/comp/brute_force.cc：

auto pool = ThreadPool::GetGlobalSearchThreadPool();
for (int i = 0; i < nq; ++i) {
    futs.emplace_back(pool->push([&, index = i] {
        ThreadPool::ScopedSearchOmpSetter setter(1);
        RETURN_IF_ERROR(brute_force_dense_impl<DataType>(xq, index, xb, inv_norms.get(),
                                                         cur_labels, cur_distances, dim, nb, topk, ...));
    }));
}
// brute_force_dense_impl：cur_query 指向第 query_idx 条，nx 恒为 1
faiss::cppcontrib::knowhere::knn_L2sqr(cur_query, xb, dim, /*nx=*/1, nb, topk, cur_distances, cur_labels, nullptr, id_selector);
  1. 怎么拆。BruteForce::SearchWithBuf 对每条查询向全局搜索池 push 一个任务；任务内先把 OpenMP 线程数设成 1，再以 query_idx 取出这一条查询调 faiss，nx 恒为 1。
  2. 拆到哪个池。这个池属于 Knowhere，连接器没有自己的池。knowhere::ThreadPool 来自 Knowhere 依赖的 milvus-common，包着一个 folly 的 CPUThreadPoolExecutor，随 libknowhere.so 加载进每个 executor 的 JVM，一个进程一个，该 executor 上所有任务共用。
  3. 池有多大。第一次用到时按整机硬件线程数创建，除非先调过 knowhere_search_thread_pool_resize；连接器目前没有调，这就是 G4 要补的选项。
  4. 为什么 Milvus 这么设计。在线服务一次请求只带几条查询，拆开才能用满多核、延迟最低。
  5. 为什么在连接器里不对。exact 模式里一个任务拿着几百到几千条查询，对着几十 MiB 的底库反复调；多核已经由 Spark 的任务用上了，每个核却在用最慢的取数方式（1.3）。

1.2 faiss 的分流：为什么永远走逐行

faiss 有逐行和 SGEMM 两条路，按查询数和有没有选择器分流；Knowhere 传进来的 nx 永远是 1，阈值又是 16384，SGEMM 那条路一次都到不了。代码在 cppcontrib/knowhere/utils/distances.cpp：

if (res.sel || nx < distance_compute_blas_threshold) {
    exhaustive_L2sqr_seq<BlockResultHandler>(x, y, d, nx, ny, res);      // 逐行
} else {
    exhaustive_L2sqr_blas<BlockResultHandler>(x, y, d, nx, ny, res, y_norm2);  // SGEMM
}
int distance_compute_blas_threshold = 16384;   // Knowhere 的 faiss 分支；标准 faiss 里是 128000，上游默认 20
  1. 分流条件。带选择器（位图）或查询数小于阈值，走逐行的 exhaustive_L2sqr_seq；否则走 SGEMM 的 exhaustive_L2sqr_blas。
  2. 阈值。Knowhere 的 faiss 分支设成 16384；标准 faiss 里是 128000，faiss 上游默认 20。
  3. 结果。nx 恒为 1，永远小于阈值，进逐行；带位图时 res.sel 非空，同样进逐行。所以 exhaustive_L2sqr_blas 在 Knowhere 里一次都没跑过。

1.3 逐行与分块的差别：每搬进一个数能用几次

乘加次数定死是 nq × N × d，快慢只看每从内存搬进一个数能用几次。逐行用 1 次就丢，分块用几百到几千次。

  1. 算得远比搬得快。8375C 一个 vCPU 每秒约 930 亿次乘加，从 L3 往一个核搬数每秒只有约 70 亿个 float（27 GB/s）。一个数搬进来至少要用十几次，乘加单元才不空转。
  2. 逐行：一个数用 1 次。老入口的内核 fvec_L2sqr_batch_4_avx512 把一条查询留在寄存器，扫一遍底库，底库每个数取进来做一次乘加就丢；nq 条查询把底库扫 nq 遍。瓶颈在带宽，所以加线程没用：8 个线程抢同一条 L3，每行反而从 125 ns 涨到 168 ns。
  3. 分块：一个数用几百到几千次。SGEMM 把底库切成 1024 行一块、查询切成 4096 条一块（distance_compute_blas_database_bs、distance_compute_blas_query_bs），一块底库取进缓存后对整块查询一次算完 Q·Bᵀ，每个数取进来服务整块查询。瓶颈换成乘加单元。
  4. 实测（8375C，单线程）。逐行每行 125 ns：内核 23.7，搬数 89，过滤加堆 12。同一个 knn_L2sqr、同一份数据整批传走 SGEMM，8.0e7 对/秒对 8.1e6 对/秒，9.9 倍。

名词

  • SGEMM：BLAS 单精度矩阵乘的标准例程名，S 单精度、GE 一般矩阵、MM 矩阵乘。OpenBLAS、MKL 都实现它。
  • Q·Bᵀ：Q 是 nq × d 的查询矩阵，B 是 N × d 的底库矩阵。乘积是 nq × N 的表，第 (i, j) 格是查询 i 与底库 j 的内积，一次矩阵乘算完所有对。
  • 从内积到距离：IP 直接用内积。L2 按 ‖x‖² + ‖y‖² − 2x·y 还原，两个范数事先算好，负数截成 0。

实测把这个差别量了出来（Xeon 8375C，单线程）：逐行路径每行 125 纳秒，其中内核本身 23.7 纳秒，从 L3 把这一行搬进来 89 纳秒，逐行过滤加堆 12 纳秒；同一个 knn_L2sqr、同一份数据整批传走 SGEMM，8.0e7 对/秒对 8.1e6 对/秒，9.9 倍。瓶颈从内存带宽换成了乘加单元。

1.4 新入口 knowhere_bruteforce_batched 做了什么

把整批查询一次传给 faiss 换来 SGEMM，同时把调用内部压成单线程，并行交给 Spark 的任务数。不改 faiss，不改老入口，在 C 接口层直接调 faiss 导出的三个函数（src/c_api/c_api.cc，b9497f4f）：

Require(FP32 底库与查询; metric 是 L2、IP 或 COSINE);
SingleThreaded single;   // RAII 对象：构造时改设置，作用域结束时恢复
knn_L2sqr(xq, xb, d, nq, nb, k, distances, ids, nullptr, nullptr);   // 整批 nq；老入口这里是 1
// IP 调 knn_inner_product；COSINE 先归一化查询、按底库范数倒数调 knn_cosine，与老入口相同
  1. 整批传。
    • 改调用：nx 从 1 变成 nq，faiss 才会走 exhaustive_L2sqr_blas。
    • 改阈值：distance_compute_blas_threshold 从 Knowhere 分支的 16384 临时改成 faiss 上游默认的 20，否则几百到几千条的查询组仍不够数。
  2. 调用内部单线程。并行交给 Spark 的任务数，调用内部两个库都压成 1。
    • 多出来的两层并行：走上 BLAS 路径后，OpenBLAS 算 sgemm 自带线程池；faiss 把 Q·Bᵀ 换算成距离那段循环是 omp parallel。两者默认都起满整机线程。
    • 为什么不能留：Spark 已经在这台机器上跑着 N 个任务，各自都调这个入口。再让两个库各开一套线程就是几十倍的超卖，两套线程池的空闲线程还互相自旋抢核；实测 7 加 7 个线程，吞吐只有单线程的一半。
    • 为什么不值得留：一次调用内多线程本身不划算，4 个 OpenBLAS 线程只有 2.3 倍；N 个单线程任务是 N 倍。
    • 怎么压：OpenMP 的线程数是每个调用线程各一份，在任务线程上设 1 即可。OpenBLAS 的是全进程一份（pthreads 版；local 版本的设置函数改的也是它），只能在有批量调用在跑时全进程保持 1。
  3. 改完恢复。阈值与 OpenBLAS 线程数都是全进程共享，同一进程里的老入口和建索引也在用，所以由 RAII 对象管。
    • 谁改谁恢复：第一个进入的调用保存旧值、写新值，最后一个退出的恢复；用互斥锁和在途计数配合，抛异常也会恢复。
    • 老入口不受影响：它以 nx = 1 调 faiss，够不到任何阈值，行为不变。

1.5 连接器怎么接

连接器按元素类型和度量选入口；新入口只收一块连续、没有洞的底库矩阵，所以批里有不该参与的行时，先把要参与的行拷成一块，搜完再把行号换回去；并行度交给 Spark 任务。代码在 core/…/index/ExactScan.scala：

private val BatchedMetrics = Set("L2", "IP", "COSINE")
if (dtype == DType.FLOAT32 && BatchedMetrics(metric)) batched(...) else perQuery(...)

// compact：把没被排除的行按原顺序拷进新缓冲，连续的一段一次拷；batchRows(k) 记下新缓冲第 k 行原来是批内第几行
var start = excluded.nextClearBit(0)
while (start < rows) {
  val end = ... excluded.nextSetBit(start) ...            // [start, end) 是连续的一段保留行
  target.setBytes(written.toLong * rowBytes, run)          // 这一段整体拷进新缓冲
  var row = start
  while (row < end) { batchRows(written) = row; written += 1; row += 1 }
  start = excluded.nextClearBit(end)
}
// collect：引擎返回的行号先查 batchRows 换回批内行号，再加批首行得到段内行号
  1. 分派。ExactScan.batch 看元素类型和度量：float32 且 L2、IP、COSINE 走 batched；其余元素类型走原来的 perQuery，位图原样交给老入口。
  2. 批里有不该参与的行时：先把参与的行拷成一块，再把行号换回去。
    • 为什么有这件事：一批底库里有些行不该参与，就是被删除的、被过滤条件排掉的、向量为空的行（SegmentVectors.Batch.excluded）。老入口用一张位图告诉 faiss 跳过它们；新入口不收位图，因为 faiss 一看到选择器就走回逐行路径（1.2），而 SGEMM 要的是一块连续的矩阵，中间不能有洞。
    • 做了什么：把要参与的行按原顺序拷进一块新缓冲，被排除的行不拷，得到一个没有洞的小矩阵。连续的保留行算一段，一段一次拷，删得少的批就是几次大拷贝。同时记一张表 batchRows：新缓冲第 k 行原来是批内第几行。
    • 怎么换回来：faiss 返回的行号是新缓冲里的。collect 先查 batchRows 换回批内行号，再加这一批在段里的起始行，得到段内行号；顺手检查换回来的行确实没被排除。
    • 代价：多一次内存拷贝，拷的量是保留行的字节数，每批每个查询组一次，与查询条数无关。没有排除行的批不拷，直接把 Arrow 的缓冲借给 faiss。
  3. 块大小。base 块改成常量 32 MiB（SearchResources.DefaultBatchBytes）：入口内部自己按 4096 × 1024 分块，32 与 128 MiB 实测同速；之前按 L3 推块大小的公式是给逐行内核的。
  4. 并行度来自任务。spark.task.cpus 取 1。段组少于并发数时，SearchPlan.rangeCount 把查询切成 R = max(1, min(⌈并发数 ÷ 段组数⌉, ⌊查询数 ÷ 2,048⌋)) 个连续范围；按字节切出的查询组少于 R 时，evenGroups 把查询集均分成一个范围一组（决策 28、32）。任务数 = 段组数 × R，代价是底库读取乘 R。

1.7 UAT 实测：CPU 时间降 10 倍，总时长为什么只降三成

2026-09-21 到 23 的 UAT 实测：CPU 时间降了 10 倍，总时长只降三成，因为剩下的时间花在读底库上。

  1. 工作量相同。1k 查询 × 31M 行 = 3.1e10 对距离，两条路径算的对数一样。
  2. CPU 时间。老路径 executor CPU 6,308 秒，新路径 581 到 634 秒。每 CPU 秒算的对数从 4.9e6 到 4.9e7 至 5.3e7，正是 1.3 那个 9.9 倍在集群上的体现。
  3. 总时长。只从 320 秒到 231 秒。读 95 GB 底库串行在任务里，每任务 44 到 62 MB/s，CPU 只占运行时间的 13% 到 22%，其余时间在等 S3。
  4. 剩下的问题。算术这一半解决了，下一半在读取与计算的重叠。

二、大段建索引：6.2 GB 为什么建不了，地址入口怎么绕过

2.1 改造前的五步链路：两处 int 卡住 2 GiB

建索引是这条链路上唯一一次把整个 segment 装进一块缓冲的地方，五步里有两步用 int 计长度，6.2 GB 在第一处就停下。

  1. 第一处 int：连接器自己写死。IndexWriter.assemble 把整段向量装进一块 ArrowBuf（容量是 long），随后交出 ByteBuffer 时写死了上限（core/…/index/IndexWriter.scala）。UAT 上的报错就出在这一步：A segment of 6233038848 vector bytes exceeds one build buffer。 
    require(buffer.capacity() <= Int.MaxValue,
        s"${buffer.capacity()} vector bytes do not fit one ByteBuffer; build from the address")
buffer.nioBuffer(0, buffer.capacity().toInt).order(ByteOrder.nativeOrder())
  2. 第二处 int：Java 类型决定。KnowhereIndex.build(ByteBuffer …) 经 NativeBuffers.region 只查 direct、可写、字节序，JNI 用 GetDirectBufferAddress 与 GetDirectBufferCapacity 取地址和长度。容量虽以 jlong 返回，ByteBuffer 的 capacity、position、limit 在语言里都是 int，任何 direct buffer 都不能超过 231 − 1 字节；Arrow 的 nioBuffer(long, int) 因此只能切出 2 GiB 以内的窗口。
  3. 其余三步没有上限。Arrow 的缓冲用 long 计容量，分配器对超过 Integer.MAX_VALUE 的请求直接走 Unsafe 分配，所以 6.2 GB 的 ArrowBuf 分得出来；knowhere_vectors 的 bytes 是 uint64、rows 是 int64；Index::Build 自己复制一份向量再建图。

2.2 C 层本来就是 64 位

C 接口从一开始就用 64 位长度和行数，并自己做溢出、容量、对齐检查，没有 2 GiB 的概念。

typedef struct { const void* data; uint64_t bytes; int64_t rows; int32_t dimensions; int32_t dtype; } knowhere_vectors;

uint64_t CheckVectors(const knowhere_vectors* vectors) {
    Require(vectors->rows >= 0 && vectors->dimensions > 0, ...);
    const uint64_t row_bytes = ... CheckedBytes(vectors->dimensions, element);   // 乘法溢出检查
    const uint64_t bytes = CheckedBytes(vectors->rows, row_bytes);
    CheckBuffer(vectors->data, vectors->bytes, bytes, element);   // 容量够、非空、按元素宽度对齐
    return bytes;
}
  1. 类型。knowhere_vectors 的 bytes 是 uint64，rows 是 int64。
  2. 检查。CheckVectors 先算 rows × 每行字节，两次乘法都带溢出检查；CheckBuffer 查缓冲容量装得下、指针非空、地址按元素宽度对齐。
  3. 所有权。knowhere_index_build 校验后先把整份向量 memcpy 进 IndexResource.build_data（c_api.cc 412 到 414 行），再把这份拷贝交给 Index::Build，调用返回后调用方的缓冲可以释放。这份拷贝是索引资源的成员，Build 返回后不释放，索引关闭才走。

2.3 地址入口：跳过用 int 的两步

Java 加一个重载，JNI 加一个 native 方法，用地址和 64 位长度直接填同一个 knowhere_vectors、调同一个 knowhere_index_build（42019082）。

// Java
public synchronized void build(long address, long bytes, long rows, int dimension, String parameters) {
    if (address == 0L) throw new IllegalArgumentException("A native address is required");
    if (bytes < 0L)    throw new IllegalArgumentException("The byte length is negative");
    NativeBindings.indexBuildAddress(requireHandle(), address, bytes, rows, dimension, dtype.code, parameters);
}
// JNI
knowhere_vectors vectors{reinterpret_cast<const void*>(static_cast<uintptr_t>(address)),
                         static_cast<uint64_t>(bytes), rows, dimension, dtype};
CheckStatus(env, knowhere_index_build(handle, &vectors, config.get()));
  1. 绑定层。KnowhereIndex.build(long address, long bytes, long rows, int dimension, String parameters) 查零地址、负长度后转 NativeBindings.indexBuildAddress；JNI 把地址和长度原样填进 knowhere_vectors。ByteBuffer 版入口保留给小数据与单测。
  2. 连接器：装配。Assembled 暴露 address = buffer.memoryAddress() 与 byteLength = buffer.capacity()，不再转 ByteBuffer。
  3. 连接器：构建。IndexWriter.buildFromAddress 要求地址非零、bytes ≥ rows × 每行字节数；SegmentIndexBuild 改走它，并在构建期间持有 Assembled 不关闭；NativeVectorIndex.build(indexType, dataType, version, address, bytes, rows, dimension, parameters) 校验索引版本区间后转调。

2.4 谁保证那块内存合法：以前是 JVM，现在是调用方

以前 ByteBuffer 由 JVM 担保地址和长度都对；现在调用方自报地址和长度，代码只能查零地址、负长度、容量和对齐，查不了那块内存是否真的存在。

以前谁保证ByteBuffer 的容量由 JVM 保证：地址合法、区间可读、长度不会报大
现在谁保证调用方自报地址与长度，并保证那块内存是活的、按行主序本机字节序放着向量、调用返回前不释放不改写。连接器传的是分配器给出的 capacity()，且 Assembled 在构建期间不关闭
仍然查什么Java 与 JNI 查零地址、负长度；C 层 CheckBuffer 查容量装得下 rows × 每行字节、地址按元素宽度对齐；两侧都查不了那块内存是否真的存在
没放开什么行数仍限 231：null 行位图按 Int 索引；6.2 GB 的 768 维 float32 是 200 万行，远在其下

2.5 内存占多少：构建时三份东西，加载时从 3 倍降到 2 倍

构建期间同时有三份东西在内存里，其中一份是 C API 自己拷的；Cardinal 引擎的索引虽小，构建峰值却是向量的 4.6 倍，executor 的预留要按这个倍数算。加载侧原来也多拷一份，523518f7 已去掉。

  1. 三份东西。Arrow 装配的整段向量（6.2 GB，算在任务的 Arrow 上限里；Netty 分配器对超过 Integer.MAX_VALUE 的请求直接走 Unsafe，不进池）、C API 在 build_data 里拷的一份（索引关闭前一直在）、索引自己存的一份（faiss HNSW 存原始向量，Cardinal 存 BF16 加量化结构）。
  2. faiss HNSW。索引保存原始向量，每段索引 6.2 到 6.7 GB，executor 峰值 15 到 18 GB。
  3. Cardinal 引擎。向量以 BF16 存、带 RBQ8 精化与 SQ4 图量化（Cardinal 的量化格式名），索引只有 2.2 GB；构建峰值却到 21 到 28.5 GiB，是向量的 4.6 倍。executor 的 memoryOverhead 要按最大段乘这个倍数留，30 GiB 只差 1.5 GiB。
  4. 线程。Knowhere 的构建池按整机起线程，8 核的任务实测用 14 到 15.7 核，这是线程池选项 G4 的现场。
  5. 加载侧的同一模式，Knowhere 523518f7 已改；连接器当前运行的 gitlink b9497f4f 不含这一改动。
    • 原来：读回索引搜索时，knowhere_index_deserialize 也先把 BinarySet 的字节拷一份（IndexResource.deserialized_data），加载峰值是文件的 3 倍，常驻 2 倍。
    • 现在：调用方 BinarySet 的条目按 shared_ptr 追加进一个局部 BinarySet 交给引擎，拷贝去掉，峰值降到 2 倍，常驻不变。常驻的 2 倍是 Cardinal 适配器持有的原始字节加加载出的结构：它在 Deserialize 里把 GetByName 拿到的 shared_ptr 存成成员，字节随索引存活，调用方关掉 BinarySet 也不悬空；faiss 系经 MemoryIOReader 读进自己的结构，不留引用。
    • 契约：BinarySet 一经交给 deserialize 就冻结，之后 knowhere_binary_set_write 返回 KNOWHERE_INVALID_ARGUMENT，allocate 换新缓冲和 close 仍允许。既堵住往被索引引用的字节里写，也堵住另一线程在 Deserialize 进行中写同一缓冲。
    • 建索引侧未动：build_data 那一份仍在，是下一条候选。连接器侧的现状：gitlink 是 b9497f4f，规划器里「加载时多一份」的常量 SearchPlan.Footprint.IndexLoadingCopies 仍为 1，加载峰值仍按 3 倍规划。跟进：gitlink 指到 523518f7，常量 1 改 0，重编 Cardinal 原生包，UAT 复验加载峰值。

三、Cardinal 构建下的 HNSW 是另一种索引：建出来的文件为什么读不回

带 Cardinal 的 Knowhere 里，HNSW 这个名字指的是 Cardinal 的索引，写出的文件格式与 faiss 的不同；连接器读文件时只认 faiss 的头，所以整段拒绝。修法是让它也认 Cardinal 的头。

  1. 名字换了主人。编进 Cardinal 后，Knowhere 把 faiss 的 HNSW 注册为 HNSW_DEPRECATED，HNSW 这个名字归 Cardinal（src/index/hnsw/faiss_hnsw.cc 的 KNOWHERE_WITH_CARDINAL 分支）。含 Cardinal 的 bundle 上 build_index 建出来的就是 Cardinal 索引。
  2. 文件长什么样。Cardinal 经 BinarySet 序列化的流：开头是 Cardinal 的头，依次 8 字节版本、8 字节索引名 unknown、8 字节索引类型 HNSW、8 字节数据类型 BF16、维度、行数、8 字节度量、8 字节总长度，头之后是索引数据。没有 Milvus 写 _mem.index.bin 时那 24 字节的 CARD footer。
  3. 连接器为什么拒绝。PayloadFormatProbe 读文件开头判断用哪个引擎加载，原来只认两种：faiss 的 IH* 魔数，和 Milvus 文件末尾的 CARD footer。Cardinal 的流两样都没有，读回时整段拒绝：Persisted HNSW payload starts with …。
  4. 修法。捕获的头从 4 字节扩到 32 字节；声明的索引类型是 HNSW 且偏移 16 处写着 HNSW 时，选 Cardinal 引擎加载，流本身的校验交给 Knowhere（PR #164，issue #163）。

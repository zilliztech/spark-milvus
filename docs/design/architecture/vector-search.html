使用 Milvus 索引文件完成向量查询

Spark 的每个任务加载固定快照中对应段的向量索引，执行搜索并读取命中行；Spark 合并所有段的候选，返回全局 TopK。 TopK 指按指定距离或相似度排序的前 K 条结果。近似最近邻搜索（ANN）通过索引减少搜索工作量，其召回率需要相对于精确搜索验证。

本页是 issue #125 在 refactor/v2 的实现契约。 2026-09-16 已接入类型化索引元数据、持久化文件解码、Knowhere 加载与搜索、过滤位图、按行号回表及 Spark 全局 TopK；索引由任务独占，不设跨任务缓存。 2026-09-16 04:48 UTC，真实 UAT 的十万行 HNSW/COSINE 查询验收通过：原始 JNI 对照、独立全量参考、标量/空值过滤和回表均通过。上游 DiskANN 测试仍失败，当前 Cardinal 产物仅供本机验证，详见第 6.4 节。扩展范围统一记录在总体设计第 4 节。

交付范围当前代码查询入口 执行流程索引元数据原生接口 结果语义资源与失败实现与验收

1. 交付从真实索引文件开始，到全局查询结果结束

本次实现 V1 的原生接口、V2 的持久化索引加载、V5 的原生暴力执行，以及 V7「显式向量索引查询与全局 TopK」。 索引入口默认严格加载，只有权威来源明确无索引且用户设置 allowUnindexed=true 时才回退。V4 跨任务缓存与 W6 索引写出不在本次实现中。

当前代码范围为非 nullable FloatVector、CPU HNSW、L2/IP/COSINE，且索引覆盖整个 sealed segment。 sealed segment 是已经封存的数据段。文件路径支持 Milvus binlog/Parquet 封装及 Cardinal 原始 CARD 流，按真实 payload 标识选择 Faiss 或 Cardinal 引擎。 nullable 行号映射、DiskANN 本地文件管理器、Faiss 量化与 multi-view 索引尚未支持；Cardinal 已验证的真实样本及边界见第 6.4 节。

Storage V2 和 V3 共用同一查询计划与索引执行器。它们的快照解析、列组读取与回表分别由现有存储适配承担。 输入中任何段不满足支持条件，必须按明确策略处理，不能漏掉该段继续返回看似完整的答案。查询过程只读固定快照与对象存储。

2. 当前实现贯通元数据、执行器和 Spark 结果计划

持久化索引与原有逐段暴力搜索共用读取适配；索引执行、过滤和格式解析留在 core。

3. 显式查询方法，返回的 DataFrame 包含全局合并

2026-09-16：用户要求完成使用索引的开发，本节确定为实现契约。新增入口采用下述显式方法；旧逐段暴力入口保留。索引入口默认严格使用持久化索引，缺失信息、损坏文件、不兼容引擎均报错。仅来源明确无索引时允许显式选择原生暴力回退。索引对象由任务独占并关闭，跨任务缓存仍属 V4 后续能力，不作为本次正确性的前提。

spark-base 的 spark.read 包提供 MilvusSearch.search。 它接收快照定位和查询参数，构造计划，不立即执行 action。共享源码覆盖四条 Spark 线；apps.search 只放调用示例和作业。 当前调用方式如下；真实 Cardinal 运行状态见第 6.4 节。

val hits = MilvusSearch.search(
  spark = spark,
  options = Map("milvus.snapshot.path" -> snapshotPath),
  vectorColumn = "embedding",
  queryVector = Array(0.1f, 0.2f, 0.3f),
  k = 10,
  metric = "COSINE",
  searchParameters = Map("ef" -> "64"),
  filter = Some("category == \"books\""),
  outputColumns = Seq("id", "name")
)
hits.show(false)

filter 按既有 R7 的 Milvus 表达式契约进入 core.expr，示例表示在满足类别条件的行中搜索。 搜索返回后的 hits.filter(...) 是对搜索结果再过滤，语义不同。PlanParser 与 Evaluator 实现比较、IN、IS NULL、AND/OR/NOT 及三值逻辑；不支持的表达式在执行前报错。

  • 输入是固定快照的定位、字段名、一个查询向量、K、metric、搜索参数、过滤表达式和输出列。任意 join/union 后的 DataFrame 不属于此入口的输入契约。
  • 解析复用 SnapshotSources → MilvusTable。同一个 Snapshot 经共同规划器生成任务；方法内不另写快照枚举或对象存储读取逻辑。
  • 返回列为请求的业务列加 _segment_id: Long、_row_offset: Long、_score: Double。规划期拒绝名称冲突；schema、InternalRow 和列批必须一致。
  • 单查询输入先完成交付；多查询批处理以后扩展请求结构，不在这一版假装支持。向量长度、有限数值、K、metric 和索引参数均严格校验；COSINE 的零向量按明确错误处理。
  • 旧 vector.search.* 暴力入口保留段内 TopK；全局结果由显式 MilvusSearch.search 构造。没有添加负责推导全局合并的 Spark 扩展规则。

4. 每段产候选，Spark 负责跨段合并

索引搜索是同一个读取任务的一种执行方式。普通扫描、筛选列读取和命中行回取共用 SegmentReaderRegistry。 索引句柄只在 executor 创建。

  1. driver 固定快照、每段数据版本、索引构建和文件集合。core.read.plan 负责投影成可序列化 SegmentReadTask；Spark 只适配为 InputPartition。
  2. executor 先确定搜索执行方式，再打开所需数据列。校验索引描述后为本任务解析持久化文件并创建 Knowhere 索引；不会先拉取原始向量批，也不获取跨任务缓存。
  3. 只读取构建删除/过滤位图所需的主键、时间戳和标量列。将位图与查询向量交给索引执行器，得到该段有效候选。
  4. 以命中 offset 经共同 reader 的 take 读取输出列，恢复候选分数次序。首版每段回取局部候选，至多约 段数 × K 行，再送入全局合并。
  5. MilvusSearch.search 组合 Spark 已有的 orderBy + limit，最终返回 K 条或全部可用结果。全量向量和索引对象都不收集到 driver。

此处的全局排序属于向量查询方法构造的 Spark 计划，不实现通用 SupportsPushDownTopN。 查询分支不得把普通扫描的局部 Limit 当作索引搜索前的行数截断，否则会排除本应参与搜索的数据。

5. 索引文件引用跟随固定快照，不能按目录猜测

集合级索引定义与段级索引文件分开建模。根 JSON 的 indexes 说明字段上的索引定义，真正可加载的文件引用需要从快照对应的段记录取得。 现有 Avro schema 已定义 index_files；解析器必须读取并保留它。V3 数据 Manifest 的索引登记是另一种来源，不能当成唯一前提。

模型变更需要保存和校验的内容
Snapshot.indexes字段 id、索引 id/名称、类型和参数。与 schema 的向量类型、维度和请求 metric 一致。
SegmentIndexcollection/partition/segment/field/index/build id、文件引用、行数、序列化大小，以及来源提供的各类版本。区分 index_version（构建/路径版本）、current_index_version（向量格式版本）、index_store_path_version（文件路径布局版本）。
索引状态Available 表示来源完整且有索引；Unindexed 表示权威来源明确无索引；Unknown 表示来源没有提供足够信息。空列表不能代替 Unknown。
SegmentReadTask固定的数据布局版本、不可变索引描述和删除来源；查询另以 SegmentIndexQuery.Request 传入执行器。跨进程只携带描述和配置，不携带文件内容、已解码索引或 native pointer。

索引读取从已选快照的段记录开始，补齐 SegmentManifestReader → SnapshotCatalog → Segment → SegmentReadTask。 解析 Milvus 元数据仍由其现有解析器负责；milvus-storage 的 Manifest 由原生层解析。Milvus binlog 的共同事件与 Parquet payload 解析归 core.codec，索引加载归 core.index。V2 resolver 和 backup 来源必须保留它们实际拥有的索引信息，缺信息就标 Unknown。

所有路径经 core.path 归一，文件访问复用 core.io.ObjectStore 及 milvus-storage 的 C filesystem。 同一版本同时决定索引、列组和删除视图；无法证明行号对应关系时拒绝加载。不能在搜索中重新查询在线最新索引，也不能通过列举 index_files/ 找“最新”文件拼入旧快照。 若来源没有某个版本字段，按其已验证的格式契约处理，不能虚构版本值。

6. 解码 Milvus 文件，再交给 Knowhere

Knowhere 的 BinarySet 是按名称组织的二进制块集合。对象存储中的一个索引文件并不一定就是一个可直接加载的块。 加载必须处理以下步骤：

  1. 校验对象大小并识别文件格式。Milvus envelope 解析 descriptor/index events，再按 NONE、INT8 Parquet 或旧 STRING payload 解码；Cardinal 原始流按第 6.3 节校验 CARD footer。不能跳过一个固定长度文件头就认定完成解码。
  2. 按目标版本验证过的文件命名规则取得 BinarySet entry name；Milvus 的内存索引加载链使用文件 basename，不能假设事件头含原始块名。出现 SLICE_META 时，按其记录的逻辑块名、分片数量和总长度还原；未切片对象不要求该字段存在。16 MiB 是某些版本的默认切片值，不是解码常量。
  3. 验证构建引擎、索引类型、向量类型和格式版本，创建匹配的 Knowhere 实例，再调用 Deserialize。
  4. 调用索引的 Search，传入查询、参数及排除位图；按已经验证的 label 映射输出段内物理行号和分数。

解码格式的依据是 Milvus 的 DataCodec、 PayloadReader 和 Slice。 实现时锁定目标 Milvus 版本并用它生成的文件验证这些格式分支。

6.1 当前交付：加载 Knowhere PR #1829 的原生产物

Knowhere 的 C 接口、JNI、Java API 和原生库加载器由上游分支提供。 构建来源固定为 PR #1829 的 LawrenceTL92/knowhere-contrib 仓库、codex/knowhere-jni-pr 分支，提交 9dc2b8ad537502d408bc33af05727453295d6622。 Connector 的 native-vector 消费该提交编译的 Java 和原生产物；原先计划在本仓库编写 mv_* shim 和 JNI 的方案由此替代。

NativeVectorLibrary 是 Connector 的加载入口：可以显式初始化，暴力和索引搜索在首次使用时调用同一个入口。 它调用上游 io.knowhere.Knowhere.cAbiVersion()，触发上游加载器；上游绑定校验 C 接口的二进制兼容版本（ABI）为 1，Connector 读取版本范围供诊断。 同一类加载器内的并发调用共享已完成的初始化；加载失败和版本不匹配直接传播，不能被解释成无索引、空结果或自动切换搜索算法。 当前普通扫描不需要向量库，不能在 Connector 类初始化或打开普通扫描时强制加载。

原生产物保留上游 native/knowhere/1/<platform> 布局。平台选择、依赖集合、校验和验证、临时目录提取及本地库加载顺序都由上游加载器负责； 本仓库不增加第二个提取器、System.load 路径或 native 方法声明。打包保留 io.knowhere 包名，不能通过 shading 改写 JNI 所依赖的 Java 类名。 上游 Java API 以 Java 11 为基线；本模块不引入 Spark 或 Arrow。

该上游构建需要在 JVM 启动前预加载 JRE 的 libjsig，使原生库与 JVM 的信号处理兼容。启动脚本和实际 driver/executor 环境必须在启动进程时满足该条件， Java 加载入口无法在 JVM 已启动后补做它。构建和部署同时核验目标平台、CPU 架构、依赖集合及 C++ 运行时；具体命令见 库加载构建说明。

native-vector/knowhere.properties 是提交、源码归档摘要与 API 版本的共同来源。 sbt 仅构建固定源码中的 Java API，输出进入模块的 target 缓存；原生编译显式调用 scripts/build-knowhere.sh build。 已有固定 CI 产物可通过同一脚本的 import-ci 校验源树及摘要后导入。平台 JAR 保持上游字节不变，旁置文件记录来源提交与 JAR 摘要。 -Dknowhere.native.jar 选择的平台 JAR 进入运行时和 assembly，构建校验来源、平台、ABI 和文件摘要；普通编译不要求原生库。

库加载的验证条件是：从固定提交编译的分发产物中加载 JNI，校验 ABI 和版本；重复及并发初始化正确；缺少产物、错误平台或不兼容 ABI 明确失败。 纯 JVM 测试覆盖初始化状态和错误传播，实际原生产物的独立 JVM 测试验证启动环境、资源打包及上游加载行为。 持久化文件解码、Deserialize、搜索、回表和 Spark 全局 TopK 已接入代码；它们的运行验收必须使用实际索引，库加载成功不能代替。跨任务缓存尚未实现。

2026-09-16 的库加载实测中，与既有 native-storage 以两种顺序加载并查询版本均通过；额外的真实搜索探针发现，先加载现有 storage 的 Folly 再启动 Knowhere 搜索线程会崩溃。 相同 Folly 版本的两套构建不能据名称推定二进制兼容。第 6.2 节的共享依赖打包已解决所记录 OSS 和 Cardinal 组合的该问题；两个组合分别通过两种顺序的真实 L2/IP/COSINE BruteForce、排除位图与 storage I/O。兼容记录只认精确二进制摘要，固定加载顺序不作为解决方案。

随后对完整重定位的检查发现，旧 Arrow 存在 9 个未导出的 AWS CRT 引用，合并后的 Folly 存在 4 个缺少 libaio 依赖声明的引用。上述延迟绑定下的功能通过仅覆盖实际执行路径；修正原生依赖的重新编译尚在进行。新产物按 原生验收规则 检查全部符号、立即绑定加载及两种加载顺序，再运行真实实例回归。

6.2 当前查询入口改用 Knowhere BruteForce

现有 vector.search.* 入口保留逐段扫描，由 io.knowhere.Knowhere.bruteForce 对每批向量计算 TopK。 不为每批临时建立 FLAT 索引，也不读取持久化索引文件。集合级持久化查询使用第 3 节的 MilvusSearch.search。

spark.read.SegmentVectorSearch 只做 Spark 字段校验、Arrow 到向量值的转换以及命中行复制。 core.index.BruteForceSearch 管理每批的向量缓冲、排除位图、原生调用和跨批 TopK；结果携带原始段内行号和调用方提供的行值。 native-vector 的 NativeVectorSearch 触发已定义的库加载，再委托上游 Java API；不声明新的 JNI 方法。

一批对应一次同步调用。基向量、查询、位图、ID 和分数使用 Arrow allocator 分配的直接缓冲，调用结束后释放；查询生命周期通过 close 结束。 排除位图按最低位优先编码，1 表示删除或向量为 null；保留这些行的位置以维持原始 row offset。 有效向量的维度必须与查询相同，元素必须是有限值；空查询、非法 K、错误维度和格式损坏明确报错，不跳过异常或回退 JVM 距离计算。 每批至多返回 K 条，核心层合并为每段 K 条，只有进入候选集的行才复制；批数增长不增加保留行数。

Knowhere 输出 float32 分数。IP 和 COSINE 降序；L2 原生为平方距离。core.index.BruteForceSearch 保留原生分数并据此合并 TopK；只有旧逐段入口的 spark.read.SegmentVectorSearch 在输出时对 L2 取一次平方根，保持该入口的欧氏距离语义。索引模式显式允许的无索引回退沿用平方距离，不执行开方后再平方。 删除和 null 在搜索前排除，不能先取 K 再删；未填满的原生结果（ID=-1）不返回。 相等分数按已返回候选的段内行号排序，原生在第 K 名处的并列截断不承诺稳定 ID。此旧入口只保证段内 TopK，集合级合并由 MilvusSearch.search 提供。

这条路径会同时使用 storage 与 Knowhere。两者同名的动态依赖必须来自已验证的同一组产物，不能通过强制先加载 Knowhere 或预加载某份 Folly 掩盖冲突。 交付验证包含两种加载顺序的真实 BruteForce、L2/IP/COSINE、跨批 TopK、删除/null、非法数据及缓冲释放；原生库缺失或调用失败直接报错。

当前 Linux x86-64 的已验证组合采用 Knowhere 平台 JAR 内的共享依赖作为共同版本。 选中 knowhere.native.jar 时，构建将其非 Knowhere 引擎库生成到 storage 的 managed resources，并同步替换 storage 中指向相同 SONAME 的文件别名； 原始资源保留在源码目录，产物中每个 storage 资源路径只有一份有效文件。Knowhere 自身的平台 JAR 与 manifest 不变，两种加载顺序解析到字节相同的共享库。 构建扫描 native-vector/storage-compatibility*.properties，要求平台、storage 引擎摘要与 Knowhere JAR 摘要恰好匹配一条记录；缺失或重复匹配均失败。每条记录保存共享库摘要及 SONAME 别名，其他组合必须验证后登记，不能自动混用依赖。 不选 Knowhere 时 storage 的打包保持原样。验证记录涵盖两种顺序的 BruteForce 和本地读写，完整 storage UT 随最终产物配置运行。

6.3 索引文件解析与原生资源的归属

源码核对更正了初稿的依赖假设：固定的 milvus-storage 没有 Milvus index binlog 解码接口；现有 core.delete.DeltaLogReader 已在 JVM 解码同一种 descriptor/events 和 Parquet payload。将共同格式解析提取至 core.codec.BinlogCodec，删除与索引两条调用复用它；不再新增另一套 C 格式实现。文件访问仍全部经过 ObjectStore → native-storage → C filesystem，codec 只接受已经读到的字节，不访问文件系统。这个归属符合第二层负责 Milvus 存储格式、第一层只包装已有原生接口的分层。

core.index.MilvusIndexFileDecoder 校验 index event、标识及 payload 类型，再由加载器按文件名与 SLICE_META 还原 BinarySet。单对象长度必须能由 JVM byte array 表达，超限在分配前失败。BinarySet.write 复制 payload，固定 Knowhere C API 的 deserialize 再复制 BinarySet 并由索引实例持有；因此解码 payload 复制完成后释放、输入 BinarySet 在 deserialize 后释放，索引在任务结束时关闭。加密文件和 nullable 行号映射在具备相应实现前明确拒绝，不当成无索引。

真实云端文件还存在另一种已核对的格式：Cardinal 直接写出的 _mem.index.bin 没有 Milvus descriptor/event。其最后 24 字节是 little-endian 的 CARD magic、序列化版本、global metadata offset 与 tenant metadata offset。IndexFileCodec 只在文件列表恰有这一个文件、footer 版本为 1 且两个偏移在文件内且顺序正确时采用这条格式分支；不能把任意非 binlog 文件当作原始索引。该文件不含 Milvus collection/segment/build 标识，来源依靠快照钉住的对象路径；加载后仍验证索引维度和行数。

Cardinal v3.0.8 的 know/cardinal.cc 中，Serialize 的 FileManager 分支和 BinarySet 分支调用同一个 index_->Save：前者写 _mem.index.bin，后者写 BinarySet[Type()]。因此 HNSW 的 CARD 文件完整字节可交给 BinarySet["HNSW"]，再通过上游 Java/JNI 的 deserialize 加载；不需要另写 JNI、抽取原始向量或重新建索引。这个转换依赖 Cardinal 引擎，不能用于开源 Faiss HNSW。构建从已验证的平台 JAR provenance 生成 META-INF/milvus/knowhere-runtime.properties 的 with_cardinal，NativeVectorLibrary.RuntimeInfo.cardinalSupported() 暴露这一事实；缺少该能力时，在反序列化之前明确拒绝 CARD 文件。

引擎选择依据完整逻辑 payload 的格式标识，不依据文件是否有 Milvus envelope。复制切片时只额外保留前 4 与后 24 字节，不二次下载：CARD footer 对应 Cardinal，要求 vector index version ≥9；Faiss 的 IHNf（Float32 HNSW Flat）与 IHN9（HNSW FlatCosine）对应 Faiss，要求 version ≥6。含 Cardinal 的 Knowhere 将 Faiss 注册为 HNSW_DEPRECATED，未含 Cardinal 时注册为 HNSW；两者的 BinarySet key 都是 HNSW。NativeVectorIndex.Loader.load(engineType) 把 factory 的 engine name 与 payload key 分开，同一个产物可加载这两种已支持的文件。Faiss 的量化 HNSW、multi-view 和没有已核对格式标识的旧文件明确拒绝，不让错误引擎先尝试反序列化。

首版加载边界为单个对象不超过 256 MiB、组装后的 BinarySet 总计不超过 1 GiB、SLICE_META 不超过 1 MiB。复制到原生 BinarySet 使用 1 MiB 临时缓冲；超限报错，不能等待分配失败后回退。搜索仅接收 HNSW 的 ef 参数，必须为正整数且不小于 topK；默认取 max(64, topK)。过滤后候选不足时至多尝试 8 次，逐次扩大 ef；仍不足明确失败，不执行 connector 自行决定的全量向量扫描。

这些对象与组装 payload 上限不等于原生引擎内部的反序列化内存预算：当前上游 C/JNI 没有暴露该预算控制，不能声称仅靠外层长度校验即可安全加载任意内部损坏的文件。交付日志记录每个对象实际读取的字节数、格式与引擎选择、成功的原生 deserialize 次数、search 调用次数和耗时；不会把快照声明的 serializedSize 当成实际读取量，也不记录凭证或存储 properties。

core.index 经 native-vector 使用固定提交提供的接口。C 接口、JNI 参数转换、异常转换与资源释放契约由 Knowhere 上游维护； 缺失能力继续在上游补齐。当前调用边界如下，运行兼容性仍按实际文件验证。

能力职责与资源所有权
版本与特性查询区分 C ABI 版本、库构建版本、引擎与索引格式能力；文件加载前核对后三者，不能把 ABI 校验当成文件兼容校验。

6.4 索引查询的首个里程碑必须使用 Milvus 生成的文件

已有本地实测材料证明：一个十万行 V3 段的索引引用位于快照段记录的 index_files，其数据 Manifest 的 indexes 为空。 文件总量约 41.6 MB，声明 HNSW/COSINE，向量格式版本为 10；2026-09-16 经 NativeObjectStore 读取真实对象后确认其 CARD footer，必须使用包含 Cardinal 的 Knowhere 构建。开源构建的 ABI/版本范围正确不表示它能加载这个文件。

对应 Milvus 提交 bb20ce26f 使用 Knowhere v3.0.10。 该版本的 HNSW 注册名称随 Cardinal 构建选项变化。 验证使用目标实例的真实索引与真实数据独立全量参考：本地 Spark 直接读取 S3 索引，另将同一 UAT 快照的十万行向量读出，以独立 Double COSINE 计算参考结果；没有使用 Milvus 在线 Search 服务对拍。本地生成的开源索引只能补充格式测试，不能替代真实实例数据验收。固定 PR 的 WITH_CARDINAL 构建分别钉住 Cardinal v2.5.112 与 v3.0.8；保持同一套上游 C/JNI 接口，按实际引擎格式加载。云端兼容取决于对应引擎及可用原生依赖，不能只因元数据同为 HNSW 就推定字节兼容。 性能报告、样本路径和云端环境标识保留在验证产物中，不写入通用源码。

2026-09-16 04:48 UTC 的实际结果：Spark 4.0 / Java 21 / local[2]，读取真实快照的 100,000 行、128 维向量作为独立参考；查询向量取其中一行，topK=10、ef=256。无过滤、标量组合过滤和空值过滤三种查询分别排除 0、80,000、90,000 行；投影值、物理行号、排序、与原始 JNI 的命中集合及 Float32 分数全部通过。三个查询的严格 Top10 ID 召回率均为 100%，最大分数绝对误差分别为 5.4300e-5、6.6219e-5、5.9342e-5；该结果只描述此样本和这三个查询，不构成其他查询的召回保证。

每次查询读取同一个 41,606,363 字节的已有索引，一次 deserialize、一次 search，没有回退。端到端耗时约 18.9、19.8、21.5 秒，主要耗在约 15–16 秒的索引读取；search 调用约 13、8、4 毫秒。没有跨查询缓存，不能把原生调用时间写成完整查询延迟。测试未调用在线 Search 服务，未创建或修改远端对象。

本次 Cardinal 平台 JAR SHA-256 为 e57bcca5a96e5cb0a249d79d8f0d6e758c994b80f4b3b4dab40e39b5b6ced726，对应 storage 共存记录为 native-vector/storage-compatibility-cardinal.properties。原始上游 CTest 为 2/3、Java/JNI 为 10/11、Python 为 13/13，JNI 诊断通过；C 和 Java 的 DiskANN v1 精确距离断言失败，量化结果为 1.0306964 而期望值为 1.0。原始断言未修改，正常构建脚本仍失败退出；单独诊断产物保留 build.validated=false。HNSW version 10 / Cardinal v2 的专项通过不改写这些失败。

Cardinal 的上游配置含 -march=native，本机为 Intel Xeon Gold 6338、GLIBC 2.35，未验证其他 CPU/旧 GLIBC；打包器另有 milvus-common 许可证材料缺项。本次证明本机真实 HNSW 查询可用，不把诊断产物作为可分发版本。中文报告和日志存于同一工作区的 milvus-spark-demo/INDEX_RESULTS.md 与 reports/persisted-index-search/。

7. 删除、过滤、行号和分数必须在同一视图下解释

7.1 先构造排除位图，再执行 TopK

core.delete 结合主键和行时间戳处理删除，包含继承的 delete-only 段；不能把删除简化为一个主键集合。 core.expr 对过滤列求值。两者输出按物理行号对齐的位图，合并后约定 1 表示排除。 过滤为 false 或 null 的行都不参与搜索；索引 label 与物理行号的映射必须经过 fixture 验证。

索引查询的 MilvusSearch.filter / vector.search.filter 使用既有 Expr、手写 PlanParser 与 Evaluator，已实现比较、IN、IS NULL、AND/OR/NOT；其他表达式明确拒绝。 R6 的普通扫描入口按谓词设计把 DataSource V2 Predicate 翻成字段 id / 类型绑定的 PredicateExpr，由 PredicateEvaluator 求值；带 vector.search.* 的读取不接受 Spark 谓词，整棵作为 residual 由 Spark 在 TopK 后求值。两条合同不能混淆彼此的语义和过滤顺序。

过滤后仍有至少 K 条有效数据时，不能因“先取 K 再过滤”只返回少量结果。优先使用索引的 bitmap 过滤；若该实现会产生不足 K 的候选，必须按其受支持的搜索参数扩大搜索或继续遍历，直到满足 K、确认有效数据不足，或明确报告搜索不能完成。 允许调整的参数为 ef，最多 8 次尝试，规则见第 6.3 节；仍不足且有效行充足时明确失败，不能无限重试或静默改为暴力搜索。 候选扩大不等于精确召回保证；召回率单独验证。读取主键和过滤列可能扫描整段，但不应因此读取所有原始向量逐条计算距离。

7.2 按物理行号回取业务列

SegmentReader.take(offsets, columns) 已接通 StorageNative 对 loon_take 与 Manifest reader 对应入口的绑定。 使用匹配的 reader handle 类型，返回 Arrow 批并遵守 C Data Interface 的 release 契约；批导入/释放后，还要通过 loon_free_chunk_arrays 释放外层结果数组。

空 offsets 直接返回空结果，不调用拒绝空输入的 loon_take。其他情况先校验 offset 在段行数范围内，排序去重后调用 take，再依据映射恢复搜索次序。候选分数绑定原始 offset，不能和排序后的行错配。 非 nullable FloatVector 首先验证一对一映射；nullable、剔除部分行后压缩 ID 或重排行号的索引需要恢复其专用映射后才进入支持范围。

7.3 分数和全局排序是公开契约

_score 按 Milvus 对应 metric 的含义返回：COSINE、IP 越大越好；L2 使用平方欧氏距离且越小越好。 旧 JVM 实现对 L2 开根号，不能原封不动作为新分数契约。首个支持组合验证 COSINE；其他 metric 启用前各自核对数值与排序。

索引段与显式无索引回退段都把 Knowhere 的原生 Float32 分数直接转成 Double。不能把回退段的欧氏距离重新平方来恢复分数：平方距离 2.0 经该运算会变成 2.0000000000000004，使原本同分的索引与回退候选在全局排序中不再同分。验收同时检查旧逐段入口返回 sqrt(2)、索引模式回退返回 2.0，以及混合段同分候选仍按段号和行号排序。

_score 保留 Knowhere 返回的 Float32 数值，不读原始向量重新计算。字段的 FloatVector 类型不表示索引内部保存了全部原始 Float32：真实 UAT 的 CARD metadata 指定 RBQ3 搜索、RBQ8 重排，最高精度数据集仍是 RBQ8。Cardinal v3.0.8 的 SearcherDispatcher 选择已有数据集中的最高精度 refiner，Refiner 依照其量化配置计算距离；HasRawData 对该组合返回 false。evaluator_quant_tolerance_ratio 用于量化选择，不是分数误差上限。因此这种索引返回近似分数，不承诺与原始向量独立计算的 COSINE 相差小于固定阈值。这里的 Cardinal 内部量化与尚未支持的 Faiss 量化 payload 是不同的序列化格式。

真实数据验收分别检查两个问题：通过原始上游 Knowhere Java/JNI 直接加载同一个 CARD 文件，用相同 query、ef 和基于参考行构造的排除位图，核对 Connector 的命中行号与分数是否保持引擎结果；另以真实 Float32 向量独立计算精确 TopK，报告严格 ID 召回率、允许 Float32 舍入差异的边界召回率及分数误差。后者衡量这份持久化索引的近似搜索质量，不把未经引擎保证的误差阈值当作接口正确性断言，也不通过读取全量原始向量改写查询结果。

每段最多交出 K 条有效候选。Spark 在这些候选上按 score 排序，再用 _segment_id、_row_offset 稳定打破平分并取 K。 这是索引候选的全局 TopK，不承诺 ANN 与精确搜索返回相同 ID。native 封装先按锁定版本契约剔除正常缺位项（如 label = -1 及对应 padding score），返回有效结果数；再对真实命中的越界 label、非有限分数和维度不匹配报错，不得用最大值替代异常。

8. 任务独占索引，失败不能伪装成未建索引

当前每个任务创建自己的 PersistedIndexSearch，搜索后在 finally 中关闭索引；构造异常释放已分配的 BinarySet、解码对象和临时缓冲。查询向量、参数、位图及结果缓冲均为此次调用所有，不跨任务共享。

IndexCache 尚未实现。V4 扩展需要解决身份隔离、并发搜索、引用计数、峰值内存与取消释放；它不改变本次任务独占的资源契约，也不作为当前查询正确性的前提。

向量搜索与建索引

向量搜索只有一个入口：输入一组查询，Spark 按段并行、按查询合并，Knowhere 在每个任务里一次算完整组查询；精确扫描和索引探查是同一个段内执行器的两种策略；建索引是写之后单独的一步。

TopK 是按距离或相似度排序的前 K 条结果。精确搜索把每个向量都算一次距离；近似最近邻搜索（ANN）借助索引只算一部分向量。Knowhere 是 Milvus 的向量检索引擎库，负责距离计算、建索引和索引搜索。

MilvusSearch.search 的查询集入口、exact 与 index 两种模式、build_index、write_snapshot 与 restore_snapshot 已实现，各自验证过的范围记录在能力行 V5、V7、W6、W8；Milvus v3.0.2 已实测能恢复连接器写出的快照，从连接器发起的 restore_snapshot 只经单元测试与假客户端验证，尚未对真实实例跑过。DataFrame 与 SQL 计划里的入口是长期优化项（2.10），未开始。统一构建已改为固定上游 Conan recipe revision，并在独立 CMake 中显式声明集成链接；当前 Knowhere gitlink 为 29210a33，旧 9dc2b8ad 产物的验收只作为历史，当前组合须重新构建和复验。

一、结论

  1. spark.read.MilvusSearch.search 是唯一的向量搜索入口，输入查询集，输出每条查询的全局 TopK（决策 16）。
  2. mode = exact 对每个段做精确扫描；mode = index 用快照钉住的持久化索引，快照确认未建索引的段在 allowUnindexed 打开时改用精确扫描。
  3. 执行分两个 Spark 阶段：第一阶段每个任务处理一个段组，任务内先合并，再按查询合并出全局 TopK；第二阶段只为最终命中的行回表取输出列。段组数按真实的并发数定：index 模式每个 executor 同时只跑一个搜索任务，段组数通常等于 executor 数；exact 模式每个任务占 spark.task.cpus 个核。任务内按内存决定哪一边留在内存：本任务的查询放得进堆，就留查询、段逐个读一遍；放不下，就把段组留在堆外、查询组逐组流过；段组也放不下才增加段组数。查询组是查询集按 milvus.search.group.max.bytes 切出的一部分；exact 模式段组少于并发数时再把查询组切成几个连续的查询范围，一个任务是（段组，查询范围），见 2.1 第一阶段。
  4. 查询集不超过 milvus.search.queries.max.bytes 时由 driver 广播，每个 executor 常驻一份；超过时在 executor 上按查询组打包，写成每组一个分区的 shuffle 输出，第一阶段的任务逐组读取，同一时刻至多持有一组在搜索、一组在读取，查询集多大都不改变这个量（2.1 查询集下发）。
  5. 计算与格式分开：Milvus 的 TableFormat 打开段、生成排除位图、读出索引并按地址取行；计算只在它交出的向量缓冲或索引句柄上求 TopK，不打开存储、不执行删除规则（table-version.html 第三节）。能力在 driver 规划时核对。
  6. Knowhere 只在 native-vector 与 core.index 里调用；每批向量或每个索引，一次调用算完一组查询。
  7. 建索引由 CALL milvus.system.build_index(...) 另起作业完成，结果经 Milvus 的外部快照恢复交付（W6、W8）。
  8. 让搜索直接写在 DataFrame 或 SQL 计划里（单条查询是压在 Milvus 表上的「按距离函数排序取前 K」，查询集是与 Milvus 表以 knn 为条件的 join）是长期优化项，设计与开发提纲见 2.10。

1.1 入口

MilvusSearch.search(
  spark: SparkSession,
  options: Map[String, String],          // 快照定位与存储选项，与 format("milvus") 相同
  queries: DataFrame,                    // query_id BIGINT，vector
  vectorColumn: String,
  k: Int,
  metric: String,
  mode: String = "index",                // "index" 或 "exact"
  searchParameters: Map[String, String] = Map.empty,
  filter: Option[String] = None,         // Milvus 表达式，搜索前生效
  outputColumns: Seq[String] = Seq.empty,
  allowUnindexed: Boolean = false
): DataFrame

另有一个以 queryVector: Array[Float] 代替 queries 的重载，它构造只有一行、query_id = 0 的查询集，返回同样的列。

底库是一份表输入：options 给出 Milvus 快照的版本选择和它的 StorageBinding，今天实现的是 Milvus 这一种 TableFormat。其他格式的表输入和只能扫描的 DataFrame 输入以后接入同一个入口，不另开入口；DataFrame 输入在规划时只接受 mode = exact 且 outputColumns 为空。

规划时核对的能力：

  1. exact：每个单元能扫描，向量列的 VectorLayout 在支持范围内。
  2. index：向量列在每个段上声明了可用的索引，声明的引擎与索引版本能被当前 Knowhere 构建加载，label 对应段内物理行号；allowUnindexed = true 时，快照确认未建索引的段改按 exact 核对。
  3. outputColumns 非空：每个单元支持按地址取行。

任一项不满足，driver 报错并列出不满足的段。

对象约定
查询集query_id 为非空且唯一的 BIGINT。vector 的类型随字段：FloatVector、Float16Vector、BFloat16Vector 用 ARRAY<FLOAT>，Int8Vector 用取值在 −128 到 127 的 ARRAY<SMALLINT>，BinaryVector 用 BINARY；长度等于字段维度，元素为有限值；COSINE 的查询向量范数大于零
结果列依次是 query_id BIGINT、rank INT（从 1 开始）、_score DOUBLE、_segment_id BIGINT、_row_offset BIGINT，后接 outputColumns；每条查询最多 K 行，行之间的先后以 rank 为准
K正整数。单条查询要放得进一组，即「维度 × 元素宽度 + K × 48 字节」不超过 milvus.search.group.max.bytes；不受 Milvus 在线服务 topK 上限 16384 的约束
过滤filter 按 R7 的 Milvus 表达式在搜索前排除行；对结果 DataFrame 再调用 filter 只作用于已选出的行
外表__virtual_pk__ 作为普通输出列，按 read.html 1.1 的系统字段规则读时合成

milvus.search.queries.max.bytes1073741824查询集走广播的字节上限：不超过就在 driver 上收集并广播，每个 executor 常驻一份；超过就在 executor 上按查询组打包成 shuffle 输出，任务逐组读取，不经 driver（2.1）
milvus.search.group.max.bytes536870912一组查询在一个任务里的内存上限，按「组内查询数 ×（维度 × 元素宽度 + K × 48 字节）」计，前一项是查询矩阵，后一项是这组的 TopK（每条候选一个 40 字节的对象加一个 8 字节的引用）；查询集按它分组，逐组读取时一个任务至多持有两组
milvus.search.segments.max.bytes自动一个 executor 为搜索留在堆外的段数据字节上限：exact 模式是向量，index 模式是索引。除以该 executor 同时运行的搜索任务数，是一个任务的段额度（2.1 driver 一条）。不设时按 executor 内存推出（搜索路径的资源自适应 3.3）；段组实际超过时改为每组重读。任务的 Arrow 分配仍受 milvus.read.arrow.max.bytes 约束

index 模式的搜索 stage 与建索引 stage 由连接器声明每个任务占 spark.executor.cores 个核（Spark 的 stage 级任务资源，TaskResourceProfile），每个 executor 同时只跑一个这类任务，Knowhere 的进程级线程池用满该 executor 的核；打包查询组的 stage 按堆声明每任务的核数，让同时打包的组放得进堆（2.1）；其余 stage 按 spark.task.cpus（默认 1）并行。Spark 只在关闭动态分配时让这类任务使用默认的 executor，Kubernetes、YARN 与 standalone 都支持；local 模式与开启动态分配时不声明，由提交方把 spark.task.cpus 设为 executor 核数，driver 日志写明走的是哪一种。 钉住的 Knowhere 子模块 Java API 已提供 resizeSearchThreadPool 与 resizeBuildThreadPool，连接器尚未调用；对应选项随 G4 落地（capabilities.md 第 11 节），GPU 开关上游未提供（README 第 5 节）。

两条旧路径已随本入口删除：vector.search.* 读选项连同 SegmentVectorSearch、SegmentIndexSearch、扫描里的搜索分支，以及它们在 core 的 SegmentIndexQuery、PersistedIndexSearch、BruteForceSearch；spark-base filter 包的 VectorBruteForceSearch 连同 apps-4.0 的测试。SQL 距离函数保留（V8）；vector_knn 已删除（决策 24）。

两个阶段的计数与耗时累加到下列累加器，每完成一步就加一次，不等任务结束。Knowhere 在自己的线程池里计算，这部分 CPU 不计入 Spark 的任务 CPU 时间，看 knowhere.nanos。

看这些数有两个地方，时机不同。Spark 的 stage 页面与 REST 只在任务结束后显示具名累加器：执行器的心跳把运行中任务的累加器全部送到 driver，而 AppStatusListener 只接受 internal.metrics. 开头的名字，其余丢弃。所以运行中的进度由 SearchProgress 监听同一批心跳写进 driver 日志，每个心跳周期一行，并在搜索开始时打一行说明这些行是谁写的、字段各是什么；作业结束后的终值在 stage 页面上看。两个量带分母：compared.pairs 的分母是查询数乘各段行数（仅 exact），segment.searches 的分母是查询组数乘段数（两种模式都有）。两者作业开始前就写在 driver 日志的计划行里。

1.4 成本与模式选择

查询少时，两种模式的主要成本都是读对象存储；查询多时，exact 的计算随查询数线性增长，index 每条查询只计算搜索路径上节点的距离。

成本exactindex
每段读取向量列 N × d × 4 字节（float32），加删除与过滤列；查询分几组都只读一遍索引文件，与向量列同一量级：Cardinal 的量化索引更小，Faiss HNSW Flat 含原始向量和图；有删除或过滤时加这些列
每段计算Q × N × d 次乘加；批量距离入口实测每核 8.1e7 对/秒（768 维，124.7 GFLOP/s），按查询逐行的 bruteForce 每核 8.1e6每条查询的距离计算次数与 ef 和图的出度同量级
查询集不超过 queries.max.bytes：driver 广播，每个 executor 收一份并常驻。超过：打包一次；每个任务把自己查询范围内的组各读一遍，合计「段组数 × 查询集字节」，本 executor 打包的组读本地盘，其余经网络；executor 本地盘上两次 shuffle 各约一份查询集
合并段组数 × Q × K × 24 字节的 shuffle；查询分几组都是这个量，多组时按查询组分批交出
回表命中行所在的行组；每个输出列组的行组约 1 MB

N 是段行数，d 是维度，Q 是查询数。召回基准与少量查询用 exact；查询集大且接受近似结果时用 index，它读取的字节与 exact 相当，省掉的是 Q × N × d 的计算。

二、原理

2.1 执行链

  1. driver。SnapshotSources 解析快照并应用分区与段选择，ReadPlan.of 生成段任务；能力在这一步核对（1.1），段任务表广播给第二阶段。core.index.SearchPlan 按下面的顺序定出第一阶段的任务，所用的量 driver 上都已知：
    1. 查询组：查询集按 milvus.search.group.max.bytes 切成查询组。
    2. 并发数 = executor 数 × 每个 executor 同时运行的搜索任务数：index 模式在集群上是 1（1.1 的 stage 级任务资源），其余情况是 executor 核数 ÷ spark.task.cpus。
    3. 每个任务两块额度：查询额度在堆上，是 Spark 不管理的那部分堆除以同时运行的任务数；段额度在堆外，公式见 search-resources.html 3.3。段的常驻字节 index 模式取快照记录的索引字节，exact 模式取行数 × 向量宽度。
    4. 先试查询留在内存：段组数取 min(段数, 并发数)，exact 模式再按下一条切查询范围；本任务的查询（id 与 TopK 状态，走 shuffle 时加上正在读入的一组）放得进查询额度，本任务查询矩阵的堆外拷贝加最大一段及其加载峰值放得进段额度，就选这种。段按常驻字节从大到小放进当前最轻的段组。
    5. 否则段组留在内存：一组的常驻字节加最大一段的加载峰值和一个查询组的矩阵，不超过段额度；段组数取 max(并发数, 装下所有段所需的组数)，不超过段数；行数未知的段按段额度的一半估。
    6. exact 模式段组数少于并发数时，查询组按顺序切成 R 个连续范围，R = min(查询组数, ⌈并发数 ÷ 段组数⌉)（决策 28）。
    driver 日志 Search budget 一行写明选中的顺序、并发数、段组数、每任务两块内存的需求与额度。
  2. 查询集下发，两条路，任务形态与结果相同，传输量与内存不同。查询集的字节数不超过 milvus.search.queries.max.bytes 时，driver 收集它、查 query_id 唯一、拼成查询矩阵（查询 id 数组，加一块按行连续、类型与字段一致的数值），用广播变量下发：每个 executor 取一份，常驻到作业结束，查询组是这份矩阵里的区间。 超过时查询集不经 driver，也不整份驻留在任何一个 executor 上：
    1. 打包：query_id 的唯一性先在 executor 上按 query_id 聚合查一遍。每条查询按它在查询集里的序号归入 driver 规划的查询组，按组重分区、组内按序号排序，打包成一条记录（查询 id 数组、按行连续的向量字节）。打包结果以组号为键再做一次 shuffle，每组一个分区，由打包它的 executor 写在本地盘上。一组一个打包任务，各组并行。
    2. 读取：第一阶段的 RDD（SearchQueryRanges）以（段组，查询范围）为分区，分区号 = 段组号 × 范围数 + 范围号，对打包结果是窄依赖；任务按组号顺序一次读一组。任务开始时就为第一组创建 shuffle reader，这一组的读取与加载段组同时进行；每把一组交给搜索，就为下一组创建 reader，远程的字节在这一组搜索期间到达：不超过 spark.network.maxRemoteBlockSizeFetchToMem（默认 200 MB）的放在内存，更大的写到本地盘。本 executor 打包的组在交出时从本地盘读。任务同一时刻至多持有一组在搜索、一组在读取。
    3. 传输量：每个任务把自己范围内的组各读一遍，一次作业合计「段组数 × 查询集字节」，本 executor 打包的组读本地盘，其余经网络。广播是每个 executor 一份。
  3. 第一阶段。index 模式一个任务一个段组，答完本作业的每个查询组；exact 模式一个任务是一个段组和一个查询范围，任务数 = 段组数 × R。任务按 driver 选定的顺序答自己的查询：
    1. 查询留在内存：任务先拿到本任务的全部查询组（广播时是广播变量里的区间，走 shuffle 时逐组读完），每组拷成一块查询矩阵，配一个 TopK 合并器；然后逐个打开段（SegmentSearch.runGroups）：exact 逐批读向量，每批对各查询组各调一次批量距离入口，index 加载索引后对各查询组各探查一次；一个段用完即关，下一个段再打开。所有段处理完，按查询组交出候选。每个段只读一遍，查询集每个任务只拿一次；只有一个查询组时就是这种顺序。
    2. 段组留在内存：任务先把段组读进内存（SegmentSearch.hold），exact 留下向量批，index 留下索引句柄；查询组一个接一个在这份数据上算，每组算完交出自己的候选并释放这组的堆。查询组是流过来的，只过一遍，所以两条下发路都只读一遍底库。段组实际读出来超过段额度时，hold 释放已读的返回 Overflow，任务退回逐组重读，代价是 I/O × 组数。
    3. exact 模式的查询范围：批量距离入口在任务线程上单线程执行，一次搜索的并行度就是同时运行的任务数；段组数不少于并发数时 R = 1。每个范围各读一遍自己的段组：底库读取量乘 R，距离计算量不变，耗时在核数允许的范围内除以 R。范围以整个查询组为单位，一组按 group.max.bytes 定大小（768 维 float32、64 MiB 为 21,845 条查询），实测读 1 字节底库对应的计算时间是读取时间的数倍，重读的代价在计算之内。index 模式不切：每个任务要加载段的索引（8 CU 的段，Cardinal 索引约 2.5 GB），切分等于重复加载；Knowhere 的索引搜索本身在进程线程池里按查询并行。
    两种顺序的 shuffle 量都是「段组数 × 查询数 × K × 24 字节」，切成查询范围也不变：每条查询在每个段组上仍只算一次。每条候选是查询 id、段 id、行号和分数。
  4. 合并。候选按查询序号 groupBy，用 functions.udaf 包装的 TopKAggregator 聚合；聚合缓冲是有界堆，每步只留 K 条，排序规则见 2.6。聚合结果展开成带 rank 的命中行。
  5. 第二阶段。outputColumns 非空时，命中行按段 id 重新分区，分区内按段 id 与行号排序；每段经 Milvus 的 TableFormat 对去重后的行号调用 SegmentReader.take，Arrow 行经 ArrowConverter 和 CatalystTypeConverters 转成 Row，由 createDataFrame 组成结果。outputColumns 为空时，命中行就是结果。
  6. 指标。两个阶段的计数与耗时累加到 1.3 列出的 milvus.search.* 累加器。

2.2 Knowhere 对接

Knowhere 只认内存缓冲和位图；core.index 把 Arrow 批变成它的输入，再把它的输出换回段内行号。

项目约定
基向量与查询各一块按行连续的直接内存，本机字节序、按元素宽度对齐，另传行数、维度和类型；两者类型与维度相同；查询可以有多行
排除位图覆盖基向量的全部行，最低位优先，1 表示排除
参数JSON，含距离与 ef；K 以函数参数为准
输出查询数 × K 的 int64 行号与 float32 分数，未填满处行号为 −1
内存缓冲由 JVM 的 Arrow allocator 分配，同步调用期间借给 Knowhere；构建与反序列化时 Knowhere 另存一份
线程bruteForce 与索引搜索：任务线程发起同步调用，计算在 Knowhere 的进程级线程池里执行。批量距离入口：在任务线程上单线程执行（OpenMP 与 OpenBLAS 线程数 1），不进线程池，并行由 Spark 任务之间承担

float32 的精确扫描不走 bruteForce，走 Knowhere C ABI 新增的批量距离入口 knowhere_bruteforce_batched（决策 27，2026-09-22）。它把整组查询一次交给 Knowhere 自带的 faiss（faiss::cppcontrib::knowhere::knn_L2sqr / knn_inner_product / knn_cosine），faiss 按 4,096 条查询 × 1,024 行分块走 SGEMM（OpenBLAS）。bruteForce 按单条查询切任务，faiss 每次只见到 1 条查询于是逐行扫描，一行 3 KB 向量只服务一条查询：8375C 上单核 8.1e6 对/秒；批量入口同一函数、同一数据 8.1e7 对/秒（124.7 GFLOP/s，物理核峰值的 67%），结果逐条一致。分层实测见资源自适应 2.5。批量入口不接受位图，有排除行的批先压紧（2.3）；元素类型不是 float32 的字段仍走 bruteForce。faiss 的分流阈值与 OpenBLAS 的线程数在这个进程里各只有一个值，批量调用在途期间分别是 20 与 1，最后一个在途调用结束时恢复。

向量缓冲满足以下条件时直接交给 Knowhere：布局是 fixed_size_binary、fixed_size_list，或各行偏移恰为「起点加行号乘维度」的 list；这一批的向量列没有空值；元素类型与字段一致；数据起点按元素宽度对齐。 Milvus 在 V2、V3 段里写出的非 nullable 向量都是 fixed_size_binary 布局。条件之外，KnowhereBuffers 把这一批拷进一块自有缓冲，空值行在位图里排除。查询矩阵在任务开始时写进一块直接内存，整个任务复用。

2.3 精确扫描

  1. 任务逐段处理。Milvus 的 TableFormat 为每个段打开一个 SegmentReader，逐批读向量列，以及删除与过滤要用的主键、时间戳和标量列，段只读一遍；每批交出向量缓冲、由 core.delete 与 core.expr 生成的排除位图和这一批的起始行号。
  2. ExactScan 把向量缓冲和一组查询交给批量距离入口，一批一次调用。位图里有排除行时，先把可见行按原顺序拷进一块连续缓冲、记下压紧行号到批内行号的映射，调用后按映射换回；拷贝量是可见行的字节数，每批每组一次；没有排除行时缓冲原样借出。元素类型不是 float32 的字段走 bruteForce，位图原样传入。批量入口内部按 4,096 条查询 × 1,024 行分块，一批的大小不再受 L3 约束，只决定每次调用的固定开销与任务内存，默认 32 MiB，见 搜索路径的资源自适应。只有一个查询组时算完即释放；有多个查询组时，整个段组的批留在内存里，每个查询组都在它们上面算过之后一起释放，保留的字节不超过任务的常驻额度，超过则改为逐组重读。
  3. Knowhere 返回的行号从这一批第 0 行算起，加上这一批的起始行号就是段内行号；结果并入该组的 TopKMerger。段内行号不受保留策略影响，候选不需要再拼回段上。
  4. 一个查询组算完它能看到的全部数据后，这组每条查询的有界堆就是要交出的候选。任务内存是这个段组的向量、一组查询的矩阵和这组的 TopK。

2.4 索引探查

索引从快照钉住的段记录取得，与数据、删除同属一个版本。快照 JSON 的 indexes 给出字段上的索引定义；段记录 Avro 的 index_files 给出可加载的文件。 SegmentIndex 记录 collection、分区、段、字段、索引与构建 id，文件引用，行数，序列化大小，以及三种版本：index_version 是构建与路径版本，current_index_version 是向量格式版本，index_store_path_version 是文件路径布局版本。 段的索引状态有三种：Available 表示来源完整且有索引，Unindexed 表示来源明确没有索引，Unknown 表示来源给不出。段任务只携带这些描述。

  1. 每个字段在一个段上只选一个索引；它的段 id、分区 id、距离与行数都要与钉住的段一致；位图行数上限是 231。
  2. 有删除或过滤时，Milvus 的 TableFormat 只读主键、时间戳和过滤列，生成整段的排除位图；位图对本组查询共用。
  3. TableFormat 读出并解码本段的索引文件，交出索引句柄；IndexProbe 在句柄上搜索本组查询一次，搜完即关闭。每个段的索引在任务里只加载一次。
  4. 搜索参数按索引家族给：HNSW 家族只接受 ef（正整数，不小于 K，默认 max(64, K)），IVF 家族只接受 nprobe（正整数，默认 16），FLAT 与 BIN_FLAT 不接受参数。某条查询的有效候选不足 K 而段内有效行足够时，该参数翻倍重试，最多 8 次，上限是段的行数。
  5. label 换段内行号看这一列有没有空值。非 nullable 列的 label 就是段内行号；nullable 列只对有值的行建索引，label 是「第几个有值的行」，索引文件里的 valid_data 位图（最低位优先，1 表示该行有值）给出对应关系。IndexRowMapping 按它把 label 换成段内行号，也把要排除的段内行号换成要屏蔽的 label；没有值的行不在索引里，不必屏蔽。nullable 列的索引文件没有这份位图，或位图的置位数与索引行数不符，都在打开索引时报错。越界 label 与非有限分数报错，−1 填充位丢弃。

2.5 索引文件解码与引擎选择

载荷名就是索引类型，格式标记核对到家族为止。Knowhere 的 Serialize 把索引写成一块以索引类型命名的载荷（HNSW、HNSW_SQ、IVF_FLAT…），Milvus 按同名写成索引文件，所以取哪块载荷由快照声明的 index_type 决定。载荷开头四个字节是写入方记下的索引类标记，同一个索引类型有多个：HNSW_SQ 在 COSINE 加 SQ4U 量化下写 IHNa，在 L2 下写 IHNs。逐个钉死会把当前 Knowhere 读得了的文件拒掉，所以核对到家族为止——HNSW 家族 IH*，IVF 家族 Iw*，浮点 FLAT 家族 Ix*（IxF2 是平方 L2，IxFI 是内积），二值索引不论结构都是 IB*，Cardinal 流看末尾 24 字节的 CARD——这仍然挡得住把 IVF 流当 HNSW 加载，读不了的组合由 Knowhere 自己拒绝。

引擎与索引版本在规划时声明，执行时核对。BinarySet 是按名字组织的二进制块集合；下面的解码归 Milvus 的 TableFormat。

  1. 描述快照时，TableFormat 对每个段的索引对象只读头尾若干字节：Milvus 封装取 descriptor 与载荷开头的标识，Cardinal 流取末尾 24 字节；由此得出引擎与索引版本，写进该段的索引能力。各段并发读取。
  2. Milvus 封装的文件由 core.codec.BinlogCodec 解开 descriptor 与 index event，MilvusIndexFileDecoder 按 NONE、INT8 Parquet 或 STRING 载荷取出字节；块名取文件的 basename。 依据是 Milvus 的 DataCodec、PayloadReader 与 Slice。
  3. 出现 SLICE_META 时，IndexFileCodec 按其中记录的块名、分片数和总长度拼回原块；SLICE_META 不超过 1 MiB。
  4. Cardinal 直接写出的 _mem.index.bin 没有 Milvus 封装：文件列表恰有这一个文件，末尾 24 字节是小端的 CARD 标识、序列化版本和两个元数据偏移，版本为 1 且偏移在文件内有序时，整个文件作为 BinarySet["HNSW"]。
  5. 标识与引擎的对应：CARD 对应 Cardinal，要求向量格式版本不低于 9，并要求含 Cardinal 的 Knowhere 构建；IHNf（float32 HNSW Flat）、IHN9（HNSW FlatCosine）、IxF2（FLAT）与 IwFl（IVF_FLAT）对应 Faiss，要求版本不低于 6。家族清单与它们的字节标记同在 core.codec.VectorIndexFamilies：能加载的类型和能识别的标记是同一件事，分成两处就会出现「声明支持但读不了」。 含 Cardinal 的构建把 Faiss 引擎注册为 HNSW_DEPRECATED，其余构建注册为 HNSW；两者的块名都是 HNSW，NativeVectorIndex.Loader 分开处理引擎名与块名。
  6. executor 解码出完整载荷后，再核对标识与声明一致。Milvus 封装的单个对象不超过 256 MiB；拼好的载荷没有上限，SLICE_META 的 total_len 在分配原生内存前与各切片对象在存储上的字节数之和核对，大于即拒绝，复制完须恰好等于切片载荷之和（为何不设上限见 搜索路径的资源自适应 3.4）。未切片的 Cardinal 原始流按对象在存储上的大小分配，同样没有上限：先读末尾 24 字节校验 footer，再把对象切成 8 MiB 的区间，不创建整文件 JVM 数组。两种格式的读取都由 core.io.ConcurrentRangeReads 并发发出：原始流按区间，Milvus 封装按切片对象；同时在途的请求最多 32 个，本 JVM 各任务已请求、未消费的字节共用一个预算，取最大堆的 1/16，在 64 到 256 MiB 之间。字节按列表顺序交回任务线程，由任务线程以 1 MiB 为块按偏移复制进 BinarySet，原生载荷只有一个写入方。对象存储的一次区间请求要等一个往返和单条连接的传输：2.58 GB 的 Cardinal 对象按 8 MiB 顺序读是 47 MB/s，32 个区间在途是 1.1 GB/s。短读立即失败，每次分配前记一行日志；复制完成即释放解码缓冲，反序列化完成即关闭输入 BinarySet，索引句柄由任务持有。
  7. Faiss 量化 HNSW、multi-view、加密文件、nullable 行号映射和没有已知标识的文件，在规划时即判为不可加载。

2.6 结果语义

  1. 先排除，再选 TopK。Milvus 的 TableFormat 经 core.delete 按主键与行时间戳判断删除，包括继承的删除段；core.expr 对过滤列求值，结果为 false 或 null 的行排除。两者合成按段内行号对齐的位图。
  2. 行号。_row_offset 是删除过滤前的段内物理行号，与索引 label 一致；外表的 iceberg、lance 段用读取器给出的删除后行号，与 Milvus 的虚拟主键一致。
  3. 分数。_score 是 Knowhere 返回的 float32 转成的 DOUBLE：COSINE、IP 越大越好，L2 是平方欧氏距离，越小越好；HAMMING、JACCARD 越小越好。 量化索引返回近似分数：UAT 上 Cardinal 索引用 RBQ3 搜索、RBQ8 重排，不保存原始 float32。
  4. 排序。同一查询内按分数排序，分数相同时按段 id、再按行号升序；合并与 rank 都用这条规则。
  5. 回表。take 接收去重升序的行号，结果按行号拼回命中行；空行号集不调用 take。

2.7 建索引与交付

CALL milvus.system.build_index(...) 在 driver 上另起 Spark 作业，每段一个任务回读向量列、构建、编码、写出，driver 汇总索引记录后交付。Milvus 建索引也是读原始向量、Knowhere 构建、序列化成 BinarySet、封装上传并上报文件列表四步，连接器按同样的步骤分到各层。

  1. 规划与构建钉在同一个快照版本上；分片按段 id 的连续区间划分；调优参数由 Spark 层解析后传给 Knowhere 的构建参数。
  2. 任务把整段向量读成一块缓冲，一次交给 Knowhere 构建；任务内存按两份原始向量加图结构估算。
  3. IndexWriter 交出 BinarySet；Milvus 的 TableFormat 一侧分块读出，由 core.codec 按目标 Milvus 的封装与切片规则编码，按 Milvus 的命名、经输出的 StorageBinding 写到对象存储；任务返回文件列表、大小、索引版本、向量格式版本和参数。
  4. driver 把索引记录写进作业清单，core.write.commit 写出快照 JSON 与段 Avro 清单；restore_snapshot 先按 SnapshotBundle 的根规则核对快照，再调 Milvus 的外部快照恢复（RestoreExternalSnapshot），可选轮询 GetRestoreSnapshotState 到作业结束；Milvus 复制段文件与索引文件、分配新的 build id，生成新 collection（W8）。给已有 collection 的段补索引，是把索引写进段 Manifest 的 indexes，需要 Milvus 按它加载（README 第 5 节）。
  5. 索引的引擎与参数取目标 Milvus 能加载的组合：面向云上用含 Cardinal 的 Knowhere 构建，参数与云上的自动索引一致，该产物在云上作业运行时提供。第一版建向量索引，范围与 2.4、2.5 的加载器一致。
  6. 建好的索引由 2.4 的加载器读回搜索，与精确扫描比较召回率。

外部恢复对路径的硬要求：Milvus 从快照元数据的 URI 推出一个 bundle 根，要求段清单和所有数据文件都在这个根之下（ValidateExternalSnapshotPaths，防止一份被篡改的元数据把恢复引向别处的文件）。所以 write_snapshot 的 output 必须是数据路径的祖先前缀——为已有 collection 建索引时就是实例自己的根，索引对象也要写在同一个根下。写到别的前缀，文件都对，恢复也会以「data path ... is outside source root」拒绝。

这一轮暴露并修掉的三处：段清单映射只写了连接器自用的 segmentIDLong，Milvus 读 segmentID，于是「references unknown segment 0」；快照文档是合成的最小集合，缺 collection.virtual_channel_names 等恢复要用的字段，改成从源快照复制、只替换本作业拥有的部分；索引定义写成 field_id 等下划线名，Milvus 用 protojson 解析并丢弃未知字段，恢复出来的 collection 于是有一个建在字段 0 上的索引，改成它自己文档里的 collectionID/fieldID/indexID。

2.10 长期优化：DataFrame 与 SQL 计划里的入口

MilvusSearch.search 是一个不在 Spark 计划里的静态 Scala 方法：PySpark 与 SQL 没有入口，它不能与 where、select、join 组成一个计划，快照解析与过滤也是扫描之外的第二条路。长期目标是让用户只写 DataFrame 或 SQL，由 Spark 的规划器把搜索交给现有的执行体（SearchPlan、SegmentSetSearch、TopKMerger、SearchTake），core 不改。本节是这项优化的设计与开发提纲；落地时更新决策 16，并按「移除是设计工作」处理 MilvusSearch.search 与 apps 的 V8 表达式。

两种形状，DataFrame、SQL 与 PySpark 写法一致：

// 单条查询：按距离排序取前 K。call_function 是 Spark 3.5 起按名字调用函数的公开方法，
// 也可写 expr("l2_distance(vec, array(...))")；装了会话扩展后函数按裸名可用
spark.table("milvus.db.coll")
  .where("category = 'a'")
  .orderBy(call_function("milvus.system.l2_distance", col("vec"), lit(q)))
  .limit(10)

// 查询集：queries 有 q 一列（查询向量），每行各取前 K
queries.join(spark.table("milvus.db.coll"),
  expr("milvus.system.knn(vec, q, 10, 'L2')"))

单条查询取的是 SQL 数据库里最通行的写法（pgvector、ClickHouse、DuckDB、Snowflake、Oracle 23ai 都是 ORDER BY distance LIMIT k）；查询集用 join 而不是 BigQuery VECTOR_SEARCH、Databricks vector_search 那样的表值函数，因为 Spark 给 Scala 注册的表值函数在四条线上都接不到 TABLE(...) 参数，而 join 条件能同时引用两侧的列。

函数。六个函数是 Milvus catalog system 命名空间下的 ScalarFunction。没有配置 catalog、只用 format("milvus") 的会话，由 MilvusSparkSessionExtensions 以同名注册同一批函数，构造出的表达式是 ApplyFunctionExpression，Spark 的翻译规则对两种来源一视同仁。五个距离函数有 JVM 实现（V8 的算法），Spark 用它对各分区交回的候选重排序；knn 只能作 join 条件，直接求值报错。

单条查询的机制。Spark 的 V2ScanRelationPushDown 规则看到 Sort 加 Limit 直接压在扫描上、且 where 里的谓词全部下推时，把排序键经 V2ExpressionBuilder 翻成 V2 表达式后调 MilvusScanBuilder.pushTopN(orders, limit)。目录函数调用翻成 UserDefinedScalarFunc，Spark UDF 翻不过去。pushTopN 只接受一种形状：一个排序键，是上表的距离函数，第一个参数引用本表的向量列，第二个参数是数组或二进制字面量，方向与该函数的 metric 一致。满足则记下 PushedSearch（布局、字段 id、查询向量、K、metric、mode、参数），isPartiallyPushed 返回 true；其他形状返回 false 并记下理由。有 PushedSearch 的 MilvusScan 不再一段一分区，而是按 SearchPlan.segmentSets 分段组，每个分区在自己的段组上跑 SegmentSetSearch（一个查询组，一条查询），再经 SearchTake 取本分区那最多 K 行的输出列。Spark 收到各分区的候选后用函数的 JVM 实现重算距离、排序、取 limit，这一步就是全局合并；量化索引在段内按近似分数选候选，最终顺序按精确距离。分数由用户 select 函数值得到，不另出 _score 列。

查询集的机制。MilvusSparkSessionExtensions 注入的策略匹配「一侧是查询计划、另一侧是 DataSourceV2ScanRelation(MilvusScan)、条件仅为 knn 的 inner join」，替换成物理算子 VectorSearchExec，与 CALL 语法同一种「逻辑节点加策略」接法。它执行两个阶段：查询侧执行成 RDD 后按 SearchLimits.queriesMaxBytes 决定 collect 加广播还是 packedGroups 的 shuffle 下发，SearchPlan.of 分段组与查询组，第一阶段每任务 SegmentSetSearch.run，TopKMerger 按查询合并，第二阶段 SearchTake 回表；查询侧的行由算子编号（zipWithIndex）作为 query_id，用户不再提供。输出列是查询侧的全部列、Milvus 侧已投影的列，加 _score、_segment_id、_row_offset；每条查询最多 K 行，同一查询内的先后按 2.6 的排序规则。

失败语义，在 1.3 之外增加两行：

情况行为
index 模式下某段没有可加载的索引pushTopN 抛错而不是返回 false：返回 false 会让 Spark 退成全表扫描加 JVM 排序，把一次索引查询变成全量读而不告诉用户
单条查询：排序键不是距离函数、排序键多于一个、where 里有未下推的谓词、排序与 limit 之间夹着别的算子Spark 不调 pushTopN。注入的规划器策略在优化后的计划上运行，发现「Limit 之下的 Sort 以距离函数为键、压在没有 PushedSearch 的 Milvus 扫描上」时报错，理由取 MilvusScan.declinedSearch（pushTopN 拒绝时记下的原因）或计划形状（夹在中间的 Filter 及其条件）。没有 Limit 的距离排序是全排序，不是 TopK 查询，不报错。优化器扩展点不能用：Pre CBO Rules 批次在 Early Filter and Projection Push-Down 之前运行，看不到下推结果
查询集：join 不是 inner、k 或 metric 不是字面量、Milvus 一侧与 join 之间有未下推的 Filter、条件里还有别的谓词策略报错，写明不满足的项；不把搜索前过滤改成搜索后过滤

已在 Spark 3.5.0 与 4.2.0 的 jar 上核对的事实。

  • SupportsPushDownTopN、FunctionCatalog、UnboundFunction、ScalarFunction、UserDefinedScalarFunc、ApplyFunctionExpression(ScalarFunction, Seq[Expression])、Expressions.sort/column、functions.call_function、NoSuchFunctionException(Identifier) 两条线都有；共享源码可以直接用（modules.md 第 4 节第 10 条）。
  • V2ExpressionBuilder 在两条线上都把 ApplyFunctionExpression 翻成 UserDefinedScalarFunc；Spark 自己的 UDF 不翻。
  • ResolveFunctions 在参数解析完成后才调用函数的 builder（Analyzer：case u if !u.childrenResolved => u），所以会话注册的 builder 可以按参数类型 bind 后再构造 ApplyFunctionExpression。
  • V2ScanRelationPushDown 只在 Sort 加 Limit 直接压在扫描上、且残余过滤为空时调 pushTopN；排序键经 translateSortOrders，翻不过去就整个不推。
  • 规划器策略（injectPlannerStrategy）在优化后的计划上运行，能看到 MilvusScan 的下推状态，返回 Nil 不影响其他策略，抛错即中止规划。
  • DataSourceV2ScanRelation 的构造器参数个数在 3.5 与 4.2 不同，匹配它只能用类型模式加 .scan，不能用 unapply。

三、简洁性带来的好处

  1. 一个入口。单条查询是一行的查询集，exact 与 index 共用快照解析、合并、回表和结果列。
  2. 一个段内执行器。精确扫描与索引探查输入输出相同，未建索引的段直接换策略，结果照常合并。
  3. 只用 Spark 公开接口。两个阶段由 RDD、shuffle、广播变量、类型化聚合和 createDataFrame 组成，四条 Spark 线共用一份代码。
  4. 读取沿用 Milvus 的 TableFormat。扫描向量、生成位图、加载索引和回表，与表读取用同一个 reader 和同一套读取规则；计算不认识存储和格式，换一种表输入不改计算。
  5. Knowhere 的调用集中在两个包。第 1 层只转交，第 2 层负责缓冲与语义，上层不接触原生对象。

四、这样设计带来的好处

  1. 一次扫描服务整组查询。每批向量一次调用算完整组查询，读取和解码的成本与查询条数无关。
  2. 跨任务只传最小候选。第一阶段每条候选 24 字节，任务内先合并，shuffle 量随段组数增长，与段数无关；输出列只为最终每条查询的 K 行回表，回表量是「查询数 × K」行。
  3. 提交时不必调 spark.task.cpus。搜索与建索引的 stage 自己声明每任务占满 executor 的核，其余 stage 按默认的每任务一核并行；段组数按真实的并发数与内存定，查询集读几遍、要合并多少候选，都随之最少。
  4. 查询集的大小不受 executor 内存限制。大查询集只打包一次，任务逐组读取，一个任务同一时刻至多持有两组；下一组的读取与当前组的搜索同时进行。
  5. 结果与 Milvus 口径一致。距离计算与索引搜索都由 Knowhere 完成，分数与 Milvus 相同；行号与索引 label 相同，外表的虚拟主键可以直接对账。
  6. 精确结果直接做基准。同一查询集分别跑 exact 与 index，结果里的 _segment_id 与 _row_offset 就是行身份，调用方 join 一次得到召回率，连接器不为此另出作业。
  7. 向量不逐行拷贝。满足布局条件的批，数据缓冲原样交给 Knowhere，JVM 不物化向量。
  8. 失败直接可见。缺索引、格式不受支持、文件出错都报错，结果行数只在有效行不足时少于 K。
  9. 建索引、索引搜索、精确扫描互相验证。建好的索引由同一个加载器读回，再与精确扫描比较。

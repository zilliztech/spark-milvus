使用 Milvus 索引文件完成向量查询

Spark 的每个任务加载固定快照中对应段的向量索引，执行搜索并读取命中行；Spark 合并所有段的候选，返回全局 TopK。 TopK 指按指定距离或相似度排序的前 K 条结果。近似最近邻搜索（ANN）通过索引减少搜索工作量，其召回率需要相对于精确搜索验证。

本页是 issue #125 的开发方案草稿，基于 refactor/v2 · a070569。 本次交付设计文档，尚未实现或运行索引搜索。查询入口、回退策略和能力范围的建议待审阅；未定事项统一记录在总体设计第 4 节。

交付范围当前代码查询入口 执行流程索引元数据原生接口 结果语义缓存与失败开发顺序

1. 交付从真实索引文件开始，到全局查询结果结束

本 issue 覆盖 V1 的原生加载与搜索接口、V2 的持久化索引加载、V4 的持久化索引缓存，以及拟新增的 V7「显式向量索引查询与全局 TopK」。 V7 尚未加入正式能力承诺；评审通过后再同步能力行和实现包。若接受显式无索引回退提案，本 issue 同时实现 V5 的原生执行部分，入口和回退规则依决策 16。 W6 索引写出、V4 的任务内建索引来源继续由各自设计承载。

首个互操作验证目标建议为开源 Milvus 生成的 CPU HNSW、非空 FloatVector、COSINE、覆盖整个 sealed segment 的索引。 sealed segment 是已经封存的数据段。选择这个组合是因为 nullable 向量需要额外的行号映射，DiskANN 需要本地文件管理器，云端 HNSW 还需要确认实际索引引擎。 这些依赖核验完成后沿同一接口扩展支持矩阵；不能仅凭索引名称相同就声明兼容。

Storage V2 和 V3 共用同一查询计划与索引执行器。它们的快照解析、列组读取与回表分别由现有存储适配承担。 输入中任何段不满足支持条件，必须按明确策略处理，不能漏掉该段继续返回看似完整的答案。查询过程只读固定快照与对象存储。

2. 当前缺口分布在元数据、执行器和 Spark 结果计划

现有逐段暴力搜索不能通过替换一个距离函数变成索引搜索。需要改动的代码与原因如下。

现有位置当前事实本次改动

native-vector、core.index只有包说明和占位文档。实现文件解码接口、Knowhere 加载/搜索、版本校验和缓存。
core.read.plan、core.read.exec已有 SegmentReadTask 和批读取；SegmentReader 只有 next()、deliveredRows，没有按行号取列接口。统一规划查询任务；在共同 reader 中增加 take，供搜索和其他下游算子复用。
spark.read.SegmentVectorSearchrun 全扫向量、保留每段 K 条；搜索分支应用删除但不应用普通扫描的标量过滤。将段内计算交给 core，搜索前生成排除位图。
spark.read.MilvusScan、spark.options搜索结果追加距离值，但 scan 没有相应结果 schema；没有全局合并；错误的查询参数可能被解析成未开启搜索。显式结果 schema、严格参数校验，以及属于公开查询入口的全局排序与 K 限制。

代码依据： SnapshotJson、 Avro 投影、 段内搜索、 SegmentReader。 这些是源码核对结果，不是运行性能结论。

3. 推荐显式查询方法，返回的 DataFrame 已包含全局合并

建议在 spark-base 的现有 spark.read 包提供 MilvusSearch.search。 它接收快照定位和查询参数，构造计划，不立即执行 action。共享源码覆盖四条 Spark 线；apps.search 只放调用示例和作业。 以下签名用于评审，尚不可调用。

val hits = MilvusSearch.search(
  spark = spark,
  options = Map("milvus.snapshot.path" -> snapshotPath),
  vectorColumn = "embedding",
  queryVector = Array(0.1f, 0.2f, 0.3f),
  k = 10,
  metric = "COSINE",
  searchParameters = Map("ef" -> "64"),
  filter = Some("category == \"books\""),
  outputColumns = Seq("id", "name")
)
hits.show(false)

filter 按既有 R7 的 Milvus 表达式契约进入 core.expr，示例表示在满足类别条件的行中搜索。 搜索返回后的 hits.filter(...) 是对搜索结果再过滤，语义不同。R7 的解析器尚未实现，必须与共同的表达式求值器一并补齐本次支持的过滤范围，遇到不支持的表达式在执行前报错。

  • 输入是固定快照的定位、字段名、一个查询向量、K、metric、搜索参数、过滤表达式和输出列。任意 join/union 后的 DataFrame 不属于此入口的输入契约。
  • 解析复用 SnapshotSources → MilvusTable。同一个 Snapshot 经共同规划器生成任务；方法内不另写快照枚举或对象存储读取逻辑。
  • 返回列为请求的业务列加 _segment_id: Long、_row_offset: Long、_score: Double。规划期拒绝名称冲突；schema、InternalRow 和列批必须一致。
  • 单查询输入先完成交付；多查询批处理以后扩展请求结构，不在这一版假装支持。向量长度、有限数值、K、metric 和索引参数均严格校验；COSINE 的零向量按明确错误处理。
  • 旧 vector.search.* 入口和 JVM 暴力实现的退役在迁移步骤中提出；本方案不删除现有代码。若保留读选项，必须另行设计负责插入全局合并的 Spark 扩展，不能只改变 PartitionReader。

4. 每段产候选，Spark 负责跨段合并

索引搜索是同一个读取任务的一种执行方式。普通扫描、筛选列读取和命中行回取共用 SegmentReaderRegistry。 索引句柄只在 executor 创建。

  1. driver 固定快照、每段数据版本、索引构建和文件集合。core.read.plan 负责投影成可序列化 SegmentReadTask；Spark 只适配为 InputPartition。
  2. executor 先确定搜索执行方式，再打开所需数据列；不能沿用 reader 构造时立即拉取原始向量批的顺序。校验索引描述并获取缓存引用，首次加载时解析持久化文件并创建 Knowhere 索引。
  3. 只读取构建删除/过滤位图所需的主键、时间戳和标量列。将位图与查询向量交给索引执行器，得到该段有效候选。
  4. 以命中 offset 经共同 reader 的 take 读取输出列，恢复候选分数次序。首版每段回取局部候选，至多约 段数 × K 行，再送入全局合并。
  5. MilvusSearch.search 组合 Spark 已有的 orderBy + limit，最终返回 K 条或全部可用结果。全量向量和索引对象都不收集到 driver。

此处的全局排序属于向量查询方法构造的 Spark 计划，不实现通用 SupportsPushDownTopN。 查询分支不得把普通扫描的局部 Limit 当作索引搜索前的行数截断，否则会排除本应参与搜索的数据。

5. 索引文件引用跟随固定快照，不能按目录猜测

集合级索引定义与段级索引文件分开建模。根 JSON 的 indexes 说明字段上的索引定义，真正可加载的文件引用需要从快照对应的段记录取得。 现有 Avro schema 已定义 index_files；解析器必须读取并保留它。V3 数据 Manifest 的索引登记是另一种来源，不能当成唯一前提。

SegmentIndexcollection/partition/segment/field/index/build id、文件引用、行数、序列化大小，以及来源提供的各类版本。区分 index_version（构建/路径版本）、current_index_version（向量格式版本）、index_store_path_version（文件路径布局版本）。

索引读取从已选快照的段记录开始，补齐 SegmentManifestReader → SnapshotCatalog → Segment → SegmentReadTask。 解析 Milvus 元数据仍由其现有解析器负责；milvus-storage 的 Manifest 与索引二进制格式由原生层解析。V2 resolver 和 backup 来源必须保留它们实际拥有的索引信息，缺信息就标 Unknown。

所有路径经 core.path 归一，文件访问复用 core.io.ObjectStore 及 milvus-storage 的 C filesystem。 同一版本同时决定索引、列组和删除视图；无法证明行号对应关系时拒绝加载。不能在搜索中重新查询在线最新索引，也不能通过列举 index_files/ 找“最新”文件拼入旧快照。 若来源没有某个版本字段，按其已验证的格式契约处理，不能虚构版本值。

6. 解码 Milvus 文件，再交给 Knowhere

Knowhere 的 BinarySet 是按名称组织的二进制块集合。对象存储中的一个索引文件并不一定就是一个可直接加载的块。 加载必须处理以下步骤：

  1. 校验对象大小和完整性，解析 Milvus 的 descriptor/index events。按 payload 类型处理原始字节、Parquet 编码及支持版本中的旧 STRING 编码；不能跳过一个固定长度文件头就认定完成解码。
  2. 按目标版本验证过的文件命名规则取得 BinarySet entry name；Milvus 的内存索引加载链使用文件 basename，不能假设事件头含原始块名。出现 SLICE_META 时，按其记录的逻辑块名、分片数量和总长度还原；未切片对象不要求该字段存在。16 MiB 是某些版本的默认切片值，不是解码常量。
  3. 验证构建引擎、索引类型、向量类型和格式版本，创建匹配的 Knowhere 实例，再调用 Deserialize。
  4. 调用索引的 Search，传入查询、参数及排除位图；按已经验证的 label 映射输出段内物理行号和分数。

解码格式的依据是 Milvus 的 DataCodec、 PayloadReader 和 Slice。 实现时锁定目标 Milvus 版本并用它生成的文件验证这些格式分支。

6.1 C 接口与文件解析的归属

core.index.IndexFileCodec 编排加载，二进制解析落在原生层。建议在 milvus-storage 补齐索引 binlog 解码的 C 接口，由 native-storage 包装； 返回具名 payload 的地址/长度和明确释放函数。随后 native-vector 将这些 payload 组织为 BinarySet 并交给 Knowhere。 payload 由存储库分配和释放；若向量库借用地址，owner 先销毁索引与 BinarySet，再调用存储库的释放函数，不能跨库默认 delete[]。 这是需要实现的底层依赖，当前仓库没有该解码接口；不在 Scala 中重新实现一套索引 binlog/Parquet 解析器。

native-vector 的 mv_* 接口只接固定宽度数值、地址/长度、不透明句柄和 JSON。JNI 负责参数转换和错误码到异常的映射，C++ 异常不得跨 C 边界。

拟新增接口组职责与资源所有权

mv_binary_set_*创建、加入具名块、销毁。第一版由 index owner 持有解码块直到索引关闭，除非相应实现已证明 Deserialize 完整复制。

实现 VectorNative.java、C 头文件、C++ shim、loader、CMake 及构建接线。沿用 core → native-vector/native-storage 的现有依赖，不增加反向依赖。构建步骤遵守仓库 sbt skill；打包同时核验 CPU 架构、C++ 运行时、Arrow/Parquet ABI、符号隔离和可分发依赖。 本方案不把目标服务使用的原生库版本推定为项目已经集成的版本。

6.2 首个里程碑必须使用 Milvus 生成的文件

已有本地实测材料证明：一个十万行 V3 段的索引引用位于快照段记录的 index_files，其数据 Manifest 的 indexes 为空。 文件总量约 41.6 MB，声明 HNSW/COSINE，向量格式版本为 10；这些证据只证明存在索引文件，尚未证明它能被开源 Knowhere 加载。

对应 Milvus 提交 bb20ce26f 使用 Knowhere v3.0.10。 该版本的 HNSW 注册名称随 Cardinal 构建选项变化。 因此先生成可复现的开源索引作为基准，再验证目标云端产物；云端兼容取决于对应引擎及可用原生依赖，不能靠修改 index type 名称尝试兼容。 性能报告、样本路径和云端环境标识保留在验证产物中，不写入通用源码。

7. 删除、过滤、行号和分数必须在同一视图下解释

7.1 先构造排除位图，再执行 TopK

core.delete 结合主键和行时间戳处理删除，包含继承的 delete-only 段；不能把删除简化为一个主键集合。 core.expr 对过滤列求值。两者输出按物理行号对齐的位图，合并后约定 1 表示排除。 过滤为 false 或 null 的行都不参与搜索；索引 label 与物理行号的映射必须经过 fixture 验证。

本次过滤入口共用核心中间表示与求值器。先实现有明确语义和测试的比较、IN、IS NULL、AND/OR/NOT；其他表达式拒绝或按后续支持矩阵扩展。 R6 的 Spark 谓词入口按决策 20 统一为 V2 Predicate 翻译，R7 的字符串入口按 Milvus 文法解析，不能为索引查询单独复制求值逻辑。

过滤后仍有至少 K 条有效数据时，不能因“先取 K 再过滤”只返回少量结果。优先使用索引的 bitmap 过滤；若该实现会产生不足 K 的候选，必须按其受支持的搜索参数扩大搜索或继续遍历，直到满足 K、确认有效数据不足，或明确报告搜索不能完成。 允许调整的参数、最大尝试次数和搜索预算在锁定索引实现时定义；到达预算仍不足且有效行充足时明确失败，不能无限重试或静默改为暴力搜索。 候选扩大不等于精确召回保证；召回率单独验证。读取主键和过滤列可能扫描整段，但不应因此读取所有原始向量逐条计算距离。

7.2 按物理行号回取业务列

在 SegmentReader 增加共同的 take(offsets, columns)。项目固定的 milvus-storage 提交 cb22dfaa 已声明 loon_take，当前 StorageNative 尚未绑定。 使用匹配的 reader handle 类型，返回 Arrow 批并遵守 C Data Interface 的 release 契约；批导入/释放后，还要通过 loon_free_chunk_arrays 释放外层结果数组。

空 offsets 直接返回空结果，不调用拒绝空输入的 loon_take。其他情况先校验 offset 在段行数范围内，排序去重后调用 take，再依据映射恢复搜索次序。候选分数绑定原始 offset，不能和排序后的行错配。 非 nullable FloatVector 首先验证一对一映射；nullable、压缩或重排行号的索引需要恢复其专用映射后才进入支持范围。

7.3 分数和全局排序是公开契约

建议 _score 按 Milvus 对应 metric 的含义返回：COSINE、IP 越大越好；L2 使用平方欧氏距离且越小越好。 旧 JVM 实现对 L2 开根号，不能原封不动作为新分数契约。首个支持组合验证 COSINE；其他 metric 启用前各自核对数值与排序。

每段最多交出 K 条有效候选。Spark 在这些候选上按 score 排序，再用 _segment_id、_row_offset 稳定打破平分并取 K。 这是索引候选的全局 TopK，不承诺 ANN 与精确搜索返回相同 ID。native 封装先按锁定版本契约剔除正常缺位项（如 label = -1 及对应 padding score），返回有效结果数；再对真实命中的越界 label、非有限分数和维度不匹配报错，不得用最大值替代异常。

8. 缓存按索引身份隔离，失败不能伪装成未建索引

IndexCache 放在 executor 进程内，缓存键包含存储命名空间及访问身份、collection/segment/field/build id、索引格式与路径布局版本、文件集合和数据布局版本。 敏感凭证不进入日志，也不直接作为持久化 cache key。索引对象可跨查询复用；删除与过滤位图按快照、删除源和查询生成，不能复用另一个查询的 bitmap。

同一个键的并发首次加载只执行一次。缓存使用内存预算和引用计数；只有未被任务使用的对象可以逐出。 预算包括下载缓冲、payload、分片拼接与加载中索引可能同时存在的峰值。只有验证相应实现的并发 Search 安全后，才允许多个任务同时使用同一索引；否则统一串行执行该实例的查询或使用独立查询上下文。每次查询的参数、bitmap 和结果内存独立。 任务完成、取消、异常都释放引用；构造失败释放已分配资源；Cleaner 只作最后兜底。

状态建议行为
已知、完整、兼容的索引加载并搜索，记录 build、格式和缓存使用情况。
来源确认未建索引默认失败。只有用户明确选择无索引回退时，使用 native brute-force；混合索引/无索引段一起参与全局合并。
缺少索引描述、覆盖不足、格式/引擎不支持明确错误；不能推定为 Unindexed。指出受影响的段、字段及需要补齐的元数据或支持能力。
文件丢失或损坏、鉴权失败、版本冲突、内存不足传播错误。标准瞬时 I/O 重试可以执行，不能将这些错误转为暴力扫描或空结果。

记录实际索引加载/搜索次数、下载字节、向量列读取字节、过滤列读取字节、回表行数、缓存命中、native 内存与分阶段耗时。 显式回退还需记录段数与原因。这样才能区分索引查询、过滤扫描与暴力搜索，避免仅凭响应成功判断使用了索引。

9. 按依赖顺序实现，每一步都产生可验证结果

元数据解析和原生互操作可以并行；端到端集成必须等索引文件、位图和回表契约都可用。 本页列出后续开发的完成条件，本轮未执行这些测试。

顺序具体工作与文件完成条件
0 · 锁定格式与依赖用锁定版本 Milvus 原生读取代码制作最小互操作验证程序；确定 Knowhere 提交、构建引擎、CPU 架构，保存建表/插入/建索引/快照脚本和脱敏 fixture，核对目标云端产物。真实索引可恢复为 BinarySet，并被目标库加载和搜索；记录支持矩阵。此步骤验证格式与引擎，正式 C 接口和 JNI 在步骤 2 交付。
1 · 元数据贯通SnapshotJson、SegmentManifestReader、SnapshotCatalog、Segment、SegmentReadTask；补齐共同 core.read.plan 的查询描述与规划。固定快照中的所有数据段都有明确索引状态；类型、版本、路径与覆盖校验可单测；序列化任务没有原生句柄。
2 · 原生执行与缓存milvus-storage 的索引解码接口；native-storage 的包装；native-vector 的 shim/JNI/loader；core.index 的 IndexSource、IndexFileCodec、IndexCache。真实未切片/切片及支持编码均可加载；坏文件和不支持版本拒绝；并发加载、释放、取消和内存预算有测试。
3 · 过滤与回表core.delete、core.expr；spark.expr 的 V2 翻译；SegmentReader.take 与 StorageNative 的 loon_take 绑定。删除最近邻、低选择率过滤、null、重复主键时间戳、继承删除、乱序/重复 offset 均验证；输出列不含向量时仍可查询。
4 · Spark 查询契约spark.read.MilvusSearch、共同 scan/reader 适配、schema 和参数校验；apps.search 示例。两段以上查询的返回计划自带全局 TopK；K 大于/小于有效行数、投影、平分、混合段和明确回退均正确。
5 · 构建与验收native-vector 的 CMake、Makefile/Docker 构建接线；integration-4.0 真实 Milvus/对象存储测试；四条 Spark 线和 Scala 交叉编译检查。从分发 JAR 启动 executor 能加载依赖；原生内存检查通过；完成冷/热缓存下的召回、耗时和 I/O 对比。

验收至少覆盖两段以上的合成数据：保证每段确实产生索引文件，并包含删除最相近向量、过滤后少于/多于 K、相同分数、无索引段、错误版本、丢失文件和任务重试。 与目标 metric 一致的精确基准计算 recall@K；性能报告同时给出加载、过滤、搜索、回表和 Spark 合并耗时。cold cache 与 warm cache 分开记录，不事先承诺固定加速倍数。

最终交付要求索引加载和搜索计数大于零，connector 不另行读取整个向量列执行 JVM/原生暴力扫描；允许读取生成位图所需的标量列。 Knowhere 在特定 K 或过滤比例下可能内部选择暴力算法，须按实际引擎记录这种行为；加载索引本身不保证每次都执行图遍历。性能用例需同时覆盖能使用 ANN 算法的参数和引擎自行选择暴力算法的边界。 普通表扫描的行为、所有支持的 Spark 线及 Storage V2/V3 路径均需回归。新 API 和配置在启用时同步中英文 reference。

实现前按评审结论关闭总体设计的相关决策，加入 V7 能力行，并使包说明与实际代码对应。 替换旧 reader 计算逻辑后再提出旧入口和旧类型的具体删除清单；在移除文件、公开类型或测试前说明调用方影响并确认迁移安排。

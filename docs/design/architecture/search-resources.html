搜索路径的资源自适应

搜索路径上有三个与机器规格绑定的数：一次引擎调用的 base 块（32 MiB）、每个 executor 常驻的向量预算（2 GiB）、能加载的索引载荷上限（1 GiB）。三个都是常量，三个都在 2026-09-21 的测试里出了问题：32 MiB 只在单任务时合适，16 任务慢 4 到 6 倍、64 任务半小时零产出；2 GiB 按槽位一除，local[64] 下装不下一个 160 MiB 的段；1 GiB 挡掉了 Milvus 默认 1 GiB 段建出的每一个 HNSW 索引。本文把前两个改成从机器缓存、CPU 配额、内存上限和 executor 并发算出，把第三个去掉：连接器不再持有任何与机器规格相关的常量，内存归 executor 配置，连接器只算给用户看。

2026-09-21 [草稿]。数据在 128 核、L3 96 MiB、503 GB 的机器上测得（Spark 4.0 local 模式，Knowhere 29210a33），拐点位置未在其他机器复现。代码里已改：索引载荷上限 1 GiB → 8 GiB（过渡）；3.2 的块大小自适应已实现（core.index.MachineResources 探测，spark.options.SearchResources 决策，SegmentSetSearch 在 executor 上按段应用）。3.3 与 3.4 未改。

1 机制：三个数各绑一种资源

MilvusSearch.search 的执行链里，SearchPlan 把段切成段集（每任务一个）、把 query 切成组；一个任务在 SegmentSetSearch 里对本集合的段逐个处理。exact 模式读向量列，ExactScan.batch 对每个 batch 调一次 Knowhere.bruteForce；index 模式读索引文件，IndexFileCodec 解码后交给 Knowhere 反序列化再搜。

数绑定的资源今天在链上的位置
base 块 B：milvus.read.batch.max.bytesL3 缓存。一次调用内线程池的所有线程扫同一块；N 个并发任务各带一块，工作集 N × B常量 32 MiBSegmentSearch.hold 把 1 MiB 的 row group 拼成 batch，ExactScan.batch 一个 batch 一次调用
常驻预算：milvus.search.vectors.max.bytesexecutor 的堆外内存。多 query 组时段集整个留在内存里给每组算常量 2 GiB 每 executor，规划期除以槽位SearchPlan.segmentSets 按它切集合；SegmentSearch.hold 超过就 require 失败
索引载荷上限：IndexFileCodec.MaxPayloadBytes同一块堆外内存。加载时 BinarySet 一份、Knowhere 反序列化后一份常量 1 GiBIndexFileCodec.parseSlices 读 SLICE_META 的 total_len 时比较

Knowhere 的 brute_force_dense_impl（knowhere/src/common/comp/brute_force.cc）给每条 query 起一个任务放进全局搜索线程池（线程数 = 机器核数），每个任务拿着自己 4 KiB 的 query 把整个 base 块扫一遍。一次调用读 base 块 nq 遍，读取量 nq × nb × 4 KiB：块留在 L3 里是缓存带宽，留不住是内存带宽，差一个数量级。

常驻预算只在多 query 组时起作用：SegmentSetSearch 单组直接逐 batch 扫（内存只有一个 batch），多组才 hold 整个段集给每组复用，省下段的重读。上限来的路径是规划期：SearchPlan.segmentSets 用 snapshotRows × rowBytes 估段大小、按预算切集合，而行数未知的段按 0 字节计（SearchPlan.scala:153），于是预算形同虚设，集合按并发数切，运行期 hold 再按真实字节拒绝。

索引载荷不经 Java 数组：IndexFileCodec 以 1 MiB 为块把切片流式写进原生 BinarySet（binarySetAllocate(name, long length)），Knowhere 反序列化后持有自己的一份。走 Java 数组的只有 SLICE_META（≤ 1 MiB）和 nullable 的 valid_data 位图（≤ 256 MiB），各有独立上限。1 GiB 的 MaxPayloadBytes 随 a9dbb56 导入，没有记录理由；它同时充当了对不可信 total_len 的健全性校验和内存上限。

3 决策：块和预算由机器算出，上限去掉，内存归 executor

三个数按同一条原则处理：默认值在 executor 启动时从机器和并发算出，用户显式设置的选项原样使用，拿不到数据时取保守值并打日志说明来源。用户要决定的只剩 executor 给多少内存、几个核，这是 Spark 层面本来就要决定的。

3.3 常驻预算与降级

堆外可用 = 内存上限 − 堆上限 − 1 GiB（JVM 与 Spark 自身）
预算     = 堆外可用 × 0.5 / N                  0.5 留给索引加载、shuffle 和 Arrow 的其他缓冲
改动内容
默认值由上式算出；milvus.search.vectors.max.bytes 保留为覆盖，语义仍是每 executor
规划期SearchPlan.segmentBytes 对行数未知的段不再按 0 计：V3 段从 manifest 读行数（SnapshotCatalog 已能取到），仍未知的按预算的一半估并记入日志
运行期SegmentSetSearch 多组时若集合超过预算，不再 require 失败，退回单组的逐 batch 扫描，对每个 query 组重读一遍段。代价是 I/O × 组数，换来任何段大小都能跑
日志规划期一行：预算、集合数、每集合字节、是否降级

3.4 索引载荷：去掉上限，校验元数据，算内存

改动内容
去掉 MaxPayloadBytesSLICE_META 的 total_len 改为与切片实际长度之和核对，不一致即拒绝。申请的原生内存永远等于对象存储上真实存在的字节数，伪造的元数据撑不大它。SLICE_META 1 MiB 与 valid_data 256 MiB 保留，它们走 Java 数组
不按内存拒绝索引多大是用户建段时决定的；内存够不够与 Spark 读一个超大分区同类，由用户按 并发 × 索引大小 × 2 配 executor，配少了按 Spark 常规方式失败重试
算给用户看规划期一行 INFO：每任务索引字节、加载峰值（× 2）、本 executor 合计（× N）、堆外可用；加载前一行实际申请字节数。原生 bad_alloc 不产生 Java 异常，日志是事后唯一的依据
段大于内存时HNSW 一个图必须整体可寻址，不能部分加载；出路是 mmap（Knowhere 有 enable_mmap，Java 绑定缺从文件加载的入口，需补 JNI），慢但不失败。把段切成多个小图不取：2026-09-21 实测 64 小图比暴力搜索还慢，且 Milvus 认一段一索引，快照恢复不进 Milvus

过渡状态：1 GiB → 8 GiB 已改（IndexFileCodec.scala:27，测试用实测的 1,111,588,231 字节），让默认段大小的索引先能加载；上面的校验替换后这个常量删除。

搜索路径的资源自适应

搜索路径上有三个与机器规格绑定的数：一次引擎调用的 base 块（32 MiB）、每个 executor 常驻的向量预算（2 GiB）、能加载的索引载荷上限（1 GiB）。三个都是常量，三个都在 2026-09-21 的测试里出了问题：32 MiB 只在单任务时合适，16 任务慢 4 到 6 倍、64 任务半小时零产出；2 GiB 按槽位一除，local[64] 下装不下一个 160 MiB 的段；1 GiB 挡掉了 Milvus 默认 1 GiB 段建出的每一个 HNSW 索引。本文把前两个改成从机器缓存、CPU 配额、内存上限和 executor 并发算出，把第三个去掉：连接器不再持有任何与机器规格相关的常量，内存归 executor 配置，连接器只算给用户看。

2026-09-21 [草稿]。数据在 128 核、L3 96 MiB、503 GB 的机器上测得（Spark 4.0 local 模式，Knowhere 29210a33），拐点位置未在其他机器复现。代码里已改：索引载荷上限 1 GiB → 8 GiB（过渡）；3.2 的块大小自适应已实现（core.index.MachineResources 探测，spark.options.SearchResources 决策，SegmentSetSearch 在 executor 上按段应用）；3.3 已实现（TaskResources 给出 executor 与每个搜索任务的核数，SearchResources.segmentBudget 与 queryBudget 在 driver 上算两块额度，SearchPlan 选任务留在内存的一边并按预算一半估大小未知的段，SegmentSearch.hold 超额度返回 Overflow 后逐组重读）；3.4 已实现（MaxPayloadBytes 删除，IndexFileCodec.load 分配前以切片对象大小之和校验 total_len，分配与规划期内存预估进日志）。三节全部落地。

1 机制：三个数各绑一种资源

MilvusSearch.search 的执行链里，SearchPlan 把段切成段集、把 query 切成组，exact 模式段集少于任务槽时再把组切成连续的查询范围，一个任务是（段集，范围）（决策 28）；一个任务在 SegmentSetSearch 里对本集合的段逐个处理。exact 模式读向量列，ExactScan.batch 对每个 batch 调一次 Knowhere.bruteForce；index 模式读索引文件，IndexFileCodec 解码后交给 Knowhere 反序列化再搜。

数绑定的资源今天在链上的位置
base 块 B：milvus.read.batch.max.bytes任务内存与每次调用的固定开销。2026-09-22 起 exact 走批量距离入口，入口内部按 4,096 条查询 × 1,024 行分块，B 不再绑 L3；此前绑 L3 是因为按查询逐行的内核每次调用把块读 nq 遍（2.1、2.2 的数据）常量 32 MiB（决策 27）；2026-09-21 到 22 之间曾按 L3 自适应，更早是常量 32 MiBSegmentSearch.hold 把 1 MiB 的 row group 拼成 batch，ExactScan.batch 一个 batch 一次调用
常驻预算：milvus.search.vectors.max.bytesexecutor 的堆外内存。多 query 组时段集整个留在内存里给每组算常量 2 GiB 每 executor，规划期除以槽位SearchPlan.segmentSets 按它切集合；SegmentSearch.hold 超过就 require 失败
索引载荷上限：IndexFileCodec.MaxPayloadBytes同一块堆外内存。加载时 BinarySet 一份、Knowhere 反序列化后一份曾是常量 1 GiB；2026-09-21 起无上限，total_len 在分配前与切片对象在存储上的字节数核对IndexFileCodec.load 在 parseSlices 之后、创建 Loader 之前

Knowhere 的 brute_force_dense_impl（knowhere/src/common/comp/brute_force.cc）给每条 query 起一个任务放进全局搜索线程池（线程数 = 机器核数），每个任务拿着自己 4 KiB 的 query 把整个 base 块扫一遍。一次调用读 base 块 nq 遍，读取量 nq × nb × 4 KiB：块留在 L3 里是缓存带宽，留不住是内存带宽，差一个数量级。exact 自决策 27 起不再走这条内核；2.1 到 2.4 的数据是它的，2.5 是替代它的批量入口的实测。

常驻预算只在多 query 组时起作用：SegmentSetSearch 单组直接逐 batch 扫（内存只有一个 batch），多组才 hold 整个段集给每组复用，省下段的重读。上限来的路径是规划期：SearchPlan.segmentSets 用 snapshotRows × rowBytes 估段大小、按预算切集合，而行数未知的段按 0 字节计（SearchPlan.scala:153），于是预算形同虚设，集合按并发数切，运行期 hold 再按真实字节拒绝。

索引载荷不经 Java 数组：IndexFileCodec 以 1 MiB 为块把切片流式写进原生 BinarySet（binarySetAllocate(name, long length)），Knowhere 反序列化后持有自己的一份。走 Java 数组的只有 SLICE_META（≤ 1 MiB）和 nullable 的 valid_data 位图（≤ 256 MiB），各有独立上限。1 GiB 的 MaxPayloadBytes 随 a9dbb56 导入，没有记录理由；它同时充当了对不可信 total_len 的健全性校验和内存上限。前者现在由 store.size 之和承担，后者取消（3.4）。

3 决策：块取常量，预算由机器算出，上限去掉，内存归 executor

块取常量 32 MiB（3.2）；预算的默认值在 executor 启动时从机器和并发算出，用户显式设置的选项原样使用，拿不到数据时取保守值并打日志说明来源。用户要决定的只剩 executor 给多少内存、几个核，这是 Spark 层面本来就要决定的。

3.2 base 块

B = 配置值，否则 32 MiB。批量距离入口内部按 4,096 条查询 × 1,024 行分块，B 只影响每次调用的固定开销（JNI 结果回传、每组查询的 top-k 归并）和任务内存（N 个并发任务各带一块）；实测 32 MiB 与 128 MiB 每核速率相同（8.0e7 与 8.1e7 对/秒），1 MiB 以下装不下一个 1,024 行的分块。原来的 L3 公式（可用 L3 = L3 × CPU 配额 × 0.6，B = 可用 L3 / N）针对按查询逐行的内核，随决策 27 撤销，它的实测保留在 2.1 和 2.2。仅 exact 模式；index 模式不扫 base。group.max.bytes 实测影响在 ±20% 内，不动。

已实现：常量删除；IndexFileCodec.load 解析 SLICE_META 后、创建原生 Loader 前，对每个逻辑载荷取其切片对象的 store.size 之和（这些大小随后复用给读取，不重复 stat），total_len 大于该和即拒绝，复制完仍要求恰好等于各切片载荷之和；每次原生分配前一行 Persisted index allocating；index 模式的规划按 3.3 核算每任务的索引字节与加载峰值，写进 Search budget 一行。1 GiB → 8 GiB 的过渡（296f3f9）随之退役。

3.5 底库读取：下一块提前读

exact 的读取和计算原来串行：任务线程读完一块再算，算完再读下一块。1 万条查询对 3100 万行（chenbiao-perf8-ap-exact-10k-r2-0）读 95.2 GB 用了 2,153 任务秒，每个任务 44 MB/s；1 GiB 查询集的作业里读取占任务时间 26%。SegmentVectors 为每个打开的段起一个读取线程，交出一块的同时开始读下一块，读取和 Knowhere 计算重叠；每个任务多占一块内存（32 MiB）。读取线程的异常在取下一块时抛出；段关闭时先等在途的读取结束、释放它读到的块，再关闭读取器。

实测（UAT，同数据、同资源，每个 executor 独占一台 m6i.4xlarge）：1 万条查询 442.7 → 321.4 秒，executor CPU 4,313 → 4,320 核秒，单任务读速 44 → 42.5 MB/s；1k 条查询 190.4 秒（改动前同一作业 384.5 秒，其中两个 executor 被驱逐、不可比；旧内核 320.4 秒）；两次的 top-10 与改动前逐条相同（chenbiao-perf8-ra-exact-10k-0、chenbiao-perf8-ra-exact-1k-0）。一块的计算时间是查询组条数 × 块行数 ÷ 8.2e7 对/秒，长于读一块的时间时读取从墙钟里消失；查询少时任务时间由读取速度决定。

预读之后每个任务仍只读 44–51 MB/s：一块只有一个 GET 在途，3.6 讲原因和做法。

一个段读几遍由 3.3 的选择决定：查询留在内存时每段只读一遍，段组留在内存时读一遍留下，两者都放不下时每个查询组重读一遍段。预读对三种情况都生效。

3.6 底库读取：一块的八个区间同时请求

一块 32 MiB 切成八个 4 MiB 区间同时请求，单任务读速 51.2 → 109.1 MB/s，1k 条查询的搜索 539.2 → 260.5 秒（同时段的两个作业，各 1 个 4 核 executor）。原来一块只有一个 GET 在途，单任务读速就是一条连接的速度。

  1. 一块是 milvus-storage 的一次 Parquet 读调用（ReadRowGroups），覆盖约 32 个 1 MiB 的行组。Arrow 把这些行组的列块合并成区间，区间上限是 reader.parquet.prebuffer.range_size_limit，默认 32 MiB；一个区间是一个 GET，占一条连接。
  2. Arrow 读取器默认的区间缓存是懒模式（CacheOptions::LazyDefaults：lazy = true，prefetch_limit = 0）：解码到哪个区间才请求哪个区间，同一时刻一个请求在途。milvus-storage 只改了合并上限，没有改这两项。
  3. 本仓库的原生包按 milvus-storage 的默认 WITH_CRT=OFF 编译，libmilvus-storage.so 里没有 S3Crt 符号，S3 客户端是 AWS SDK 基于 libcurl 的 S3Client，一个 GET 就是一条连接上的一个流。从 UAT pod 读这个桶，一条连接 32–95 MB/s，总吞吐随连接数增长：1 条 32 MB/s，8 条 269 MB/s，24 条 531 MB/s。
  4. 所以默认配置下一块就是一个 32 MiB 的 GET。只把区间调小，懒缓存把它们变成依次发出的多个 GET，每个都要等首字节，读得更慢：4 MiB 区间、64 个 IO 线程时单任务 28.5 MB/s。决策 30 否决拆区间时写的理由"CRT 已按分片并行"不成立。
  5. 解码不是瓶颈：同一 32 个行组从内存解码 10–18 毫秒（1.9–3.4 GB/s）。向量列是 FIXED_LEN_BYTE_ARRAY(3072)、不压缩，写入端每个行组先写约 1 MiB 的字典页再回退为 PLAIN。JVM 一侧借用 Arrow 缓冲、每块一次批量拷贝，读速指标只计原生调用内的时间，也不含它。

做法分两层：

  1. milvus-storage 新增读取器属性 reader.parquet.prebuffer.lazy（默认 true，即 Arrow 原行为）；false 时一次读调用开始就请求它的全部区间，区间在 Arrow 的 IO 线程池上并发下载。该读取器的每次预缓冲只覆盖这次调用要解码的行组，同时请求不多占字节。另加 MilvusStorageRuntime.setArrowIoThreadPoolCapacity：任何时候设定进程级 Arrow IO 线程池的大小，Arrow 自己安全地增减，要不要降由调用方定。每个在途区间占池里一个线程阻塞等 GET，池默认 8 个线程，一个 executor 的全部任务共用。
  2. 连接器的 SegmentReaderRegistry 对每个读任务设 lazy = false、区间 = 块大小 ÷ 8 且不小于 4 MiB，32 MiB 的块切成 8 个 4 MiB 区间；每次打开段读取器时，池子小于处理器数 × 8 就抬上去，不往下调——池子是进程级的，同一个 JVM 里别的读取器可能已经要了更多。一个 executor 同时跑的任务不超过处理器数，每个任务的八个区间都能同时在途。表扫描、搜索和按行号取数走同一个读取器，都受益。

限制换了一层。4 核 executor 上 4 个任务把 CPU 跑满（读取与计算共用，3.99/4 核；同样的工作 CPU 412.9 → 457.6 核秒，任务时间 1,918.7 → 960.5 秒），读速停在每任务 109 MB/s。同一 executor 只跑 1 个任务、CPU 有富余（0.91/4 核）时是 110 MB/s，可见单任务的上限来自八个区间各自的首字节等待，不是 CPU：一个 4 MiB 区间连等带传约 0.3 秒。再往上有两条路，一次多读一块或把块调大，都多占内存，本次不做。

运行时代价：每个任务在途的字节不变（仍是一块），GET 次数乘 8，95.2 GB 的底库约 2.3 万次；IO 池最多处理器数 × 8 个线程，Arrow 在有请求排队时才起线程。两个限制：Arrow 只合并区间、不拆区间，行组远大于 4 MiB 的文件每个列块仍是一个 GET，Milvus 写的段是 1 MiB 行组；IO 池按 JVM 看到的处理器数算，spark.executor.cores 大于容器的 CPU 上限时池偏小，读取排队但不出错。

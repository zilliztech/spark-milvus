表版本

每份输入在一个固定版本下描述成一个 TableVersion（表版本）：公共部分供规划和计算使用，私有部分只由该格式的 TableFormat 解释；身份放在输入自己的 StorageBinding 里，不进表版本。计算只接收格式中立的列批和声明过的能力。

结论对象计算怎么接各格式怎么填与现有代码的对应否决与代价

一、结论

  1. TableVersion 是所有输入共用的表模型，由今天的 Snapshot 演进而来（决策 25，2026-09-17 修订）。Milvus 快照、milvus-backup 导出、Milvus 外表和直接读的开放格式都产出它。
  2. 表版本分两部分。公共部分是版本、schema、单元和能力；私有部分是该格式自己的元数据，只有该格式的 TableFormat 读。计算和 Spark 层不按私有部分分支。
  3. 身份不在表版本里。每份输入、每份输出各有一个 StorageBinding，记录「位置 → 身份」；生成任务时，按单元引用的位置取属性包。
  4. 删除、合并、系统字段和类型规则都在 TableFormat 内部执行，读取器交出的批里只有有效行，或用排除位图标出无效行。core.delete 只服务 Milvus。
  5. 行地址按单元声明种类，索引按列声明 label 对应哪种地址。各格式之间不共用一种地址编码。
  6. 计算有两种输入：表输入（表版本加它的 TableFormat，能力按声明）和 DataFrame 输入（只能扫描）。能力不匹配在 driver 规划时报错。
  7. Snapshot、Segment、SegmentLayout、SegmentReadTask 只指 Milvus 的对象。格式中立的名字是 TableVersion、DataUnit、TableFormat、UnitReadTask、UnitReader、StorageBinding、ColumnId、VectorLayout。代码改名随模型拆分一起做。

二、对象

  1. 各种格式在一个版本下都是「一份 schema 加一组单元」。单元在各格式里分别是 Milvus 的段、Iceberg 的数据文件、Hudi 的 file slice、Lance 的 fragment、Paimon 的 split。TableVersion 按这个形状定义，任何格式都能填进去。
  2. 公共部分只放下游据此做决定的信息，不含任何一种格式的专有概念。规划用行数和字节数，投影用列，搜索用向量布局，回表和索引结果用地址种类，能力核对用能力声明。collection id、分区 id、storage_version、Milvus 类型、protobuf schema 都在 Milvus 私有部分。
  3. schema 以 Arrow 类型为中立类型系统。每列用 ColumnId 标识，标识由格式给出：Milvus 用字段 id，Iceberg 与 Lance 用各自的 field id，没有 id 的 Parquet 用列名。向量列带 VectorLayout，即元素类型、维度和数据缓冲的排列（Milvus 的 FixedSizeBinary、开放格式的 FixedSizeList 或 List），计算按布局直接读缓冲，不复制。VectorLayout 就是 read.html 6.4 里放在 core.schema 的向量布局描述。Spark 类型映射、谓词绑定和列裁剪都按 ColumnId 与 Arrow 类型工作。
  4. TableFormat 解释私有部分，做三件事。
    1. 描述（driver）：按输入的位置、StorageBinding 和版本选择，产出 TableVersion。
    2. 规划（driver）：按投影和谓词、用该格式自己的统计剪掉单元，产出 UnitReadTask。
    3. 打开（executor）：UnitReader 交出 Arrow 批；声明了能力的，再提供按地址取行和索引句柄。
  5. 删除由所属格式执行。Milvus 的 L0 删除和「主键加行时间戳」规则在 Milvus 的 TableFormat 里，经 core.delete 执行。Iceberg 的 equality delete 按 Iceberg 的规则执行：键可以是多列，null 与 null 相等，先后按文件的 sequence number 比；它与 Milvus 规则不同，两者不共用实现。Hudi、Paimon 的按键合并发生在一个单元之内，由读取器执行。
  6. 行地址按单元声明。声明三件事：地址种类（删除前的物理位置、删除后的位置、稳定行 id）；是否支持按地址取行；地址总是和单元 id 一起出现，不编码进同一个整数。Milvus 普通段的地址是删除前的段内物理行号，索引 label 就是它；Milvus 外表的地址由 Milvus 的 TableFormat 按外表规则声明（read.html 1.1）；直接读 Lance 时用 Lance 自己的行地址。外表路径和直接读的路径各自声明，互不通用。
  7. 能力在规划时核对。计算声明需要什么，表版本声明能提供什么；不匹配时在 driver 报错，并列出不满足的单元。不从格式名或存储位置推断能力。
  8. 身份属于输入和输出。StorageBinding 随输入或输出传递，单元只记位置引用；同一个表版本换一份绑定，就能以另一个身份读。按桶配置的 Hadoop 键只在输入没给身份时用来推导（storage-auth.html）。

三、计算怎么接

计算只接收格式中立的数据：列批、按 VectorLayout 解释的向量缓冲、排除位图、按需的地址列和索引句柄。计算不打开存储、不解析 schema、不执行删除规则。

  1. 表输入。UnitReader 在 executor 上交出批；能力按表版本的声明。Spark 层按单元分发任务，再全局合并结果。
  2. DataFrame 输入。任意 Spark 数据源或 join 的结果，只声明「扫描」。K-means、精确 TopK 可以直接使用；要求索引或按地址取行的计算在规划时拒绝。只需要扫描的开放格式场景，先用该格式的 Spark 数据源交 DataFrame 即可，需要固定版本、回表或索引时再为它写 TableFormat。
  3. 索引。TableFormat 为单元提供索引句柄和 label 对应的地址种类；计算在句柄上探查，回表经同一单元的 UnitReader 按地址取行。今天的 SegmentIndexQuery 按此拆成两半：打开段、算排除位图、加载索引文件归 Milvus 的 TableFormat；在向量缓冲或索引句柄上求 TopK 归计算。
  4. 写。写接收数据和输出的 StorageBinding 与格式，不接收输入的表版本。写 Milvus 段时，目标 collection 的 schema 由目标的 Milvus TableFormat 给出。

例：客户桶里的 Parquet 查询集（输入 A）查我们桶里的 Milvus 快照（输入 B），结果写到另一个桶的 Parquet（输出 D）。三份绑定各自独立；精确模式只要求 B 能扫描，索引模式还要求 B 的向量列声明了可用的索引，并且支持按地址取行。

六、否决与代价

否决的做法：

  1. 决策 25 最初的形态。公共 schema 用 Milvus 类型与字段 id，所有单元都交给 milvus-storage 列组，跨格式共用一套删除规则，各格式共用 (单元编号 << 32) | 行号 的地址编码，存储位置的凭证放进表模型。这样直接读的开放格式要带上 Milvus 语义，Iceberg 的删除规则装不进 Milvus 的实现，读取实现在目标组合定下之前就被选定，计算也会拿到凭证。
  2. Snapshot 保持 Milvus 专用，开放格式只走 DataFrame。开放格式一旦需要固定版本的多轮读取、按地址取行或索引，就要再建一套表模型。
  3. 另建一套表模型，与 Snapshot、milvus-storage 清单并存。三套模型各自演进。
  4. 照 XTable 做格式间的语义翻译。它的公共模型不含删除，官方说明只同步写时复制视图。

代价：

  1. schema 改为 ColumnId 加 Arrow 类型后，今天按 Milvus FieldSchema 和 milvus.field_id 工作的 Spark 类型映射、谓词绑定、列裁剪、向量解码都要改。
  2. DataFrame 输入进入原生计算时，要把行转成向量缓冲，有复制开销；性能关键的场景走表输入。
  3. 各开放格式的读取实现分别选定（决策 26），不同实现覆盖的存储后端和能力不同，设计要逐个格式写明。

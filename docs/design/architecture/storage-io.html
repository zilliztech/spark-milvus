存储通路

第 1 层与第 2 层之间的契约:对象存储上的字节怎么到 JVM,JVM 里的数据怎么回到对象存储。 读写共用这一层,所以它单独一篇;读那一侧的现状与设计见 read.html,分层见 modules.md。

跨 JNI 边界的只有两样东西:小块元数据的字节,和大块列数据的地址。 列数据本身从不进 JVM。

一、第 1 层有两个面

两个面的接口形状不同,因为契约不同。

交字节的面交地址的面
C 入口loon_filesystem_*loon_segment_reader_*、loon_record_batch_reader_*、writer 那组
JVM 接口core.io.ObjectStorecore.read.exec 的 SegmentReader
方法长相readAll(key): Array[Byte]收发 ArrowArray/ArrowSchema 的地址

分界线是文件大小和解析器归属。元数据是 avro、json、parquet footer, JVM 有现成解析器,文件又小,拷进来最省事。列数据量大,拷一次就等于白做零拷贝, 而 C 那边本来就有完整的 parquet 解码器。

删除日志走交字节这一面,但读出来的是真实的主键和时间戳值,不是元数据。 它在这一侧的原因是格式是 parquet 而解析在 JVM(core.delete.DeltaLogReader), 并且它在 executor 上由 core.read.exec.DeletePlans 按任务读取,driver 上的 DeleteFileListing 只列出路径与条数。

二、地址这一面怎么交接

每批分配两个空的 C 结构体,让对面填,填完立刻释放结构体本身,数据留给拿到它的那一方。

2.1 读:C 填,JVM 收

val arr = ArrowArray.allocateNew(allocator)     // 两个空壳
val sch = ArrowSchema.allocateNew(allocator)
try {
  reader.readNextBatchScala(rbrHandle, arr.memoryAddress(), sch.memoryAddress())
  Data.importVectorSchemaRoot(allocator, arr, sch, null)   // 数据交给 root
} finally {
  arr.close(); sch.close()                      // 只释放空壳
}

最后那两个 close 释放的是结构体本身。数据由 VectorSchemaRoot 持有,它的释放由 allocator 管。

2.2 写:JVM 填,C 收

// 打开 writer 时一次
Data.exportSchema(allocator, arrowSchema, null, arrowSchemaC)
w.create(basePath, arrowSchemaC.memoryAddress(), writerProperties)

// 每批一次
val arrowArrayC = ArrowArray.allocateNew(allocator)
try {
  Data.exportVectorSchemaRoot(allocator, root, null, arrowArrayC)
  writer.write(arrowArrayC.memoryAddress())
} finally {
  arrowArrayC.close()
}

2.3 两侧不对称的三处

读写
schema 过界次数每批一次(C 填),另加打开时一次(JVM 声明要哪些列)只在打开时一次,之后每批只过 ArrowArray
schema 方向打开时 JVM→C,每批 C→JVM只有 JVM→C
close() 的含义纯粹释放空壳,数据已归 VectorSchemaRoot成功时 C++ 的 ImportRecordBatch 已把 release 移走,close 只清结构体内存;失败时若 release 还在,先调用 release() 释放导出引用,再用 close() 释放结构体

写侧那个 schema 结构体活到 writer 关闭,不能在第一批之后释放。

2.4 一个消费方一份 schema

loon_writer_new 与 loon_reader_new 都接管交给它们的 ArrowSchema。C Data Interface 的 schema 是移动语义,导入方拿走 release。所以同一个导出好的结构体不能先给 writer 再给 reader——第二次会拿到 Cannot import released ArrowSchema。每个消费方各导出一份。

JVM 侧那一半仍然要 close:结构体的内存是 allocator 分配的, 接管只拿走 release,不负责释放外壳。

2.5 不用 ArrowArrayStream

C 层有 loon_segment_reader_get_stream,上游 Java 绑定有 MilvusSegmentReader.getStream,我们一处都不用。 Arrow Java 的 ArrowReader.loadNextBatch 在多批之间共用同一个 VectorSchemaRoot,并且忽略 ArrowArray 的 offset 字段。 底层 C++ reader 一旦返回 RecordBatch::Slice 的结果,第一批之后的每一批都显示成同一份数据, 不抛异常。这是 milvus-storage#493,MilvusStorageFFITest 是它的回归用例。

Connector 调用上游 MilvusStorageReader.openRecordBatchReaderScala 和 readNextBatchScala，每批分别导入新的 ArrowArray/ArrowSchema。切片物化和复制统计统一实现在上游 JNI。上游仍为其他调用方保留 stream 接口。

三、句柄的所有权

这三条弄错了都不报错,所以写死。

  1. 句柄不跨序列化边界。句柄是本进程内的指针。 SegmentReadTask 里只装描述(段路径、manifest 版本、要读的列、fs.* 属性), executor 拿到描述之后才开句柄。
  2. 构造到一半失败要自己回滚。Spark 只对构造完成的 reader 调 close(),构造过程中开了一半的句柄它不管。所以构造块用 try/catch 包住,失败时释放已经拿到的一切再抛;每个句柄字段用 var 加 0L/null 初始化,让回滚能判断哪些已分配。 MilvusRowPartitionReader 的 releaseAll() 就是这个。
  3. close() 必须幂等。Spark 在错误路径上可能重复调用, 释放后把字段置回哨兵值。

四、这条性质的代价,以及决策 12

「列数据不进 JVM」这句话有一个前提:JVM 不需要按行改动这批数据。删除生效时这个前提不成立。

DeletePlan 按主键加时间戳查(containsLongPk(pk, rowTs)), 判断一行删没删要先读出该行的 PK 列和 timestamp 列再查表。 读这两列不破坏上面那条性质——Arrow 视图能直接读 C 的内存。 破坏它的是下一步:留下来的行要交给 Spark,而 Spark 的 ColumnarBatch 没有表达行有效性的成员(3.5.5 与 4.1.3 都只有 setNumRows、numRows、column、getRow)。 实现选的是不拷贝:SelectedRowsColumn 包住原列,持一张存活行下标表,每次取值多一次查表; 本页早先写的「只能把存活行物化成新的一批」与代码不符,2026-09-16 改正。

决策 12 选了做 R4。无删除的段批原样包成 ColumnarBatch 直通, 这条性质完整成立;有删除的段多读两列、全行扫描、再按下标映射,代价是每次取值多一次查表,不是拷贝。取这个代价的理由是有删除的段在多数情况下是少数, 换来的是无删除的段省掉逐行 arrowToInternalRow。见 README 第 6 节。

五、指标:这条通路上量什么(G5)

一条 Spark 任务读一个段,报八个数(七个 sum、一个 max);写一个段,报五个数。指标名带 milvus. 前缀。全部由句柄自己记,任务结束时经 DataSource V2 的 CustomTaskMetric 交给 Spark,在 SQL 页的算子节点上可见。 没有这些数,README 第 1 节「6 次拷贝降到 2 次」和 2.4 的批大小、off-heap 预算(G3)都量不出来。

5.1 每个数在哪一侧取

原则:谁持有句柄谁记数,不设全局计数器。C 侧的数记在句柄的 holder 结构体里 (RecordBatchReaderHolder、writer 的 holder),JVM 侧的数记在包装句柄的对象里 (NativeSegmentReader、SegmentWriter)。一个句柄对应一个 Spark 任务, 所以按任务上报不需要任何汇总表,也没有锁。

数读 / 写在哪取回答什么问题
jni.calls、jni.nanos读、写JVM 侧,包装类在每次 上游 JNI 调用前后取 System.nanoTime跨界多少次、花了多久;按批跨界所以次数应等于批数加常数
arrow.batches、arrow.bytes读、写JVM 侧,导入(读)或导出(写)时对 VectorSchemaRoot 每个向量的 getBufferSize 求和吞吐:交接过界的 Arrow 字节数,除以 jni.nanos 就是通路带宽
copies、copied.bytes读C 侧,recordBatchReaderReadNext 里每次 arrow::Concatenate 记一次和它的字节数;JVM 经 recordBatchReaderStatsScala(handle) 取回2.5 那个过渡实现今天到底拷了多少;上游导出 loon_record_batch_reader_* 后这两个数应归零
rows.materialized读JVM 侧,行式 reader 每批结束时加上这批转成 InternalRow 的行数(触到的行减去按删除跳过的行);列式 reader 报 0,有删除的批经 SelectedRowsColumn 按下标映射,不转行「6 次到 2 次」的 JVM 那一半:列式路径这个数为 0
arrow.allocated.max读、写JVM 侧,ArrowAllocator.get.getAllocatedMemory 在每批之后取一次,记最大值;跨任务按 max 汇总,不按 sumnative 内存占用的可见部分,也是 G3 预算要卡的同一个数

切片批只重写偏移和位图(上游需求,未实现)。目标是上游 JNI 逐批读取时,对带 offset 的列只调整缓冲区起点:定长列（数值、fixed_size_binary、fixed_size_list 的子数组）移动数据缓冲区起点并重建位图, 变长列（string、binary、list）只重写 offsets 缓冲区,数据缓冲区共享。这样 copies 与 copied.bytes 在切片批上只剩位图与偏移的大小, 普通 collection 与 external collection 同样受益。当前 gitlink(storage d287d05)的 cpp/src/jni/reader_jni.cpp loon_record_batch_reader_read_next 对每个 offset 非 0 的列仍整列 arrow::Concatenate 一次并计入 copies;这一项列在 README 第 5 节的上游需求里,尚未落地。

5.2 两处量不到,写在前面

  1. 段数据从对象存储读了多少字节,等上游 JNI 绑定后可量。交地址的那一面,读文件发生在 libmilvus-storage 自己的文件系统里,不经过我们的 JNI。C 接口 loon_filesystem_get_metrics（ffi_filesystem_metrics_c.h，milvus-storage #630 起）已经按文件系统实例累计读取字节; 上游 JNI 绑定它之后,任务在开始和结束时各取一次,差值就是本任务的对象存储读取量。文件系统实例按 address 加 bucket 在进程内共享, external collection 读客户桶的字节也由此可见。绑定之前,「读吞吐」报的是交接过界的 Arrow 字节。见 README 第 5 节。
  2. native 内存的总量,量不到。libmilvus-storage 内部的 Arrow 内存池不可见。 arrow.allocated.max 只覆盖 JVM allocator 记账的部分:JVM 自己分配的 buffer,加上 C Data 导入时以 ForeignAllocation 登记进来的 C 侧 buffer。导入的 buffer 由 allocator 释放,所以这个数在 JVM 侧就能算准; 它就是 G3 将来要限的数,两条能力用同一个口径。

5.3 不设开关

能力表 G5 那行写的是「会话配置开关」。这里不设:每个数每批加一次,一批几千行,一次 System.nanoTime 加一次 LongAdder.add 在批的代价里量不出来; C 侧是 holder 里的一个整数自增。开关本身反而是一个 option、一处 executor 上的判断和一份文档。 如果实测某个数有代价,先去掉那个数,不加开关。

5.4 怎么到 Spark UI

读:MilvusScan.supportedCustomMetrics 声明八个 CustomMetric(七个 sum、一个 max), MilvusRowPartitionReader 与 MilvusColumnarPartitionReader 的 currentMetricsValues 从 SegmentReader.metrics 取当前值;Spark 在任务结束时收走。写:Write.supportedCustomMetrics 加 DataWriter.currentMetricsValues,从 SegmentWriter.metrics 取,共五个。四条 Spark 线(3.5 到 4.2)接口一致。 不做 Prometheus 之类的外部导出:Spark 已经把任务级指标聚到 SQL 页和事件日志里,再导一遍是第二条路。

统一搜索入口落地后，搜索的两个阶段不经过扫描，读取与 Knowhere 的计数累加到 milvus.search.* 累加器（vector-search.html 2.1）。命中行回表在 SearchTake 里用独立的 ArrowAllocator.forSearchTask，不经过 MilvusRowPartitionReader，后者已没有索引查询路径。这里统计 storage JNI 与 Arrow 交接，Knowhere 搜索耗时仍由索引执行记录。

5.5 类型放哪

  • milvus-storage 上游 JNI 的 holder 持有计数，MilvusStorageReader.recordBatchReaderStatsScala(handle) 返回三个 long；native-storage 编译该绑定，原生库资源由统一平台包或上游回退路径提供。
  • core.read.exec:SegmentReader.metrics: ReadMetrics;core.write.exec:SegmentWriter.metrics: WriteMetrics。两个都是几个 long 的 case class,core 不知道 Spark。
  • spark.metrics:把它们翻成 CustomMetric / CustomTaskMetric,读写两张清单,只此一处;spark.read 的两个 reader 和 spark.write 的 DataWriter 只是取值上报。每个指标一个无参构造的类:driver 的 SQL 监听器按计划里记下的类名新建实例来聚合任务值,带参构造的类在这一步报错,SQL 页上就没有数(2026-09-16 UAT 发现)。

验收在工作单 #01:core 里用本地后端读一个已知段,断言八个数落在预期范围;UAT 读 3000 行的段, SQL 页上看到这八个数(MetricsTest 断言声明数与 ScanMetrics.supported 一致)。

六、JNI 统一由 milvus-storage 提供

2026-09-16 按用户要求迁移：Connector 移除自有 C++ JNI、StorageNative native 声明、异常类型及原生加载器，直接使用 milvus-storage 子模块的 io.milvus.storage 绑定。native-storage 仍是第 1 层构建模块，编译固定子模块的 Java/Scala API，并把 native-runtime 选出的 JNI 路径交给上游加载器；统一平台包提供 libmilvus-storage-jni 及其依赖，没有统一包时保留上游资源与系统库回退。不再编译 libnative-storage-jni，不保留旧类名的转发接口。现有 R4、写执行及 G5 的行为保持。

文件系统访问、批读取复制统计、写出列组信息、manifest 的完整释放和 transaction 的统计登记已在 milvus-storage 子模块补齐。实现归 cpp/src/jni 与 java/src/main；Connector 的 core.io、core.read.exec、core.write.exec 调用这些上游对象，不引入 Hadoop 或另一套 C 桥接。上游已经存在的 reader、writer、transaction 接口直接复用。

读取的并发也归上游（决策 31）。读取器属性 reader.parquet.prebuffer.lazy 决定一次 Parquet 读调用的区间是按解码顺序逐个请求（true，Arrow 默认），还是调用开始时一起请求（false）；core.read.exec.SegmentReaderRegistry 对每个读任务设 false 并给出区间大小。每个在途区间在进程级的 Arrow IO 线程池上占一个线程阻塞等 GET，上游 MilvusStorageRuntime.setArrowIoThreadPoolCapacity 设定该池的大小，Connector 在打开段读取器时按处理器数 × 8 只往上抬。原生包不带 CRT，S3 客户端是基于 libcurl 的 S3Client，一个区间就是一条连接上的一个 GET。

take 必须由上游拥有整个 loon_take 返回数组，并暴露可逐批读取、提前关闭的结果句柄，统一调用 loon_free_chunk_arrays；调用方不计算连续数组的释放地址。每批继续导出独立 ArrowArray/ArrowSchema，保留切片归零及复制计数。manifest 与其借用的 column groups 分开管理，reader 关闭后释放完整 manifest。Java 方法抛出的异常立即返回，UTF 字符串及局部引用在失败路径释放，不转换成空值。

上游当前 API 含 Scala，因此按 Connector 的 Scala 2.12/2.13 矩阵从固定子模块源码编译，不引入只支持 2.13 的预编译 JAR，也不传递上游示例构建中的 Spark 依赖。Arrow 仍由各 Spark 线选择。统一平台包模式由 native-runtime 校验 storage、Knowhere 及共同依赖并只解压到一个目录；Connector 的 NativeStorageLibrary 取得其中 libmilvus-storage-jni.so 的绝对路径，临时写入 milvus.storage.native.path，再由上游 NativeLibraryLoader 执行 System.load，调用结束后恢复原属性。显式路径指向另一文件或上游加载器在交接前已经完成加载时直接报错。没有统一平台包时，仍由上游加载器选择原有平台资源或系统库路径。

验收依次覆盖源码与 Scala 交叉编译、原生异常与加载检查、本地文件和 Arrow 读写及 take、真实 UAT 快照与持久化索引查询、最终 assembly 的加载和运行。取消的测试单列原因，不作为通过；当前结果见下节。

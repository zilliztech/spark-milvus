Spark 接口边界

本页说明第 3 层怎样把 Spark DataSource V2 调用变成第 2 层的可序列化描述，以及怎样把执行结果交回 Spark。 模块分层见 modules.md，读写机制分别见 read.html 与 write.html，用户 option 见 中文参考和英文参考。

第 3 层解析 Spark 输入、固定一次跨层合同；第 2 层不接收 Spark 类型，也不重新解释用户字符串。 driver 把 option、schema 和固定 Snapshot 变成类型化配置与任务描述；executor 只按描述打开资源。 四条 Spark 线共享 spark-base 主体，只有 Spark 公共接口确实不同的适配代码留在按线模块。

一、三个 Spark 入口

读取的表必须持有已经解析好的 Snapshot，scan 不再次访问服务以决定读哪个版本。 写入先从同一 Snapshot schema 取得字段 id、逻辑类型和向量维度。连接服务、读取对象存储与打开 JNI 句柄各自只有现有的一条路径； 第 3 层不能为某一种 Spark 入口另建一套存储访问。

三、option 在 driver 只解析一次

所有用户提供的正整数、正长整型和布尔值走 OptionParsing。键不区分大小写；值先去除首尾空白。 正数只接受十进制数字且必须大于零，id 列表按各自合同接受非负值；布尔只接受不区分大小写的 true / false。空白、负数、零、非十进制形式和溢出都抛 IllegalArgumentException，错误同时给出 option 键与原始值。未提供时保持既有默认值。

用户 option类型与默认值跨层形式执行映射
milvus.read.batch.max.rows正 Int，8192ReadLimits，保存在每个 SegmentReadTaskreader.record_batch_max_rows
milvus.read.batch.max.bytes正 Long，33554432；最大 4294967296reader.record_batch_max_size
milvus.read.arrow.max.bytes正 Long，Long.MaxValuetask Arrow child allocator 的最大分配字节
milvus.write.file.rolling.bytes正 Long，2147483648MilvusOption.writeFileRollingByteswriter.file_rolling.size

原始 fs.* bag 只负责存储位置和认证。即使用户同时传入上表中的上游原生键， 类型化 read/write 值也覆盖它，防止跳过 connector 的范围校验。rolling 属性只传给 segment writer； ObjectStore、统计文件与 manifest 提交继续使用纯存储属性。

四、executor 资源所有权

进程级 Arrow root（connector 生命周期）
  └─ task child（PartitionReader 生命周期，有 maxBytes）
       ├─ SegmentReader 的 Arrow C Data struct 与导入批
       └─ 行式/列式当前批
  └─ search task child（ArrowAllocator.forSearchTask，SearchTake 的回表批，不经 PartitionReader）

MilvusPartitionReaderFactory 创建 task child，然后用它打开 SegmentReader。 行式与列式基础 reader 都明确持有 child；metadata 与 Limit 包装器把 close 委托到底层。 正常关闭先释放当前批，再关闭 native reader，最后关闭 child。基础 reader 的关闭幂等；factory 在构造失败时关闭已经取得的每个资源， 因为 Spark 不会关闭一个没有成功返回的 reader。SegmentReader 只借用调用方 allocator，不得关闭 child；task 更不能关闭进程级 root。

边界：milvus.read.arrow.max.bytes 只覆盖 Arrow Java allocator 能核算的内存。 milvus-storage 的 native 内存池目前没有 per-reader 限额接口。上游也没有独立的每 task 预取队列上限属性， 因此 G3 不声明已经提供 prefetch limit。

五、交付顺序与验收门

  1. 先在本页、读写设计与决策日志确定 option 名、默认值、跨层类型和资源所有权。
  2. 在 spark.options 严格解析；解析失败必须发生在 driver 规划或写构建阶段。
  3. 把读取限制加入可序列化任务并在 core.read.exec 映射；把 rolling 限制只传给两个原生 segment writer。
  4. 建立 task child allocator；覆盖行式、列式、向量路径、构造失败、正常关闭与重复关闭。
  5. 同步能力表、双语 reference 与相关 package.scala，再跑每条受影响 Spark 线的编译和聚焦测试。
验收：默认值不改变既有行为；option 大小写不影响解析；空值、零、负数、非数字与溢出错误包含键和值； read task 序列化后保留全部限制；原生属性使用类型化值；关闭 task child 后全局 root 仍可分配；V2/V3 writer 都得到同一个 rolling 属性。

六、不在本设计内的项

milvus.filter 的标量合同见表达式设计：第 3 层负责严格解析、 按固定快照校验并补齐内部读取列，第 2 层在 Arrow 批上求值。本页仍不改变 W6 索引构建参数，不建立索引/GPU/cache 预算，也不以 connector 本地开关绕过 milvus-storage 尚未提供的 native 内存与预取接口。这些能力必须先有各自设计 和上游可调用接口，才能加入跨层合同。

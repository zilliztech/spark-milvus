存储访问层设计

能力 R3。分层与包边界见 modules.md， 认证机制见 storage-auth.html。

状态：待评审。第二节的设计是推荐方案，尚未写进决策日志。

一、要解决的问题

读一张 Milvus 表要在对象存储上打开五种文件。现在一个进程里有四条互不相干的打开方式。

打开方式用在哪怎么配
java.io.FileInputStream快照 JSON不配，只能读本地文件
HadoopIO.readAllBytes段 manifest、删除文件收一个 Hadoop Configuration
FileSystem.get 直接调parquet footer同上，另加 parquet 的 InputFile 适配
C++ 的 loon_*列组数据、索引文件收一个 fs.* 属性包

四条路各自解析配置、各自归一路径、各自处理凭证，同一件事做了四遍且互不一致。今天的症状：

  1. 配置在五个文件里各解析一遍，默认值和校验都不同。开发用的 a-bucket、localhost:9000、minioadmin 落在生产路径上， 非 IAM 模式漏配桶名会安静地连错桶。
  2. 路径在七处各归一一遍，规则不同。格式里同一个位置有六种写法， 而 resolveManifestDeltaPath 这个函数同时做归一和拼 _delta/， 把通用逻辑和格式知识混在一起。
  3. Azure 与 GCS 读不了。JVM 侧只带 hadoop-aws 与 hadoop-aliyun， 代码只认 s3://、s3a://、oss://、file://。 客户的 Milvus 建在 Azure 或 GCS 上时，第一步打开快照 JSON 就失败。
  4. OSS 要靠改全局状态才能用两套身份。hadoop-aliyun 没有按桶配置， backfill 只能备份八个全局键、改写、还原，并禁用 FileSystem 缓存。 这段代码隐含一个没人测的单线程前提。
  5. 3.5 线出不了 Scala 2.12 产物。四条 Spark 线都还引用上游 milvus-storage 的 Java 绑定，它只发 2.13。

二、设计

一条打开方式，一份配置，一种路径表示。

  1. 打开文件只经 milvus-storage 的 C filesystem，JVM 侧通过 native-storage 的 JNI 调它。
  2. 配置只解析一次，在 core.credential，产出它的 properties。
  3. 路径只有一种表示，在 core.path，格式里的六种写法在边界上收敛成 (bucket, key)。

格式包按路径要字节，拿到字节。凭证、端点、FileSystem 这些词不出现在它们的签名里。

2.1 每个包变成什么

包职责规模
core.io拿着 JNI 句柄，提供 open、read、list、stat、create薄，是封装不是实现
core.credential用户选项转 properties，一次解析一次校验今天散在五个文件里的逻辑收成一处
core.path六种路径写法转 (bucket, key)今天散在七处
native-storage包 loon_filesystem_* 与 loon_exttable_read_manifest新代码，本设计的主要工作量

2.2 五个症状怎么被解决

症状解法
配置解析五遍只有 core.credential 一处解析
路径归一七遍只有 core.path 一处归一；格式知识（_delta/、_metadata/manifest-N.avro）留在 core.delete 与 core.manifest
Azure 与 GCS 读不了C filesystem 有 azure 与 gcp 实现
OSS 要改全局状态loon_filesystem_get(properties, path) 每次带一份属性，按路径隔离
3.5 线出不了 2.12上游 Java 绑定被 native-storage 取代

三、为什么是这个设计

因为要的东西 C 层已经写好了，而且比我们能在 JVM 侧写出来的更全。

3.1 文件系统

loon_filesystem_get(properties, path, path_len, out_handle)   // 内部有 FilesystemCache
loon_filesystem_read_file_all(handle, path, path_len, out_data, out_size)
loon_filesystem_open_reader / reader_readat(handle, offset, nbytes, out_data)
loon_filesystem_reader_readat_async / reader_supports_async
loon_filesystem_list_dir(handle, path, recursive, out_list)   // {path, is_dir, size, mtime_ns}
loon_filesystem_get_file_info / get_path_info / get_file_stats
loon_filesystem_open_writer / writer_write / writer_flush / writer_close
loon_filesystem_write_file / create_dir / delete_file
loon_filesystem_get_metrics / list_metrics / reset_metrics

底座是 arrow::fs::FileSystem，文件系统实现有 s3、gcp、azure、local。

3.2 七个云的凭证，含国内三家

cloud_provider 认识 aws、aliyun、azure、gcp、huawei、tencent、local。 s3/provider/ 下有阿里云的 RAM、STS 与 OIDC 角色链（ACK 上对应 IRSA 的那套）、 腾讯云与华为云的凭证与 STS 客户端。在 JVM 侧补齐等于用 Scala 重写这几家的 STS 客户端。 明细见 storage-auth.html 2.1。

3.3 manifest 与写侧提交

loon_exttable_read_manifest(path, properties, out_manifest)
// 头文件原注释：output manifest (includes column groups, delta logs, and stats)

loon_transaction_begin / commit / get_manifest / get_read_version
loon_transaction_add_column_group / add_delta_log / add_index_info / add_lob_file
loon_transaction_update_stat / drop_column / drop_index / append_files

这覆盖了 core.manifest 与 core.write.commit 两个包的大半工作。

3.4 代价

平台要为我们接一套显式临时凭证：不走 Hadoop 的连接器拿不到 spark.hadoop.fs.*。 这不是新问题，云上同一个文件里已经为 Lance 做过——解析卷路径、assume 角色、 把临时凭证经 storageOptions 交过去。

四、读一张表要打开哪些文件

五个入口分支，用户给的东西不同，最终都归结成一个对象存储路径：collection 名（调 gRPC CreateSnapshot 拿 s3Location）、快照路径、milvus.snapshot.manifests 或 milvus.snapshot.v2.segments、milvus.backup.dir、遗留 client 模式。

文件路径怎么来谁解析字节
快照 JSON起点路径本身JVM
V3 段 manifest<段基路径>/_metadata/manifest-<N>.avro，先列目录取最大 NJVM，或改用 loon_exttable_read_manifest
V2 段 manifest快照 JSON 的 manifest_list 列出的 avro，裸二进制无 OCF 头JVM，外挂 avsc 按格式版本解
删除文件<段基路径>/_delta/<文件名>JVM
parquet footer列组文件尾部，恢复 V2 packed 段的字段 idJVM
列组数据manifest 里记的路径C++
索引文件manifest 的索引登记C++（未建）

用哪条通路由解析者决定，不由文件类别决定：列组 parquet 是数据，但 JVM 会打开它读 footer——V2 packed 段的字段 id 只写在 parquet 的 schema 里。同一个物理文件，两侧都碰。

4.1 路径的六种写法

s3a://bucket/key
s3://bucket/key                                   → 改写成 s3a
_delta/xxx                                        → 相对段基路径
/xxx                                              → 带前导斜杠，仍相对段基路径
files/insert_log/<collection>/<partition>/<segment>/<field>/<log>
a-bucket/files/...                                → 带桶名不带 scheme

六、下一步

  1. native-storage 的 JNI，包 loon_filesystem_* 与 loon_exttable_read_manifest。本设计的主要工作量，第 1 层由此从「以后再说」 变成关键路径。

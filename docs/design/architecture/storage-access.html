存储访问层设计

能力 R3。分层与包边界见 modules.md， Hadoop 侧的认证机制见 storage-auth.html。

路线已定（2026-09-11）：打开文件全部经 milvus-storage 的 C filesystem，JVM 侧走 JNI。 理由是格式实现与 Milvus 天然一致，升级时不需要两边再对一遍。

一、要解决的问题

读一张 Milvus 表要在对象存储上打开五种文件。现在一个进程里有四条互不相干的打开方式。

打开方式用在哪怎么配
java.io.FileInputStream快照 JSON不配，只能读本地文件
HadoopIO.readAllBytes(已删除)段 manifest、删除文件收一个 Hadoop Configuration
FileSystem.get 直接调parquet footer同上，另加 parquet 的 InputFile 适配
C++ 的 loon_*列组数据、索引文件收一个 fs.* 属性包

四条路各自解析配置、各自归一路径、各自处理凭证，同一件事做了四遍且互不一致。今天的症状：

  1. 配置在五个文件里各解析一遍，默认值和校验都不同。开发用的 a-bucket、localhost:9000、minioadmin 落在生产路径上， 非 IAM 模式漏配桶名会安静地连错桶。
  2. 路径在十二处各归一一遍，规则还不一致：有的认 oss://，有的只认 s3:// 和 s3a://，有的把不认的 scheme 当合法路径透传。 其中 resolveManifestDeltaPath 同时做归一和拼 _delta/，把通用逻辑和格式知识 混在一起；MilvusBackfill 里另有两处反向操作，从 URI 里把桶名抠出来—— 说明 (bucket, key) 这个表示已经有人需要了。
  3. Azure 与 GCS 读不了。JVM 侧只带 hadoop-aws 与 hadoop-aliyun， 代码只认 s3://、s3a://、oss://、file://。 客户的 Milvus 建在 Azure 或 GCS 上时，第一步打开快照 JSON 就失败。
  4. OSS 要靠改全局状态才能用两套身份。hadoop-aliyun 没有按桶配置， backfill 只能备份八个全局键、改写、还原，并禁用 FileSystem 缓存。 这段代码隐含一个没人测的单线程前提。
  5. 3.5 线出不了 Scala 2.12 产物。四条 Spark 线都还引用上游 milvus-storage 的 Java 绑定，它只发 2.13。

1.1 同一个位置的七种写法

s3a://bucket/key
s3://bucket/key                                   → 改写成 s3a
oss://bucket/key                                  → 阿里云，backfill 按 cloud provider 改写
_delta/xxx                                        → 相对段基路径
/xxx                                              → 带前导斜杠，仍相对段基路径
files/insert_log/<collection>/<partition>/<segment>/<field>/<log>
bucket/files/...                                  → 带桶名不带 scheme

二、设计

一条打开方式，一份配置，一种路径表示。

  1. 打开文件只经 milvus-storage 的 C filesystem，JVM 侧通过 native-storage 的 JNI 调它。
  2. 配置只解析一次，在 core.credential，产出 C 层的 fs.* 属性包。
  3. 路径只有一种表示，在 core.path，七种写法在边界上统一成 (bucket, key)。

格式包按路径要字节，拿到字节。凭证、端点、FileSystem 这些词不出现在它们的签名里。

2.1 每个包变成什么

包职责规模
core.io拿着 JNI 句柄，提供 open、read、list、stat、create薄，是封装不是实现
core.credentialfs.* 与 extfs.* 转属性包，一次解析一次校验今天散在五个文件里的逻辑合成一处
core.path七种路径写法转 (bucket, key)今天散在十二处
native-storage包 loon_filesystem_* 与 loon_exttable_read_manifest新代码，本设计的主要工作量

2.2 core.path 产出什么

C 层已经有这个类型，StorageUri{scheme, address, bucket_name, key}， 解析与渲染规则在 fs.cpp。core.path 的产出必须跟它逐条对上， 不能另立一套。

输入C 层怎么解
解析不出 schemekey = 整个字符串，bucket_name 与 address 为空
scheme://bucket/keyhost 就是桶名，path 是 key
scheme://address/bucket/keyMilvus 格式，只有 include_address=true 时这么解

由此定三条：

  1. 类型是 Located(bucket, key)，key 是桶相对的，不带前导斜杠。 bucket 允许为空——本地模式和纯相对路径都没有桶。
  2. 交给 C filesystem 的是 key，不是 bucket/key。 FilesystemCache 把底层 filesystem 包在 FileSystemProxy(bucket, fs) 这个子树里，桶名会自动补上；JVM 侧先拼一遍就出 a-bucket/a-bucket/files/…，MilvusV2BinlogWriter 的注释记着这个坑。 桶名走 fs.bucket_name，或多桶时走 extfs.<名字>.bucket_name。
  3. 无 scheme 的路径一律当 key。所以 files/insert_log/… 和 bucket/files/… 这两种写法在字符串上分不开，parse 必须由调用方告诉它 默认桶是什么，不能靠猜第一段是不是桶名。

三个操作，格式知识一个都不带：

parse(raw: String, defaultBucket: String): Located   // 七种写法归一
resolve(base: Located, child: String): Located       // 路径拼接
uri(l: Located, scheme: String): String              // 渲染回 URI，给迁移期的 Hadoop 调用方

_delta/、_metadata/manifest-N.avro 这些拼接留在 core.delete 与 core.manifest，它们调 resolve。

2.3 为什么是这条路线

因为要的东西 C 层已经写好了，而且比我们能在 JVM 侧写出来的更全。

  • 文件系统：loon_filesystem_* 是一整套——open、readat（含异步）、 list_dir、stat、writer、create_dir、delete、指标，底座是 arrow::fs::FileSystem， 后端有 s3、gcp、azure、local。
  • 七朵云的凭证，含国内三家：阿里云的 RAM、STS 与 OIDC 角色链，腾讯与华为的 STS 客户端。在 JVM 侧补齐等于用 Scala 重写这几家的 STS 客户端。
  • manifest 与写侧提交：loon_exttable_read_manifest 直接返回解析好的 列组、删除日志与统计；loon_transaction_* 覆盖 core.write.commit 的大半。

代价有两项。一是 native-storage 的 JNI 封装，本设计的主要工作量。 二是存量部署要多一套配置：今天 spark.hadoop.fs.* 喂的是 Hadoop，C 层不认， 翻译要落在这个仓库之外（3.3），托管平台那边要排期。这是离开 Hadoop 的真实代价—— Hadoop 的按 scheme 分派本来替我们做了这件事。

五个症状的去处：配置解析与路径归一各收进一个包；Azure 与 GCS 靠 C 的 azure、gcp 实现； OSS 的全局状态改写被 extfs.* 取代（3.5）；上游 Java 绑定被 native-storage 取代，2.12 交叉编译解锁。

三、凭证怎么到 C 层

core 只认一套 fs.* 属性包，不认识云，也不认识 scheme。 按云分派在 C 层的 fs.cloud_provider。这跟 Hadoop 时代 connector 把 Configuration 原样传下去是同一个形状——屏蔽差异的那一层从 Hadoop 换成了 C， connector 两边都不认识云。

3.1 core 的输入契约

一个 Map[String, String]，键全是 fs.*，多桶时是 extfs.<名字>.*（3.5）。core.credential 校验必填项、拒绝空值， 然后原样交给 C。它不按云分支，不认识 s3a、oss、abfs 这些 scheme，也没有任何一家云的名字出现在它的代码里。

C 从两个地方取凭证：属性包和进程环境。真正的凭证不走属性包——静态密钥是唯一例外。 属性包里带的是「去哪里取」和「取谁的」：fs.role_arn 系列说 AssumeRole 成谁， fs.use_iam 说去环境里找，fs.azure_* 与 fs.gcp_target_service_account 是那两家的跨租户参数。 取值顺序写死在 s3_filesystem_producer.cpp：fs.role_arn 非空就 AssumeRole； 否则 fs.use_iam 为真就按云选 STS provider；再否则用静态密钥 （Azure 上 fs.access_key_id 是 account name，密钥是 fs.access_key_value）。

3.3 谁来填这个属性包

用户直接给 fs.*，这是 core 认识的唯一形式。

运行环境里已经有 Hadoop 风格配置的时候（spark.hadoop.fs.s3a.assumed.role.arn 这类），把它翻成 fs.* 不是 core 的事。翻译只有两个合法落点：

  1. 产出配置的那一方直接产出 fs.*。托管平台自己就知道角色 ARN 和端点，多注入一套键即可。这是长期形态。
  2. 第 3 层一个垫片，读 spark.hadoop.fs.* 产出 fs.*， 只为让存量部署不改配置就能跑。它必须写明退出条件和时间点，否则就是 AGENTS.md 禁止的烟囱。 已实现为 spark-base 的 HadoopStorageConfig：纯键名翻译， 按本表映射，cloud_provider 从出现键的命名空间推（s3a→aws、oss→aliyun）， 两个命名空间都在则留空让 C 层校验报错。退出条件是产出配置的一方直接产出 fs.*。

两个落点都在 core 之外。下表是给它们用的，不是 core 的代码：

值本身是可以复用的：平台注入的是角色 ARN、会话名、端点，不是 access key 或 session token， C 层认同样的输入（3.4）。可复用说的是值，不是说 core 应该去读它们。

都是两步：先用 pod 的机器身份换一份临时凭证，再拿它调 AssumeRole 换成客户角色。

3.5 多个桶用不同身份

extfs.<名字>.<属性> 注册多套文件系统配置，<属性> 就是 fs. 后面那一截：

extfs.source.address        = oss-cn-hangzhou-internal.aliyuncs.com
extfs.source.bucket_name    = customer-bucket
extfs.source.role_arn       = <客户角色>
extfs.milvus.address        = ...
extfs.milvus.bucket_name    = milvus-bucket

loon_filesystem_get(properties, path) 拿到带 scheme 的路径时按 address + bucket 匹配到对应的一组，匹配不上落回默认的 fs.*。

backfill 今天要备份八个 fs.oss.* 全局键、改写、还原、禁用 FileSystem 缓存 （见 backfill-storage.html），这套动作在 extfs.* 下不存在：源桶和 Milvus 桶各注册一个名字，一次传进去，不改任何共享状态。

3.6 长作业的凭证刷新

每个进程各自持一个会自我刷新的 provider，作业跑多久都不掉凭证。 Hadoop 和 C 层都是这么做的，不是我们要挑的东西：hadoop-aws 的 AssumedRoleCredentialProvider 按 fs.s3a.assumed.role.session.duration （默认 1h）到期前自己续；C 层 AWS 距过期 60 秒内重新 AssumeRole；C 层阿里云距过期 180 秒内 重跑两步链，且第一步每次重新打开并读 ALIBABA_CLOUD_OIDC_TOKEN_FILE， 所以 kubelet 轮换投影 token 之后读到的是新的那份。

会过期的是另一种做法：driver 调一次 STS，把换出来的 access key、secret、session token 随配置发给 executor。云上 Lance 那条路走的就是这个，凭证一过期作业就失败，只能靠调大 duration 顶。我们不走这条。

四、三层怎么衔接

三个边界，每个边界只许通过一种东西。越界的东西一旦变多，上一层就开始知道下一层的实现。

4.1 C 与 JVM 的衔接

边界上的东西怎么过去约束
配置Map[String,String] 转成两个 const char* 数组，调 loon_properties_createJNI 不看键名，也不认识云。一旦它认识，云知识就有了第二个落点
句柄loon_*_new / _open 返回的 handle 存成 JVM 侧的 Long进程内指针，不可序列化。不许进 InputPartition
数据Arrow C Data Interface：每批一组 ArrowArray + ArrowSchema零拷贝。不用 ArrowArrayStream——Arrow Java 的 loadNextBatch 共享 VectorSchemaRoot 且忽略 offset，遇到 RecordBatch::Slice 会每批返回同一份数据。理由与替代读法见 storage-io.html 第二节
错误LoonFFIResult 转成 JVM 异常，然后 loon_ffi_free_resultC 侧不抛异常过界；每个返回码都要判

句柄不可序列化这一条决定了读路径的形状。Spark 把 InputPartition 序列化后发到 executor，所以它里面只能装描述——段路径、manifest 版本、要读的列名、 fs.* 的 map。executor 拿到描述后才调 loon_segment_reader_open 开句柄， 读完关掉。

4.2 原生库有多大，这是个约束

libmilvus-storage.dylib 481 MB，JNI 桥 libmilvus-storage-jni.dylib 只有 177 KB。两个都要进产物：桥依赖大库。

段大小是什么
__TEXT288 MB代码。arrow 27.8 万个符号、rust bridge 4.6 万、parquet 2.9 万、AWS 1.4 万、Azure 0.6 万——整个依赖树静态链进来了
__LINKEDIT162 MB102 万个符号。strip -x 后整库降到 315 MB
其余9 MB__DATA_CONST 与 __DATA

静态链接是有意的：JNI 库要能独立加载，不能要求宿主机装一堆动态库。 otool -L 显示只有 folly、glog、protobuf、grpc 这几个还是动态依赖。

三条后果，都还没有人处理：

  1. 没有 strip，白背 166 MB。Release 构建保留了全部符号，而这是要进 fat jar 的东西。 剥离在 milvus-storage 的 CMake 做还是在我们的打包步骤做，没有定。
  2. 运行时要解压到磁盘。NativeLibraryLoader 把 JAR 里 native/<platform>/ 下的库全部解压到临时目录再 System.load。 每个 executor 进程启动都要写这近 500 MB。
  3. 多平台产物按平台各一份。一个同时带 linux 和 darwin 的 fat jar 是两倍。

315 MB 仍然很大。真要再降只能让 arrow 改成动态链接，那是上游的构建策略， 不是这一层能单方面定的。这条记在这里是因为它影响第 1 层怎么打包、fat jar 多大、 executor 启动多久，而此前的设计里一个字都没提。

4.4 谓词下推：C 的入口是坏的，我们不用它

format_reader.h 里基类是这样的：

[[nodiscard]] virtual arrow::Status set_predicate(const std::string& /*predicate*/) {
  return arrow::Status::OK();
}

参数名被注释掉了。收下一个谓词，返回成功，什么都不做。只有 VortexFormatReader 覆写了它，而 Vortex 在 capabilities.md 第 10 节里明确不做。所以对 parquet 列组调 loon_segment_reader_get_filtered_stream，不报错也不过滤，调用方拿到全量数据却以为 已经过滤过了。

这是缺陷，不是「还没做」。接受参数、返回成功、忽略参数，正是 AGENTS.md 里「禁止外围兜底」说的那个形状。基类该返回 NotImplemented，这条列在第六节。我们这边则是 core.io 根本不暴露这个入口——不是「记得别调」，留着它早晚有人用。

但它修不修都不改变我们的设计。R6/R7 在 JVM 侧算是决策日志 2026-09-09 定的， 理由与这个空实现无关：R7 要按 Milvus 的 Plan.g4 文法逐条复刻 JSON、Array、 json_contains 的语义，C 层没有这套。真正省 I/O 的是 R10 那条统计剪枝（4.5）。

4.5 R10 为什么只能在 C 里做

不是「在 JVM 侧写一份 footer 解析是烟囱」，是写了递不进去。 FFI 里没有任何 row group 相关的入参：loon_segment_reader_open 收 segment_path、version、schema、 needed_columns、config、properties，没有「只读这几个 row group」这一项。JVM 侧就算把 footer 读了、把该跳的 row group 算出来，也没有地方把结果交出去。 剪枝要真省 I/O，必须发生在读的那一侧。

它要两边各做一件事：Milvus 写统计文件并登记进 manifest 的 stats （那个 map 的形状就是为此准备的，R9 的段级布隆过滤器走同一条路）， milvus-storage 的 reader 用它剪 row group。两件都不在这个仓库里， 已经在 README 第 5 节那张表里；在它们落地前 R10 不交付， 它的优先级是 P1。

五、读一张表要打开哪些文件

五个入口分支，用户给的东西不同，最终都归结成一个对象存储路径：collection 名（调 gRPC CreateSnapshot 拿 s3Location）、快照路径、milvus.snapshot.manifests 或 milvus.snapshot.v2.segments、milvus.backup.dir、遗留 client 模式。

判断谁解析字节只看一条：格式属于 milvus-storage 就由 C 解析，属于 Milvus 的元数据 才由 JVM 解析。milvus-storage 是 Milvus 原生的实现，格式以它为准；在 JVM 侧再写一份 解析器，等于同一个格式有两份实现，版本一升就要对两遍。

5.1 V2 为什么不能砍

V2 不是老版本，是当前默认。Milvus 的存储版本升级 compaction 里， 目标版本取 storage.StorageV2，只有 paramtable.Get().CommonCfg.UseLoonFFI 为真才改成 V3；而 common.storage.useLoonFFI 默认 false（2.6.7 引入）。 默认部署的 Milvus 新段写 V2，compaction 的目标版本也是 V2。

只支持 V3 等于在默认配置的 Milvus 上一个段都读不了，而 K1「Storage V2 packed 段」在 capabilities.md 里是 P0。

六、对 milvus-storage 的需求

七项。每一项都不在 JVM 侧绕过——milvus-storage 是我们自己的仓库，缺什么补什么。

6.1 我们自己提 PR

可行，瓶颈是 review 不是代码。仓库是公开的 milvus-io/milvus-storage，最近 80 个提交里 jiaqizho 占 58 个——单一主力维护者， 而我们 spark 侧一次都没提过。它有六条 CI，其中 error-handling-ratchet 说明错误处理 有量化门槛；229 个源文件配 67 个测试文件，不带测试的 PR 基本过不了。

按这个顺序提：先第 3 项——一行修复加一个测试，形态上是「帮你们发现一个静默失效」， 最容易过，用来建立往来；第 7 项紧随其后，它是纯挪动、不改逻辑、已有测试覆盖， 而且我们这边有一份现成的过渡实现可以作为「有人真的需要它」的证据；再把第 4、5、6 项打成一个 PR， 三个属性都是同一套机械改动；第 1 项放最后，它要加 FFI 结构体， 第一次接触就送这个，压在队列里的概率很高。

真正的瓶颈是维护者的时间。这六项里哪一项进了关键路径，与其提 PR 不如先找人对排期。

八、要在真实环境验的

已验（2026-09-12，UAT aws-usw2）。JNI 真的能读出真实 Milvus 数据。 取一个实例的段 binlog（4133761 字节），两条路各读一遍，字节的 sha256 完全一致： 本地后端（fs.storage_type=local）读下载到磁盘的那份；AWS S3 后端读桶里的原对象。 凭证走 pod 的 IRSA token 从本机 AssumeRole 换来。手工验证入口是 StorageNativeUatTest，无凭证时自动 cancel，不进 CI。
顺带实证了 3.7 的 fs.session_token 缺口是真挡路，不只是读代码推断的。 临时凭证必带 session token。把 fs.access_key_id + fs.access_key_value 放进属性包（没有 session token 的位置），C 层 HeadObject 直接 ACCESS_DENIED； 同一份凭证用 aws cli 带上 token 能读、去掉 token 就 403，两相对照坐实了是 token 被丢了。 改走 fs.use_iam=true、让 C 层默认链从进程环境读 AWS_SESSION_TOKEN， 就读通了。结论：executor 上用临时凭证走 S3，今天只能靠 use_iam 加环境变量， 属性包这条路要等上游加 fs.session_token（第七节第 4 项）。
  1. EKS pod 里 C 层默认链拿到的是 IRSA 投影的 service-account token，不是节点实例角色。 代码上成立（3.4）。本机用同一套 token 换出的凭证经 use_iam 读通了 UAT 桶， 但那是本机默认链读环境变量，不等于 EKS pod 内的行为，仍要在 pod 里跑一次确认。
  2. ACK pod 里 RRSA 注入的三个环境变量齐全，OIDC 角色链两步都成功。
  3. OSS 经 arrow 的 S3 客户端读写与今天的 hadoop-aliyun 结果一致。C 层把阿里云当 S3 兼容端点， 并强制 virtual-host 寻址。只有这一家有「和原来一致吗」的检查，因为只有 S3 和 OSS 今天有 JVM 那条路可比；Azure、GCS、腾讯、华为是从读不了变成能读，没有「原来的行为」可对。

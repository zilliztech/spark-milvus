存储访问层设计

本页对应能力 R3。术语、分层与包边界见 modules.md，能力编号见 capabilities.md。

状态：证据齐了，路线待评审。认证那一趴已完成（见 storage-auth.html），它查到的事实回填进了本页第四节。 原先列的四件待查现在只剩一件，而它不足以挡住路线。 本页给出推荐与理由，决定尚未写进决策日志，等评审。

一、位置与职责

位置：core 内部，所有格式包的下面。职责：把格式里的引用变成字节。

它不认识快照、manifest、删除文件、列组，一个都不认识。判据：一个包如果在解析不属于它的字节， 就是放错了位置。core 里 path、credential、io 三个包没有任何解析器， 其余包各有各的编码——snapshot 用 ObjectMapper，manifest 用 Avro 的 DataFileStream， delete 用 ByteBuffer 加 ObjectMapper，schema 只碰 CollectionSchema，codec 只碰 ByteBuffer。

二、读一张表要打开哪些文件

五个入口分支，用户给的东西不同，但都归结成一个对象存储路径：collection 名（连接器调 gRPC CreateSnapshot 拿 s3Location）、快照路径、milvus.snapshot.manifests 或 milvus.snapshot.v2.segments（离线段列表）、milvus.backup.dir、遗留 client 模式。

文件路径怎么来谁解析
快照 JSON起点路径本身JVM
V3 段 manifest<段基路径>/_metadata/manifest-<N>.avro，N 要先列 _metadata/ 取最大值JVM
V2 段 manifest快照 JSON 的 manifest_list 列出的 avro，裸二进制无 OCF 容器头，外挂 avsc 按格式版本解JVM
删除文件<段基路径>/_delta/<文件名>JVM
parquet footer列组文件的尾部，只读 footer，恢复 V2 packed 段的字段 idJVM
列组 parquetmanifest 里记的路径C++
索引文件manifest 的索引登记C++（未建）

判据不是「manifest 还是数据」，是谁解析。列组 parquet 文件是数据，但 JVM 会打开它读 footer——V2 packed 段的字段 id 只写在 parquet 的 schema 里，别处没有。同一个物理文件，两条通路都碰。

路径的六种写法

格式内部写引用不统一，代码里实际出现过这六种：

s3a://bucket/key
s3://bucket/key                                   → 被改写成 s3a
_delta/xxx                                        → 相对段基路径
/xxx                                              → 带前导斜杠，仍相对段基路径
files/insert_log/<collection>/<partition>/<segment>/<field>/<log>   → 桶内相对 key
a-bucket/files/...                                → 带桶名不带 scheme

这里要区分两件现在混在一起的事。路径归一（六种形状收敛成 bucket 加 key）是通用的， 不需要知道文件是什么。路径构造（V3 的 manifest 在 _metadata/manifest-N.avro、 删除文件在 _delta/ 下）是格式知识，属于 manifest 和 delete 包。 现在 MilvusStorageV3ManifestReader.resolveManifestDeltaPath 把两件事写在同一个函数里， 它既做 s3/s3a 归一，又知道 _delta/ 这个目录名。

不在本页。通用机制、判断原则、各云覆盖、SDK 版本与实测事实都在 storage-auth.html，作业侧的多桶访问在 backfill 的多桶存储访问。 本页只用到那边的两条结论，见 4.3。

四、关键发现：C 层已经有完整的文件系统与 manifest 接口

读 milvus-storage/cpp/include/milvus-storage/ 的 C 头文件得出。这一条推翻了本页之前的方案。

凭证包在 properties 里。文件系统实现有 s3、gcp、azure、local 四种， OSS 与 COS 走 S3 兼容端点——但凭证不是：阿里云、腾讯云、华为云各有独立的 provider 与 STS 客户端，见 4.5。 loon_filesystem_get 的注释写明：路径带 scheme 时会去解析 extfs.* 配置。

4.2 manifest 与事务

loon_exttable_read_manifest(manifest_file_path, properties, out_manifest)
// 头文件原注释：output manifest (includes column groups, delta logs, and stats)

loon_transaction_begin / commit / get_manifest / get_read_version
loon_transaction_add_column_group / add_delta_log / add_index_info / add_lob_file
loon_transaction_update_stat / drop_column / drop_index / append_files

read_manifest 不只读字节，它返回解析好的列组、删除日志和统计， 那正是 core.manifest 整个包要做的事。事务那组覆盖写侧的提交语义。

4.3 认证与多云：C 层已经解决

七个云的凭证 C 层已经写好，含国内三家。cloud_provider 认识 aws、aliyun、azure、gcp、huawei、tencent、local。s3/provider/ 下有阿里云的 RAM、STS 与 OIDC 角色链（ACK 上对应 IRSA 的那套）、腾讯云与华为云的凭证与 STS 客户端。 我们 JVM 侧只有 S3 与 OSS，Azure 与 GCS 一行都没有。明细见 storage-auth.html 2.1。

按路径隔离 vs 备份还原全局键。hadoop-aliyun 3.4.1 没有按桶配置 机制（jar 里没有 propagateBucketOptions，也没有 fs.oss.bucket. 前缀， 同版本 hadoop-aws 两样都有）。所以 backfill 在一个作业里用两套身份访问 OSS，只能备份八个 全局键、改写、还原，并禁用 FileSystem 缓存，且隐含一个没人测的单线程前提。 而 loon_filesystem_get(properties, path) 每次带一份属性，天然按路径隔离， 不存在需要备份还原的全局状态。明细见 backfill 的多桶存储访问。

4.4 被推翻的方案

本页早先的方案是在 Scala 里定义 ObjectStore（open / list / stat / create）， 用 Hadoop FileSystem 实现，前提是「原生层只会打开数据文件」。这个前提不成立。 在已有通路旁边再建一条 Scala 的，按 AGENTS.md 的原则就是烟囱。

五、路线：推荐与剩余未知

5.1 四件待查现在的状态

原先列的现在
小文件跨 JNI 的开销不是阻断项。这些读是对象存储上的 HTTPS 请求，几十毫秒；JNI 跨界微秒级，且 loon_filesystem_get 内部用 FilesystemCache 缓存句柄。相差三到四个数量级，测了也不改变决定。当初把「没测过」当成了「不确定」
C++ 没有 HDFS 实现不影响。Milvus 的 storageType 只有 local 与 remote，格式路径永远不在 HDFS 上；用户自己的源数据走 spark.read，与本层无关
平台注入的 s3a 配置将失效有现成解法。平台确实重度依赖（SparkCspRuntimeSupport 注入整套 spark.hadoop.fs.*），但同一个文件里已有 Lance 的先例：不走 Hadoop 的连接器，平台自己 assume 角色、拿临时凭证、经 storageOptions 显式交过去。需要平台配合，不是技术障碍
OSS 走 S3 兼容端点是否与 hadoop-aliyun 一致仍未查。唯一剩下的

5.2 推荐

统一走 C 的 filesystem。支持它的证据有四条，按分量排：

  1. 七个云的凭证已经写好，含国内三家的 STS 与阿里云的 OIDC 角色链。JVM 侧补齐等于用 Scala 重写一遍这几家的 STS 客户端。
  2. 按路径隔离，不需要备份还原全局键。这直接解决 backfill 现在那段绕过 hadoop-aliyun 能力缺失的代码，以及它隐含的单线程前提。
  3. loon_exttable_read_manifest 返回解析好的列组、删除日志与统计， loon_transaction_* 覆盖写侧提交。这是 core.manifest 与 core.write.commit 两个包的大半工作。
  4. 关掉 Azure 与 GCS 的读取缺口，同时解锁 3.5 线的 Scala 2.12 产物 （它现在卡在只发 2.13 的上游 Java 绑定上）。

反对它的只有一条：平台要为我们接一套显式临时凭证。而那套在同一个文件里已经为 Lance 做过。

5.3 剩余未知怎么处理

OSS 走 S3 兼容端点的行为差异，不足以挡住整个路线。若真有差异， OSS 可以先继续走 Hadoop，其余后端走 C，两条并存一段时间——这属于 AGENTS.md 说的「有记录、有收敛条件的临时状态」，不是补丁。

六、下一步

路线评审通过后，工作顺序是：

  1. native-storage 的 JNI，包 loon_filesystem_* 与 loon_exttable_read_manifest。第 1 层从「以后再说」变成关键路径。
  2. core.path 的 StoragePath。不依赖路线，两条路都要把六种路径写法收敛， 并把 resolveManifestDeltaPath 里混着的格式知识摘回 core.delete。
  3. core.credential 收敛。五处复制收成一处。

另有一条不依赖本路线、可以并行的：第 3 层把 MilvusDataSource 那 2880 行拆成 catalog、table、scan，MilvusOption 拆成 options。P0 里 R2、R5、R15、R17 的 实现位置都落在这几个现在还空着的包上。

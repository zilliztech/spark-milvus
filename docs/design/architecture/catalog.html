Catalog：目录、表 DDL 与固定快照

对应能力索引中的 R1、R2、C1、C2。固定快照与四种来源见 snapshot.html，读取执行见 read.html。

Catalog 有三条明确分开的路径：目录发现只调用 ListDatabases 和 ShowCollections；表加载把三段表名和时间旅行参数翻译成一个 固定 Snapshot；表 DDL 先完整校验 Spark schema 与 Milvus 表属性，再调用 collection 和 index RPC。目录发现不打开对象存储、不读取快照、不规划 Scan；创建 collection 不伪造快照， 因此新表只有在 Milvus 产生快照后才能通过现有 MilvusTable 读取。

一、名称与配置

只接受 catalog.database.collection。 Spark 已经从标识符中移除了 catalog 名，传给 MilvusCatalog 的 Identifier 必须恰有一段 namespace；它是 Milvus database，table name 是 collection。二段名没有默认 database，四段名也不截断。

spark.sql.catalog.milvus = com.zilliz.spark.connector.catalog.MilvusCatalog
spark.sql.catalog.milvus.milvus.uri = https://example-milvus:19530
spark.sql.catalog.milvus.milvus.token = user:password
spark.sql.catalog.milvus.fs.address = s3.us-west-2.amazonaws.com
spark.sql.catalog.milvus.fs.bucket_name = your-milvus-bucket
spark.sql.catalog.milvus.fs.root_path = files
spark.sql.catalog.milvus.fs.cloud_provider = aws
spark.sql.catalog.milvus.fs.region = us-west-2
spark.sql.catalog.milvus.fs.use_ssl = true
spark.sql.catalog.milvus.fs.use_iam = true
SHOW NAMESPACES IN milvus;
SHOW TABLES IN milvus.default;
SELECT id, embedding FROM milvus.default.products;
输入处理原因
spark.sql.catalog.<name>.*Spark 去掉前缀后交给 initialize；Catalog 保存不可变副本一次注册可承载连接、对象存储和读取选项
database、collection表加载与目录发现都以本次标识符为准；初始化配置里的同名 option 不限制目录，也不覆盖标识符一个 Catalog 可以安全访问多个 database 和 collection
snapshot、backup 离线模式拒绝离线文件没有可验证的三段目录关系，继续由 format("milvus") 承载

已知表名的加载只调用现有 getCollectionInfo(database, collection) 取得 collection id； 它不先调用目录 RPC。目录发现只需 milvus.uri 与认证配置；对象存储配置只在加载表和读取 数据时使用。

二、单层目录

Catalog 根目录的直接子项是 Milvus database，database 的直接表是 collection；没有第二层 namespace。目录名与 collection 名按 Milvus 返回值原样交给 Spark，不转小写、不裁空白、不改名、 不去重。返回顺序不是接口合同，调用方和测试不能依赖服务端顺序。

Spark Catalog 调用结果远端调用
listNamespaces() 或 listNamespaces([])每个 database 变成一段 namespace：[database]ListDatabases
listNamespaces([database])database 存在时返回空数组，因为它是叶子；不存在时抛 NoSuchNamespaceExceptionListDatabases，只核验存在性

空 database 的 listTables 返回空数组，不等于 database 不存在。ShowCollections 列出 Milvus 元数据里的全部 collection，即使某个 collection 还没有可读快照；目录发现不以快照目录 是否存在来过滤结果。SHOW TABLES ... LIKE 的匹配由 Spark 在结果上完成，Connector 不另发 带模式的 RPC。

listNamespaces 收到两段或更多段时抛 NoSuchNamespaceException； listTables 必须恰有一段 database，根目录和嵌套名字都抛同一 Spark 标准异常。因此 SHOW TABLES IN milvus 不会隐式使用 default，也不会把多个 database 的 collection 摊成一张表。namespaceExists 对根目录或嵌套名字返回 false。

Catalog 不缓存目录。每次发现都创建一个短生命周期的 MilvusClient，成功和失败都关闭； 结果反映本次 RPC 对当前凭证可见的 database 与 collection。

三、一次解析，沿用一条读链

三个入口只在快照选择方式上不同。 选中的 Snapshot 在 loadTable 内解析一次并放进 MilvusTable；schema、ScanBuilder、分区规划和 reader 使用同一个对象，不在 executor 或 scan 创建时重新查询最新快照。

Spark 调用快照选择
loadTable(identifier)SnapshotCatalog.latest
loadTable(identifier, version)非空的 version 作为快照名，调用 byName
loadTable(identifier, timestamp)Unix 微秒先转 HybridTS 上界，再调用 asOf

四、时间参数在 Catalog 边界换单位

Spark 的时间是 Unix epoch 微秒，snapshot_info.create_ts 是 Milvus HybridTS。 后者的高位是 Unix epoch 毫秒，低 18 位是同一毫秒内的逻辑时钟；它表示各 channel seek position 的最小快照边界，不是 API 调用完成时间。Snapshot.createdAt 保留 原始 HybridTS，core 的 SnapshotCatalog.asOf 合同不改变。SQL 时间字面量先按 spark.sql.session.timeZone 解析；loadTable(identifier, timestamp) 收到的是 UTC epoch 微秒。

Catalog 先令 millis = floorDiv(epochMicros, 1000)，再生成该毫秒的最大 HybridTS： (millis << 18) | ((1 << 18) - 1)。低 18 位必须全为 1，否则同一毫秒内 logical 大于 0 的快照会被漏掉。负时间饱和到 Long.MinValue，超过 HybridTS 可表示范围的 时间饱和到 Long.MaxValue，两端都不发生移位溢出。

时间旅行只选择已有快照元数据，不提供保留策略。 Connector 不保留旧段文件； compaction 或 GC 回收快照引用的段后，按名字或时间选中该快照仍可能在读取数据文件时失败。

五、CREATE TABLE 的公开合同

CREATE 的输入只有三段表名、Spark schema 和一组扁平表属性。 Catalog 先在 driver 上把三者完整转换成 collection schema 与向量索引请求；任何未知属性、无效字段引用、类型冲突、 分区变换或不支持的列特性都会在第一个 RPC 前失败。通过校验后先确认 database 存在且 collection 不存在， 再创建 collection，并按字段创建向量索引。连接、认证和 database 仍取自 Catalog 初始化配置与三段表名。每次 create/drop 使用一个短生命周期 client，成功和远端失败都执行 close；关闭失败单独传播，已有主失败时则成为 suppressed cause。 校验失败发生在 client 创建以前。

CREATE TABLE milvus.default.products (
  id BIGINT NOT NULL,
  title STRING,
  embedding ARRAY<FLOAT>
)
TBLPROPERTIES (
  'milvus.primary.key' = 'id',
  'milvus.field.title.data_type' = 'varchar',
  'milvus.field.title.max_length' = '512',
  'milvus.field.embedding.data_type' = 'float_vector',
  'milvus.field.embedding.dim' = '768',
  'milvus.index.embedding' =
    '{"index_type":"HNSW","metric_type":"COSINE","M":16,"efConstruction":200}'
);

字段名在 milvus.primary.key、milvus.field.<field>.* 和 milvus.index.<field> 中按 schema 原名精确匹配，只有 data_type 的值不区分 大小写。整数参数必须是落在 Int 范围内的规范十进制正整数，形式为 [1-9][0-9]*；不接受 正号、前导零、空白或小数。未知 Spark 类型直接拒绝，不能退化成 Binary 或 String。Milvus Int8 Array 在现有读链中固定呈现为 Array<Short>，因此 Catalog 拒绝会在读取后变成另一种 schema 的 Array<Byte>；本合同不为它新增第二套元素类型属性。

Spark SQL 生成的 ArrayType.containsNull 和 MapType.valueContainsNull 默认可为 true，而且 SQL DDL 没有可靠的元素 NOT NULL 表达；Catalog 接受这两个 schema 标记，不把它们解释成 Milvus 支持 null 元素。字段本身的 nullable 仍保留并用于主键校验。元素级 null 不在 Catalog 建表合同内，调用方不能据此认为后续写入支持 null 元素。

索引 JSON 必须是 object，且必须有字符串 index_type 和字符串 metric_type；可选的 index_name 也必须是字符串。其余键原样成为 Milvus index params，但键必须非空，值只能是字符串、数字或布尔值，并规范成字符串交给 Milvus；null、array 和嵌套 object 都拒绝。解析拒绝重复 JSON key 和尾随内容；index_type、metric_type 以及 存在时的 index_name 都不能为空，同一次 CREATE 内显式 index_name 不能重复。属性名拼错、字段不存在、 同一类型上出现无意义的 dim/max_length/max_capacity，以及向量没有索引， 都属于定义错误，不能被忽略。

Spark 自己附带的建表属性只有三项得到明确处理：provider 省略或等于 milvus；table comment 成为 collection description；column comment 成为对应 field description；owner 由 Spark 管理，Catalog 忽略。其他非 Milvus bookkeeping 属性以及 所有未知的 milvus.* 属性都拒绝。

5.2 创建顺序与可见性

CREATE 成功只表示 collection 与索引请求成功，不表示已经有可读快照。Catalog 不生成空快照，也不把刚提交的 schema 包成一个本地 Table；共享 createTable 因而返回 null，而不是伪造一个随后无法扫描的 MilvusTable。在线侧产生快照后，既有的固定 快照读链才会看到该 collection。

创建 collection 与创建索引不是一个事务。如果 collection 已成功而 后续某个索引 RPC 失败，Catalog 保留已经创建的 collection 和此前成功的索引，并把原错误交给用户； 它不会自动 drop collection 回滚。自动回滚可能删除并发方已开始使用的 collection，也会掩盖真实失败。 当前不支持可完成的 CTAS：collection 创建后没有可供 Spark 写入的 Connector 快照，命令会失败并可能留下 空 collection，需要用户显式删除。即使以后接通，collection 创建、Spark 写段和段登记也没有共同事务。

六、DROP TABLE 与条件竞态

dropTable 使用三段表名构造短生命周期客户端，先确认 database 与 collection 是否存在。 任一确认不存在都返回 false；两者存在时调用 DropCollection，成功返回 true。认证、授权、网络、超时、 限流和非成功状态都保留为错误，不能伪装成 false。

Spark 的 IF EXISTS / IF NOT EXISTS 与 Catalog 的存在性检查都是条件 DDL， 不是服务端 compare-and-set。检查以后到 create/drop RPC 以前，另一个客户端可能创建或删除同名 collection；最终结果以 Milvus 对变更 RPC 的响应为准，Connector 不吞掉这类竞态，也不靠重试改变语义。

CREATE 预检确认 database 不存在时抛 NoSuchNamespaceException，确认 collection 已存在时 抛 TableAlreadyExistsException。两项只转换已确认的元数据结果；预检本身的服务故障仍保留。 预检以后仍可能发生并发变更，因此它用于给 Spark 标准错误，不提供锁。

七、失败与不支持的修改

无效请求在 driver 规划期失败，只把能够确认的“不存在”翻成 Spark 标准语义。 表名层级错误、空版本、非 client 模式给出 IllegalArgumentException；表加载中 Milvus 明确返回 collection / database 不存在时，Catalog 抛 NoSuchTableException，使 tableExists 和 SQL 缺表行为符合 Spark 约定。collection 已存在但指定名字或时间点 没有快照候选时，保留含选择条件和 metadata prefix 的 SnapshotNotFoundException；整个 prefix 为空也保留明确错误，因为它可能是尚无快照，也可能是 bucket 或 fs.root_path 配错。 缺失或冲突的 create_ts、网络、认证、对象存储和解析异常同样保留原错误链，不能被改成 空表或 false。

目录发现只把两类已确认的结果翻成 Spark 语义：成功 RPC 的空名字列表是空结果；Milvus 明确报告 database 不存在时是 NoSuchNamespaceException，而 namespaceExists 才返回 false。认证、授权、网络、超时、限流、RPC 不可用、非成功状态与响应解析失败保留原异常链， 不能伪装成空目录、空 collection 列表或 namespace 不存在。异常带操作名与请求的 database，但不带 token 或对象存储密钥。

DDL 只开放 collection 的 create 与 drop。 createNamespace、alterNamespace、dropNamespace 以及 table 的 alter、rename 都明确抛出 UnsupportedOperationException。autoID、dynamic field、partition key、table constraint、generated/default/identity column 与 Spark partition transform 也不在合同内。Catalog 不提供 namespace owner、comment、location、database id 或创建时间；loadNamespaceMetadata 只确认 database 存在并返回空表。表 DDL 不新增 Procedure、Scan、对象存储或原生实现。已加载的 MilvusTable 仍沿用现有 append 写链。

八、四条 Spark 线

TableCatalog 与 SupportsNamespaces 的这组接口在 Spark 3.5、4.0、 4.1、4.2 共用一份主体，放在 spark-base。 每条线只保留公开的无参 MilvusCatalog 和本线的 createTable 输入适配：3.5 接收 StructType，4.0 接收 Column[]，4.1/4.2 接收 TableInfo，随后都调用 同一份 schema/属性校验与 RPC 编排。行为测试覆盖目录矩阵、属性和类型校验、发 RPC 前失败、create/drop 路由、索引阶段失败、客户端关闭、Spark SQL 路由和表加载；共享主体由四条线分别编译，Spark 3.5 同时 验证 Scala 2.12 与 2.13。

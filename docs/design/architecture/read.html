读路径

能力 R1、R2、R3、R4、R5、R8、R10、R14、R17。取字节和交接 Arrow 那一层见 storage-io.html,分层见 modules.md。

第 3 层仍然直接调第 1 层,读这条路上第 2 层是空的。 两个 PartitionReader 都在 spark-base,现在调的是 native-storage 的 JNI(不再是上游绑定),中间仍然不经过 core; 而 core.read.plan 与 core.read.exec 只有一个空的 package.scala。本页先说清第 3 层现在怎么读的,再说要往第 2 层填什么。

一、读一张表只有一种读法

表面上分很多种情况,实际只有一种读法。两个 PartitionReader 最后都调同一个上游 MilvusStorageReader,唯一的实质差别是列组清单谁算出来的。

分发在 MilvusPartitionReaderFactory.createReader,按分区类型匹配, 不读 storage_version;落到 case _ 就抛 This connector requires Milvus 2.6+ (Storage V2)。

V3 线V2 线
段怎么描述manifest 路径 + readVersion列组:字段 id、文件路径、每文件行数
列组清单原生库读 manifest 得 columnGroupsPtrMilvusStorageColumnGroups.createFromGroups 在 JVM 拼
取字节、凭证、Arrow 出口都走 native-storage 的 JNI;凭证是 StorageProperties.from(options) 产出的 fs.* 属性包

所以改造只有一个切入点。要做的是换掉那一个调用,保留两种产生它输入的方式, 而不是把两条线各改一遍。

V2 线多一道自查:driver 把每个列组文件的行数传下来,reader 累计实际交付的行数,少了就报错。 这是防上游 milvus-storage#657 之前的版本在多文件列组里只读第一个文件—— 那个缺陷不抛异常,只会让 DataFrame 静悄悄变短。

二、段从哪来:一个 Snapshot,四个来源

分岔只在 getTable 一处。spark.options.SnapshotSources.forRead 按 ReadMode 构造一个 SnapshotSource,调用一次得到 Snapshot;MilvusTable 持有它,交给 MilvusScan, 规划只有一条路:DeletePlanning 出删除计划,SnapshotPartitions.build 出一组 InputPartition。 设计见 snapshot.html 第二节。

来源触发产出
SnapshotCatalog.atmilvus.snapshot.path:直接读一个快照 JSON,不经服务V3 + V2
ClientSnapshotSourcemilvus.uri:DescribeCollection 取 id,快照目录里按名或取最新,R16 选择器过滤V3 + V2

driver 侧要开的四类文件——快照 manifest、V2 段的 manifest 与 parquet footer、删除日志、备份元数据—— 已经全部走 交字节那一面。

三、不支持 storage_version 0/1

三处挡在外面:legacy client 入口 filter(_.storageVersion >= 2) 后为空就抛 requires Milvus 2.6+;按 segment 精确查时报 storage_version < 2; 工厂的 case _。没有任何路径会去读逐字段的 V1 binlog。

insert_log/{collection}/{partition}/{segment} 是 Milvus 放段数据的目录, 与 storage_version 无关。V3 的 manifest basePath 就在这个目录下, SnapshotPartitions.build 正是靠 pathParts.lastIndexOf("insert_log") 往后数两级反推 partitionID。看到 insert_log 就断定是 V1,是读错了—— UAT 取下来的那个段文件 4133761 字节,偏移 0 是 PAR1,末尾也是 PAR1, 中间没有 Milvus 的 event 头,是一个 V2 列组的纯 parquet。

全仓唯一解析 Milvus event 格式的地方是 core.delete.DeltaLogReader, 它读删除日志,在 driver 上跑,两条线共用。

五、要往第 2 层填的两个包

分界线一句话:plan 在 driver 上跑,产物必须可序列化; exec 在 executor 上跑,是 core 调原生层的唯一地方。

段列表 ──plan──> SegmentReadTask(可序列化,发到 executor)
                    │
                    └──exec──> SegmentReader ──> 批 ──> Spark

5.1 core.read.plan

类型是什么
SegmentReadTask一个分区要读什么:段路径、storage_version、manifest 版本、列名、fs.* 属性、删除文件位置。只有描述,没有句柄、没有 Configuration、没有打开的资源
ReadPlan一组 SegmentReadTask,加规划期就能算出来的总行数、字节数(供 R13)
Partitioner怎么切分区。默认一段一分区;R19 按分区报分区、R16 段选择落在这里

剪枝(R9 段级、R10 row group 级)也在本包:规划期用统计信息把不需要的段和文件从 SegmentReadTask 里去掉。R10 依赖仓库外的两件事,见 storage-access 4.5。

5.2 core.read.exec

trait SegmentReader extends AutoCloseable {
  def next(): Option[ColumnBatch]              // 逐批，EOF 返回 None
  def take(rowIds: Array[Long]): ColumnBatch   // R14 回表
}

SegmentReaderRegistry: storage_version -> SegmentReader 工厂

注册表在 core,实现可以在 compat。V2 packed 的实现放 compat.v2,启动时注册进来;core 不反向依赖 compat。这是能力 K1 写死的约束。

这个注册表取代 spark 层现在的做法——MilvusPartitionReaderFactory.createReader 按 InputPartition 的具体类型做模式匹配,两条线各一个分支。 分发移到 core,spark 层只留 Spark 接口的对接。

两条线各自的列组清单怎么来留在各自的实现里,取字节与 Arrow 交接统一走 storage-io 定的那两个面。所有权那三条规则同样在那篇。

六、列式出口:做,R4 已定

今天全仓没有任何列式输出——没有 ColumnarBatch、没有 ArrowColumnVector、没有 supportColumnarReads, 两条读线都是行式 PartitionReader[InternalRow]。所以 R4 是从零开始。

决策 12 选了做。出口形态:无删除的批原样包成 ColumnarBatch 直通, 有删除的批把存活行物化成新的一批。物化无法回避,理由与代价见 storage-io 第四节。ColumnBatch 的定义据此定型,core.read.exec 不再被挡。

6.1 向量列默认要转,零拷贝因此只落在标量列

Milvus 把所有向量类型都存成 Arrow 的 FixedSizeBinary, 而 Spark 的 ArrowColumnVector 不认这个类型——4.1.3 的 initAccessor 认的列表里没有 FixedSizeBinaryVector, 也没有 FixedSizeListVector。原样塞进去会抛不支持的类型, 所以向量列的容器必然要换。

决策 6 选了默认转成 Spark 原生类型,与 1.x 的 SparkTypes 一致:

Milvus 类型存储里的 Arrow 类型默认输出
FloatVectorFixedSizeBinary(dim*4)ArrayType(FloatType)
Float16Vector / BFloat16VectorFixedSizeBinary(dim*2)ArrayType(FloatType)
Int8VectorFixedSizeBinary(dim)ArrayType(ShortType)
BinaryVectorFixedSizeBinary((dim+7)/8)BinaryType
SparseFloatVectorBinaryMapType(LongType, FloatType)

代价:向量列逐元素转,零拷贝在默认路径上只剩标量列,而 Milvus 表的字节绝大部分是向量; fp16 与 bf16 还要内存翻倍,dim=1024 存储里 2KB、Spark 侧 4KB。

出口是读选项 milvus.read.vector.raw:打开后向量列出 BinaryType, 字节不动,零拷贝成立。它服务的是把字节直接喂给原生库的批量作业(backfill、暴力搜索), 那些场景转成 Array[Float] 再转回字节是纯浪费。

七、其余没定的

  1. 向量搜索这条分支怎么放。存量 MilvusV3PartitionReader 里有 performSegmentVectorSearch,和普通扫描是两条并行路径。它属于 V*,本页不设计, 但 SegmentReader 接口要留得下它,不能设计成只能顺序扫。
  2. R5 列裁剪怎么传到底。loon_segment_reader_open 收 needed_columns,V2 那条线怎么表达列裁剪要单独确认。
  3. 谓词。C 那条路不可用(loon_segment_reader_get_filtered_stream 收下谓词、返回 OK、然后忽略,见 storage-access 4.4),由 core.expr 在 JVM 侧求值。

八、开发大纲

第 1 层与第 3 层的对接已完成。两个 reader、两个 writer 都走 native-storage 的 JNI,凭证四处统一 StorageProperties.from, 上游绑定不再进构建,3.5 线的 Scala 2.12 解锁。剩下的是把分发与出口下沉到第 2 层。

  1. 写 core.read.plan 的 SegmentReadTask。已完成。 SegmentReadTask 只装描述,句柄开在 executor 上;段布局的两种来源(V3 的 manifest 路径加版本、V2 已物化的列组)是 SegmentLayout 的两个 case,那是两条线唯一的实质差别。 删除来源单独建模成 DeleteSource:Materialized 是今天的做法—— driver 把主键 map 序列化进每个分区,也是 README 第 1 节列的 1.x 代价之一; Files 只给 delta log 路径、读留给 executor,是要去的方向。 两个 case 都在,迁移就是换 planner 产出哪一种,不用改这个类型。 spark 层的两个 InputPartition 已经改成携带它: MilvusV3InputPartition 从 12 个字段降到 7 个, MilvusV2InputPartition 从 9 个降到 3 个, 留在分区上的只有 spark 侧与向量检索特有的那些。 随之有一个产品可见的行为变化: StorageProperties.from 从每个 task 的 reader 构造里移到规划期跑一次, 所以存储配置不全的读现在在规划期就失败,不再是每个 task 各失败一次。
  2. 写 core.read.exec 的 SegmentReader 与注册表。已完成。 开原生 reader、逐批取 Arrow、按序释放句柄这一整套从两个 spark reader 的构造块搬进 core, 两处各写一遍变成一处;registry 按 SegmentLayout 分发。 列名解析做成 columnNameFor: Long => Option[String] 参数而不是内聚进去—— manifest 按字段 id 匹配列、schema 里字段名就是 id,列组布局用字段自己的名字, 这不是 core 能替调用方决定的。ColumnBatch 与 take 仍不写: 列式出口的 Spark 那一半是 Spark 类型,归第 3 层,进 core 的仍是 VectorSchemaRoot。
  3. 列式出口。决策 12 定了做,决策 6 定了向量列默认转、 另给 milvus.read.vector.raw 出原始字节。要新写 ColumnVector 与 ColumnarBatch 的一侧, 并处理有删除的批要物化存活行。
  4. 写侧下沉 core.write.exec 与 core.write.commit。 backfill 分支走已有的 BatchUpdateManifest,可以做;append 分支等 Milvus 新增 RegisterSegments,那条不在我们手上(能力 W1)。

九、欠的两笔

  1. per-batch reader 是过渡实现。结束条件是上游从 libmilvus-storage 导出 loon_record_batch_reader_*,见 storage-access 需求 7。在那之前 native-storage 依赖 Arrow C++,而 Arrow C++ 没有稳定 ABI——头文件必须与 libmilvus-storage 静态链进去的那份一致,不一致编译不报错、运行时崩。
  2. CI 不构建原生库。所以每一个真正调 C 的套件在 CI 上都会 cancel: 读 UAT 段、写回读、多文件列组、切片回归,全部只在开发机上跑过。 这是目前最大的覆盖缺口。

读路径

对应能力索引中的 R2、R3、R4、R5、R8–R17。取字节和交接 Arrow 那一层见 storage-io.html,分层见 modules.md。

第 3 层只负责 Spark 接口，第 2 层完成规划和读取执行。 表加载（getTable / loadTable）解析一次固定 Snapshot，core.read.plan 把它变成可序列化任务， core.read.exec 在 executor 上打开第 1 层 JNI reader。行式与列式出口消费同一个 SegmentReader；V2/V3 的列名差异由 ColumnBinding 封装，行式主循环不再分叉。

一、读一张表只有一种读法

表面上有 V2/V3、行式/列式，实际只有一个开段入口。 两种 InputPartition 都携带 SegmentReadTask， SegmentReaderRegistry 按其 SegmentLayout 打开原生 reader； MilvusRowPartitionReader 和 MilvusColumnarPartitionReader 只决定把同一批 Arrow 数据呈现成 InternalRow 还是 ColumnarBatch。

分发在 MilvusPartitionReaderFactory,只按出口选:默认列式,milvus.read.columnar=false 或带向量检索时走行式;不再按分区类型分支。落到不是 MilvusInputPartition 的分区就抛 IllegalArgumentException。

V3 线V2 线
段怎么描述SegmentLayout.Manifest:manifest 路径 + readVersionSegmentLayout.ColumnGroups:字段 id、文件路径、每文件行数,driver 上由 compat.v2 从快照或 footer 恢复
列名字段 id 的字符串,时间戳列叫 "1"字段名
开段、取字节、凭证、Arrow 出口都是 core.read.exec 开的同一个 NativeSegmentReader;凭证是任务里的 fs.* 属性包

列裁剪传的是快照 schema 中的真实字段 id。V3 把 id 映射成 Manifest 列名，V2 把 id 映射成 footer 里的字段名；缺少 milvus.field_id、请求未知字段或遇到存储中缺列都直接报错， 不再按 Spark schema 的位置猜 id，也不以 null 补缺列。

已知物理行数的任务由 ExpectedRowsSegmentReader 统一检查：只有读到 EOF 时才比较 实际交付行数，少读或多读都失败。行式与列式共用这层；Limit 提前关闭 reader 是正常行为， 没有读到 EOF，因此不做完整行数断言。

二、段从哪来:一个 Snapshot,四个来源

分岔只在表加载一处。DataSource 的 getTable 与 Catalog 的 loadTable 都调用 MilvusTables.load；它让 spark.options.SnapshotSources.forRead 按 ReadMode 构造一个 SnapshotSource,调用一次得到 Snapshot;MilvusTable 持有它,交给 MilvusScan, 规划只有一条路:core.read.plan.DeleteFileListing.of 列出删除文件,ReadPlan.of 出任务,MilvusScan.inputPartitions 包成 InputPartition。 设计见 snapshot.html 第二节。

来源触发产出
SnapshotCatalog.atmilvus.snapshot.path:直接读一个快照 JSON,不经服务V3 + V2
ClientSnapshotSourcemilvus.uri:DescribeCollection 取 id；DataSource 按配置名或最新，Catalog 按 latest/version/timestampV3 + V2

四个来源解析完以后，统一调用 Snapshot.narrow 应用 milvus.partitions 与 milvus.segments。每个请求 id 都要存在，两个选择器同时给时取交集； 段 id 不属于所选分区时也报错，不返回意外的空读。收窄数据段不会丢掉适用于它们的分区 L0 与 全 collection L0 删除段。

读取配置在 driver 规划期严格解析：布尔选项只接受 true / false， 字段、分区与段列表不接受空项、负数或非数值，milvus.snapshot.max.json.bytes 必须为正整数。vector.search.query 与 vector.search.topK 必须成对给出， 前者是非空的有限数字数组，后者是正整数；显式提供的空白值同样非法，不能通过默认值关闭功能。

动态字段同样遵循真实字段 ID 绑定：enable_dynamic_field=true 时，快照 schema 必须包含唯一的 $meta JSON 字段、动态标记和非系统字段 ID。缺失或不一致会在规划期失败；连接器不会用 “最大字段 ID + 1”猜测物理列，以免 schema 演进后静默丢失或读取错误数据。

driver 为快照 JSON、V2 段 Avro、parquet footer 与备份元数据打开的 ObjectStore 都由 SnapshotSources 管理。元数据完整物化后立即关闭；主读取失败、 关闭失败与并发 footer 读取失败都保留原始错误，并在所有已启动工作结束后释放 store。 删除文件内容不在这里读取。

三、数据段只支持 storage_version 2/3

数据段只接受 storage_version = 2 或 3；其他布局在快照物化或任务规划时失败。 L0 是删除段而不是数据段，按删除描述保留，不进入数据 reader。没有任何路径读取逐字段的 V1 binlog。

insert_log/{collection}/{partition}/{segment} 是 Milvus 放段数据的目录, 与 storage_version 无关。V3 的 manifest basePath 就在这个目录下, 快照元数据提供 segment id、partition id 和 base path，规划不从目录层级反推这些 id。 看到 insert_log 不能判断存储版本；V2 列组与 V3 段目录都可以位于该前缀下。

全仓唯一解析 Milvus event 格式的地方是 core.delete.DeltaLogReader, 它在 executor 上读取任务描述的删除文件，两条存储线共用。

类型是什么
SegmentReadTask一个分区要读什么：段 id、分区 id、布局、schema 字节、真实字段 id、fs.* 属性和删除文件描述。只有可序列化描述，没有句柄、Configuration 或打开的资源

R9 在任务生成前由 core.stats 判定可移除的数据段， core.snapshot 应用该结果；本包只把剪后的快照变成任务。R10 仍未实现， 不在 JVM 中用段级统计模拟 row group 剪枝；它依赖仓库外的两件事，见 storage-access 4.5。

5.2 主键 Bloom 段级剪枝与运行时过滤

R9 只从主键的等值和 IN 提取有限候选值。布尔组合遵循可证明的集合语义： AND 与其他条件并存时可使用已知的主键集合，两个主键集合取交集； OR 只有两边都能提取主键集合时才取并集。NOT、范围、其他字段、 类型不符或无法翻译的条件不产生剪枝输入。这个过程只改变要读的段，R6 仍在行上执行完整谓词。

V2 从 segment manifest 的 statslog_files 取主键字段的统计路径；V3 从已钉住版本的 Manifest stats["bloom_filter.<field id>"] 取路径。路径只通过 core.io.ObjectStore 打开。Milvus 的 StatsWriter.Generate 写单个 JSON object， GenerateList 写 JSON array；读取者同时接受两种根形状。路径集合中有 basename 为 1 的 compound 文件时与 Milvus 一样只读该文件，否则每个列出的文件都是该段的一部分。

只有所有相关文件都成功读取、JSON 中每个统计都与主键字段及类型匹配，并且每个候选值在每个统计中都确定不存在时，才移除段。任意路径缺失、空文件、损坏 JSON、不支持的 Bloom 类型、字段或主键类型不匹配、以及跨 bucket 路径都保留该段。Bloom 的假阳性也只会多读一个段，不会丢行。

R18 在固定 Snapshot 的普通扫描上实现 SupportsRuntimeV2Filtering，只向 Spark 公布主键属性。每次 filter 调用提取一个主键集合，与该 Scan 先前收到的集合继续取交集；相同输入幂等。变化后废弃已生成的 partition 数组，但复用 driver 上按段和路径缓存的统计输入，只在内存中重新判定。剪后 Snapshot 保留每个剩余数据段所在分区的 L0 和 collection 级 L0，不把删除来源当成数据段剪掉。

带 vector.search.* 的 TopK 读取不公布运行时过滤属性，也不接受该剪枝；Spark 的运行时条件仍在 TopK 之后执行，不改变 TopK 候选集语义。R18 只做段级剪枝，不声称 row group 剪枝；后者仍是 R10 的仓库外依赖。

5.4 每个任务的批大小与 Arrow 上限

driver 把三个用户值严格解析成 ReadLimits，由 ReadPlan.of 放进每个 SegmentReadTask，随 Spark 分区序列化到 executor。SegmentReaderRegistry 在打开 原生 reader 时把 batchMaxRows 映射为 reader.record_batch_max_rows，把 batchMaxBytes 映射为 reader.record_batch_max_size；类型化值覆盖原始属性包中同名键，避免绕过 driver 校验。

用户 option默认值生效点
milvus.read.batch.max.rows8192原生 reader 每批最大行数
milvus.read.batch.max.bytes33554432，最大 4294967296原生 reader 每批目标字节上限
milvus.read.arrow.max.bytesLong.MaxValue当前 Spark read task 的 Arrow child allocator 硬上限

MilvusPartitionReaderFactory 为每个任务从进程级 root 建一个 child allocator；行式、列式、 暴力搜索与持久化索引回表都使用它。最终的基础 PartitionReader 明确持有 child，先关闭当前批和 SegmentReader，再关闭 child；metadata 与 Limit 包装器只委托 close。构造中途失败时 factory 关闭已打开的 reader 和 child，重复关闭是空操作，任何任务都不会关闭进程级 root。

Arrow 上限约束由该 child 分配或导入的 JVM Arrow buffer，不包含 libmilvus-storage 自己的 native 内存池。上游当前没有每个 reader 的预取队列上限接口， 所以 G3 的预取上限仍未映射，不能用批字节上限冒充。

六、行式与列式出口

列式出口已有,且是默认:MilvusColumnarPartitionReader,milvus.read.columnar=false 才走行式; 带向量检索的读回落行式,因为那一步(SegmentVectorSearch)逐行算距离,归属是决策 16。 普通扫描接受的 DataSource V2 谓词由 core.expr.PredicateEvaluator 对 Arrow 批求值， milvus.filter 由 core.expr.Evaluator 对同一批求值；两者各自产生排除位图， 都不引起行式回落。完整语义见谓词下推设计。

没有删除和两个谓词位图排除的批直接包装成 ColumnarBatch；需要排除行时，reader 逐行计算 isDeleted || sparkPredicateBitmap.isExcluded || milvusFilterBitmap.isExcluded。列式出口通过 SelectedRowsColumn 按存活行下标重映射,不复制整列 buffer；行式出口在物化 InternalRow 前直接跳过该行。 两种出口都在底层 reader 读到 EOF 时执行同一个物理行数校验， 因此不会一条报短读、另一条静默返回。理由与代价见 storage-io 第四节。

6.1 向量列默认要转,零拷贝因此只落在标量列

Milvus 把所有向量类型都存成 Arrow 的 FixedSizeBinary, 而 Spark 的 ArrowColumnVector 不认这个类型——4.1.3 的 initAccessor 认的列表里没有 FixedSizeBinaryVector, 也没有 FixedSizeListVector。原样塞进去会抛不支持的类型, 所以向量列的容器必然要换。

决策 6 选了默认转成 Spark 原生类型,与 1.x 的 SparkTypes 一致:

Milvus 类型存储里的 Arrow 类型默认输出
FloatVectorFixedSizeBinary(dim*4)ArrayType(FloatType)
Float16Vector / BFloat16VectorFixedSizeBinary(dim*2)ArrayType(FloatType)
Int8VectorFixedSizeBinary(dim)ArrayType(ShortType)
BinaryVectorFixedSizeBinary((dim+7)/8)BinaryType
SparseFloatVectorBinaryMapType(LongType, FloatType)

代价:向量列逐元素转,零拷贝在默认路径上只剩标量列,而 Milvus 表的字节绝大部分是向量; fp16 与 bf16 还要内存翻倍,dim=1024 存储里 2KB、Spark 侧 4KB。

出口是读选项 milvus.read.vector.raw:打开后向量列出 BinaryType, 字节不动,零拷贝成立。它服务的是把字节直接喂给原生库的批量作业(backfill、暴力搜索), 那些场景转成 Array[Float] 再转回字节是纯浪费。

6.2 元数据列

milvus.extra.columns 的输出只包含三个规范名，并始终按下表顺序追加：

列来源含义
_segment_idSegmentReadTask.segmentId当前数据段 id，行式与列式都按 task 填
_row_offsetreader 的物理行位置删除过滤前在段内的行号；跨批连续，Limit 与删除不重新编号

6.3 类型与 schema

SparkTypes.toStructField 是快照 schema、Table 与 reader 共用的映射。字段名、真实字段 id、Milvus 类型、nullable、主键/分区键/聚类键标记和向量维度都来自同一个 FieldSchema。支持范围是 Bool、整数、浮点、String、VarChar、Text、JSON、标量 Array 与六种 向量；Geometry、Timestamptz、ArrayOfVector/struct-array 和未知类型尚未实现。 fieldIDs 在 inferSchema 和 Table 构建时都过同一份快照字段表； 外部 .schema() 的非元数据字段必须恰好对应选中 id，名称和 Spark 类型不能与快照冲突。 遇到不支持的类型、schema 中缺字段或 Arrow 批缺请求列时直接失败，不退成 BinaryType 或 null。

七、不在本链路内的能力

  1. 向量搜索这条分支怎么放。spark.read.SegmentVectorSearch 是行式 reader 的可选阶段(#06 从 V3 reader 里拆出),和普通扫描是两条并行路径。它属于 V*,本页不设计, 但 SegmentReader 接口要留得下它,不能设计成只能顺序扫。
  2. 两种谓词入口。R7 的手写 PlanParser 同时服务普通扫描的 milvus.filter 与向量查询的 MilvusSearch.filter / vector.search.filter； 前者在普通扫描的 JVM Arrow 批上求值，后者在持久化索引搜索前求值，两种 option 不能混用。 R6 的 Spark V2 谓词按独立设计只在普通扫描的 JVM Arrow 批上求值； 带 vector.search.* 的读取全部作为 residual 留给 Spark，因此 Spark 条件在 TopK 后执行。C 的 loon_segment_reader_get_filtered_stream 会忽略传入谓词,连接器不调用它,见 storage-access 4.4。
  3. 回表与 row group 剪枝。take（R14）和统计驱动的 row group 剪枝 （R10）仍是独立能力，不通过普通顺序扫描的外围分支模拟。

八、实现状态

固定快照的普通读取链路已经贯通三层。第 3 层解析一次 Snapshot 并对接 Spark， 第 2 层规划任务、读取删除文件并统一打开段 reader，第 1 层经 JNI 交付 Arrow 批。 下面保留各次下沉的边界，未完成项只列不属于这条普通读取链路的能力。

  1. 写 core.read.plan 的 SegmentReadTask。已完成。 SegmentReadTask 只装描述,句柄开在 executor 上;段布局的两种来源(V3 的 manifest 路径加版本、V2 已物化的列组)是 SegmentLayout 的两个 case,那是两条线唯一的实质差别。 删除来源单独建模成 DeleteSource:Files 只给删除文件、读留给 executor,#13 起 planner 只产出它; Materialized 装一份现成的 plan,driver 不再产出(它曾把主键 map 序列化进每个分区,README 第 1 节列的 1.x 代价之一)。 两个 case 都在,迁移就是换了 planner 产出哪一种,没改这个类型。 spark 层的两个 InputPartition 已经改成携带它: MilvusV3InputPartition 从 12 个字段降到 7 个, MilvusV2InputPartition 从 9 个降到 3 个, 留在分区上的只有 spark 侧与向量检索特有的那些。 随之有一个产品可见的行为变化: StorageProperties.from 从每个 task 的 reader 构造里移到规划期跑一次, 所以存储配置不全的读现在在规划期就失败,不再是每个 task 各失败一次。

  3. 删除读取下沉 executor。已完成(#13)。driver 上只剩 DeleteFileListing.of: V2 段的删除文件在快照里,V3 段的在它的 manifest 里(driver 打开 manifest 列文件、解析版本,不读删除文件), L0 段的文件按分区挂到该分区每个任务上;ReadPlan.of 把它们装进 DeleteSource.Files。 executor 上 core.read.exec.DeletePlans 按任务读文件成 plan,读不到抛异常让 task 失败,不再有空 plan 兜底。 spark.read.plan 包、V2 分区上的 L0 标记、reader factory 里的继承 plan 合并都删掉。 代价:L0 文件对分区内每个段生效,现在每个 task 各读一遍(原来 driver 读一次),driver 不再持有任何主键 map。 UAT 三个带删除的快照(V2 加 L0、V3 加 L0、V3 折进清单)都读回 2990 行。

读路径

能力 R1、R2、R3、R4、R5、R8、R10、R14、R17。取字节和交接 Arrow 那一层见 storage-io.html,分层见 modules.md。

读一张表只有一条路:driver 在 core.read.plan 规划出任务,executor 在 core.read.exec 开段, spark.read 用一个行式 reader 和一个列式 reader 把 Arrow 批交给 Spark。 两条存储线的差别只剩列怎么命名,由 ColumnBinding 的两个实现承担; reader 的主循环不知道自己读的是哪条线。本页先说第 3 层现在怎么读,再说还差什么。

一、读一张表只有一种读法

表面上分很多种情况,实际只有一种读法。两种 InputPartition 都装一个 SegmentReadTask,SegmentReaderRegistry.open 按任务的 SegmentLayout 开同一个 NativeSegmentReader;executor 侧只有一个行式 reader MilvusRowPartitionReader 和一个列式 reader MilvusColumnarPartitionReader, 两条线共用。唯一的实质差别是列叫什么名字:manifest 布局的列名是字段 id,列组布局的列名是字段名, 这一层差别封在 V3ColumnBinding / V2ColumnBinding 里。

分发在 MilvusPartitionReaderFactory,只按出口选:有谓词或向量检索走行式,否则按 milvus.read.columnar;不再按分区类型分支。落到不是 MilvusInputPartition 的分区就抛 IllegalArgumentException。

V3 线V2 线
段怎么描述SegmentLayout.Manifest:manifest 路径 + readVersionSegmentLayout.ColumnGroups:字段 id、文件路径、每文件行数,driver 上由 compat.v2 从快照或 footer 恢复
列名字段 id 的字符串,时间戳列叫 "1"字段名
开段、取字节、凭证、Arrow 出口都是 core.read.exec 开的同一个 NativeSegmentReader;凭证是任务里的 fs.* 属性包

行式 reader 有一道自查:SegmentReadTask.expectedRows 给出布局声明的行数时(列组布局给,manifest 布局不给), reader 在读完时对比实际交付的行数,少了就抛 IllegalStateException。 这是防上游 milvus-storage#657 之前的版本在多文件列组里只读第一个文件—— 那个缺陷不抛异常,只会让 DataFrame 静悄悄变短。

二、段从哪来:一个 Snapshot,四个来源

分岔只在 getTable 一处。spark.options.SnapshotSources.forRead 按 ReadMode 构造一个 SnapshotSource,调用一次得到 Snapshot;MilvusTable 持有它,交给 MilvusScan, 规划只有一条路:core.read.plan.DeleteFileListing.of 列出删除文件,ReadPlan.of 出任务,MilvusScan.inputPartitions 包成 InputPartition。 设计见 snapshot.html 第二节。

driver 侧要开的四类文件——快照 manifest、V2 段的 manifest 与 parquet footer、删除日志、备份元数据—— 已经全部走 交字节那一面。

三、不支持 storage_version 0/1

三处挡在外面:legacy client 入口 filter(_.storageVersion >= 2) 后为空就抛 requires Milvus 2.6+;按 segment 精确查时报 storage_version < 2; 工厂的 case _。没有任何路径会去读逐字段的 V1 binlog。

insert_log/{collection}/{partition}/{segment} 是 Milvus 放段数据的目录, 与 storage_version 无关。V3 的 manifest basePath 就在这个目录下, SnapshotPartitions.build 正是靠 pathParts.lastIndexOf("insert_log") 往后数两级反推 partitionID。看到 insert_log 就断定是 V1,是读错了—— UAT 取下来的那个段文件 4133761 字节,偏移 0 是 PAR1,末尾也是 PAR1, 中间没有 Milvus 的 event 头,是一个 V2 列组的纯 parquet。

全仓唯一解析 Milvus event 格式的地方是 core.delete.DeltaLogReader, 它读删除日志,在 driver 上跑,两条线共用。

四、离目标还差什么

取字节那一面已经到位,交地址那一面一步没动。

五、要往第 2 层填的两个包

分界线一句话:plan 在 driver 上跑,产物必须可序列化; exec 在 executor 上跑,是 core 调原生层的唯一地方。

段列表 ──plan──> SegmentReadTask(可序列化,发到 executor)
                    │
                    └──exec──> SegmentReader ──> 批 ──> Spark

5.1 core.read.plan

类型是什么
SegmentReadTask一个分区要读什么:段路径、storage_version、manifest 版本、列名、fs.* 属性、删除文件位置。只有描述,没有句柄、没有 Configuration、没有打开的资源
ReadPlan一组 SegmentReadTask,加规划期就能算出来的总行数、字节数(供 R13)。ReadPlan.of(snapshot, properties, applyDeletes, deletes, readVersions) 是规划本身:V3 段一个 manifest 任务、有数据的 V2 段一个列组任务、delete-only 段跳过,V3 任务带分区继承的 L0 删除和自己的删除之并,V2 任务只带自己的。已做(#12)
Partitioner怎么切分区。没有:一段一分区是唯一策略,R19 按分区报分区、R16 段选择定了再加,接口按那时的两种实现定

剪枝(R9 段级、R10 row group 级)也在本包:规划期用统计信息把不需要的段和文件从 SegmentReadTask 里去掉。R10 依赖仓库外的两件事,见 storage-access 4.5。

trait SegmentReader extends AutoCloseable {
  def next(): Option[ColumnBatch]              // 逐批，EOF 返回 None
  def take(rowIds: Array[Long]): ColumnBatch   // R14 回表
}

SegmentReaderRegistry: storage_version -> SegmentReader 工厂

注册表在 core,实现可以在 compat。V2 packed 的实现放 compat.v2,启动时注册进来;core 不反向依赖 compat。这是能力 K1 写死的约束。

这个注册表已经取代 spark 层原来的做法——MilvusPartitionReaderFactory.createReader 按 InputPartition 的具体类型做模式匹配,两条线各一个 reader。#06 之后分发在 core, spark 层一个行式 reader、一个列式 reader,只留 Spark 接口的对接。

两条线各自的列组清单怎么来留在各自的实现里,取字节与 Arrow 交接统一走 storage-io 定的那两个面。所有权那三条规则同样在那篇。

六、列式出口:做,R4 已定

列式出口已有:MilvusColumnarPartitionReader,milvus.read.columnar=true 开启, 有谓词或向量检索时回落行式。下面是它的设计。

决策 12 选了做。出口形态:无删除的批原样包成 ColumnarBatch 直通, 有删除的批经 SelectedRowsColumn 按存活行下标映射,不拷贝。理由与代价见 storage-io 第四节。ColumnBatch 的定义据此定型,core.read.exec 不再被挡。

6.1 向量列默认要转,零拷贝因此只落在标量列

Milvus 把所有向量类型都存成 Arrow 的 FixedSizeBinary, 而 Spark 的 ArrowColumnVector 不认这个类型——4.1.3 的 initAccessor 认的列表里没有 FixedSizeBinaryVector, 也没有 FixedSizeListVector。原样塞进去会抛不支持的类型, 所以向量列的容器必然要换。

决策 6 选了默认转成 Spark 原生类型,与 1.x 的 SparkTypes 一致:

Milvus 类型存储里的 Arrow 类型默认输出
FloatVectorFixedSizeBinary(dim*4)ArrayType(FloatType)
Float16Vector / BFloat16VectorFixedSizeBinary(dim*2)ArrayType(FloatType)
Int8VectorFixedSizeBinary(dim)ArrayType(ShortType)
BinaryVectorFixedSizeBinary((dim+7)/8)BinaryType
SparseFloatVectorBinaryMapType(LongType, FloatType)

代价:向量列逐元素转,零拷贝在默认路径上只剩标量列,而 Milvus 表的字节绝大部分是向量; fp16 与 bf16 还要内存翻倍,dim=1024 存储里 2KB、Spark 侧 4KB。

出口是读选项 milvus.read.vector.raw:打开后向量列出 BinaryType, 字节不动,零拷贝成立。它服务的是把字节直接喂给原生库的批量作业(backfill、暴力搜索), 那些场景转成 Array[Float] 再转回字节是纯浪费。

七、其余没定的

  1. 向量搜索这条分支怎么放。spark.read.SegmentVectorSearch 是行式 reader 的可选阶段(#06 从 V3 reader 里拆出),和普通扫描是两条并行路径。它属于 V*,本页不设计, 但 SegmentReader 接口要留得下它,不能设计成只能顺序扫。
  2. R5 列裁剪怎么传到底。loon_segment_reader_open 收 needed_columns,V2 那条线怎么表达列裁剪要单独确认。
  3. 谓词。C 那条路不可用(loon_segment_reader_get_filtered_stream 收下谓词、返回 OK、然后忽略,见 storage-access 4.4),由 core.expr 在 JVM 侧求值。

八、开发大纲

第 1 层与第 3 层的对接已完成。行式与列式 reader、两个 writer 都走 native-storage 的 JNI,凭证四处统一 StorageProperties.from, 上游绑定不再进构建,3.5 线的 Scala 2.12 解锁。剩下的是把分发与出口下沉到第 2 层。

  1. 写 core.read.plan 的 SegmentReadTask。已完成。 SegmentReadTask 只装描述,句柄开在 executor 上;段布局的两种来源(V3 的 manifest 路径加版本、V2 已物化的列组)是 SegmentLayout 的两个 case,那是两条线唯一的实质差别。 删除来源单独建模成 DeleteSource:Files 只给删除文件、读留给 executor,#13 起 planner 只产出它; Materialized 装一份现成的 plan,driver 不再产出(它曾把主键 map 序列化进每个分区,README 第 1 节列的 1.x 代价之一)。 两个 case 都在,迁移就是换了 planner 产出哪一种,没改这个类型。 spark 层的两个 InputPartition 已经改成携带它: MilvusV3InputPartition 从 12 个字段降到 7 个, MilvusV2InputPartition 从 9 个降到 3 个, 留在分区上的只有 spark 侧与向量检索特有的那些。 随之有一个产品可见的行为变化: StorageProperties.from 从每个 task 的 reader 构造里移到规划期跑一次, 所以存储配置不全的读现在在规划期就失败,不再是每个 task 各失败一次。
  2. 规划本身进 core.read.plan。已完成(#12)。 段列表怎么变成任务这段计算原来是 spark 层的 SnapshotPartitions.build, 现在是 ReadPlan.of,输入输出全是 core 类型;MilvusScan.inputPartitions 只把任务包成两种 InputPartition,加上向量检索、分区名、选项。 纯搬,行为不变:规划的 50 个用例一个断言没改。
  3. 删除读取下沉 executor。已完成(#13)。driver 上只剩 DeleteFileListing.of: V2 段的删除文件在快照里,V3 段的在它的 manifest 里(driver 打开 manifest 列文件、解析版本,不读删除文件), L0 段的文件按分区挂到该分区每个任务上;ReadPlan.of 把它们装进 DeleteSource.Files。 executor 上 core.read.exec.DeletePlans 按任务读文件成 plan,读不到抛异常让 task 失败,不再有空 plan 兜底。 spark.read.plan 包、V2 分区上的 L0 标记、reader factory 里的继承 plan 合并都删掉。 代价:L0 文件对分区内每个段生效,现在每个 task 各读一遍(原来 driver 读一次),driver 不再持有任何主键 map。 UAT 三个带删除的快照(V2 加 L0、V3 加 L0、V3 折进清单)都读回 2990 行。
  4. 两个行式 reader 合成一个。已完成(#06)。MilvusV3PartitionReader 与 MilvusV2PartitionReader 各写一遍的主循环变成一个 MilvusRowPartitionReader:拉批、逐行交付、跳过已删行、有谓词时逐行求值、读完按 SegmentReadTask.expectedRows 核对总行数(原来只有 V2 有这道自查,现在 manifest 布局给出行数时同样受益)。 两条线的列名规则和从 schema 推需要哪些列,原来是两个 reader 的伴生对象,现在归各自的 ColumnBinding; 向量检索拆成 SegmentVectorSearch,谓词求值拆成 RowFilters,都是纯函数,单独有用例。 行为不变:UAT 的 V3 折进清单、V2 加 L0、全类型三个快照读回的行数与列值与合并前一致。
  5. 写 core.read.exec 的 SegmentReader 与注册表。已完成。 开原生 reader、逐批取 Arrow、按序释放句柄这一整套从两个 spark reader 的构造块搬进 core, 两处各写一遍变成一处;registry 按 SegmentLayout 分发。 列名解析做成 columnNameFor: Long => Option[String] 参数而不是内聚进去—— manifest 按字段 id 匹配列、schema 里字段名就是 id,列组布局用字段自己的名字, 这不是 core 能替调用方决定的。ColumnBatch 与 take 仍不写: 列式出口的 Spark 那一半是 Spark 类型,归第 3 层,进 core 的仍是 VectorSchemaRoot。
  6. 列式出口。决策 12 定了做,决策 6 定了向量列默认转、 另给 milvus.read.vector.raw 出原始字节。要新写 ColumnVector 与 ColumnarBatch 的一侧, 有删除的批经 SelectedRowsColumn 按下标映射。
  7. 写侧下沉 core.write.exec 与 core.write.commit。core.write.exec 已做（#07）：两个 writer 的 native 调用进了 core，ManifestTransaction 提交清单；作业级提交是 #08。 backfill 分支走已有的 BatchUpdateManifest,可以做;append 分支等 Milvus 新增 RegisterSegments,那条不在我们手上(能力 W1)。

九、欠的两笔

  1. per-batch reader 是过渡实现。结束条件是上游从 libmilvus-storage 导出 loon_record_batch_reader_*,见 storage-access 需求 7。在那之前 native-storage 依赖 Arrow C++,而 Arrow C++ 没有稳定 ABI——头文件必须与 libmilvus-storage 静态链进去的那份一致,不一致编译不报错、运行时崩。
  2. CI 不构建原生库。所以每一个真正调 C 的套件在 CI 上都会 cancel: 读 UAT 段、写回读、多文件列组、切片回归,全部只在开发机上跑过。 这是目前最大的覆盖缺口。

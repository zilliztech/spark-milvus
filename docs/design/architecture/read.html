读路径

对应能力索引中的 R2、R3、R4、R5、R8–R17、R20。取字节和交接 Arrow 那一层见 storage-io.html,分层见 modules.md。

第 3 层只负责 Spark 接口，第 2 层完成规划和读取执行。 表加载（getTable / loadTable）解析一次固定 Snapshot，core.read.plan 把它变成可序列化任务， core.read.exec 在 executor 上打开第 1 层 JNI reader。行式与列式出口消费同一个 SegmentReader；V2/V3 的列名差异由 ColumnBinding 封装，行式主循环不再分叉。

一、读一张表只有一种读法

表面上有 V2/V3、行式/列式，实际只有一个开段入口。 两种 InputPartition 都携带 SegmentReadTask， SegmentReaderRegistry 按其 SegmentLayout 打开原生 reader； MilvusRowPartitionReader 和 MilvusColumnarPartitionReader 只决定把同一批 Arrow 数据呈现成 InternalRow 还是 ColumnarBatch。

分发在 MilvusPartitionReaderFactory,只按出口选:默认列式,milvus.read.columnar=false 走行式;不再按分区类型分支。向量检索不经扫描出口(见第七节)。落到不是 MilvusInputPartition 的分区就抛 IllegalArgumentException。

driver 为快照 JSON、V2 段 Avro、parquet footer 与备份元数据打开的 ObjectStore 都由 SnapshotSources 管理。元数据完整物化后立即关闭；主读取失败、 关闭失败与并发 footer 读取失败都保留原始错误，并在所有已启动工作结束后释放 store。 删除文件内容不在这里读取。

三、数据段只支持 storage_version 2/3

数据段只接受 storage_version = 2 或 3；其他布局在快照物化或任务规划时失败。 L0 是删除段而不是数据段，按删除描述保留，不进入数据 reader。没有任何路径读取逐字段的 V1 binlog。

insert_log/{collection}/{partition}/{segment} 是 Milvus 放段数据的目录, 与 storage_version 无关。V3 的 manifest basePath 就在这个目录下, 快照元数据提供 segment id、partition id 和 base path，规划不从目录层级反推这些 id。 看到 insert_log 不能判断存储版本；V2 列组与 V3 段目录都可以位于该前缀下。

Milvus event 封装只由 core.codec.BinlogCodec 解析,core.delete.DeltaLogReader 与持久化索引解码(core.codec.IndexFileCodec)共用它;DeltaLogReader 在 executor 上读取任务描述的删除文件，两条存储线共用。

5.2 主键 Bloom 段级剪枝与运行时过滤

R9 只从主键的等值和 IN 提取有限候选值。布尔组合遵循可证明的集合语义： AND 与其他条件并存时可使用已知的主键集合，两个主键集合取交集； OR 只有两边都能提取主键集合时才取并集。NOT、范围、其他字段、 类型不符或无法翻译的条件不产生剪枝输入。这个过程只改变要读的段，R6 仍在行上执行完整谓词。

V2 从 segment manifest 的 statslog_files 取主键字段的统计路径；V3 从已钉住版本的 Manifest stats["bloom_filter.<field id>"] 取路径。路径只通过 core.io.ObjectStore 打开。Milvus 的 StatsWriter.Generate 写单个 JSON object， GenerateList 写 JSON array；读取者同时接受两种根形状。路径集合中有 basename 为 1 的 compound 文件时与 Milvus 一样只读该文件，否则每个列出的文件都是该段的一部分。

只有所有相关文件都成功读取、JSON 中每个统计都与主键字段及类型匹配，并且每个候选值在每个统计中都确定不存在时，才移除段。任意路径缺失、空文件、损坏 JSON、不支持的 Bloom 类型、字段或主键类型不匹配、以及跨 bucket 路径都保留该段。Bloom 的假阳性也只会多读一个段，不会丢行。

R18 在固定 Snapshot 的普通扫描上实现 SupportsRuntimeV2Filtering，只向 Spark 公布主键属性，且只在主键在读取列里时公布：Spark 按 Scan 的输出列解析这些属性，Spark 4.2 在规划每个 Scan 时都解析（SPARK-56467），主键被列裁剪去掉时公布它会让查询在规划阶段报错；按主键 join 时主键总在输出列里。每次 filter 调用提取一个主键集合，与该 Scan 先前收到的集合继续取交集；相同输入幂等。变化后废弃已生成的 partition 数组，但复用 driver 上按段和路径缓存的统计输入，只在内存中重新判定。剪后 Snapshot 保留每个剩余数据段所在分区的 L0 和 collection 级 L0，不把删除来源当成数据段剪掉。

R18 只做段级剪枝，不声称 row group 剪枝；后者仍是 R10 的仓库外依赖。

5.4 每个任务的批大小与 Arrow 上限

driver 把三个用户值严格解析成 ReadLimits，由 ReadPlan.of 放进每个 SegmentReadTask，随 Spark 分区序列化到 executor。SegmentReaderRegistry 在打开 原生 reader 时把 batchMaxRows 映射为 reader.record_batch_max_rows，把 batchMaxBytes 映射为 reader.record_batch_max_size；类型化值覆盖原始属性包中同名键，避免绕过 driver 校验。同一处还固定写入 reader.parquet.prebuffer.lazy=false 与按 batchMaxBytes 切成 8 个区间的 reader.parquet.prebuffer.range_size_limit（决策 31，见 storage-io 第六节）。

用户 option默认值生效点
milvus.read.batch.max.rows8192原生 reader 每批最大行数
milvus.read.batch.max.bytes33554432，最大 4294967296原生 reader 每批目标字节上限

MilvusPartitionReaderFactory 为每个任务从进程级 root 建一个 child allocator；行式、列式、 暴力搜索与持久化索引回表都使用它。最终的基础 PartitionReader 明确持有 child，先关闭当前批和 SegmentReader，再关闭 child；metadata 与 Limit 包装器只委托 close。构造中途失败时 factory 关闭已打开的 reader 和 child，重复关闭是空操作，任何任务都不会关闭进程级 root。

Arrow 上限约束由该 child 分配或导入的 JVM Arrow buffer，不包含 libmilvus-storage 自己的 native 内存池。上游当前没有每个 reader 的预取队列上限接口， 所以 G3 的预取上限仍未映射，不能用批字节上限冒充。

六、行式与列式出口

列式出口已有,且是默认:MilvusColumnarPartitionReader,milvus.read.columnar=false 才走行式。 向量搜索不走扫描出口,它是 MilvusSearch.search 的两阶段作业(见 vector-search.html 第一节)。 普通扫描接受的 DataSource V2 谓词由 core.expr.PredicateEvaluator 对 Arrow 批求值， milvus.filter 由 core.expr.Evaluator 对同一批求值；两者各自产生排除位图， 都不引起行式回落。完整语义见谓词下推设计。

没有删除和两个谓词位图排除的批直接包装成 ColumnarBatch；需要排除行时，reader 逐行计算 isDeleted || sparkPredicateBitmap.isExcluded || milvusFilterBitmap.isExcluded。列式出口通过 SelectedRowsColumn 按存活行下标重映射,不复制整列 buffer；行式出口在物化 InternalRow 前直接跳过该行。 两种出口都在底层 reader 读到 EOF 时执行同一个物理行数校验， 因此不会一条报短读、另一条静默返回。理由与代价见 storage-io 第四节。

6.1 向量列默认要转,零拷贝因此只落在标量列

Milvus 把所有向量类型都存成 Arrow 的 FixedSizeBinary, 而 Spark 的 ArrowColumnVector 不认这个类型——4.1.3 的 initAccessor 认的列表里没有 FixedSizeBinaryVector, 也没有 FixedSizeListVector。原样塞进去会抛不支持的类型, 所以向量列的容器必然要换。

决策 6 选了默认转成 Spark 原生类型,与 1.x 的 SparkTypes 一致:

Milvus 类型存储里的 Arrow 类型默认输出
FloatVectorFixedSizeBinary(dim*4)ArrayType(FloatType)
Float16Vector / BFloat16VectorFixedSizeBinary(dim*2)ArrayType(FloatType)
Int8VectorFixedSizeBinary(dim)ArrayType(ShortType)
BinaryVectorFixedSizeBinary((dim+7)/8)BinaryType
SparseFloatVectorBinaryMapType(LongType, FloatType)

代价:向量列逐元素转,零拷贝在默认路径上只剩标量列,而 Milvus 表的字节绝大部分是向量; fp16 与 bf16 还要内存翻倍,dim=1024 存储里 2KB、Spark 侧 4KB。

出口是读选项 milvus.read.vector.raw:打开后向量列出 BinaryType, 字节不动,零拷贝成立。它服务的是把字节直接喂给原生库的批量作业(backfill、暴力搜索), 那些场景转成 Array[Float] 再转回字节是纯浪费。

6.3 类型与 schema

SparkTypes.toStructField 是快照 schema、Table 与 reader 共用的映射。字段名、真实字段 id、Milvus 类型、nullable、主键/分区键/聚类键标记和向量维度都来自同一个 FieldSchema。支持范围是 Bool、整数、浮点、String、VarChar、Text、JSON、标量 Array 与六种 向量；Geometry、Timestamptz、ArrayOfVector/struct-array 和未知类型尚未实现。 fieldIDs 在 inferSchema 和 Table 构建时都过同一份快照字段表； 外部 .schema() 的非元数据字段必须恰好对应选中 id，名称和 Spark 类型不能与快照冲突。 遇到不支持的类型、schema 中缺字段或 Arrow 批缺请求列时直接失败，不退成 BinaryType 或 null。

七、不在本链路内的能力

  1. 向量搜索。MilvusSearch.search 是一条独立的两阶段作业,不经扫描出口。它属于 V*,本页不设计, 但 SegmentReader 接口要留得下它:逐批交出向量列,以及按地址取行。
  2. 两种谓词入口。R7 的手写 PlanParser 同时服务普通扫描的 milvus.filter 与向量搜索的 MilvusSearch.filter； 前者在普通扫描的 JVM Arrow 批上求值，后者在搜索前生成排除位图。 R6 的 Spark V2 谓词按独立设计只在普通扫描的 JVM Arrow 批上求值。C 的 loon_segment_reader_get_filtered_stream 会忽略传入谓词,连接器不调用它,见 storage-access 4.4。
  3. 回表与 row group 剪枝。take（R14）和统计驱动的 row group 剪枝 （R10）仍是独立能力，不通过普通顺序扫描的外围分支模拟。

八、实现状态

固定快照的普通读取链路已经贯通三层。第 3 层解析一次 Snapshot 并对接 Spark， 第 2 层规划任务、读取删除文件并统一打开段 reader，第 1 层经 JNI 交付 Arrow 批。 下面保留各次下沉的边界，未完成项只列不属于这条普通读取链路的能力。

  1. 写 core.read.plan 的 SegmentReadTask。已完成。 SegmentReadTask 只装描述,句柄开在 executor 上;段布局的两种来源(V3 的 manifest 路径加版本、V2 已物化的列组)是 SegmentLayout 的两个 case,那是两条线唯一的实质差别。 删除来源单独建模成 DeleteSource:Files 只给删除文件、读留给 executor,#13 起 planner 只产出它; Materialized 装一份现成的 plan,driver 不再产出(它曾把主键 map 序列化进每个分区,README 第 1 节列的 1.x 代价之一)。 两个 case 都在,迁移就是换了 planner 产出哪一种,没改这个类型。 spark 层的两个 InputPartition 已经改成携带它: MilvusV3InputPartition 从 12 个字段降到今天的 3 个(task、partitionName、milvusOption), MilvusV2InputPartition 从 9 个降到 2 个(task、milvusOption), 分区上不再有向量检索字段。 随之有一个产品可见的行为变化: StorageProperties.from 从每个 task 的 reader 构造里移到规划期跑一次, 所以存储配置不全的读现在在规划期就失败,不再是每个 task 各失败一次。
  2. 规划本身进 core.read.plan。已完成(#12)。 段列表怎么变成任务这段计算原来是 spark 层的 SnapshotPartitions.build, 现在是 ReadPlan.of,输入输出全是 core 类型;MilvusScan.inputPartitions 只把任务包成两种 InputPartition,加上分区名与规范化选项。 纯搬,行为不变:规划的 50 个用例一个断言没改。
  3. 删除读取下沉 executor。已完成(#13)。driver 上只剩 DeleteFileListing.of: V2 段的删除文件在快照里,V3 段的在它的 manifest 里(driver 打开 manifest 列文件、解析版本,不读删除文件), L0 段的文件按分区挂到该分区每个任务上;ReadPlan.of 把它们装进 DeleteSource.Files。 executor 上 core.read.exec.DeletePlans 按任务读文件成 plan,读不到抛异常让 task 失败,不再有空 plan 兜底。 spark.read.plan 包、V2 分区上的 L0 标记、reader factory 里的继承 plan 合并都删掉。 代价:L0 文件对分区内每个段生效,现在每个 task 各读一遍(原来 driver 读一次),driver 不再持有任何主键 map。 UAT 三个带删除的快照(V2 加 L0、V3 加 L0、V3 折进清单)都读回 2990 行。
  4. R9 段级主键 Bloom 剪枝与 R18 段级运行时过滤。已完成。 SegmentStatistics 显式区分 V2 列出的 statslog、V3 Manifest 内统计和不可知； PrimaryKeyBloomPruner 一次读取并缓存每段的统计输入，单 object、compound array、 多非 compound 文件都按本节的保守规则判定。MilvusScan 只在普通扫描实现 SupportsRuntimeV2Filtering，重复调用累计取交集并重建 partition 数组，不重读统计。 R10 仍列在 capabilities 第 11 节，没有 row-group 实现或代理。
  5. 两个行式 reader 合成一个。已完成(#06)。MilvusV3PartitionReader 与 MilvusV2PartitionReader 各写一遍的主循环变成一个 MilvusRowPartitionReader:拉批、逐行交付、跳过已删行、有谓词时逐行求值、读完按 SegmentReadTask.expectedRows 核对总行数(原来只有 V2 有这道自查,现在 manifest 布局给出行数时同样受益)。 两条线的列名规则和从 schema 推需要哪些列,原来是两个 reader 的伴生对象,现在归各自的 ColumnBinding; 当时拆出的 V1 RowFilters 是过渡实现, R6 由 spark.expr 翻译 V2 Predicate,再由 core.expr 对列批统一求值。 行为不变:UAT 的 V3 折进清单、V2 加 L0、全类型三个快照读回的行数与列值与合并前一致。
  6. 写 core.read.exec 的 SegmentReader 与注册表。已完成。 开原生 reader、逐批取 Arrow、按序释放句柄这一整套从两个 spark reader 的构造块搬进 core, 两处各写一遍变成一处;registry 按 SegmentLayout 分发。 列名解析做成 columnNameFor: Long => Option[String] 参数而不是内聚进去—— manifest 按字段 id 匹配列、schema 里字段名就是 id,列组布局用字段自己的名字, 这不是 core 能替调用方决定的。ColumnBatch 与 take 仍不写: 列式出口的 Spark 那一半是 Spark 类型,归第 3 层,进 core 的仍是 VectorSchemaRoot。

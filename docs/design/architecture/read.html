读路径

能力 R1、R2、R3、R4、R5、R8、R10、R14、R17。取字节和交接 Arrow 那一层见 storage-io.html,分层见 modules.md。

第 3 层仍然直接调第 1 层,读这条路上第 2 层是空的。 两个 PartitionReader 都在 spark-base,现在调的是 native-storage 的 JNI(不再是上游绑定),中间仍然不经过 core; 而 core.read.plan 与 core.read.exec 只有一个空的 package.scala。本页先说清第 3 层现在怎么读的,再说要往第 2 层填什么。

一、读一张表只有一种读法

表面上分很多种情况,实际只有一种读法。两个 PartitionReader 最后都调同一个上游 MilvusStorageReader,唯一的实质差别是列组清单谁算出来的。

分发在 MilvusPartitionReaderFactory.createReader,按分区类型匹配, 不读 storage_version;落到 case _ 就抛 This connector requires Milvus 2.6+ (Storage V2)。

V3 线V2 线
段怎么描述manifest 路径 + readVersion列组:字段 id、文件路径、每文件行数
列组清单原生库读 manifest 得 columnGroupsPtrMilvusStorageColumnGroups.createFromGroups 在 JVM 拼
取字节、凭证、Arrow 出口都走 native-storage 的 JNI;凭证是 StorageProperties.from(options) 产出的 fs.* 属性包

所以改造只有一个切入点。要做的是换掉那一个调用,保留两种产生它输入的方式, 而不是把两条线各改一遍。

V2 线多一道自查:driver 把每个列组文件的行数传下来,reader 累计实际交付的行数,少了就报错。 这是防上游 milvus-storage#657 之前的版本在多文件列组里只读第一个文件—— 那个缺陷不抛异常,只会让 DataFrame 静悄悄变短。

二、段从哪来:四个规划入口

分岔全在 driver 侧。四个入口产出的形状一样:一组 InputPartition 加每段的删除计划。

入口触发产出
planInputPartitionsFromClientSnapshot默认路径:gRPC 建快照,服务端已把两类段分开返回V3 + V2
planInputPartitionsFromSnapshotsnapshot 模式,选项里直接给 manifest 列表和 V2 段列表V3 + V2
planInputPartitionsFromBackupbackup 模式,BackupMetaReader.toV2Segments 转备份元数据只有 V2
planInputPartitionsFromLegacyClient指定了 partition/segment,快照快路径关掉时只有 V3;遇到 V2 段报错,让用户改用快照模式

driver 侧要开的四类文件——快照 manifest、V2 段的 manifest 与 parquet footer、删除日志、备份元数据—— 已经全部走 交字节那一面。

三、不支持 storage_version 0/1

三处挡在外面:legacy client 入口 filter(_.storageVersion >= 2) 后为空就抛 requires Milvus 2.6+;按 segment 精确查时报 storage_version < 2; 工厂的 case _。没有任何路径会去读逐字段的 V1 binlog。

insert_log/{collection}/{partition}/{segment} 是 Milvus 放段数据的目录, 与 storage_version 无关。V3 的 manifest basePath 就在这个目录下, buildSnapshotPartitions 正是靠 pathParts.lastIndexOf("insert_log") 往后数两级反推 partitionID。看到 insert_log 就断定是 V1,是读错了—— UAT 取下来的那个段文件 4133761 字节,偏移 0 是 PAR1,末尾也是 PAR1, 中间没有 Milvus 的 event 头,是一个 V2 列组的纯 parquet。

全仓唯一解析 Milvus event 格式的地方是 core.delete.MilvusDeltaLogReader, 它读删除日志,在 driver 上跑,两条线共用。

四、离目标还差什么

取字节那一面已经到位,交地址那一面一步没动。

状态
driver 侧做完了。MilvusScan.storeFor 建 NativeObjectStore,属性由连接器自己的 fs.* 选项与 fs.s3a.*/fs.oss.* 翻译出来的键合并,前者优先;桶为空时用 fs.storage_type=local。core.io.hadoop 已删除,core 与 compat 的主代码里没有一处 org.apache.hadoop
executor 侧已经走我们的 JNI。还没做的是把分发与出口下沉到 core.read.exec——现在它们仍然是 spark 层的两个分支
代价driver 现在要能加载 libmilvus-storage。CI 不构建原生库,所以这条路径在 CI 上没有端到端覆盖;单元测试用 LocalObjectStore 覆盖各格式的解析

五、要往第 2 层填的两个包

分界线一句话:plan 在 driver 上跑,产物必须可序列化; exec 在 executor 上跑,是 core 调原生层的唯一地方。

段列表 ──plan──> InputSpec(可序列化,发到 executor)
                    │
                    └──exec──> SegmentReader ──> 批 ──> Spark

5.1 core.read.plan

类型是什么
InputSpec一个分区要读什么:段路径、storage_version、manifest 版本、列名、fs.* 属性、删除文件位置。只有描述,没有句柄、没有 Configuration、没有打开的资源
ReadPlan一组 InputSpec,加规划期就能算出来的总行数、字节数(供 R13)
Partitioner怎么切分区。默认一段一分区;R19 按分区报分区、R16 段选择落在这里

剪枝(R9 段级、R10 row group 级)也在本包:规划期用统计信息把不需要的段和文件从 InputSpec 里去掉。R10 依赖仓库外的两件事,见 storage-access 4.5。

5.2 core.read.exec

trait SegmentReader extends AutoCloseable {
  def next(): Option[ColumnBatch]              // 逐批，EOF 返回 None
  def take(rowIds: Array[Long]): ColumnBatch   // R14 回表
}

SegmentReaderRegistry: storage_version -> SegmentReader 工厂

注册表在 core,实现可以在 compat。V2 packed 的实现放 compat.v2packed,启动时注册进来;core 不反向依赖 compat。这是能力 K1 写死的约束。

这个注册表取代 spark 层现在的做法——MilvusPartitionReaderFactory.createReader 按 InputPartition 的具体类型做模式匹配,两条线各一个分支。 分发移到 core,spark 层只留 Spark 接口的对接。

两条线各自的列组清单怎么来留在各自的实现里,取字节与 Arrow 交接统一走 storage-io 定的那两个面。所有权那三条规则同样在那篇。

六、列式出口:做,R4 已定

今天全仓没有任何列式输出——没有 ColumnarBatch、没有 ArrowColumnVector、没有 supportColumnarReads, 两条读线都是行式 PartitionReader[InternalRow]。所以 R4 是从零开始。

决策 12 选了做。出口形态:无删除的批原样包成 ColumnarBatch 直通, 有删除的批把存活行物化成新的一批。物化无法回避,理由与代价见 storage-io 第四节。ColumnBatch 的定义据此定型,core.read.exec 不再被挡。

6.1 向量列默认要转,零拷贝因此只落在标量列

Milvus 把所有向量类型都存成 Arrow 的 FixedSizeBinary, 而 Spark 的 ArrowColumnVector 不认这个类型——4.1.3 的 initAccessor 认的列表里没有 FixedSizeBinaryVector, 也没有 FixedSizeListVector。原样塞进去会抛不支持的类型, 所以向量列的容器必然要换。

决策 6 选了默认转成 Spark 原生类型,与 1.x 的 DataTypeUtil 一致:

Milvus 类型存储里的 Arrow 类型默认输出
FloatVectorFixedSizeBinary(dim*4)ArrayType(FloatType)
Float16Vector / BFloat16VectorFixedSizeBinary(dim*2)ArrayType(FloatType)
Int8VectorFixedSizeBinary(dim)ArrayType(ShortType)
BinaryVectorFixedSizeBinary((dim+7)/8)BinaryType
SparseFloatVectorBinaryMapType(LongType, FloatType)

代价:向量列逐元素转,零拷贝在默认路径上只剩标量列,而 Milvus 表的字节绝大部分是向量; fp16 与 bf16 还要内存翻倍,dim=1024 存储里 2KB、Spark 侧 4KB。

出口是读选项 milvus.read.vector.raw:打开后向量列出 BinaryType, 字节不动,零拷贝成立。它服务的是把字节直接喂给原生库的批量作业(backfill、暴力搜索), 那些场景转成 Array[Float] 再转回字节是纯浪费。

七、其余没定的

  1. 向量搜索这条分支怎么放。存量 MilvusLoonPartitionReader 里有 performSegmentVectorSearch,和普通扫描是两条并行路径。它属于 V*,本页不设计, 但 SegmentReader 接口要留得下它,不能设计成只能顺序扫。
  2. R5 列裁剪怎么传到底。loon_segment_reader_open 收 needed_columns,V2 那条线怎么表达列裁剪要单独确认。
  3. 谓词。C 那条路不可用(loon_segment_reader_get_filtered_stream 收下谓词、返回 OK、然后忽略,见 storage-access 4.4),由 core.expr 在 JVM 侧求值。

八、开发大纲

  1. 把交地址那一面的 C 入口一次封完,读写一起。reader 那组 (loon_record_batch_reader_*、loon_segment_reader_*、 loon_exttable_read_manifest)加 writer 那组,外加自己的加载器—— NativeStorageLibrary 现在调的是 io.milvus.storage.NativeLibraryLoader, 第 1 层反过来依赖了要被替换的东西。分两次做等于把凭证、加载器、结构体那套代码写两遍。
  2. 凭证换成 core.credential。把 Properties.fromMilvusOption 换成 StorageProperties.from(options) 的 fs.* 属性包。一处改动同时服务两个 reader 和两个 writer。 临时凭证今天只能走 fs.use_iam 加环境变量,属性包缺 fs.session_token,见 storage-access 3.7。
  3. reader 换过去。V2 线先换——它的列组清单是 JVM 拼的,不依赖原生 manifest 解析, 改动面更小;V3 线随后。换完之后读出口移到 core.read.exec, spark 层只留 Spark 接口的对接。
  4. writer 换过去。backfill 分支走已有的 BatchUpdateManifest,可以做; append 分支等 Milvus 新增 RegisterSegments,那条不在我们手上。
  5. 删掉上游绑定。读写都搬完才删得掉,legacyJni 那四处、 3.5 线出不了 Scala 2.12 产物,跟着一起解决。

第 1、2、3 步做完,读这条路就不再经过上游绑定。第 4、5 步是写侧,能力 W1 的交付还等 Milvus 新增 RegisterSegments。

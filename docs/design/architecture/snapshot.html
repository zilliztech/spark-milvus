快照对象模型

能力 R2、R3、R9、R16、C3、K2、K3。规划期怎么把段变成分区见 read.html 第五节，分层见 modules.md。 本页是工作单 #03、#04 的设计。#03（对象、SnapshotCatalog、使用点切换）已实现并在 UAT 真实快照上端到端跑通；#04（SnapshotSource 接口与注册表）未做。

读的唯一输入是一个 Snapshot 对象。 段列表有两个来源，格式不同；统一的不是输入格式，是解析后的对象。两个来源各实现一个 SnapshotSource，产出同一个 Snapshot；driver 把 Snapshot 投影成每分区一个 SegmentReadTask；executor 只见 SegmentReadTask。 一个来源给不出的字段在对象上必须显式标为「未知」，不能用空值冒充「没有」。

一、对象

两个对象，一个描述整次读，一个描述一个段；V2 与 V3 段用同一个 Segment 表示，差别收在布局字段里。 全部放 core.snapshot，纯数据，不持句柄，不依赖 Spark。

1.3 删除文件：三种状态，不能合并

「有删除文件」「没有删除文件」「不知道有没有」是三种状态，今天的代码把第三种当成第二种，1.x 的 legacy 入口因此把已删除的行读回来。 LegacyClientPlanner 造 SegmentReadTask 时不填 deletes，默认是 DeleteSource.None，reader 于是不做删除过滤，没有任何报错。

sealed trait DeleteFiles
object DeleteFiles {
  case object Empty extends DeleteFiles                      // 来源确认没有删除
  final case class Listed(files: Seq[DeltaLogRef]) extends DeleteFiles   // V2：Avro 里列了
  final case class InManifest(version: Long) extends DeleteFiles         // V3：Manifest 该版本里列了，executor 上读
  case object Unknown extends DeleteFiles                    // 来源给不出
}

Unknown 遇到 milvus.read.apply.deletes=true（默认值）必须在规划期报错， 错误信息说明哪个来源、为什么给不出。用户显式关掉删除过滤才能读。这条规则与 core.read.plan.DeleteSource.Files.materializedPlan 抛异常是同一个原则：读不到删除就不能装作没有删除。

三、SnapshotCatalog：列目录、选一个、解析

主路径不经 Milvus 服务，只靠对象存储：列 snapshots/{coll}/metadata/ 前缀，按名、按时间点或取最新选一个，解析成 Snapshot。 走 core.io.ObjectStore，不碰 Hadoop。

  1. 选快照。今天的入口：milvus.snapshot.path 直接给一个快照 JSON，不经服务；或给 milvus.uri，由 DescribeCollection 取 collection id 后按 milvus.client.snapshot.name 选名字、缺省取最新。R2 的三种写法：version 是快照名，精确匹配；timestamp 取 createdAt 不晚于它的最新一个；两者都不给取 createdAt 最大的。目录里只有 JSON 文件名可用时， 按时间点选要打开候选 JSON 读 create_ts；README 第五节向 Milvus 要的 catalog 文件到位后改为只读一个文件。
  2. 解析 JSON。今天 MilvusSnapshotReader.parseSnapshotMetadata 做的事，产物从 SnapshotMetadata（JSON 的形状）改为 Snapshot。JSON 里 V3 段在 storagev2_manifest_list， 每项是一段 {"ver": N, "base_path": ...}；键名里的 V2 指 milvus-storage 库的清单格式版本，不是段的 storage_version， 解析器负责把这个名字翻正，对象上只剩 storageVersion = 3。
  3. 补 V2 段的列组。JSON 的 manifest_list 指向 Avro 文件，Avro 里是 V2 段的 binlog 列表； 列组的字段集合要再开每个 parquet 的 footer 读 group_field_id_list。这一步今天在 compat.v2.FooterV2SegmentResolver， 位置不变，由 SnapshotCatalog 经注册表调用（K1 的约束：core 不依赖 compat）。
  4. 不做的。不建快照、不删快照、不 Flush；建和删是 A1 的 CALL，在第 3 层经 client.api，不在读路径上。

四、边界：Snapshot 留在 driver，SegmentReadTask 去 executor

Snapshot 不实现 Serializable，这是有意的。 它带整张 schema、全部段和索引定义，大小随段数增长；每个 task 需要的只是自己那一段。 core.read.plan 的 Partitioner 把它投影成每段一个 SegmentReadTask，只有 SegmentReadTask 序列化发出去。

Segment 的字段到 SegmentReadTask
id、partitionId、layout原样
Snapshot.schemaschemaBytes，protobuf 字节，每个分区一份
deletesDeleteSource：Listed 和 InManifest 变 Files，executor 上读； Empty 变 None；Unknown 在规划期已经报错，到不了这里。今天的 Materialized（driver 读完删除日志把主键表塞进分区）是过渡，见 read.html 第八节
rows不进 SegmentReadTask；ReadPlan.totalRows 从 Snapshot 算，给 R13

R16 的分区和段选择、R9 的段级剪枝都在投影之前对 Snapshot.segments 过滤，是 Partitioner 的输入，不是新的来源。

六、字段的取舍标准

字段跟着消费者走，不跟着 Milvus 走。快照 JSON 是 DataCoord 的内部结构 （milvus internal/datacoord/snapshot.go 的 SnapshotData），段 manifest 是 milvus-storage 的 manifest.h，两者都没有公开契约，键名和格式版本都改过。模型取它们的语义，不取它们的结构；每个字段能回答 「谁读它」「来自哪个键」「哪个来源给不出」三个问题，缺一个就不进模型。

动作标准
加字段四条全满足：(1) 有消费者，能指出能力编号或 core 包；(2) 有来源，对照表写明 Milvus 的键和最早出现的格式版本； (3) 缺失有语义，四个来源各标「有 / None / Unknown」；(4) 解析按版本分支，旧版本没有的填 None，不猜默认值。 SegmentIDs、BuildIDs、2PC 的 state 没有消费者，不进模型
减字段只在消费者消失时删，走「移除是设计工作」的规则，决策日志一行。Milvus 删了键而我们仍消费：字段不删，来源标 None，解析器按版本处理，README 第五节提 ask
改名Milvus 改键名只改解析器别名，模型不动。模型字段按语义命名，不跟键名：storagev2_manifest_list 装的是 V3 段
版本模型不带版本号。解析器认快照的 format_version 与 manifest 的 version，各自声明支持区间，超出报错不静默读。core 测试资源里每个格式版本留一份样本（JSON、Avro、manifest），解析器测试跑全部版本

Milvus 变更时的顺序：先更新下面的对照表，再按标准定模型动不动，再加解析器的版本分支，最后补该版本的样本文件。对照表是唯一的记录处。

快照对象模型

对应能力索引中的 R2、R3、R8、R9、R13、R16、C3、K3。规划期怎么把段变成分区见 read.html 第五节，分层见 modules.md。 对象、SnapshotCatalog、SnapshotSource 与 Table 持有 Snapshot 均已实现。

读的唯一输入是一个 Snapshot 对象。 段列表有四种入口，格式不同；统一的不是输入格式，是解析后的对象。各入口产出同一个 Snapshot，公共出口再应用分区与段选择；driver 把 Snapshot 投影成每个数据段一个 SegmentReadTask；executor 只见 SegmentReadTask。 一个来源给不出的字段在对象上必须显式标为「未知」，不能用空值冒充「没有」。

一、对象

两个对象，一个描述整次读，一个描述一个段；V2 与 V3 段用同一个 Segment 表示，差别收在布局字段里。 全部放 core.snapshot，纯数据，不持句柄，不依赖 Spark。

1.3 删除文件：三种状态，不能合并

「有删除文件」「没有删除文件」「不知道有没有」是三种状态，不能互相代替。 来源把它明确写进 Segment.deletes；默认开启删除时，未知状态在规划期失败，读取失败则在 executor 失败。两处都不允许退成空删除计划。

sealed trait DeleteFiles
object DeleteFiles {
  case object Empty extends DeleteFiles                      // 来源确认没有删除
  final case class Listed(files: Seq[DeltaLogFile]) extends DeleteFiles  // V2：Avro 里列了
  case object InManifest extends DeleteFiles                             // V3：由 Segment.layout.Manifest 钉住的版本列出
  case object Unknown extends DeleteFiles                    // 来源给不出
}

Unknown 遇到 milvus.read.apply.deletes=true（默认值）必须在规划期报错， 错误信息说明哪个来源、为什么给不出。用户显式关掉删除过滤才能读。这条规则与 core.read.plan.DeleteSource.Files.materializedPlan 抛异常是同一个原则：读不到删除就不能装作没有删除。

二、四种入口，一个接口，一次解析

接口只有一个方法，没有参数：一个实现在构造时就绑定了自己的定位信息，调用它得到 Snapshot。 定位信息各不相同（快照目录里的路径、backup 目录加 collection 名、option 串），所以它们是各实现的构造参数，接口不假装能统一。

SnapshotSources 同时拥有 driver store 的生命周期。catalog、client 与 backup 来源都在 store 打开期间把需要的元数据、Avro 与 footer 完整物化；成功或失败后立即关闭。backup 的并发 footer 任务先全部结束再关闭 store，主异常保留，关闭异常作为 suppressed exception 附上。返回的 Snapshot 不持有 store 或 native handle。

2.0 不在读时建快照：1.x 的「读前 CreateSnapshot、读完 DropSnapshot」快路径随 A6 一起删除（决策 11）。读之前快照必须已存在，由 Milvus 自动建或用户经 A1 的 CALL 建；连接器只经 SnapshotCatalog 选一个读。

三、SnapshotCatalog：列目录、选一个、解析

主路径不经 Milvus 服务，只靠对象存储：列 snapshots/{coll}/metadata/ 前缀，按名、按时间点或取最新选一个，解析成 Snapshot。 走 core.io.ObjectStore，不碰 Hadoop。

  1. 选快照。今天的入口：milvus.snapshot.path 直接给一个快照 JSON，不经服务；或给 milvus.uri，由 DescribeCollection 取 collection id 后按 milvus.client.snapshot.name 选名字、缺省取最新。R2 的三种写法：version 是快照名，精确匹配；timestamp 取 createdAt 不晚于它的最新一个；两者都不给取 createdAt 最大的。目录里只有 JSON 文件名可用时， 按时间点选要打开候选 JSON 读 create_ts；README 第五节向 Milvus 要的 catalog 文件到位后改为只读一个文件。
  2. 解析 JSON。core.snapshot.json.SnapshotJson.parse 得到 JSON 的形状 SnapshotJson，SnapshotCatalog.fromMetadata 把它变成 Snapshot。JSON 里 V3 段在 storagev2_manifest_list， 每项是一段 {"ver": N, "base_path": ...}；键名里的 V2 指 milvus-storage 库的清单格式版本，不是段的 storage_version， 解析器负责把这个名字翻正，对象上只剩 storageVersion = 3。
  3. 补 V2 段的列组。JSON 的 manifest_list 指向 Avro 文件，Avro 里是 V2 段的 binlog 列表； 列组的字段集合要再开每个 parquet 的 footer 读 group_field_id_list。这一步今天在 compat.v2.FooterV2SegmentResolver， 位置不变，由 SnapshotCatalog 经注册表调用（K1 的约束：core 不依赖 compat）。
  4. 归一路径。用户直接给的 s3a://bucket/key 或 s3://bucket/key 按标准 URI 解析。快照 JSON、Avro 与 footer 是 Milvus 产生的元数据， 其中 s3://endpoint:port/bucket/key 只在 authority 显式带端口，或 authority host 与 fs.address 的 endpoint host 精确匹配时按 endpoint 形式解析；其余情况 authority 仍是桶。段数据、删除文件与 Manifest 最终都成为 Snapshot.bucket 下的 key。
  5. 不做的。不建快照、不删快照、不 Flush；建和删是 A1 的 CALL，在第 3 层经 client.api，不在读路径上。

四、边界：Snapshot 留在 driver，SegmentReadTask 去 executor

Snapshot 不实现 Serializable，这是有意的。 它带整张 schema、全部段和索引定义，大小随段数增长；每个 task 需要的只是自己那一段。 core.read.plan.ReadPlan.of 把它投影成每个数据段一个 SegmentReadTask，只有 SegmentReadTask 序列化发出去。

六、字段的取舍标准

字段跟着消费者走，不跟着 Milvus 走。快照 JSON 是 DataCoord 的内部结构 （milvus internal/datacoord/snapshot.go 的 SnapshotData），段 manifest 是 milvus-storage 的 manifest.h，两者都没有公开契约，键名和格式版本都改过。模型取它们的语义，不取它们的结构；每个字段能回答 「谁读它」「来自哪个键」「哪个来源给不出」三个问题，缺一个就不进模型。

动作标准
加字段四条全满足：(1) 有消费者，能指出能力编号或 core 包；(2) 有来源，对照表写明 Milvus 的键和最早出现的格式版本； (3) 缺失有语义，四个来源各标「有 / None / Unknown」；(4) 解析按版本分支，旧版本没有的填 None，不猜默认值。 SegmentIDs、BuildIDs、2PC 的 state 没有消费者，不进模型
减字段只在消费者消失时删，走「移除是设计工作」的规则，决策日志一行。Milvus 删了键而我们仍消费：字段不删，来源标 None，解析器按版本处理，README 第五节提 ask
改名Milvus 改键名只改解析器别名，模型不动。模型字段按语义命名，不跟键名：storagev2_manifest_list 装的是 V3 段
版本模型不带版本号。解析器认快照的 format_version 与 manifest 的 version，各自声明支持区间，超出报错不静默读。core 测试资源里每个格式版本留一份样本（JSON、Avro、manifest），解析器测试跑全部版本

Milvus 变更时的顺序：先更新下面的对照表，再按标准定模型动不动，再加解析器的版本分支，最后补该版本的样本文件。对照表是唯一的记录处。

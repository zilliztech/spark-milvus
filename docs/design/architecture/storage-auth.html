对象存储认证：机制与设计

本页记录大数据生态处理文件系统认证的既有机制、我们的判断原则、按原则得出的结论， 以及支撑结论的实测事实。存储访问层的整体设计见 storage-access.html，模块边界见 modules.md。

结论先行。连接器不构造凭证，但也不能完全不管。JVM 侧继承 Spark 的 Hadoop 配置；需要写配置时只写按桶的键，且只在平台没设时补；原生侧只传位置与模式，不传密钥。 现有的 provider 链逻辑保留，要治的是六处复制和写死的默认值。 详见第三节。

一、既有机制：Hadoop 兼容文件系统怎么处理认证

Spark、Hive、Flink、Iceberg、Delta 都建在这套机制上。它由四件事组成。

1.1 一个入口，按 scheme 分发

FileSystem.get(URI, Configuration) 是唯一入口。URI 的 scheme 通过 fs.<scheme>.impl 选实现：s3a、abfs/abfss、gs、hdfs、file。 抽象在文件系统 API 这一层，不在凭证这一层。

1.2 认证不是 API，是配置键

没有任何跨文件系统的凭证接口。认证全部表达成 Configuration 里的键， 每个文件系统占一个命名空间：

文件系统认证相关的键
s3afs.s3a.access.key、secret.key、session.token、aws.credentials.provider、assumed.role.arn
abfsfs.azure.account.auth.type、account.oauth.provider.type、account.key.<account>
gsfs.gs.auth.type、auth.service.account.json.keyfile
hdfsdfs.*，身份走 Kerberos 的 UGI

Kerberos 与 AKSK 没有共同结构，不可能统一。所以这套机制的做法是按 scheme 分发、 各占一个键命名空间，谁都不管谁。它屏蔽的是文件访问的 API 差异，不是认证差异。

1.3 provider 链

fs.s3a.aws.credentials.provider 是一串类名，按顺序尝试。abfs 和 gs 是同样的形状。 默认链由 hadoop-aws 的版本决定。

1.4 按桶、按账号覆盖

fs.s3a.bucket.<桶名>.<键> 覆盖全局的 fs.s3a.<键>， hadoop-aws 在建 FileSystem 实例时把它提升成该实例的值。abfs 对应 fs.azure.account.key.<account>。

一个作业用两套身份访问两个桶，只能靠这个机制，没有别的办法。 Spark 的会话级配置表达不了「读 A 桶用身份 X，写 B 桶用身份 Y」。

1.5 Spark 怎么接

spark.hadoop.<键> 会被拷进 Hadoop 的 Configuration；连接器取 sessionState.newHadoopConf() 往下传。Kerberos 场景另有 delegation token： driver 收集后分发给 executor。

二、判断原则

由上面的机制得出五条，用来判断连接器该不该碰认证：

  1. 不构造凭证，把拿到的 Configuration 传给 FileSystem.get。
  2. 必须写配置时只写按桶或按账号的键，不写全局键。写全局键等于改整个会话的安全边界。
  3. 不覆盖已设好的 provider，只在缺失时补。
  4. 不内置默认值。端点、密钥、桶名没配就应该失败。
  5. 不重复。同一段逻辑只存在一处。

三、我们的设计

3.1 JVM 侧：继承，不构造

取 sessionState.newHadoopConf() 往下传。平台通过 spark.hadoop.fs.s3a.* 配置一次，连接器不写任何凭证代码。Iceberg 的 HadoopFileIO 与 Delta 都是这样。

3.2 例外：跨账号双桶必须由连接器写按桶键

backfill 同时读源桶、写 Milvus 桶，两个桶可能属于不同账号，端点、密钥、区域都不同。 会话级配置表达不了，所以连接器必须写 fs.s3a.bucket.<桶>.*。 这是原则 2 允许的形态，也是现有代码 configureHadoopS3ForPath 的 isSource 参数存在的原因。

3.3 例外：平台已选的 AssumeRole 不能被覆盖

托管运行时可能已经全局或按桶选好了 AssumeRole provider，用于它的数据角色或外部卷。 连接器只在该桶没有 AssumeRole 时才补自己的链。对应原则 3，也是提交 d823ec0 fix: [backfill] honor platform AssumeRole configuration (#108) 的由来。

3.4 例外：静态密钥要钉住 provider

用户给了 AKSK 时强制 SimpleAWSCredentialsProvider， 否则会被全局配置的 provider 链遮蔽。这是 Hadoop 的真实行为，不是防御性编程。

3.5 原生侧：只传位置与模式，不传密钥

milvus-storage 的 C 层有自己的 SDK，在同一个 pod 里自己做发现。它认识的键分四类：

类别键
身份模式fs.use_iam、fs.role_arn、fs.session_name、fs.external_id、fs.iam_endpoint
位置fs.address、fs.bucket_name、fs.root_path、fs.region、fs.cloud_provider
静态密钥fs.access_key_id、fs.access_key_value
各云专属fs.azure_client_id、fs.azure_tenant_id、fs.gcp_credential_json、fs.gcp_target_service_account、fs.oss.endpoint

fs.cpp:104 与 117 里 use_iam 为真时走另一条分支， 不取静态密钥，由它自己的 SDK 发现。所以云上的正确配置是 fs.use_iam=true 加位置信息，一个密钥都不传。

3.6 两侧发现的一致性

两个 SDK 各自发现，在干净的 IRSA 场景下会得到同一个身份——同一个 pod、同一个 token 文件。 它们只在一侧被显式配置、另一侧没有时才分叉。规则： 要么两侧都不配，要么两侧配一致，不存在只配一侧。

3.7 要治的两处

六处复制。凭证构建散在 MilvusOption、loon/Properties、MilvusDataSource、 MilvusBackfill、BackfillConfig、ListV2SegmentsApp， 而 core.credential 是空包。逻辑正确但没有落点，收敛成一处。

写死的默认值。a-bucket、localhost:9000、 minioadmin 在生产路径上，违反原则 4，漏配桶名会安静地连错桶。 移到显式的测试配置，漏配就失败。对应 README 第 4 节决策 21。

四、实测事实

以下是读源码与 jar 得到的，不是推断。

4.1 EKS 上 SDK v1 默认链不可靠，所以有那条显式链

MilvusBackfill.scala 的注释原文：SDK v1 的 DefaultAWSCredentialsProviderChain 在 EKS pod 上不总是先取投影进来的 service-account web identity token，会回落到节点的 EC2 实例角色，拿到节点的角色。 所以顺序是刻意排的：WebIdentity → EnvironmentVariable → IAMInstance。

4.2 v1 类名在 hadoop-aws 3.4.1 上仍然可用，但依赖我们自带 v1 SDK

我们钉 hadoop 3.4.1，hadoop-aws 3.4.x 已迁到 AWS SDK v2。读 CredentialProviderListFactory.java：v1 到 v2 的映射表只有五条。

v1 类名映射到
com.amazonaws.auth.AnonymousAWSCredentialsAnonymousAWSCredentialsProvider
com.amazonaws.auth.EC2ContainerCredentialsProviderWrapperIAMInstanceCredentialsProvider
com.amazonaws.auth.InstanceProfileCredentialsProviderIAMInstanceCredentialsProvider
com.amazonaws.auth.EnvironmentVariableCredentialsProviderv2 的 EnvironmentVariableCredentialsProvider
com.amazonaws.auth.profile.ProfileCredentialsProviderv2 的 ProfileCredentialsProvider

WebIdentityTokenCredentialsProvider 不在表里。 不在表里的类走这条路径：先查用户自定义的 fs.s3a.aws.credentials.provider.mapping；再试按 v2 实例化，失败； 然后 if (isAwsV1SdkAvailable()) 用 AwsV1BindingSupport 按 v1 实例化； v1 SDK 不在 classpath 就抛异常。

我们的依赖同时有两代：software.amazon.awssdk:*:2.30.38 和 com.amazonaws:aws-java-sdk-core:1.12.780。后者的 jar 里确实有 com/amazonaws/auth/WebIdentityTokenCredentialsProvider.class。

所以现在能工作，但它靠的是我们特意带着 v1 core SDK。 一旦有人以「统一到 v2」为由删掉 aws-java-sdk-core，这条链会在实例化时失败， 而失败发生在连接对象存储的那一刻，不在编译期。

更稳的两种写法，二选一：换成 v2 的 software.amazon.awssdk.auth.credentials.WebIdentityTokenFileCredentialsProvider （已在我们的 auth-2.30.38.jar 里），或者显式配 fs.s3a.aws.credentials.provider.mapping 把 v1 名映射过去。 换之前要在真实 EKS 上验证 v2 的这个 provider 行为与 v1 一致。

4.3 仓库内两代类名并存

MilvusDataSource.scala:918 用 v2 的 software.amazon.awssdk.auth.credentials.DefaultCredentialsProvider， MilvusBackfill.scala:2589 与 ListV2SegmentsApp.scala:307 用 v1 名。 收敛成一处时要一并统一。

4.4 Milvus 自己不支持 HDFS

configs/milvus.yaml 的 storageType 只有 local 和 remote，cloudProvider 是 aws、gcp、gcpnative、azure、aliyun、tencent。 所以 Milvus 格式的路径永远不在 HDFS 上。用户自己的源数据走 spark.read.parquet(path)（MilvusBackfill.scala:733）， 用的是用户自己的 Hadoop 配置，与本层无关。

本层的范围因此是：Milvus 格式的路径，加 milvus-backup 的导出目录，两者都在对象存储上。

五、被否决的方案

方案否决理由
造一个跨文件系统的凭证抽象Kerberos 与 AKSK 无共同结构。业界的做法是按 scheme 分发加命名空间透传，不是统一凭证
默认什么都不配，让默认链发现SDK v1 默认链在 EKS 上会拿到节点角色。这正是现有显式链要解决的问题
删掉六处 provider 链逻辑会连同跨账号双桶、平台 AssumeRole 两个真实场景和一个缺陷规避一起删掉。要治的是复制与默认值，不是逻辑

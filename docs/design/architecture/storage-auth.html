对象存储认证：信息从哪来、怎么提取、怎么传下去

存储访问层的整体设计见 storage-access.html， 模块边界见 modules.md。仓库内有配套 skill .agents/skills/spark-milvus-storage-auth/。

一条链，三段。Spark 的配置里带着「怎么取凭证」的参数； 第 3 层把它们提取出来翻成 fs.*；core.credential 校验后原样交给 C， C 自己去换凭证。连接器不构造凭证，也不认识云。

第 3 层那段翻译是垫片，不是长期形态。 按 storage-access.html 3.3， 长期形态是产出配置的一方直接产出 fs.*，翻译这一步消失。 垫片的退出条件就是那一天，在此之前它必须只做键名翻译，不加逻辑。

一、认证信息是什么

1.1 三个来源

来源长什么样谁写的

1.2 传下来的不是凭证，是取凭证的参数

托管平台注入的全部内容：一个角色 ARN、一个会话名、一个 provider 类名。 没有 access key，没有 secret，没有 session token。真正的机器身份是 K8s 投影进 pod 的 web identity token 文件，两侧的 SDK 各自去读。

spark.hadoop.fs.s3a.aws.credentials.provider          = org.apache.hadoop.fs.s3a.auth.AssumedRoleCredentialProvider
spark.hadoop.fs.s3a.assumed.role.arn                  = <客户数据角色 ARN>
spark.hadoop.fs.s3a.assumed.role.credentials.provider = com.amazonaws.auth.DefaultAWSCredentialsProviderChain

spark.hadoop.fs.oss.assumed.role.arn          = <客户数据角色 ARN>
spark.hadoop.fs.oss.assumed.role.session.name = <实例 id 拼出的会话名>
spark.hadoop.fs.oss.credentials.provider      = com.zilliz.cloud.hadoop.AliyunOSSRoleCredentialsProvider

这条性质决定了整个设计：可以把值提取出来换个键名交给 C，因为里面没有秘密。 两侧做的是同一件两步动作，逐步对照见 storage-access.html 3.4。

1.3 Hadoop 那套键是怎么组织的

Spark、Hive、Flink、Iceberg、Delta 都建在 Hadoop 兼容文件系统上。 它抽象的是文件访问 API，不是认证。认证没有跨文件系统的接口——Kerberos 与 AKSK 没有共同结构——所以每个文件系统占一个键命名空间，谁都不管谁。

文件系统scheme认证键实现来自
Amazon S3、MinIOs3afs.s3a.access.key、secret.key、session.token、aws.credentials.provider、assumed.role.arnhadoop-aws
阿里云 OSSossfs.oss.accessKeyId、accessKeySecret、credentials.providerhadoop-aliyun
Azure Data Lake Gen2abfsfs.azure.account.auth.type、account.key.<account>、account.oauth2.msi.*hadoop-azure，我们没带

还有三条机制在提取时用得上：

  1. provider 链：fs.s3a.aws.credentials.provider 是一串类名，按顺序尝试， 第一个给出凭证的胜出。默认链由实现的版本决定，不同版本不一样——第五节就是被这一点咬的。
  2. 按桶覆盖：fs.s3a.bucket.<桶名>.<键> 覆盖全局的 fs.s3a.<键>。一个作业用两套身份访问两个桶只能靠它，因为 Spark 的会话级配置 表达不了「读 A 桶用身份 X，写 B 桶用身份 Y」。hadoop-aliyun 没有这个机制， backfill 因此只能改全局键再还原（见 backfill-storage.html）。
  3. spark.hadoop.<键> 透传：Spark 把这个前缀下的键拷进 Hadoop 的 Configuration，连接器取 sessionState.newHadoopConf() 拿到。

二、怎么提取

2.1 一个出口

提取的结果只有一种形式：一个 Map[String, String]，键全是 fs.*，多桶时是 extfs.<名字>.*。 core.credential 是唯一的出口，它校验必填项、拒绝空值，然后原样交给 C。

输入有两处，出口只有一个：

  1. 用户在 .option() 里直接给的 fs.*——不需要翻译，核对键名即可。
  2. Spark 配置里的 spark.hadoop.fs.*——由第 3 层的垫片读出来翻成 fs.*。键名对照表在 storage-access.html 3.3，不在这里重列。

两处都不进 core：core.credential 收到的永远是已经翻好的 fs.*， 它不认识 s3a、oss、abfs 这些 scheme。

2.2 现在的两个坑

坑一：用户选项有两套键名，差别只有大小写。 MilvusOption.scala 里声明了一套 camelCase 的 fs.* 常量， 而 loon/Properties.scala 读的、reference-cn.md 写的、C 认的都是 snake_case：

MilvusOption 声明的实际生效的被引用次数
fs.bucketNamefs.bucket_name2（都在一个三选一的兼容列表里）
fs.accessKeyId / fs.accessKeyValuefs.access_key_id / fs.access_key_value0
fs.storageTypefs.storage_type0
fs.cloudProviderfs.cloud_provider0
fs.useIamfs.use_iam0

十八个常量里十七个零引用。用户照着这批名字配，配了不生效，也不报错。 只有桶名例外——MilvusDataSource.connectorS3BucketOption 依次试 fs.bucket_name、fs.bucketName、s3.bucketName 三个拼法。 这批常量随 core.credential 一起清掉，属于删除，按 AGENTS.md 要先确认。

坑二：同一段提取逻辑有五份。loon/Properties（原生属性包）、 MilvusDataSource（按桶 Hadoop 配置）、MilvusBackfill、 BackfillConfig、apps/tools 下的 ListV2SegmentsApp 与 ReadSourceOnlyApp，而 core.credential 是空包。 逻辑本身正确，只是没有落点。

三、怎么传下去

3.1 一个 Map 一路到底

从 core.credential 出来之后，这个 map 不再被任何一层解释。 native-storage 的 JNI 把它转成两个 const char* 数组调 loon_properties_create，不看键名也不认识云；C 侧按 fs.storage_type 与 fs.cloud_provider 分派，自己去换凭证。 分派表见 storage-access.html 3.2。

3.2 到 executor 怎么传

句柄不过界，map 过界。C 返回的 handle 是进程内指针， Spark 会把 InputPartition 序列化发到 executor，所以 InputPartition 里只装描述——段路径、manifest 版本、要读的列名、fs.* 的 map。 executor 拿到描述后才开句柄，读完关掉。细节见 storage-access.html 4.1。

凭证本身不需要分发，因为传的从来不是凭证：每个 executor 进程各自持一个会自我刷新的 provider，作业跑多久都不掉（3.6）。

3.3 迁移期两条通路并存

C 通路接上之前，JVM 侧的 Hadoop 通路还在线上跑：MilvusDataSource 取 sessionState.newHadoopConf() 往下传，第 4 层的作业按需写按桶的键。 两条通路在干净的 IRSA/RRSA 场景下拿到同一个身份——同一个 pod、同一个 token 文件； 只有一侧被显式配置、另一侧没有时才分叉。规则：两侧都不配，或两侧配一致。

这期间守四条：不构造凭证；必须写配置时只写按桶或按账号的键，不写全局键； 不覆盖已设好的 provider，只在缺失时补；不内置默认值，端点、密钥、桶名没配就应该失败。

四、local 与 remote 两种模式

两个「local」不是一回事，这是最容易混的地方。

  • --master local[*] 是 Spark 的部署模式：driver 和 executor 跑在同一个 JVM 进程里，不需要集群。
  • fs.storage_type = local 是 C 层的存储后端：读本地磁盘上的文件， 不连对象存储，不需要任何凭证。

两者正交。本地开发最常用的组合其实是「Spark local 模式 + storage_type=remote 连本机 MinIO」， 不是两个 local 一起用。

4.1 三种组合

组合Sparkfs.storage_type要什么用来验什么
A. 纯本地文件local[*]local只要磁盘上有一份段数据格式解析、读路径逻辑。不碰认证
B. 本地 MinIOlocal[*]remote本机 MinIO 在 9000，静态 AK/SK静态密钥这条路径、端点与桶的配置、S3 协议行为
C. 真集群k8sremoteEKS/ACK pod、IRSA 或 RRSAAssumeRole 链、token 轮换。第六节那三条只能在这里验

组合 B 与 A 已在 UAT 数据上验过（2026-09-12）。取一个真实实例的段 binlog， 本地后端和 AWS S3 后端经 JNI 各读一遍，字节一致；细节和 fs.session_token 的实证见 storage-access.html 第八节。

A 和 B 覆盖不了认证：A 根本不走凭证，B 只走静态密钥那一条分支 （fs.role_arn 空且 fs.use_iam 假）。AssumeRole 与 web identity token 两条路在本地无法构造，因为它们要的是 K8s 投影进来的 token 文件。

4.2 本地要跑起来需要什么

  1. JDK 21。Java 26 上每个起 SparkSession 的测试都会以 UnsupportedOperationException: getSubject is not supported 中止—— Subject.getSubject 被移除而 Spark 还在调。看起来像代码问题，不是。
  2. 原生库。make build-milvus-storage 后 make copy-native-libs，需要 conan。不建就只有两个用例失败 （MilvusStorageFFITest、MilvusStorageMultiFileGroupTest），其余照跑。 在 macOS 上已验证可用，产物 libmilvus-storage-jni.dylib； 构建前提与产物尺寸见 contributing.md。
  3. 组合 B 还要一个 MinIO，监听 9000，建好桶。 integration-4.0 的用例假定端点 localhost:9000、凭证 minioadmin/minioadmin。

4.3 现在缺什么

  1. 仓库里没有起 MinIO 的东西。没有 docker-compose， integration-4.0 的注释写着「需要 MinIO 在 9000」，怎么起没有写。 每个人自己想办法，而端点和凭证又写死在用例里。
  2. 组合 A 只被两个原生用例走过。fs.storage_type = local 只出现在 MilvusStorageFFITest 与 MilvusStorageMultiFileGroupTest 里， 没有任何一个用例从 Spark 那一侧走这条路。 （这两个用例本身已经能在本地跑了，见 contributing.md。）
  3. 组合 B 的配置写死在用例里，不能换端点换桶。

这三条是本地开发体验的事，不是设计问题，但它们决定了改动能不能被快速验证。 core.credential 落地时一起做：把端点、桶、凭证做成用例可配， 给组合 A 补一条能在本地跑的读路径用例。

五、AWS SDK v1 升 v2

必须升，理由是供应链不是技术。1.x 已于 2025-12-31 结束支持，不再有安全补丁。 全仓对 com.amazonaws 的引用只有五处，全是配置值里的类名字符串，没有一处 import，所以不涉及代码迁移。我们这边的类名已经换完：

原来现在
com.amazonaws.auth.WebIdentityTokenCredentialsProvidersoftware.amazon.awssdk.auth.credentials.WebIdentityTokenFileCredentialsProvider
com.amazonaws.auth.EnvironmentVariableCredentialsProvider同名的 software.amazon.awssdk 版本
com.amazonaws.auth.DefaultAWSCredentialsProviderChain（在 MilvusOption 里）随 MilvusS3Option 一起删除

5.1 换类名必须同时加 sts 模块

v2 的 WebIdentityTokenFileCredentialsProvider 要 software.amazon.awssdk:sts 才能工作，否则它会静默不生效、回落到链上的下一个 provider——在 EKS 上就是节点实例角色。这个依赖已经加上， StsWebIdentityCredentialsProviderFactory 已在产物里。

5.2 v1 依赖删不掉，原因在仓库外

云平台注入的 spark.hadoop.fs.s3a.assumed.role.credentials.provider 是 com.amazonaws.auth.DefaultAWSCredentialsProviderChain——v1 类名， 而且不在 hadoop-aws 那张只有五条的 v1→v2 映射表里，所以必须有 v1 实现类在运行时 classpath 上。

hadoop-aws 3.4.1 解析一个 provider 类名的顺序是：查内置五条映射 → 查用户配的 fs.s3a.aws.credentials.provider.mapping → 按 v2 实例化 → 失败且错误是「不是 v2 实现」时， 若 v1 SDK 在 classpath 上就用 AwsV1BindingSupport 按 v1 实例化，不在则抛异常。

顺序不可颠倒：先换类名、在真实 EKS 上验证、再删依赖。先删依赖会在建 FileSystem 那一刻失败，而不是编译期。

未核实的一点：spark-data-service 自己声明了 com.amazonaws:aws-java-sdk-bundle:1.12.262 并用 shade 打包， 但它是原样打进产物还是做了 relocate 或排除，没有确认。这决定了删掉我们这份依赖之后 运行时还有没有 v1 类。

六、实测事实

  1. hadoop-aws 3.4.1 的 v1→v2 映射表只有五条，WebIdentityTokenCredentialsProvider 与 DefaultAWSCredentialsProviderChain 都不在其中。读 CredentialProviderListFactory.java 源码得出。
  2. 我们同时依赖 software.amazon.awssdk:*:2.30.38 与 com.amazonaws:aws-java-sdk-core:1.12.780；后者的 jar 里确有 com/amazonaws/auth/WebIdentityTokenCredentialsProvider.class。
  3. EKS 上 SDK v1 默认链不可靠：不总是先取投影进来的 service-account token， 会回落到节点的 EC2 实例角色。来自 MilvusBackfill.scala 的原注释。 C 层那条没有这个问题——AWS C++ SDK 的默认链把 web identity 排在实例元数据之前。
  4. Milvus 的 storageType 只有 local 与 remote， 本层永远不会去 HDFS 上找 manifest。用户自己的源数据走 spark.read.parquet(path)，与本层无关。

七、被否决的方案

方案否决理由
造一个跨文件系统的凭证抽象Kerberos 与 AKSK 无共同结构。业界做法是按 scheme 分发加命名空间透传
默认什么都不配，让默认链发现SDK v1 默认链在 EKS 上会拿到节点角色，这正是现有显式链要解决的问题
删掉六处 provider 链逻辑会连同跨账号双桶、平台 AssumeRole 两个真实场景和一个缺陷规避一起删掉
先删 v1 依赖再换类名连接时才失败，把可控验证变成线上故障
把 Hadoop 键的翻译放进 core等于把 Hadoop 按 scheme 分派本来替我们做的事捡回来，还是按云做的。见 storage-access.html 3.3

八、剩下的

  1. v2 的 WebIdentity provider 与 v1 的等价性，要在真实 EKS 上验（组合 C）。 本页这条 Hadoop 通路在 C 通路接上之前还在线上跑。
  2. 五处复制与那批 camelCase 僵尸常量，等 core.credential 落地一起清。 清常量属于删除，要先确认。
  3. 本地测试环境的三个缺口（4.3），随 core.credential 一起做。

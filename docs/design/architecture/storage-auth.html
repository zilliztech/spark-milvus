对象存储认证：机制、覆盖与设计

存储访问层的整体设计见 storage-access.html， 模块边界见 modules.md。仓库内有配套 skill .agents/skills/spark-milvus-storage-auth/。

结论。连接器不构造凭证，但不能完全不管：跨账号双桶和平台已选的 AssumeRole 两个场景只能由它处理。现有 provider 链逻辑保留，要治的是六处复制和写死的默认值。 另外两件必须做：AWS SDK v1 已于 2025-12-31 结束支持，升到 v2；JVM 侧只支持 S3 与 OSS， Azure 与 GCS 读不了，是真缺口。

一、既有机制

Spark、Hive、Flink、Iceberg、Delta 都建在 Hadoop 兼容文件系统这套机制上。它由五件事组成。

1.1 一个入口，按 scheme 分发

FileSystem.get(URI, Configuration) 是唯一入口。URI 的 scheme 通过 fs.<scheme>.impl 选实现。抽象在文件访问 API 这一层，不在凭证这一层。

1.2 认证不是 API，是配置键

没有任何跨文件系统的凭证接口。Kerberos 与 AKSK 没有共同结构，不可能统一。 所以每个文件系统占一个键命名空间，谁都不管谁：

文件系统scheme认证键实现来自
Amazon S3、MinIOs3afs.s3a.access.key、secret.key、session.token、aws.credentials.provider、assumed.role.arnhadoop-aws
Azure Data Lake Gen2abfs、abfssfs.azure.account.auth.type（SharedKey / OAuth / Custom / SAS）、account.oauth.provider.type、account.key.<account>、托管身份走 account.oauth2.msi.*hadoop-azure
Google Cloud Storagegsfs.gs.auth.type（APPLICATION_DEFAULT / SERVICE_ACCOUNT_JSON_KEYFILE / COMPUTE_ENGINE）、auth.service.account.json.keyfileGCS connector，Google 维护

HDFShdfsdfs.*，身份走 Kerberos 的 UGIhadoop-hdfs

1.3 provider 链

fs.s3a.aws.credentials.provider 是一串类名，按顺序尝试，第一个能给出凭证的胜出。 abfs 与 gs 是同样的形状。默认链由实现的版本决定，不同版本不一样，这一点后面会咬人。

1.4 按桶、按账号覆盖

fs.s3a.bucket.<桶名>.<键> 覆盖全局的 fs.s3a.<键>； hadoop-aws 在建 FileSystem 实例时把它提升成该实例的值。abfs 对应 fs.azure.account.key.<account>。

一个作业用两套身份访问两个桶，只能靠这个机制。 Spark 的会话级配置表达不了「读 A 桶用身份 X，写 B 桶用身份 Y」。

1.5 Spark 怎么接，凭证怎么到 executor

spark.hadoop.<键> 拷进 Hadoop 的 Configuration；连接器取 sessionState.newHadoopConf() 往下传。Kerberos 场景另有 delegation token： driver 收集后随任务分发给 executor，executor 不需要长期密钥。 S3A 也有对应的 fs.s3a.delegation.token.binding。

二、各云的覆盖现状

Milvus 自己支持六种后端（configs/milvus.yaml 的 cloudProvider： aws、gcp、gcpnative、azure、aliyun、tencent，加 storageType: local）。 我们两条通路的覆盖并不一致。

后端Milvus我们的 JVM 侧milvus-storage 的 C 侧
Amazon S3、MinIO是hadoop-awss3
阿里云 OSS是hadoop-aliyun走 S3 兼容端点
Google Cloud Storage是无gcp
Azure Blob是无azure
腾讯云 COS是无未确认
本地是filelocal

缺口：代码里只认 s3://、s3a://、oss://、 file:// 四种 scheme，依赖里只有 hadoop-aws 与 hadoop-aliyun。 客户的 Milvus 建在 Azure 或 GCS 上时，我们连快照 JSON 都打不开，读在第一步就失败—— 而原生层本来能读那上面的数据文件。

2.1 C 层已经解决了，包括国内三家

milvus-storage 的文件系统建在 arrow::fs::FileSystem 上，各云有自己的 producer。 cloud_provider 认识七个：aws、aliyun、azure、gcp、huawei、tencent、local， 比 Milvus 的 yaml 里列的还多一个华为。

这基本定死了路线。JVM 侧补齐等于用 Scala 与 Hadoop 的方式重写一遍 AliyunRAMSTSClient、TencentCloudSTSClient、HuaweiCloudSTSClient。 而且 AWS 的 IRSA 顺序问题我们已经手工趟过一遍（见 第五节）， 阿里云的 OIDC 是同一类问题，C 层那个 AliyunOIDCAssumeRoleChainProvider 就是它的答案。 按 AGENTS.md 的原则，在它旁边再建一条是标准的烟囱。

三、判断原则

  1. 不构造凭证，把拿到的 Configuration 传给 FileSystem.get。
  2. 必须写配置时只写按桶或按账号的键，不写全局键——写全局键等于改整个会话的安全边界。
  3. 不覆盖已设好的 provider，只在缺失时补。
  4. 不内置默认值。端点、密钥、桶名没配就应该失败。
  5. 不重复。同一段逻辑只存在一处。

四、我们的设计

4.1 JVM 侧：继承，不构造

取 sessionState.newHadoopConf() 往下传。平台通过 spark.hadoop.fs.s3a.* 配置一次，连接器不写凭证代码。Iceberg 的 HadoopFileIO 与 Delta 都是这样。

4.2 例外一：跨账号双桶必须写按桶键

backfill 同时读源桶、写 Milvus 桶，两个桶可能属于不同账号，端点、密钥、区域都不同。 会话级配置表达不了，所以连接器必须写 fs.s3a.bucket.<桶>.*。 这是原则 2 允许的形态，也是 configureHadoopS3ForPath 有 isSource 参数的原因。

4.3 例外二：平台已选的 AssumeRole 不能被覆盖

托管运行时可能已经全局或按桶选好 AssumeRole provider，用于它的数据角色或外部卷。 连接器只在该桶没有 AssumeRole 时才补自己的链。对应提交 d823ec0 fix: [backfill] honor platform AssumeRole configuration (#108)。

4.4 例外三：静态密钥要钉住 provider

用户给了 AKSK 时强制 SimpleAWSCredentialsProvider，否则会被全局 provider 链遮蔽。 这是 Hadoop 的真实行为，不是防御性编程。

4.5 原生侧：只传位置与模式，不传密钥

milvus-storage 的 C 层有自己的 SDK，在同一个 pod 里自己发现身份。它认识的键：

类别键
身份模式fs.use_iam、fs.role_arn、fs.session_name、fs.external_id、fs.iam_endpoint
位置fs.address、fs.bucket_name、fs.root_path、fs.region、fs.cloud_provider
静态密钥fs.access_key_id、fs.access_key_value
各云专属fs.azure_client_id、fs.azure_tenant_id、fs.gcp_credential_json、fs.gcp_target_service_account、fs.oss.endpoint

fs.cpp:104 与 117 里 use_iam 为真时走另一条分支， 不取静态密钥。云上的正确配置是 fs.use_iam=true 加位置信息，一个密钥都不传。

4.6 两侧一致性

两个 SDK 各自发现，在干净的 IRSA 场景下得到同一个身份——同一个 pod、同一个 token 文件。 只有一侧被显式配置、另一侧没有时才分叉。规则：两侧都不配，或两侧配一致。

4.7 要治的两处

六处复制：凭证构建散在 MilvusOption、loon/Properties、 MilvusDataSource、MilvusBackfill、BackfillConfig、 ListV2SegmentsApp，而 core.credential 是空包。逻辑正确但没有落点。

写死的默认值：a-bucket、localhost:9000、 minioadmin 在生产路径上，漏配桶名会安静地连错桶。对应决策 21。

五、AWS SDK v1 升 v2 的设计

5.1 为什么必须升

时间事件
2018-11AWS SDK for Java 2.x GA，是对 1.11.x 的重写
2024-07-311.x 进入维护模式，只收关键缺陷与安全更新
2025-12-311.x 结束支持，不再发版

我们依赖 com.amazonaws:aws-java-sdk-core:1.12.780，它已经停止支持， 不会再有安全补丁。这是供应链问题，不是技术偏好。

5.2 现在为什么还能跑：hadoop-aws 的映射与回退

我们钉 hadoop 3.4.1，hadoop-aws 3.4.x 已迁到 SDK v2。 读 CredentialProviderListFactory.java，一个 provider 类名的解析顺序是：

  1. 查内置的 v1→v2 映射表，只有五条，命中则替换并打 warn
  2. 查用户配的 fs.s3a.aws.credentials.provider.mapping，命中则替换
  3. 按 v2 类实例化
  4. 失败且错误类型是「不是 v2 实现」，判断 isAwsV1SdkAvailable()
  5. v1 SDK 在 classpath 上，用 AwsV1BindingSupport 按 v1 实例化，打 warn
  6. 不在，抛异常

内置映射表全部五条：

v1 类名映射到
com.amazonaws.auth.AnonymousAWSCredentialsAnonymousAWSCredentialsProvider
com.amazonaws.auth.EC2ContainerCredentialsProviderWrapperIAMInstanceCredentialsProvider
com.amazonaws.auth.InstanceProfileCredentialsProviderIAMInstanceCredentialsProvider
com.amazonaws.auth.EnvironmentVariableCredentialsProviderv2 的 EnvironmentVariableCredentialsProvider
com.amazonaws.auth.profile.ProfileCredentialsProviderv2 的 ProfileCredentialsProvider

fs.s3a.aws.credentials.provider.mapping 的值是逗号分隔的 旧类名=新类名 对，由 S3AUtils.getTrimmedStringCollectionSplitByEquals 解析。 它是给改不了代码的人用的逃生口。

5.3 范围：全是字符串，没有代码

全仓对 com.amazonaws 的引用只有五处，且全是配置值里的类名字符串， 没有一处 import。所以这次升级不涉及代码迁移。

位置类名内置映射
MilvusOption.scala:505DefaultAWSCredentialsProviderChain无，走 v1 回退
MilvusBackfill.scala:2589WebIdentityTokenCredentialsProvider无，走 v1 回退
MilvusBackfill.scala:2590EnvironmentVariableCredentialsProvider有
ListV2SegmentsApp.scala:307,308同上两个同上
BackfillAppTest.scala:385断言里的字符串—

顺带发现一处不一致，比升级本身更值得注意。 MilvusOption.getConf 用的是 DefaultAWSCredentialsProviderChain—— 正是 backfill 的注释指名「在 EKS 上会先拿到节点实例角色」的那条链。 也就是说 backfill 刻意避开的缺陷，连接器自己的读路径还踩着。 这条要和升级一起改，不能只换类名不换链。

5.4 目标映射

现在换成
com.amazonaws.auth.WebIdentityTokenCredentialsProvidersoftware.amazon.awssdk.auth.credentials.WebIdentityTokenFileCredentialsProvider
com.amazonaws.auth.EnvironmentVariableCredentialsProvidersoftware.amazon.awssdk.auth.credentials.EnvironmentVariableCredentialsProvider
com.amazonaws.auth.DefaultAWSCredentialsProviderChain不是换名，是换成与 backfill 一致的显式链

两个 v2 类都已在我们依赖的 auth-2.30.38.jar 里， org.apache.hadoop.fs.s3a.auth.IAMInstanceCredentialsProvider 本来就是 hadoop 的 v2 类，不动。

5.5 步骤与顺序

  1. 三处类名换成 v2，MilvusOption 的链改成与 backfill 一致的显式顺序，测试断言同步。
  2. 在真实 EKS 上验证。v1 的 WebIdentityTokenCredentialsProvider 与 v2 的 WebIdentityTokenFileCredentialsProvider 名字就不同， 一个偏向环境变量、一个偏向 token 文件路径，等价性没有验过。 当初这条链存在就是因为默认链在 EKS 上拿错角色，而这类问题本地和 CI 都测不出来。
  3. 验过之后才删 com.amazonaws:aws-java-sdk-core 依赖。

顺序不能颠倒。删依赖是编译期无感、连接时才炸的改动：provider 类名解析发生在 建 FileSystem 的那一刻，不在编译期。先删依赖再换名，等于把一次可控的验证变成线上故障。

5.6 为什么不选另外两条

方案不选的理由
保持现状继续带一个已结束支持的依赖，且任何人以「统一到 v2」为由删它都会在运行时炸
配 provider.mapping能工作，但多一项必须随处携带的配置；它是给改不了代码的人用的，我们改得了

六、实测事实

  • hadoop-aws 3.4.1 的 v1→v2 映射表只有五条，WebIdentityTokenCredentialsProvider 与 DefaultAWSCredentialsProviderChain 都不在其中。读 CredentialProviderListFactory.java 源码得出。
  • 我们同时依赖 software.amazon.awssdk:*:2.30.38 与 com.amazonaws:aws-java-sdk-core:1.12.780；后者的 jar 里确有 com/amazonaws/auth/WebIdentityTokenCredentialsProvider.class， 所以现在走的是第 5 步的 v1 回退。
  • v2 的 WebIdentityTokenFileCredentialsProvider 与 DefaultCredentialsProvider 都在 auth-2.30.38.jar 里。
  • Milvus 的 storageType 只有 local 与 remote， 本层永远不会去 HDFS 上找 manifest。用户自己的源数据走 spark.read.parquet(path)（MilvusBackfill.scala:733），与本层无关。
  • EKS 上 SDK v1 默认链不可靠：不总是先取投影进来的 service-account token， 会回落到节点的 EC2 实例角色。来自 MilvusBackfill.scala 的原注释。

七、被否决的方案

方案否决理由
造一个跨文件系统的凭证抽象Kerberos 与 AKSK 无共同结构。业界做法是按 scheme 分发加命名空间透传
默认什么都不配，让默认链发现SDK v1 默认链在 EKS 上会拿到节点角色，这正是现有显式链要解决的问题
删掉六处 provider 链逻辑会连同跨账号双桶、平台 AssumeRole 两个真实场景和一个缺陷规避一起删掉
先删 v1 依赖再换类名连接时才失败，把可控验证变成线上故障

八、未决

  1. v2 的 WebIdentity provider 与 v1 的等价性，要在真实 EKS 上验。
  2. Azure 与 GCS 的缺口怎么补：JVM 侧加依赖，还是统一走 C 的 filesystem。取决于 那个路线决定。
  3. 腾讯云 COS 在 C 侧是否支持，未确认。
  4. 六处复制收敛到哪：core.credential 还是第 3 层，同样取决于路线。
  5. 决策 21：写死的开发默认值怎么删，这是对外可见的行为变化。

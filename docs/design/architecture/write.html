写路径

能力 W1、W3，以及 W2、W4、A4 在这条路上的接口。段怎么写出去见 core.write.exec 的 package.scala，作业级提交见 core.write.commit， 取字节和交接 Arrow 那一层见 storage-io.html， 分层见 modules.md。

写一张表只有一种写法：Spark 的 DataSource V2 写协议，一个 Table、一个 WriteBuilder、每个 task 一个 SegmentWriter、driver 一个 Committer。 四段都已写完并在 UAT 桶上验过（入口是 2026-09-15 的工作单 #11；在那之前 format("milvus") 返回的 MilvusTable 只声明 BATCH_READ，用户写不了）。本页定入口怎么接、写的表从哪拿 collection schema、校验什么、哪些选项留下。

一、一条链，driver 两段、executor 一段

Spark 把写切成三段，每段在仓库里都有落点。driver 上先由 Table 和 WriteBuilder 定"写到哪、按什么 schema"，executor 上每个 task 写一个段目录并提交这个段自己的 manifest， driver 再收齐 commit message 写作业清单。登记是之后的另一个动作。

Spark 从 df.write.format("milvus").mode("append").options(...).save() 走到我们代码的顺序（Spark 4.0 的 DataFrameWriter.saveInternal）：

  1. MilvusDataSource.getTable(schema, partitioning, options)。因为 supportsExternalMetadata 是 true，Spark 传进来的 schema 是 DataFrame 自己的 schema（全部字段置为 nullable），不调 inferSchema。
  2. 检查 table.capabilities() 含 BATCH_WRITE；不含就退回 V1 写法， 我们没有 V1 写法，用户看到的是不支持。#11 之前卡在这里。
  3. AppendData.byName(relation, df)：Spark 按名字把 DataFrame 列对到 table.schema()。表的 schema 就是第 1 步传进来的 DataFrame schema，所以这一步在我们这里恒等， 对照 collection schema 的校验 Spark 不会替我们做，落在 WriteBuilder。
  4. table.newWriteBuilder(info) → build() → toBatch： MilvusV3BatchWrite 造 job id，每个 task 拿 MilvusV3PartitionWriter， driver 收齐后 commit。这三步已经存在。

mode 的四个值里只有 append 是这条路：

SaveModeSpark 做什么我们
appendAppendData，要 BATCH_WRITEW1，本页
overwriteOverwriteByExpression(true)，要 WriteBuilder 实现 SupportsTruncate，否则 TableCapabilityCheck 报错W4，工作单 #09 先写设计；本页只留接口位置
errorIfExists / ignoreTableProvider 不带 catalog 时直接抛不支持，Spark 自己的限制不做；表存不存在是 C2 的事

W1 那一行写的入口是 df.writeTo("milvus.db.coll").append()。三段名要 spark.catalog 的 MilvusCatalog（R1、C1），四条线的 catalog 包都还是空的。 format("milvus") 加选项是今天读表用的同一种过渡形式，写先接这个；catalog 落地后 writeTo 走 catalog.loadTable 拿到同一个 MilvusTable，下面的链一样。

二、写的表和读的表是同一个 Snapshot

写不看段，但要 collection schema，而 schema 已经有三条来源，都产出 Snapshot。 读路径的 getTable 通过 SnapshotSources.forRead 把 Snapshot 解析一次交给 MilvusTable（snapshot.html）。写沿用它。写新段用不到现有段的列表， 但 getTable 分不出后面是读还是写（Spark 两条路都传 schema 进来），而 withSegments = false 只是跳过 V2 段的 footer 解析、段列表照旧，所以 getTable 保持解析带段的 Snapshot；写因此多付一次段列表的代价（快照 Avro 一次读，V2 段各一次 footer）。 把段列表推迟到 Scan 是 read.plan 下沉时的事。

模式schema 从哪来写在什么场景
client（milvus.uri）DescribeCollection有活的 Milvus，写完由用户 CALL 登记
snapshot（milvus.snapshot.path）快照 JSON 的 schema离线，按某个快照的 schema 写
snapshot（milvus.snapshot.schema.bytes）选项里的 protobuf纯连接器，没有 Milvus 也没有快照目录；ConnectorWriteReadUatTest 走的就是它
backup（milvus.backup.dir）—拒绝：backup 是导出的只读副本，SnapshotOrigin.Backup 的表不声明 BATCH_WRITE

这一条定了之后，写侧现在靠手填的两个选项就没有存在的理由：字段 id 由 schema 的 fieldID 给，向量维度由 type_params 的 dim 给。

2026-09-15 经负责人同意删掉了 milvus.writer.fieldIds 和 vector.<field>.dim 两个写选项，以及无人构造的 MilvusV3WriteTable。依据：两者只在 MilvusV3PartitionWriter 里被读，值就是 collection schema 里的两列，选项是第二份真相，填错会写出和 collection 对不上的段；用户文档没有列过它们。仓库内唯一的调用方是 backfill，它原来先读快照 schema 再把字段 id 抄成字符串填进 milvus.writer.fieldIds，现在直接把 schema 交给 WriteSchema。能力表 G2 行本来就写着 2.0 的写选项要替代 milvus.writer.fieldIds。

三、WriteBuilder 校验什么

校验在 driver 的 build() 里一次做完，任何一条不过就不启动 task。 输入是 Spark 传来的 DataFrame schema（LogicalWriteInfo.schema）和 Snapshot 的 collection schema，规则按字段走：

规则依据不过时
DataFrame 的每一列在 collection 里有同名字段写不能造字段；加字段是 DDL（C2）报未知列
列的 Spark 类型等于 SparkTypes.toDataType(field) 给出的类型读写用同一份类型映射（R15）；向量列是 ArrayType(FloatType) 等，和读出来的形状一致，读回去再写不用转报类型不符，不做隐式转换——Spark 的 storeAssignmentPolicy 在这条路上没有机会介入（第一节第 3 步）
向量列每行长度等于 dim；BinaryVector 是 dim/8 字节schema 的 type_paramsexecutor 上逐行查，第一条不合就让 task 失败；driver 查不了值
collection 里每个字段（function output 除外）都要在 DataFrame 里段文件按列组写，缺列没法补；Milvus 加载段时按字段 id 找每一列报缺列，nullable 字段由调用方给 null 列。「nullable 缺列自动写 null、有 default_value 的缺列写默认值」是后续，要 writer 给不在行里的列补值
主键必须在 DataFrame 里，且 collection 不能是 autoIDautoID 的 id 由 Milvus 的分配器发，离线没有分配器报 autoID 的 collection 不能经连接器写；这是 2.0 首版的边界，不是缺陷
is_function_output 的字段（BM25 出的稀疏向量）不能出现在 DataFrame 里它由 Milvus 的 function 算，写入方给不了报不可写列
动态字段：enable_dynamic_field 时 schema 带 is_dynamic 的 JSON 字段（$meta）按普通 JSON 列写，DataFrame 里给同名列不给就按 nullable 处理
分区：DataFrame 不带分区列，写出的段不属于任何分区，登记（A4）时定段属于一个分区，Milvus 的分区不是列；作业清单里的 partition_id 是 Spark 的分区号partition key 的 collection 报不支持，分区由 key 哈希决定，2.0 首版不做

校验通过后 MilvusV3PartitionWriter 拿到的是 collection schema 投影到 DataFrame 列上的那份： Arrow schema 的列名是字段 id（和 Milvus 自己写的段一致，见 09-15 的对照），维度和 id 都从 schema 来。

四、executor：一个 task 一个段，已做

MilvusV3PartitionWriter 把 InternalRow 攒成 Arrow 批，交给 core.write.exec.V3SegmentWriter，写完 ManifestTransaction.commit 提交这个段的 manifest，回 driver 的 commit message 是段路径、manifest 版本、行数。 段目录是 StagingLayout(root, jobId).segment(partition, task)，在 insert_log/ 之外，避开 DataCoord 的 GC。这一段是 #07，规则在 core.write.exec 的 package.scala 和 storage-io.html 第三节。

Spark 重试 task 会用新的 task id 再写一个段目录，旧目录留在暂存前缀里；作业清单只记成功的那份， abort 删整个前缀。这一点靠 task id 进路径保证，不需要 task 之间协调。

五、driver：作业清单与标记，已做

MilvusV3BatchWrite.commit 把 commit message 交给 core.write.commit.Committer：先写 staging/{job}/manifest.json，再写 staging/{job}/_committed；重跑看到标记整个 no-op；abort 删前缀下所有文件。 这一段是 #08，格式和幂等规则在决策日志 09-15 那行。

六、登记之前，段还差三样

写路径到作业清单为止；段要被 Milvus 加载，文件里还缺 Milvus 自己写段时会放进去的三样东西。 09-15 用 pyarrow 对照 Milvus 写的 V3 段得出：

  1. 系统字段 RowID（字段 0）和 Timestamp（字段 1）。Milvus 的 QueryNode 加载段时按字段 id 找它们。 RowID 由 Milvus 的全局 id 分配器发，Timestamp 是写入时的 TSO；纯连接器模式两者都拿不到，见决策 22。
  2. 主键的 bloom filter：_stats/bloom_filter.<pk>，登记进段 manifest 的 stats。 连接器写段时可以算，格式按 Milvus 的 storage.BloomFilterSet，放 core.stats（零文件）。
  3. 列组切分：已做（#14）。Milvus 的规则（internal/storagecommon/split_policy.go 的默认策略）： 系统字段加主键、partition key、clustering key 一组；平均每值 ≥1024 字节的字段各一组；向量和 Text 字段各一组；其余标量一组。 core.write.exec.ColumnGroupSplit 把它表达成 milvus-storage schema_based 策略的正则列表（列名是字段 id）， task writer 在第一批 flush 时按这批的 buffer 大小估平均每值字节数再开原生 writer。

这三样是登记（A4）的前提，不是入口的前提：入口接上后，纯连接器写→读的往返不依赖它们。 三样各自是 W1 行"前提"列里的三条；3 已做，2 是新包（#15），1 等决策 22。

决策 22（README 第 4 节）：连接器写的段，RowID 和 Timestamp 从哪来。 a. 写时向 Milvus 要（AllocID、AllocTimestamp），要活的 Milvus，纯连接器模式做不到； b. 登记时由 Milvus 补——RegisterSegments 还没有，能不能改写文件要和 Milvus 侧一起定； c. 写占位（RowID 用段内行号、Timestamp 用作业时间），登记时 Milvus 只用作排序不用作真值。 选项取决于 RegisterSegments 的设计，那条在 Milvus 侧（README 第 5 节）。在定之前，client 模式可以先走 a。

七、W2 和 W4 在这条链上的位置

两种模式不另开链，只在 WriteBuilder 上多一个分支。

  • W4 overwrite / truncate：MilvusV3WriteBuilder 实现 SupportsTruncate，truncate() 记一个标志进 BatchWrite；作业清单多一个 replaces_all: true，登记时由 Milvus 把 collection 现有段全部标删再登记新段。 只接受全表；按谓词的 overwrite 不做（能力表第 10 节）。设计在工作单 #09。
  • W2 backfill：milvus.write.mode=backfill 加 milvus.write.columns， WriteBuilder 校验目标列是 collection 里已有且 Flushed 段里还没有的字段，task 往已有段的 base_path 写列组、以 ReplaceColumns 提交；分布与排序（每个 task 恰好对应一个已有段、行序与段内行号一致）见决策 10。 今天 apps 里的 backfill 通过 customPath 和 commitType 绕过 WriteBuilder 直接用 writeDataFrame，W2 落地时收进来。

八、开发大纲

  1. 入口。已做（#11）。MilvusTable 实现 SupportsWrite， SnapshotOrigin 不是 Backup 时声明 BATCH_WRITE， newWriteBuilder 返回 MilvusV3WriteBuilder(info.schema, snapshot.schema, milvusOption)； MilvusV3WriteTable 删掉。getTable 仍解析带段的 Snapshot（第二节说了为什么）。 纯连接器写只有 schema 没有段，milvus.snapshot.mode=true 加 milvus.snapshot.schema.bytes 因此成为合法的快照选项组合：一个没有段的快照。
  2. 校验。已做。第三节的表是 spark.write.WriteSchema.resolve(dataFrame, collection, mode)， 在 build() 里跑，产出带 Milvus 类型、字段 id、维度元数据的写 schema；Mode.Append 查完整性，Mode.Columns（backfill）只查给出的列。每条规则一个单测。
  3. schema 进 writer。已做。MilvusV3PartitionWriter 从列元数据取字段 id 和维度， writeDataFrame(df, options, collection) 要 collection schema，backfill 把快照里的 schema 交给它。
  4. UAT。做了纯连接器那半。ConnectorWriteReadUatTest 走 df.write.format("milvus").mode("append")：overwrite 被 Spark 拒（缺 truncate）、缺列被 WriteSchema 拒、append 写两段、作业清单和标记、读回 3000 行、abort。client 模式的写没有跑： 它和纯连接器模式只差 schema 从 DescribeCollection 来，而暂存前缀会落在实例根路径 {instance id}/staging/ 下，abort 删不掉的目录标记会留在实例前缀里。
  5. 文档。已做。reference-en/cn 的 2.4 与 3.2 节；W1 行入口注明 format("milvus") 是 catalog 落地前的形式。

第 6 节的三样和决策 22 各自开单；client 模式的写等 A4 登记一起在 UAT 上跑。

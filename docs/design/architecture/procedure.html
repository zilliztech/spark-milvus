CALL 过程

能力 A1 到 A5、A7 的 SQL 入口。过程体本身（登记、建快照、建索引）各在自己的能力行里,本页只讲 CALL milvus.system.<name>(...) 这条语句怎么从文本变成一次调用。工作单 #17。

一个解析器扩展认出 CALL milvus.system.*,把它变成一个带过程和参数的逻辑节点; 一条 planner 策略把节点变成在 driver 上跑过程体的物理节点;结果是一张表。四条线共用一份代码, 只有 antlr 生成的解析器和 ParserInterface 的适配器按线各一份。 不用 Spark 4.0 才有的 ProcedureCatalog(2026-09-10 的决定),所以 3.5 线走的是同一条路, 能力表第 4 节原来写的「3.5 暴露为同名函数」不再需要。

一、语法

过程名固定三段 milvus.system.<name>;参数是位置参数加命名参数,值只能是常量。

CALL milvus.system.register('default.spark_uat_v3',
  staging          => 'c48b088d035ecd5/staging/job-1789478390101',
  `milvus.uri`     => 'http://localhost:19531',
  `milvus.token`   => 'db_admin:***',
  `fs.bucket_name` => 'zilliz-aws-iobwa4e5ki5u5cl',
  `fs.address`     => 's3.us-west-2.amazonaws.com',
  `fs.use_iam`     => 'true')
statement     : CALL procedureName '(' (argument (',' argument)*)? ')' EOF ;
procedureName : identifier '.' identifier '.' identifier ;
argument      : constant                     # positional
              | identifier '=>' constant     # named ;
constant      : STRING | INTEGER | DECIMAL | TRUE | FALSE | NULL ;
identifier    : IDENTIFIER | BACKQUOTED_IDENTIFIER ;
规则定的是什么
第一个位置参数是 collection,写法 'db.coll';'coll' 表示 default 库和读写选项 milvus.database.name、milvus.collection.name 同一份解析,一处实现
过程自己的参数用裸标识符命名:staging => '...'每个过程声明自己的参数表,名字、类型、是否必填
连接和存储选项用反引号包住的选项名命名:`milvus.uri` => '...'选项名和 .option() 的键完全一样,不另起一套拼写;反引号是 SQL 标识符里带点的标准写法
值只能是常量过程在 driver 上跑,不需要表达式;文法不依赖 Spark 的表达式文法,四条线一份
大小写:关键字和过程名不分,参数名不分,值原样和 Spark SQL 一致

连接与存储选项走命名参数而不是会话配置。只读 MilvusCatalog 已能为表加载 保存这些属性，但 CALL 前端尚未实现，也没有把 Catalog 属性接入过程执行。第一版因此要求语句 显式携带所需选项，让一条语句自足、复制出来就能跑。以后是否允许 Catalog 属性提供默认值， 由 procedure 实现统一决定；语句中的显式参数始终覆盖默认值。

二、一次调用怎么走

  1. 解析器扩展。SparkSessionExtensions.injectParser 装一个 MilvusSqlParser(delegate)。 parsePlan 先把文本去注释、压空白、转小写,以 call milvus. 开头的才交给 antlr 生成的解析器, 其余全部原样交给 delegate。Spark 4 自己也有 CALL 语句(ProcedureCatalog), 不以 milvus. 开头的 CALL 不碰。其它 parseExpression 等方法全部转发。
  2. 逻辑节点。CallProcedure(procedure: Procedure, args: Map[String, Any]), LeafCommand,output 来自 procedure.outputSchema。 参数在建节点时按过程的参数表对好:位置参数按顺序填,命名参数按名字填,缺必填、多了不认识的、类型不对,都在这里抛。
  3. 策略。injectPlannerStrategy 装一条只认 CallProcedure 的策略,产出 CallProcedureExec。
  4. 物理节点。LeafV2CommandExec,run() 在 driver 上调 procedure.run(args), 把 Seq[Row] 转成 InternalRow。spark.sql("CALL ...") 拿到的 DataFrame 就是这张表, .show()、.collect() 都行。

三、过程体的接口

trait Procedure {
  def name: String                          // register
  def parameters: Seq[Parameter]            // Parameter(name, dataType, required)
  def outputSchema: StructType
  def run(args: ProcedureArgs): Seq[Row]    // driver 上执行
}
object Procedures { def byName(name: String): Option[Procedure] }   // 注册表,静态

ProcedureArgs 装两部分:过程自己的参数(按参数表取值),和连接、存储选项(反引号命名参数收集成的 Map[String, String],交给现有的 MilvusOption 解析)。过程体不碰 SQL,不碰 Spark 计划; Register.run(options, stagingPrefix) 就是今天的入口,只包一层 Procedure。

过程参数输出表
register(A4)collection(位置),staging(必填,作业暂存前缀,相对桶的 key)每段一行:job_id STRING, segment_id BIGINT, manifest_version BIGINT, status STRING,status 是 registered 或 already_registered
A1、A2、A3、A5、A7同一骨架,各自的能力行定参数和输出;本单只做 register

四、哪些按线各一份

东西放哪为什么
文法 MilvusCall.g4spark-base/src/main/antlr4/,一份决策 17:语法放共享目录
antlr 生成的 MilvusCallLexer / MilvusCallParser / MilvusCallBaseVisitor（包 extensions.parser）每条线的 target,构建时生成3.5 线 antlr 4.9.3,4.x 4.13.1,生成码不通用;运行时用 Spark 自带的 antlr,依赖标 provided
ParserInterface 适配器 MilvusSqlParser每条线的 extensions 目录,3.5 一份、4.x 三份相同4.0 起接口多了 parseRoutineParam,3.5 没有;这个类只做转发,几十行
访问器、CallProcedure、策略、CallProcedureExec、Procedure、注册表、MilvusSparkSessionExtensionsspark-base 的 extensions 与 procedure 包生成类在每条线里同名同包,共享源码对着各线的生成物各编一次

构建:sbt 插件 sbt-antlr4 0.8.3,每条线 antlr4Version := l.antlr、 antlr4PackageName := Some("com.zilliz.spark.connector.extensions.parser"), 文法目录指向 spark-base。这是 sbt.html 第 4 节「按线钉版本」的又一项,和 Arrow、Hadoop、Netty 一样。

用户启用:--conf spark.sql.extensions=com.zilliz.spark.connector.extensions.MilvusSparkSessionExtensions。 不设的会话里 CALL milvus.system.* 是 Spark 自己的语法错误,连接器不介入。

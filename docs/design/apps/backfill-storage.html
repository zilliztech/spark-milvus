backfill 的多桶存储访问

本页对应能力 O1，属于第 4 层。对象存储认证的通用机制与判断原则见 storage-auth.html，此处不重复。

结论。backfill 里那段写 provider 链的代码，解决的不是认证，是 一个作业要用不同身份访问多个桶。S3 有按桶覆盖机制，用它是对的； OSS 没有，只能备份改写还原全局键，那是绕过 hadoop-aliyun 的能力缺失。

一、为什么一个作业会碰多个桶

backfill 读一份源数据，算出新的列值，写回 Milvus 的段。源桶是客户的，Milvus 桶是 托管方的，两者可能属于不同账号，端点、密钥、区域各不相同。代码里的 isSource 参数就是在区分这两个桶：

configureHadoopS3ForPath(hadoopConf, path, config, isSource)
// isSource = true  → 源桶，取 config.sourceS3* 系列，缺省回落到主配置
// isSource = false → Milvus 桶，取 config.s3*

Spark 的会话级配置只能表达一套身份，所以这件事必须由作业自己处理。

二、S3：按桶覆盖，机制本来就有

hadoop-aws 支持 fs.s3a.bucket.<桶名>.<键>，建 FileSystem 实例时由 S3AUtils.propagateBucketOptions 把按桶的键提升成该实例的值。所以 backfill 写的是 fs.s3a.bucket.<桶>.*，不是全局键，不影响会话里别的读写。

2.1 provider 链什么时候才会被设

只在两个条件同时成立时：fs.use_iam 为真，且该桶没有已配置的 AssumeRole。判断走 BackfillConfig.resolveAwsS3AssumeRole，它是 「先看按桶的键，再看全局的键」。

托管平台会全局设 fs.s3a.aws.credentials.provider 为 AssumedRole provider， 所以在平台上这个分支不会执行。它只在没有平台配置的环境里生效： 开源用户自己装的 Spark，或本地测试。

链的顺序是刻意排的，理由在 storage-auth.html 第六节： 默认链在 EKS 上不总是先取投影进来的 service-account token，会回落到节点的实例角色。

三、OSS：没有按桶机制，只能改全局键再还原

hadoop-aliyun 的配置键全是全局的：fs.oss.accessKeyId、 fs.oss.accessKeySecret、fs.oss.endpoint、 fs.oss.credentials.provider。核对 3.4.1 的 jar， org.apache.hadoop.fs.aliyun.oss 下没有任何 propagateBucketOptions 或 fs.oss.bucket. 的痕迹； 同版本的 hadoop-aws 里这两样都在。

所以要在一个作业里先用身份 A 读源桶、再用身份 B 写 Milvus 桶，只能：

withScopedHadoopStorage(spark, path, config, isSource) {
  // 1. 备份 8 个 fs.oss.* 全局键的当前值
  // 2. 写入本次要用的值
  // 3. 设 fs.oss.impl.disable.cache=true
  // 4. 跑操作
  // 5. finally 还原这 8 个键
}

第 3 步不可省：FileSystem 有实例缓存，不禁用的话第二次访问会拿到缓存里那个还揣着 旧凭证的实例。

另一处（MilvusBackfill.scala:1947 附近）走的是另一种隔离：克隆一份 Configuration 给 V2SegmentLoader 读 AVRO 与 parquet footer， 不动会话里共享的那份。注释写明了目的是不污染共享的 OSS 凭证。

这是绕过，不是设计。改全局状态再还原，在并发下不安全： 同一个 SparkSession 里若有另一个线程同时读 OSS，它会看到被临时改写的键。 backfill 目前是单线程驱动这些操作，所以没有暴露，但这个前提没有写在任何地方， 也没有测试守着。

四、根因与出路

根因是 hadoop-aliyun 不支持按桶配置，不是我们的代码写得不好。 在 Hadoop 的框架内，除了改全局键再还原，没有别的表达方式。

milvus-storage 的 C 层有现成的表达方式：extfs.<名字>.<属性> 一次注册多套 文件系统配置，loon_filesystem_get(properties, path) 按 address + bucket 匹配。 源桶和 Milvus 桶各注册一个名字，不改任何共享状态，也就没有下面那条单线程前提。 细节见 storage-access.html 3.5。

五、这段代码的归宿

两处副本一起换成 extfs.*：本页讲的这处，和 ListV2SegmentsApp 里的 另一份。时间点是 core.credential 落地，见 storage-access.html 第七节。

换完之后两件事一起消失：第三节那个没人测的单线程前提， 以及平台之外那条 provider 链对 classpath 上有 STS 模块的依赖 （storage-auth.html 5.6）—— C 层自带 STS 客户端。

集成测试的 Helm 执行

spark-milvus-integration Chart 只创建一个 Kubernetes Job；Job 在单个 Pod 内以 Spark local[*] 运行 integration40/test，访问已有的 Milvus 和对象存储。

当前状态：Chart 的部署合同已经确定。现有发布镜像没有测试运行器，三个 integration suite 仍写死本机 Milvus/MinIO 配置，因此本次只能验收 Chart 的 lint 与渲染；镜像和测试配置完成前，不能声称端到端测试可运行。

objectStorage.rootPath 是 Milvus 实例已有的数据根目录，读取必须保持它不变；测试产生的新对象写到 <writePrefix>/<runId>。Chart 不把 AK/SK 写进 ConfigMap、模板或日志。

3. 一次 release 对应一次测试

  1. CI 生成唯一的 Helm release 和 runId。
  2. 命名空间及其 Secret 由集群既有流程预先创建；运行脚本拒绝创建命名空间或覆盖同名 release。
  3. 运行脚本先执行 helm lint --strict，再安装 Job，并分别监控 Complete、Failed 与 CreateContainerConfigError；脚本不主动读取凭据 Secret 的 data。Helm 默认以 Secret 保存 release metadata，CI 身份仍需具备 Helm 自身要求的 Secret 权限。
  4. Job 失败不由 Kubernetes 重试：backoffLimit 固定为 0，避免重复写入。
  5. 成功或失败都先收集 Helm 状态、Job 日志、资源描述和相关 Events。
  6. 收集完成后卸载 release；成功测试若卸载失败，CI 仍判失败。TTL 只负责 CI 被强制中断后的 Job 兜底回收。

安装不使用 --atomic。该参数会在失败时先删除 Job，使 CI 失去诊断现场。

4. 测试镜像提供固定入口

Chart 固定调用 /opt/spark-milvus/bin/run-integration-tests。测试镜像必须：

  • 使用 Java 21，并包含 Spark 4.0、已编译的 integration 测试和运行测试所需的依赖；
  • 包含同一份已验证的 storage/Knowhere 原生 bundle；当前默认调度到 amd64；
  • 包含 backfill 测试需要的 Python 与 pymilvus；
  • 以明确的数字 UID 非 root 用户运行，保证工作目录、sbt 缓存与临时目录可写；
  • 执行完整 integration40/test，并原样返回测试退出码。

发布用 Dockerfile 的 final stage 只有 Connector assembly，不能用作这个测试镜像。

5. runId 必须进入所有可变资源

Helm 已把 runId 传入 CI_RUN_ID，并用于测试写入前缀。测试代码还必须用它派生 collection、snapshot 和 writer 路径，并在结束时只删除本次运行拥有的资源。仅给每次运行换一个时间戳不能证明重试安全。

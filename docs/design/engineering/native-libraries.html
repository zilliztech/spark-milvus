独立 CMake 构建，统一 JAR 交付

目标是让读取文件的 milvus-storage 和执行向量搜索的 Knowhere 在同一个 JVM 中使用兼容的原生依赖，并把两者的链接、打包规则集中到 Spark-Milvus 自己的 CMake 工程中。所有 Conan 依赖使用固定的上游 recipe revision，集成所需的直接链接关系由本项目的 CMake 目标声明，最终随一个 JAR 交付。

2026-09-17：milvus-storage 7eb13578 与上一 Knowhere pin 1fff20db 的统一原生包已完成 Docker 构建、两个 JNI 加载顺序、实际 JNI 功能和只读真实数据验收。该 native JAR 的 SHA-256 为 838d8adef6bb660cc7f3d8024967214c67c105eee01b8f77ad4c189071de5bdf。当前 Knowhere gitlink 已前进到 29210a33，本次推送没有为该 pin 重建统一原生包，上述结果不能登记为当前 gitlink 的验收。负责人要求以实际 JVM 加载成功为准；五个依赖库的逐库重定位失败保留作诊断，不登记为通过。native-build/dependencies.json 继续固定上游 Conan recipe revision，独立 CMake 声明两个引擎的链接关系，仓库不维护自有依赖 recipe。旧源码与旧 recipe 的结果只作为历史证据。验收结果与限制见第 10 节。

为什么改收益与代价构建范围CMake 目标依赖与符号JAR加载现有改动实施顺序验收

1 为什么要改

两个引擎需要在同一个进程中共同运行，但分别构建的产物可能带入不兼容的公共依赖。例如一次索引查询先通过 storage 读取索引文件，再调用 Knowhere 加载和搜索。两个 JNI 库都进入 executor 的 JVM；操作系统动态加载器会按库名和符号解析依赖，Java 包名以及 JAR 所在目录不能隔离这些原生依赖。

早先的产物已经出现过两种具体失败：先加载 storage，Cardinal 复用了缺少 gotoblas 符号的 common；反向加载，storage 的 gRPC 初始化代码绑定到了 Knowhere common 中的全局对象和注册函数，导致进程退出。后一种失败中两边的 gRPC 版本相同，区别在于静态嵌入和动态链接混用。定位证据属于外部验证材料，不作为仓库内链接。

统一依赖解决共同加载的问题；独立 CMake 让本项目直接维护所需的构建规则。此前统一依赖的产物已通过本机测试，但构建仍调用上游 CMake，并修改 storage 的链接依赖、符号导出和 Conan 版本。继续沿用这些修改，每次升级上游都要检查它们是否仍适用。两个引擎及 JNI 的编译目标现在由本项目定义；上游提供算法、存储和 JNI 源码，本项目统一决定它们如何链接和交付。

2 能获得什么收益，需要承担什么

预期收益体现在依赖一致性、修改归属和交付方式上；每项都能通过构建产物或运行日志核对。

采取的做法具体收益如何确认
用一张 Conan 依赖图统一版本和编译选项，两个引擎链接同一套公共动态库编译使用的头文件与运行时依赖一致，减少同名不同实现被混用的情况；精确匹配 recipe revision、配置和 package ID 的 Conan 包可以复用。核对最终依赖图、编译与链接命令、实际加载文件及其摘要。
在自己的 CMake 中定义两套引擎、JNI 的链接关系和符号规则本项目的集成要求集中在一个工程中，构建相关修改可以移出 storage 上游；排查问题时可以直接找到控制该库的目标定义。上游构建文件没有 Connector 的链接修改时，新工程仍能编译；上游差异仅保留明确需要的 Java 加载接入。
一个原生资源 JAR，共享一次完整解压每种公共库只交付一份，避免两个原生包分别携带、解压自己的副本；部署时随 Connector assembly 分发。检查 JAR 内容，以及两种加载顺序和并发初始化时实际使用的目录。
固定源码、依赖和配置，并保留产物摘要后续可以确认测试和部署使用的具体版本组合，升级失败时能对照变化；每个直接依赖都固定完整的上游 recipe revision。对照来源清单、直接依赖引用和锁定文件，在干净输出目录重新构建并测试。

代价是维护引擎的构建定义。升级 storage、Knowhere 或 Cardinal 时，我们要核对新增源码、编译宏、Rust/CXX 和 JNI 生成步骤，以及 CPU 指令集选项。统一版本仍需重新编译并验证双方兼容性；内部静态依赖仍需要限制符号导出。独立 CMake 和合并 JAR 本身不会自动完成这些工作，也不替代 Java 加载器的接入。

本方案不改变查询算法，因此不承诺搜索更快。减少重复库有助于减少重复交付和解压，但 JAR 大小、启动耗时及构建耗时的变化需要在新产物上测量。

3 构建范围由我们自己的 CMake 决定

native-build/CMakeLists.txt 是唯一原生工程入口。它用 add_library、target_link_libraries 和 install 定义目标；不通过 add_subdirectory 或另一次 cmake -S 执行 storage、Knowhere、Cardinal 及其内嵌算法工程的 CMake。第三方依赖包由 Conan 构建，Rust crate 由 Cargo 构建，它们继续使用各自的构建系统。

范围是现有 R4、V1、V5 的原生运行时。复用上游 C/C++、C API、JNI 和 Java/Scala API，保持现有方法签名与库文件名；不另写 JNI，不改变查询、过滤、回表或读写语义。源码构建目标为 Linux x86_64，与当前真实实例测试环境一致。

构建每次在新的候选目录收集和验证动态库。原生 C API 测试与两种顺序的实际 JVM 加载通过后，才把候选目录移为 bundle/；逐库 ELF、重定位和 ctypes 检查保留原始诊断结果，不阻断。旧成功目录移入历史目录，失败候选保留诊断信息。相同输入可以重试，失败不能覆盖上次可用的包。输入变化继续要求新工作目录。

Linux x86_64 默认使用统一构建。其他平台在没有显式指定统一包时保留已有 storage 构建入口，不声明向量库共同加载已经验收；Linux aarch64 可以显式提供匹配平台的统一包。Make 与 Docker 按同一规则选择，源码构建的平台限制不废弃其他平台已有的 storage 使用方式。

构建责任与常见的 CMake target/install 用法一致：依赖解析产生可链接的目标，CMake 编译并安装原生产物，JAR 打包处理资源，Java 负责解压与加载。

4 接管目标及生成步骤

一个入口可以包含几份按引擎划分的 CMake 文件。每个目标的源码、生成文件、编译定义与直接依赖都在所属文件中声明，避免把同一规则分散到 Python、CMake 和 sbt。

位置负责的目标与步骤
native-build/CMakeLists.txt平台、工具链、依赖查找、两个引擎及安装目标。校验输入的源码提交、特性配置和依赖锁定文件。
native-build/cmake/Storage.cmake编译 milvus-storage、milvus-storage-jni。按上游 Cargo.lock 构建 Rust 静态库，生成 Rust/C++ 互调所需的 CXX bridge 源码和头文件；复用固定版本的 Corrosion 工具调用 Cargo。生成文件全部放入构建目录。
native-build/cmake/Knowhere.cmake编译 knowhere、knowhere_c、knowhere_jni 及使用的 Faiss、DiskANN 源码；用上游 Java 声明执行 javac -h 生成 JNI 头文件。保留不同 CPU 指令集源文件的独立编译选项，不把最高指令集选项应用于整个工程。
native-build/cmake/Cardinal.cmake按同一 Knowhere 提交指定的版本编译 libcardinalv1.so、libcardinalv2.so，声明插件与父引擎的接口和公共依赖。真实 UAT 索引验收使用启用 Cardinal 的产物。
native-build/cmake/Install.cmake 与符号清单安装引擎、JNI、插件及非系统依赖，设置相对库搜索路径，保留动态库版本名别名；控制内部静态依赖的符号导出。

源码由 superproject gitlink 固定：storage 子模块当前为上游 main 的 7eb13578，Knowhere 子模块跟随 LawrenceTL92/knowhere-contrib 的 codex/knowhere-jni-pr 分支并固定在 29210a33；Cardinal 使用该 Knowhere 提交声明的 v2.5.112 / v3.0.8。最近一次验收产物记录的是 storage 7eb13578 和 Knowhere 1fff20db，更早的历史产物记录的是 storage 5689301 和 Knowhere 9dc2b8ad；二者都不能在未重建时改写为当前提交。任一子模块更新时，Java API、原生构建来源和 provenance 必须一同更新。外部构建不往上游源码目录写补丁或生成文件。

构建保持当前特性集合：storage 的 S3、Azure、GCP、Vortex、Lance，Knowhere 的 DiskANN 与可选 Cardinal；FIU、CRT、Talon 关闭，Arrow 的 jemalloc 关闭。编译原生格式依赖不等于新增 Connector 对应能力。这组配置用于验证构建方式，不扩大 Connector 能力。

5 Conan recipe 与版本选择

Docker 使用 BuildKit 的 cache mount 保存 Conan 包、Cargo 下载的 registry/git 源码和 ccache；挂载使用 sharing=locked，避免并行构建写同一份缓存。Conan profile 与 remote 在挂载后初始化，空缓存也能完整构建。失败的 RUN 不会形成可复用镜像层，因此不能仅靠镜像层保存这些已完成的依赖；缓存复用仍由 Conan 的 revision/package ID、Cargo 和 ccache 的校验决定。引擎源码快照、CMake 输出和 Cargo 编译产物留在本次工作目录，不共用同一份原生构建状态。

native-build/dependencies.json 固定统一图中每个直接依赖的完整上游 Conan reference，包括 recipe revision。recipe 是 Conan 描述一个包如何获取、编译和被使用的配置。native-build/conanfile.py 把这些 reference 以 force=True 放进一张 host 依赖图；构建不从缓存导出、打补丁或改写 recipe，也没有仓库自有 recipe 目录。Conan 只在 recipe revision、配置和 package ID 都匹配时复用缓存二进制。

build.py 从两个 gitlink 固定的上游 conanfile.py 读取依赖声明，dependency_versions.py 将它们与 dependencies.json 比较。任何未登记的上游依赖、无法判断顺序的冲突版本，或没有选择两边较新要求的版本都会在 Conan 解析前失败。同一 profile 固定编译器和共享库选项；完整 lockfile 再固定直接与传递 recipe revision，解析后的 host 与 build graph 必须全部出现在 lock 中。

按用户要求，冲突版本在固定的上游输入中选择较新者，不自动追随远程最新版本。版本号按版本规则比较；以 Git 提交命名的版本按提交历史和接口要求确认先后，不按哈希字符串排序。当前已核对的选择为：

外部 NATIVE_WORK_DIR/provenance/ 记录 dependencies.json 摘要、两份上游依赖声明摘要、版本选择结果、直接 reference、完整 Conan lock、解析后的 package reference、package ID 与完整 graph。--conan-lock 接受前一次审核过的完整锁定文件，新目录构建时继续使用其传递依赖版本和 recipe revision；锁定文件与当前直接依赖不一致时失败。首次没有指定锁时允许解析并输出锁，后续应复用。Corrosion 按完整提交固定，显式提供的本地源码也要核对该提交及工作树状态；Rust 与 Cargo 版本一并记录。

  • 统一编译器、C++ 标准库 ABI（二进制调用约定）、构建类型及共享库选项。Arrow、Folly、OpenBLAS、gRPC、Protobuf 等公共依赖使用同一份动态实现；CMake 控制消费方的直接链接，依赖包自身的构建缺陷由固定的上游 recipe revision 修正。
  • prsbridge 只私有链接进入 storage 引擎，JNI 不再重复链接它。Rust 的 OpenSSL 使用公共动态库；内部 LZ4、XXHash、Zstandard、AWS-LC 的定义通过我们维护的链接符号清单限制导出，保留 loon_*、JNI 及公开 C++/CXX 接口。
  • 本项目的动态库目标声明直接依赖，安装副本用 $ORIGIN 查找自身目录内的库；不修改 Conan 缓存中的文件。部分上游依赖需要由 JNI 入口的完整依赖集合提供符号，当前以两个真实 JVM 加载顺序验证这一运行环境，不要求每个依赖独立加载。SONAME 是动态加载器使用的库标识，同一 SONAME 对应不同内容时打包失败，不能按文件名覆盖。
  • glibc、动态加载器、libstdc++、libgcc_s 和 libz.so.1 使用目标系统版本。现有 JVM 已加载系统 zlib，包内不再放第二份。其他非系统依赖按完整依赖关系收集，包括实际需要的编译器运行库；记录系统库最低符号版本要求。

统一动态依赖解决两个引擎之间的重复实现；符号隐藏处理无法移出的内部静态实现。该设计不承诺与同一 JVM 内任意其他 JNI 库兼容：进程已加载不兼容依赖时，仍需定位实际符号提供者。Cardinal 的 CPU 编译选项必须记录；第一轮沿用已验证主机环境，不把 linux-x86_64 宣称为任意 x86 CPU 的兼容保证。

6 一个原生资源 JAR，进入现有 assembly

CMake 把库安装到构建输出的 install/lib/，现有打包脚本校验后生成一个平台资源 JAR。该 JAR 包含两个引擎及其依赖，sbt 再把其资源合入现有 Connector assembly；用户通过 spark-submit --jars 使用最终 Connector JAR，不需要分别提供 storage 和 Knowhere 的原生 JAR。

保留资源路径 native/milvus/1/linux-x86_64/，其中放两个 JNI 库、引擎、Cardinal 插件、公共依赖和 manifest.properties。清单记录平台、源码提交、依赖配置摘要、CPU 要求、功能开关、库摘要与版本名别名；许可证随包交付。JAR 中的 provenance 只保留规范化的源码与 package 标识，以及 Conan lock、依赖 graph、构建输入和外部证据的摘要，不包含构建机绝对路径。完整 Conan graph、compile_commands.json、原生构建命令、CMake trace、构建日志和源码证据留在外部 NATIVE_WORK_DIR。

sbt 继续使用 -Dmilvus.native.bundle=/absolute/path/bundle.jar 选择和验证资源，不隐式启动 CMake 或 Conan。两个模块各自的旧原生资源在统一包模式下不参与 assembly；Java/Scala API 的编译仍由 sbt 负责。原生资源包保持无 Java 类，已有 native-runtime 随 Connector 的类一起交付。

打包前必须逐项核对实际库文件、别名、摘要与 provenance.json，并确认原生 C API 测试和两种 JVM 加载顺序通过；Cardinal 特性必须与实际插件一致。provenance 显式记录 auditPolicy=jvm-load 和两次 jvmLoadTests，不能把历史逐库审计当作 JVM 测试。混用另一次构建的库或来源记录时拒绝生成 JAR。打包与 sbt 解压后的验证都重新调用同一个 JVM 检查实现；sbt 缓存绑定 JAR、检查实现和 JRE 身份，运行时仍独立校验资源摘要。

assembly 合并原生资源时使用固定大小的缓冲区。单一来源直接交付原始输入流；同路径的多个来源逐个计算 SHA-256 和字节数，一致才保留一份，否则报错并列明来源。sbt-assembly 2.1.1 的通用 deduplicate 即使只有一个来源也会把整个文件装入内存；本地 storage 库约 478 MB，已实测在 4 GB 堆内触发内存耗尽。原生资源改用流式比较，保留冲突检查，最终打包已在相同堆上通过。受限堆回归用 64 MB 堆比较两份超过 512 MB 的输入，也验证内容冲突与异常关闭输入流。

这个插件版本遇到 CustomMergeStrategy 会关闭 assembly 产物缓存，因此重复执行 assembly 会重新合并打包。Scala/Java 增量编译、原生包验证缓存以及 Conan、ccache、Cargo 缓存不受影响；不绕过插件的缓存规则。

Make 与 Docker 共用 native-resources。Linux x86_64 默认构建统一包；其他平台没有显式统一包时保留 storage 构建。旧入口始终先运行增量构建再复制，即使库文件已经存在；Make 并行执行也遵守这个依赖顺序，避免修改源码后仍打包旧库。ARM 与 macOS 只验证了入口选择，没有执行统一原生构建或运行验收。

7 保留一个解压器，加载仍由上游 JNI 绑定发起

复用现有 native-runtime 模块中的 NativeLibraries，不新增模块。它是第 1 层的纯 Java 11 代码，不依赖 Spark、Arrow 或 JNI API；两个原生模块都依赖它，彼此不依赖。每个 driver 或 executor JVM 在首次使用时按平台解压一次。

  1. 定位唯一平台清单，把声明的所有库解压到进程私有目录并验证摘要，再向调用方返回路径。缺库、非法路径、重复资源、错误平台或损坏直接报错，不公开部分解压目录。
  2. storage 适配器 NativeStorageLibrary 从 native-runtime 取得共享目录内 libmilvus-storage-jni.so 的绝对路径，在 JVM 共享属性锁内临时设置 milvus.storage.native.path，再调用上游 NativeLibraryLoader；上游加载器校验该绝对路径并执行 System.load，调用成功或失败都恢复原属性。
  3. 向量适配器在 JVM 共享锁内临时设置 knowhere.native.path，由 Knowhere 初始化并加载同目录的 libknowhere_jni.so，成功或失败都恢复原属性。显式路径若指向另一文件则报错，不能覆盖用户配置。临时路径不能作为后续调用或另一个类加载器的用户配置遗留。

milvus-storage 的 Java 加载入口已经进入上游。NativeLibraryLoader 增加 milvus.storage.native.path：属性存在时必须指向已有的绝对文件，并在平台资源和系统库路径之前加载该文件；属性不存在时保留原有资源提取和 System.loadLibrary 路径。上游不依赖 Connector，也不改 JNI 方法、原生实现或现有版权头。Connector 的适配器负责在 storage API 首次使用前完成交接；统一包存在时，用户配置若指向另一文件，或上游加载器已在交接前完成加载，均直接报错，不能静默使用另一份库。该 Java 扩展及测试已通过 milvus-storage PR #690 squash 合入上游 main，合入提交为 7eb1357899a98c4875d51a55b135b7f8d79461ff；它与原 PR 提交 2ed8d933 的 patch-id 相同。根目录子模块和 superproject gitlink 均指向该 main 提交。上一统一平台 JAR 已按该 storage 提交与 Knowhere 1fff20db 重建，provenance 与第 10 节所列 JVM 和真实数据结果均来自这份产物；当前 Knowhere 29210a33 尚无对应的统一包。

解压锁只覆盖资源校验和文件操作，锁内不加载 JNI。动态加载器通过各库的依赖与 $ORIGIN 查找相邻文件，不逐个预加载依赖。解压缓存属于定义 NativeLibraries 的类加载器，多份隔离 Connector 类加载器不在支持范围；Knowhere 所需的 JRE libjsig 仍在 JVM 启动前配置。统一包存在但加载失败时不回到旧产物；迁移期间只有完全未选择统一包的构建才保留既有独立产物行为。

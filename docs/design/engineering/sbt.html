sbt 的原则与实践

构建配置要让维护者在模块声明附近看懂它依赖什么、如何编译和测试、是否发布；公共规则的影响范围应当由名字和调用位置说明。

本页把 AGENTS.md 的整体一致性原则落实到 sbt。modules.md 规定模块边界和兼容矩阵，本页规定如何表达这些约束。修改构建时使用仓库内的 spark-milvus-sbt skill。

1 以阅读成本判断设计

关键行为就近声明。 模块的代码依赖、是否发布、测试是否需要外部服务，应当在模块处可见。具体实现可以展开阅读，但不应靠逐层打开公共设置才发现一个模块被禁止发布。

共享同一种规则。 四条 Spark 线共用源码和构建方式，适合一个按线工厂。apps 和 integration 各只有一个实例，直接声明具体项目更容易阅读。若多个调用者应当一起接受规则变化，才有抽取的理由；少量重复可以保留。

名字说明效果。 Scala/Java 编译设置不应顺带改变发布策略。一个明确叫作 sparkFreeModuleSettings 的设置可以同时带入跨线编译基线、通用依赖和禁止 Spark 引用的检查，因为这些共同定义了第二层模块；发布开关仍写在使用处。

文件划分服务于理解。 大部分配置留在 build.sbt，公共值和构建实现可放在 project/*.scala，这是 sbt 官方建议。集中维护的价值在于一致性；一处使用的版本或坐标可以就地声明，不要求每个字面量都经过两层转发。既有文件的调整以实际阅读收益为依据。

声明按阅读顺序组织。 build.sbt 依次放导入与基础默认值、root 声明、按层排列的模块、运行配置、打包配置、发布配置。Spark 工厂紧邻各条线的声明，共享输入靠近首次使用处。发布段内依次放产物元数据、仓库与发布策略、root 的版本和凭据输入及发布实现；重排保持 ThisBuild 和项目作用域不变。

说明当前理由。 注释解释 scope、运行时约束和例外的退出条件。历史讨论进入 决策日志。缩短文件、减少重复行、增加注释都不能单独证明构建更容易理解。

2 三种关系分别表达

.aggregate 表示运行任务时覆盖哪些项目，.dependsOn 表示使用哪些项目的代码，.settings 表示应用哪些配置。聚合不会传递代码或公共配置。共享默认值由 ThisBuild 提供，项目设置可以覆盖它；root 是普通项目，不是其他项目的配置父类。见 多项目构建 和 作用域。

Compile、Test 和具体 task 的 scope 要按实际用途写出。复制设置时先确认它原来属于哪个项目与 scope，尤其是 fullClasspath、javaOptions、publish 和 assembly。共享设置需要使用当前项目的目录时，在应用该设置的项目里求值；仓库级输入才取 ThisBuild / baseDirectory。

3 模块声明的写法

普通模块使用 project.in(file(...))，项目 ID 由 lazy val 的变量名推导。变量名与既有 ID 不同，或工厂需要按参数生成 ID 时，使用 Project(id, base)；例如 nativeStorage 的 ID 是 native-storage，不能直接用变量名替代。简化声明时保持项目 ID 和目录不变。

第二层模块把边界约束和发布策略分别写出，例如：

lazy val compat = project.in(file("compat"))
  .dependsOn(core)
  .settings(
    name := "compat",
    moduleName := "spark-milvus-compat",
    Modules.sparkFreeModuleSettings,
    Modules.jacksonPin,
    publish / skip := true,
    libraryDependencies ++= Seq(/* this module's dependencies */)
  )

Spark 的四个项目保留显式名称，通过一个 sparkProject 工厂应用同一规则。工厂定义里显示代码依赖、共享源码目录、发布策略和依赖组合。增加一条线时，同时加入版本矩阵、项目声明和 root 聚合列表；显式登记便于核对覆盖范围。

apps 和 integration 使用具体项目声明，目录、代码依赖和所属 Spark 线就近可见。integration 使用普通 Test 配置，并在 root 的聚合列表之外；调用 integration40/Test/compile 编译，调用 integration40/test 才运行需要 Milvus、MinIO 的测试。

共享源码的路径直接写在对应源码设置旁边；单纯拼一次路径不需要一个包装函数。测试 JVM 选项会被多个项目共同使用，保留有明确用途的设置片段。

4 版本与依赖的写法

Spark、Scala、Java、Arrow、Hadoop、Netty 的兼容矩阵在 Versions 中统一维护，具体取值遵循 模块约束。修改一项时核对同一行的运行环境，不能用另一连接器的配置代替 Spark 发行版的实际依赖。

Hadoop 和 Netty 每条线各钉自己发行版的版本，并以 dependencyOverrides（Dependencies.lineOverrides）压住整个 classpath，不只是直接依赖。原因是 Arrow 的 Netty 分配器读 Netty 的内部结构：Arrow 12 按 Netty 4.1.82 编译，直接读 PoolArena 从 SizeClasses 继承的 chunkSize；Netty 4.1.118 起 PoolArena 不再继承 SizeClasses，第一次分配 buffer 就抛 NoSuchFieldError。3.5 线原来共用 4.0 的 Hadoop 3.4.1，它和 AWS SDK 一起把 Netty 抬到 4.1.118，3.5 线在测试 classpath 上一行数据都读不了（工作单 19，2026-09-16）。Netty 全家族压到同一版本，避免 buffer 与 handler 版本混搭。层 2 自己的测试仍用 Versions.hadoop。

CALL 的文法 spark-base/src/main/antlr4/MilvusCall.g4 一份,sbt-antlr4 在每条 Spark 线上按本线的 antlr 版本生成解析器到 target(Antlr4 / antlr4Version := l.antlr),生成物的包名固定,共享源码对着它各编一次;antlr 运行时改标 provided,跑的是 Spark 自带的那份(3.5 线 4.9.3,4.x 4.13.1)。这是决策 17 的落地。

3.5 线还有一条 JDK 约束：Arrow 12 的 MemoryUtil 反射找 DirectByteBuffer(long, int)，JDK 21 把它改成了 (long, long)，第一次经 C Data Interface 分配就抛 UnsupportedOperationException。单元测试不走这条路，仍在 JDK 21 上跑；UAT 场景套件在 3.5 线要用 JDK 17，SPARK35_TEST_JAVA_HOME 指到它，spark35 的 Test / javaHome 只在设了这个变量时生效。

Dependencies 集中共享坐标和需要一起维护的依赖组合；模块特有的依赖可以直接写在模块声明中。组合的名字要说明用途，不能仅因两个模块碰巧有相同的列表，就把它们绑定为同一种规则。

依赖声明要能解释三件事：编译用什么、运行时由谁提供、是否进入交付的 JAR。provided 和 Test 属于契约。Jackson 对齐只用于 core、compat、client，Spark 线使用自身的一组运行时依赖。整理配置时保留已有的版本、scope 和 exclusions，版本升级单独说明原因和验证依据。

native-storage 从固定的 milvus-storage/java/src/main 编译上游 Java/Scala 绑定，使用 Modules.sparkFreeModuleSettings 交叉编译 Scala 2.12/2.13，Arrow 按 4.0 线编译并标为 provided。不引入上游 sbt 项目或仅支持 Scala 2.13 的预编译 JAR。Compile / sourceGenerators 用 Sync 将上游源码复制到 sourceManaged，格式化不触及子模块原文件；清理仅作用于该任务曾生成的副本。初始化子模块是编译前提。

存储 JNI 和 NativeLibraryLoader 均归上游；资源打包 libmilvus-storage-jni、storage 引擎及依赖，不再构建或加载 libnative-storage-jni。该迁移已有 Scala 交叉编译、单元测试、原生加载及真实 UAT 结果；严格 JNI 告警与最终打包运行的边界见存储 I/O 验收状态。

native-vector 的 Knowhere API 尚未发布到公共 Maven 仓库，因此由 KnowhereBuild.settings 直接编译根目录 knowhere 子模块的 java/src/main/java。子模块跟随 PR #1829 的分支，superproject gitlink 固定精确提交；普通构建不下载源码归档，未初始化子模块时直接给出初始化命令。生成的 Java 11 API JAR 作为编译依赖传递给 core，缓存键包含 gitlink revision。 原生引擎由显式脚本构建，平台 JAR 通过 knowhere.native.jar 选择并验证来源和摘要。它只含资源，通过 Compile / unmanagedJars 随模块依赖传递到 core、Spark 的运行时及 assembly；只放 Runtime 会在现有项目间编译依赖映射中丢失。普通编译和单元测试不隐式启动 Conan/CMake。 knowhereSmoke 单独验证实际 JAR 加载，不能用未执行 smoke 的普通 UT 代替原生运行验证。操作命令见 构建说明。

统一平台包通过 -Dmilvus.native.bundle=/absolute/path/bundle.jar 选择，由 native-runtime / validatedNativeBundle 统一验证并传递资源。类路径、verifyNativeBundle 与向量模块的验证命令依赖同一任务，使用同一个解压目录和缓存。它与 knowhere.native.jar 互斥；选择后 storage 的旧 native resources 不进入 classpath，避免产生第二个目录。两个绑定都依赖纯 Java 的 native-runtime，不互相依赖。独立 CMake 构建使用 dependencies.json 固定的全部上游 recipe revision，在 CMake 目标中声明集成链接关系后产出该包。旧自有 recipe 实现下 Knowhere 9dc2b8ad 的 Cardinal 验证结果保留为历史；上一 1fff20db gitlink 的原生包已重建，JVM 与真实数据结果见第 6 节。当前 gitlink 为 29210a33，本次推送没有为它重建统一原生包。迁移前按 storage-compatibility*.properties 复制资源的办法只保留为历史路径，不参与统一包。

5 root 的交付职责

root 在模块声明处明确承担仓库任务聚合和迁移期的 assembly 交付；主 Maven JAR 绑定到 assembly，assembly 与发布都不向子项目聚合。子模块是否发布在自己的声明处可见。

root 的运行参数、assembly 规则、发布元数据分别使用 rootRunSettings、rootAssemblySettings、rootPublishingSettings 三个命名片段，并在 root 声明处应用。片段保留在同一份 build.sbt 中，维护者可以按职责展开，不引入额外的项目、插件或配置框架。片段内的设置继承应用处的项目作用域，避免在文件尾部继续追加离散的 root / ... 覆盖。

原生资源采用 NativeBundle.nativeMergeStrategy：单一来源直接传递输入流，重复来源用固定缓冲区计算 SHA-256 和字节数，内容不同则失败。不能用通用 deduplicate 将数百 MB 的动态库整体缓冲到堆内。sbt-assembly 2.1.1 的 CustomMergeStrategy 会关闭 assembly 产物缓存，重复 assembly 会重新打包；增量编译和原生构建、验证缓存保持有效。受限堆回归及实际 4 GB 堆打包结果见原生资源设计。

迁移期仍保留以下交付条件：

  • 根产物沿用现有 spark-connector 坐标、带分支与架构的版本，以及 Docker 查找的 assembly 文件名。分线发布契约和下游迁移验证就绪后，再替换这一交付入口。
  • legacyRootDeps 保留旧根产物的依赖声明；legacyRootArrow 只说明该声明的来源，最终解析版本还受依赖图影响。它不作为 Spark 线的 Arrow 基线。
  • legacyJni 与上游预编译 Scala 2.13 JAR 于 2026-09-12 移除。2026-09-16 改为从上游源码按当前 Scala 版本编译，新绑定的 Scala 2.12 交叉编译已通过；旧 unmanaged JAR 不恢复。
  • Maven POM 排除已嵌入、尚未独立发布的模块依赖，外部依赖保留。JAR 内容和依赖元数据分别核对；Maven POM 的处理不能证明本地 Ivy 发布也正确。

版本中的分支名优先取 GIT_BRANCH，否则执行 git rev-parse --abbrev-ref HEAD。这个 Git 子进程单独清空 LD_PRELOAD，防止为 JVM 预加载的 libjsig 在 Git 的标准输出中打印警告并混入版本号；sbt JVM 及测试 JVM 的预加载环境保留。修复发生在子进程环境，不过滤 Git 输出，也不要求手工设置分支名。

6 如何检查一次整改

先固定当前提交和工作区差异，再比较修改前后的项目 ID、目录、dependsOn、聚合成员、依赖版本与 scope、测试输入以及交付坐标。多人同时工作时以固定基线核对，保留期间出现的新提交和无关改动。

每次提交前先格式化，再检查格式，包括只改文档的提交。 CI 检查整个聚合项目集合，只改文档也会遇到已有源码的格式错误。四条 Spark 线共享 spark-base，格式化任务必须串行执行，避免同时写同一个文件；格式检查通过后仍须审查差异，空文件也可能通过格式检查。命令、聚合之外的 integration 项目和构建文件的补充检查统一维护在 contributing.md 的 Formatting 一节，由 sbt skill 执行。格式修复不混入无关功能改动，git diff --check 不替代 Scalafmt 检查。

格式检查通过后，每次提交前必须在 Java 21 下运行根项目的完整单元测试，包括只改文档的提交。 测试任务所需的源码与测试编译属于这项验证；开发时的 testOnly 不能替代完整运行。测试失败、套件中止或运行未完成时不得提交，修复原因后重跑完整测试。不得通过新增排除、过滤、忽略或取消条件让结果通过。既有原生库和 UAT 环境条件导致的取消要逐项说明原因，并如实报告测试及套件数量；取消不等于通过。命令及结果记录要求统一维护在 contributing.md 的 Unit tests 一节。

根项目聚合不含需要真实 Milvus、MinIO 的 integration40。额外的 Scala 交叉版本检查、集成测试、原生库构建与发布仍按任务范围和授权执行。若执行了 show、inspect、makePom 或编译测试，应分别记录它们验证了什么。静态等价、构建加载、Maven 解析和实际 Spark 运行是不同层次的证据。

审查时用具体维护动作检验可读性：增加一条 Spark 线、修改一个模块的依赖、判断一个项目是否发布。若仍需追踪多个含糊的 helper 才能作答，应先修正这些关系的表达。发布入口、能力、公共类型和测试的删除遵循 AGENTS.md 的说明与授权要求。

选择统一平台包时，NativeBundle.validate 核对平台、manifest、每个实际库和版本名别名的路径、长度及 SHA-256；provenance 固定 storage、Knowhere、Cardinal 源码 revision、Conan lock 摘要、规范化的直接上游 recipe reference、依赖 graph 摘要和库来源，不包含构建机绝对路径。完整 Conan graph、编译命令和 CMake trace 留在外部 NATIVE_WORK_DIR。旧自有 recipe 实现下的 Knowhere 9dc2b8ad Cardinal 包核对了 164 个库和 173 个别名；资源 JAR 的 SHA-256 为 4bc2488e9f38f590f9346b27a34725f4d63bddd1b518740784ad0d32c8c54c5e。

原生库验收以实际 JVM 加载为准：staging、打包和 sbt 共用 native-build/jvm_load.py，在两个独立 JVM 中分别按 storage-first 和 Knowhere-first 顺序执行两次 System.load，要求两次调用完成、顺序标记一致且进程正常退出。检查进程清空额外的 LD_LIBRARY_PATH、LD_BIND_NOW 和 JVM 注入参数，只预加载自身 JRE 的 libjsig。库文件清单、来源、架构、别名和摘要仍须通过校验；逐库 ldd -r 和 dlopen(RTLD_NOW | RTLD_LOCAL) 结果保留作诊断，不再阻断构建。跨平台包必须在对应架构执行 JVM 加载检查。

最终 assembly 还要分别执行 storage-first、Knowhere-first 和并发初始化，确认两个绑定从同一个解压目录加载并完成文件访问与实际搜索。现有功能测试设置 LD_BIND_NOW=1，但 JVM 加载原生库时可能选择延迟绑定，不能据此声称所有函数符号都已解析。System.load 成功仅证明加载期间触发的重定位、初始化函数和 JNI_OnLoad 成功；真实实例的索引反序列化、搜索和回表必须单独验收。历史 Knowhere 9dc2b8ad Cardinal 组合已通过三种初始化方式和真实十万行查询；该批次没有重跑开源 Knowhere 变体。storage 7eb13578 与上一 Knowhere pin 1fff20db 已用 native JAR SHA-256 838d8adef6bb660cc7f3d8024967214c67c105eee01b8f77ad4c189071de5bdf 通过两个 JVM 加载顺序、实际 storage/Knowhere JNI 功能、打包后并发初始化，以及 Spark 4.0.1 的十万行只读快照和三组 Cardinal 持久化索引查询。根测试为 1,132 项成功、0 项失败、105 项取消，sbt 退出 0；其中一项旧 HadoopEndpointSnapshotTest 绕过统一加载适配器，令额外严格取消检查退出 1，不能记为全部单元测试通过。真实 UAT 使用 Spark 默认依赖顺序；assembly 优先时仍会混用 Jackson Databind 2.18.0 与 Scala module 2.17.3，本轮没有修复该打包问题。这些结果不覆盖当前 Knowhere 29210a33 gitlink。

KnowhereBuild.settings 从 NativeBundle.validatedNativeBundle 已校验的 bundle metadata 读取 with_cardinal，生成 META-INF/milvus/knowhere-runtime.properties。运行时由 NativeVectorLibrary.RuntimeInfo.cardinalSupported() 读取；没有选统一平台包或使用任意 knowhere.native.path 覆盖时不声明 Cardinal 能力。迁移前的 KnowhereBuild.storageSettings、storage-compatibility*.properties 和从 Knowhere JAR 复制共享库的流程只适用于旧独立产物，其历史记录不作为统一包的兼容证明。

开发容器：一条命令配齐编译、打包、测试环境

开发容器用的镜像就是根目录 Dockerfile 里装工具链的那一段：把它拆成独立的 toolchain 阶段，Jenkins 构建和开发容器都从这一个阶段出发，开发机用 docker build --target toolchain 在本地构建它，不发布镜像。开发者打开仓库选"在容器中重新打开"，或运行 scripts/devcontainer.sh up，就得到 Conan 2.25.1、CMake 3.27.5、GCC 12、Rust、JDK 21、Scala 2.13.16、sbt 1.11.1 齐备的 shell，加上持久化的依赖缓存和一套本地 Milvus 与 MinIO。

状态：2026-09-20 已实现，验证见第 5 节。参考对象是 Milvus 仓库的 docker-compose.yml builder 服务、.env、scripts/devcontainer.sh 与 build/builder.sh。镜像不推远端、产物随源码目录 bind mount 留在宿主机，这两点记在设计索引第 6 节决策日志。

1 Milvus 的做法，取什么、不取什么

先说两个项目交付物的差别。Milvus 是一个服务，交付物是镜像，所以它既发布运行镜像也发布环境镜像，镜像仓库本来就在它的发布路径上。Spark-Milvus 交付的是一个 JAR：spark-connector-assembly-*.jar 经 sbt publish 进 Maven 快照仓库，用户用 spark-submit --jars 引用它。Docker 在这里只是构建环境，根目录 Dockerfile 的 final 阶段只为了能把 JAR docker cp 出来，发布流水线不推它。开发容器沿用同一判断：镜像是工具，不是产物，不进任何仓库。

Milvus 没有 .devcontainer/ 目录。它的开发容器是 docker-compose.yml 里的 builder 服务：镜像 milvusdb/milvus-env:<os>-<日期-提交> 由 build/docker/builder/cpu/<os>/Dockerfile 构建并发布，版本号写在检入的 .env 里；源码 bind mount 到容器里的仓库路径；ccache、Go module、Conan 2、VS Code 扩展四个缓存挂在宿主机 .docker/<arch>-<os>-* 目录；depends_on 拉起 etcd、MinIO、Pulsar、Azurite、假 GCS。scripts/devcontainer.sh up 用 awk 把 compose 文件里的 build 和 command 段注释掉、把 user 换成宿主 uid:gid 后 up -d，VS Code 再 attach 到运行中的容器；build/builder.sh 在同一镜像里跑一次性命令，是 CI 的入口。入口脚本按当前 uid 往 /etc/passwd 补一行，任意 uid 都能有 HOME。

Milvus 的做法本方案原因
环境镜像单独一个 Dockerfile，日期版本写在 .env不发布环境镜像。镜像是根目录 Dockerfile 的 toolchain 阶段，每台开发机本地构建一次，之后靠 Docker 层缓存工具链只能有一份定义。今天 Jenkins 用根目录 Dockerfile 构建发布，开发容器若另写一份，两份会各自漂移；build.html 第 2 节的版本表以 Dockerfile 为准。我们交付 JAR 不交付镜像，没有现成的镜像发布路径可搭，发布环境镜像要新增仓库、凭据和标签簿记；工具链改动少，本地重建是一次性成本
compose 里的 builder 服务 + awk 改写 + VS Code attachcompose 里的 dev 服务 + .devcontainer/devcontainer.json 引用它；CLI 用户走 scripts/devcontainer.shdevcontainer.json 是 VS Code、JetBrains Gateway 和 GitHub Codespaces 共同读的规范，uid 映射、扩展安装、attach 都有原生字段，不需要 awk 生成第二份 compose 文件
缓存挂宿主机目录 .docker/缓存用 Docker 命名卷，名字带架构；target/ 随源码 bind mount 留在宿主机Conan、sbt 缓存是海量小文件且宿主机不需要看，放命名卷在 macOS 上快。产物要挂回代码目录：assembly、原生 bundle 和测试报告在宿主机 target/ 下直接可用，与不用容器时一样
依赖服务 etcd、MinIO、Pulsar、Azurite、假 GCS只有 Milvus standalone 与它自带的 etcd、MinIO，放在 compose profile services 里按需拉起Connector 的集成测试只需要 Milvus 19530 与 MinIO 9000；Azure 与 GCS 路径由 UAT 实例验证，不在本地模拟
多个 OS 的 builder Dockerfile、GPU 变体不做发布只有一个基础镜像 spark:4.0.1-scala2.13-java21-python3-ubuntu，没有 GPU 路径
入口脚本补 /etc/passwd取。dev 阶段建用户 dev，uid、gid 由构建参数 DEV_UID、DEV_GID 决定；scripts/devcontainer.sh 从 id 取值，IDE 直接启动 compose 时用 .env 里的默认 1000 或 shell 导出的值；入口脚本只在 uid 不在 passwd 里时补一行bind mount 的源码目录必须以宿主 uid 写，否则 target/ 产物和容器里改写的源码在宿主机上归 root

2 方案：一个工具链阶段，两个使用者

两个使用者都 FROM 同一个阶段；绿色是本方案新增的部分，蓝色是今天已有的发布路径，只改基础来源。GitHub Actions 的 ci.yml 不在此方案内，保持现状。

拆阶段不改行为。今天 Dockerfile 的 builder 阶段先装工具（apt、CMake、Conan、Rust、SDKMAN），再 COPY . . 并构建。把 COPY . . 之前的部分命名为 toolchain 阶段，builder 改为 FROM toolchain AS builder，镜像层内容不变，Jenkins 的构建命令与产物不变。开发容器用 docker build --target toolchain 在本地构建它。

镜像不发布。compose 的 dev 服务只有 build（context 为仓库根，target 为 toolchain），没有 image 来源。第一次 up 在本机构建，Dockerfile 的工具链部分不变就命中 Docker 层缓存；Dockerfile 变了，下一次 up 重建，与 Jenkins 用同一份定义。没有镜像仓库、发布凭据和标签簿记要维护。.devcontainer/.env 只放 Milvus、etcd、MinIO 三个服务镜像的标签。

容器里的目录与环境变量和 builder 阶段一致。源码在 /workspace，CONAN_HOME、CCACHE_DIR、CARGO_HOME、RUSTUP_HOME、SBT_OPTS=-Xmx4g -Xms2g 与 Dockerfile 相同；PATH 上第一个 java 是 JDK 21，所以 Makefile 由 which java 反推的 JAVA_HOME 正确，Conan 只有 2.25.1 一个。Conan 的 profile 与 remote 在容器首次启动、缓存卷为空时初始化，命令与 Dockerfile 的 conan profile detect 和 conan remote add default-conan-local2 相同。NATIVE_JOBS 默认按容器可见的 CPU 数取，不再是 50，因为开发机通常给 Docker 的 CPU 少于 CI 节点。

缓存是命名卷，产物留在源码目录。compose 项目 spark-milvus-dev 下的 conan2、ccache、cargo-registry、cargo-git、coursier、ivy2、sbt 七个卷与 Jenkins 缓存目录（build-image.groovy 里 cache-init 建的七个目录）一一对应，分别挂在 /home/dev 下对应位置；dev 阶段预先建好这些目录并归 dev 用户，Docker 初始化空卷时复制这份归属，非 root 用户才写得进去。一台机器上只有一种架构的容器，卷名不带架构。target/ 不单独挂卷，它就在 bind mount 的源码目录里：target/scala-2.13/spark-connector-assembly-*.jar、target/native-build/<平台>/ 和测试报告在宿主机上直接可见。代价是 macOS 上 target/ 的读写经过文件共享，sbt 增量编译比 Linux 宿主慢；接受这一点换取产物位置与不用容器时一致。缓存卷不随容器删除而消失，scripts/devcontainer.sh clean 才删。

本地服务与测试共享网络命名空间。integration-4.0 里的 Milvus 地址写死为 http://localhost:19530，MinIO 为 9000。compose 里 milvus、etcd、minio 三个服务设 network_mode: "service:dev"，它们的端口就出现在开发容器的 localhost 上，测试代码一行不改。三个服务放在 profile services 里，只跑单测和原生构建时不拉起。

3 文件

.devcontainer/
├── devcontainer.json       dockerComposeFile 指向下面的 compose；service: dev；runServices: [dev]；workspaceFolder: /workspace
│                           remoteUser: dev；overrideCommand: false；shutdownAction: stopCompose
│                           customizations.vscode.extensions: scalameta.metals、ms-vscode.cmake-tools、
│                             rust-lang.rust-analyzer、ms-python.python
│                           postCreateCommand: scripts/devcontainer.sh init --inside（子模块、Conan profile/remote）
├── docker-compose.yml      dev（build: context=..，target=dev，args DEV_UID/DEV_GID；user 同值；entrypoint 指向下面的脚本；
│                             volumes: ..:/workspace（含 target/）与七个缓存卷；command: sleep infinity）
│                           etcd、minio、milvus（profiles: [services]，network_mode: service:dev，各一个数据卷）
├── entrypoint.sh           uid 不在 /etc/passwd 时补一行、保证 HOME 存在，然后 exec 命令
└── .env                    MILVUS_IMAGE、ETCD_IMAGE、MINIO_IMAGE 三个服务镜像的标签，DEV_UID、DEV_GID 默认 1000
scripts/devcontainer.sh     up [--services] | init | shell | run [--env-file F] <cmd…> | down | clean
                            从 id 取 DEV_UID、DEV_GID 传给 compose；run 用登录 shell，NATIVE_JOBS 默认为容器可见 CPU 数，上限 50（build.py 的 --jobs 范围）
Dockerfile                  builder 阶段拆为 toolchain（工具）、dev（用户、HOME 下的缓存目录、NATIVE_JOBS 默认值）、builder（COPY 与构建）三段
.dockerignore               排除 **/target，本地 docker build 不再把构建产物送进上下文

改动都在这几处；Makefile、build.py、sbt 构建不变。docs/contributing.md 的环境一节改为先指向开发容器，本机私有工具链前缀降为备选。

4 开发者怎么用

要做的事命令说明

CLI：scripts/devcontainer.sh up && scripts/devcontainer.sh shell		首次在本机构建 toolchain 阶段；init 初始化子模块与 Conan 配置

单元测试与格式检查sbt test；sbt 'set Global / concurrentRestrictions += Tags.limitAll(1)' scalafmtAll scalafmtCheckAll与 contributing.md 一致；JDK 21 是容器里唯一的 Java
集成测试scripts/devcontainer.sh up --services，然后 sbt integration40/testMilvus standalone 与 MinIO 在 localhost 的 19530、9000
UAT 场景套件scripts/devcontainer.sh run --env-file ~/.spark-milvus-uat.env sbt spark40/testMILVUS_UAT_* 与 AWS_* 变量从容器外的文件传入，不检入、不写进 compose
验证 Dockerfile 全量构建宿主机 docker build --build-arg PUBLISH_MAVEN=false .这一步在容器外，与 Jenkins 相同；开发容器不替代它

平台。容器的架构跟随宿主：x86_64 机器得到 linux-x86_64，Apple Silicon 得到 linux-aarch64。今天只有 linux-x86_64 有统一构建 profile，所以 Apple Silicon 上的容器能做 JVM 侧全部工作和消费别处编好的 linux-aarch64 bundle，不能从源码编统一包；platform: linux/amd64 走 Rosetta 或 QEMU 模拟编原生库，耗时以天计，不作为方案。这是 build.html 里 linux-aarch64 profile 缺失的另一面。

资源。Docker 给容器的内存至少 8 GB：sbt 4 GB 堆加原生构建的编译进程；原生全量构建时给足 CPU。命名卷大小以 Conan 缓存为主，第一次全量构建后用 docker system df -v 查看，本页不估。

5 落地与验证

2026-09-20 落地：Dockerfile 拆为 toolchain、dev、builder、final 四段，.devcontainer/ 四个文件、scripts/devcontainer.sh 与 .dockerignore 加入仓库，README.md 与 contributing.md 的环境一节改为以开发容器为入口。验证在 x86_64 Linux 宿主（128 核）上进行；本会话自身在一个容器里，宿主 Docker 看不到它的 checkout，所以 /workspace 用一个由 docker cp 填充的命名卷代替 bind mount，其余与 compose 文件一致。
